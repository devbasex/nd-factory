# nd-factory の開発の指針

このリポジトリの持ち主が決めた進め方である。AGENTS.md（守る約束）と docs/design/（設計の正本）を補い、判断に迷ったときに読む。**AI のメモリと引継ぎ文書には、ここにある指針を書かない。** 指針が増えたら、この Skill か設計書か `.ndf/` に書く。

## 進め方

| 指針 | 中身 |
| --- | --- |
| 開発の初期は厳密なフローを課さない | 承認ゲート（設計 PR のマージ・本番への反映）の外の判断は、推奨の案で決めて報告に 1 行書く。問いは短く、何のための設定かを先に書く |
| 商用利用の開始前はレッドラインの指摘も AI が決める | レビューで「人の承認が要る」とされた指摘（C1〜C8・P）は、商用利用の開始前はすべて、開始後も開発環境なら AI の判断で決め、承認資料に書く。商用利用の開始は、機能が一通りそろい β テストを経て正式版を公開するときで、持ち主が宣言する。製品の側の同じ決まりは [API の文書の人の確定の段階](../../../docs/design/api.md#人の確定の段階)（決定 156） |
| 堅牢で長期的に良い方を選ぶ | ライブラリや作り方は、今の実装からの切り替えの手間を数えず、保守の活発さ・利用の広さ・公式の部品か・自前の層の少なさで選ぶ。比べて分かる選択は問わずに決めて理由を報告する。持ち主へ問う場面は、下の「承認ゲートの外では持ち主に問わない」に従う |
| 承認ゲートの外では持ち主に問わない | 承認ゲート（設計 PR のマージ・本番系へ届く操作）以外では、持ち主に問わず、作業も頼まず、AI が推奨の案で決めて報告に書く。レーンの質問も、ゲートでなければオーガナイザーが決める。手作業の確認も AI が代行する。NDF の共通原則とプロジェクト MVV が人の承認を求める操作の扱いは、この行では変えない（持ち主、2026-11-25「承認ゲート以外の問い合わせや人に求めることが多すぎます」） |
| 2 択をそのまま渡さない | 「A か B か」を問う前に、何が何を縛っているかを 1 文で言えるか、縛っている前提そのものを変える案を比べたかを確かめる（#13 の ECR で、前提を変える案 C が漏れた） |
| 並行開発の計画はレーンで回す | 「並行開発計画」「レーン」と言われたら、`--parallel` が無くても `ndf lanes` の計画で回す。supervisor を並べない。静かなレーンはレーンの画面を見る |
| AI のメモリを使わない | 設計フェーズの間は、残したいことを設計書・`.ndf/`・この Skill に書く |

## 設計の主題

- 設計の主題は、プロジェクト MVV（`.ndf/mvv.md`）が目指す nd-factory の姿である。作り直しの手順・旧い実装との同等は主題にしない。旧い機能は「入れるかを MVV で決める材料」に留める
- A（このリポジトリのコード・CI・設置）と B（利用者のプロジェクトで NDF の工程を回すこと）を分けて書く。B の工程と品質の確かめは NDF（devbasex/ai-plugins）の担当で、nd-factory は B に対して NDF の UI に徹する（[全体の設計の該当の節](../../../docs/design/overview.md)）
- MVV に無いと言われたら、兄弟のプロジェクト（carul・carte）の `.ndf/mvv.md` と混ざっていないかを確かめる。開発の目標（Value 10〜）は carul の Value を書き直したもの

## 書き方

| 指針 | 中身 |
| --- | --- |
| 日本のエンジニアが普段使う語で書く | 直訳調の造語を使わない（鍵→キー・索引→インデックス・DB の表→テーブル・表の「許す・許さない」→可・不可・強い整合で読む→強整合で読む・月の使った量→月間利用量・道具→ツール・地図→画面マップ/ルートマップ・頭書き→ヘッダ・ID の頭→プレフィックス・失敗のアイテム→失敗したアイテム など）。定着したカタカナ語・英語がある所を和語に言い換えない。「A の B の C」と「の」を重ねた直訳の名詞句を作らない。廃止した語は `.ndf/glossary.json` の `check.banned.words` に登録し、用語集の検査で止める |
| `human_only` | 「人だけ」と書かず、日本語の文でも `human_only` と書く。「立てた人だけ」のように特定の人に限る意味は別 |
| 承認する以外の答えには理由 | 承認しない・差し戻す・取り消すなどには、どの入口からでも理由を添えられるように設計する |
| 図を確かめる | 設計 PR を承認へ出す前に、mermaid のブロックを `mermaid.parse` に通す（`mermaid@11` と `jsdom` を作業用の場所に入れる）。subgraph は `ID[ラベル]` の形、記号を含むラベルは `"…"` で囲む |
| 確定前の文書 | 確定前の要件定義書・設計書はメインディレクトリの `issues/` に置き、確定したら `docs/` へ移す |

## 検証

- 検証環境での機能の確かめは、devbasex/ai-plugins と devbasex/nd-factory の 2 つをリポジトリとして登録し、実際にスプリントが回ることで確かめる
- 画面のモックは `docs/design/mock/`。利用者に見せるときはプロジェクト Skill `mock-viewer`（`npm run mock:up` で http://ndf-mock.localhost/）を使う
