# 全体の設計: 子の課題が認可・起こし直し・公開範囲・DB の用意を 1 か所から 1 つの答えで読める（#32）

## 目的

- **今どうなっているか**: 承認済みの全体の設計（`docs/design/` の 7 本）は、4 つの事柄について文書ごとに違う答えを持つか、答えを持たない。4 つは、問いに人だけが答える範囲・答えの送達の起こし直し・起票の宛先の公開範囲・進行表の DB の用意と差し替えである。「詳細設計が持つ」と回した中身の行き先も無い
- **誰に効くか**: 全体の設計を引いて詳細設計を書く子の課題（#1・#2・#4〜#8・#11・#13・#14・#28・#29。下の「子の課題へ渡す欠け」の渡す先と同じ集まり）の担当者と、設計承認ゲートで承認する人
- **変えると何が成り立つか**: 指摘 11 件と R1〜R15 のどれについても、全体の設計の 1 か所（または渡した子の課題の本文）から 1 つの答えを読める

## 適用範囲

- **働く範囲**: このリポジトリの全体の設計（`docs/design/`）・用語集（`docs/glossary/`）・`AGENTS.md` の「コードの決まり」の 1 行と、子の課題の本文。コード・形の正本・インフラの定義は変えない
- **プロジェクトごとに違うもの**: 無し（設計の文書の改訂で、設定も引数も受けない）
- **当たるモード**: `standard`

## あるべき姿の根拠

| 根拠 | 種類 | 何を示すか |
| --- | --- | --- |
| NDF の `ndf answer` の引数のスキーマ（STD1） | 外部の一次情報 | `--reason` は必須、`--drop` は整数の配列、`--key` は「同じ鍵の答え直しは書かない」。指摘 1 と 4 の答えの出所 |
| PostgreSQL の advisory lock（STD2） | 外部の一次情報 | トランザクションの間だけ持つ排他の鎖を DB の側で取れる。指摘 9 の排他の出所 |
| DynamoDB の `TransactWriteItems`（LIB1） | 外部の一次情報 | 100 件までの書き込みと、書かない行の条件（`ConditionCheck`）を 1 つのトランザクションで照らせる。R8・指摘 10・11 の出所 |

要求と受け入れ条件は #32 の本文にある（コピーは [requirements.md](requirements.md) ）。この文書は「どう直すか」だけを扱う。直した後の文の正本は `docs/design/` で、この文書は直す中身と理由を持つ。この文書の「タスク」は ECS のタスク（DB の用意のタスク・ランナーのタスク）を指す。

## ドメインモデル

### コンテキスト

| コンテキスト（用語集の `id`） | 何の語が 1 つの意味に決まるか |
| --- | --- |
| 人の判断（`judgment`） | 承認の依頼・問い・答え・答えの送達・人だけの区分 |
| 実行（`execution`） | レーン・区間・手元のマシンの登録・起こし直し |
| プロジェクト（`project`） | 割り当てを移す流れ・GitHub の token の失効 |
| 利用者とチーム（`identity`） | ログインの組から利用者を引く行 |
| プラットフォーム（`platform`） | 進行表の DB の用意・資格情報の差し替え・サービスの表の共通の列 |

コンテキストマップの関係は、全体の設計の表を引き継ぐ。全体の設計の「実行 | 人の判断 | パートナーシップ」の 1 行を、向きごとの 2 行に分け、プロジェクトの行を変える。全体の設計が使う「パートナーシップ」は 5 つの関係の語に無い（R15）。

| 上流 | 下流 | 関係 | この変更で決めること |
| --- | --- | --- | --- |
| 実行 | 人の判断 | 公開された言語（「パートナーシップ」から替える） | 実行が出す事象（E10・E14・E19・E20）を、形の正本の事象の形で人の判断が受けて書く。答えの送達の状態（届いた・失敗）・承認の依頼と問いの取り消し・起票の結果がこの向きである（下の「集約を書き換える経路」） |
| 人の判断 | 実行 | 顧客 / 供給者（足す） | 人の判断が上流で、確定した答え（E13）と、答えの受け取りの関数（渡し中を記して答えを返す）を実行へ出す。実行の制御は人の判断の表へ直に書かず、この関数を呼ぶ |
| プロジェクト | 実行・人の判断・知らせ・操作の記録の読み出し・プラットフォーム（DB の用意） | 顧客 / 供給者（下流にプラットフォームを足す） | 進行表の DB の列と GitHub の token の世代番号はプロジェクトの集約にあり、DB の用意の引き換え・見回り・token の取り直しは、プロジェクトのモジュールの関数を呼んで書く（直に表へ書かない） |

### 集約

| --- | --- | --- | --- | --- |
| 承認の依頼 | 人の判断のモジュール | 承認の依頼 | 答え | 状態（待っている・答えた・取り消した）・答えの送達の状態・対象の課題の番号の並び・起票の結果（起票の依頼だけ。作った・作らなかった） |
| 問い | 人の判断のモジュール | 問い | 答え | 状態（同上）・人だけか（区分から決める）・答えの送達の状態 |
| 手元のマシン | 実行の制御 | 手元のマシン | — | 状態（登録待ち・`online`・`offline`）・登録の token の指紋 |
| プロジェクト | プロジェクトのモジュール | プロジェクト | リポジトリ | 移し中の印（今の移しの ID）・進行表の DB の名前と役割の名前・用意の ID と用意のタスク・差し替えの番号・GitHub の token の世代番号・版 |

#### 集約を書き換える経路

持ち主の外で起きた出来事は、持ち主のモジュールへ事象か関数の呼び出しで頼み、持ち主だけが書く。

| 書き換える値 | 起こすもの | 頼み方 | 書くもの |
| --- | --- | --- | --- |
| 答えの送達の状態（渡し中） | ランナーの受け取り（`/v1/runner/answers/list`） | 実行の制御が人の判断のモジュールの受け取りの関数を呼ぶ（人の判断が上流の顧客 / 供給者） | 人の判断のモジュール |
| 答えの送達の状態（届いた）と NDF の答えの事象の番号 | ランナー | 送達の事象（E14） | 人の判断のモジュール |
| 答えの送達の状態（未渡し・渡し中から失敗へ）・承認の依頼と問いの取り消し | 実行の制御（レーンの失敗・取り消し。割り当ての移しは E18 を受けた実行の制御がレーンを取り消す） | レーンの終わりの事象（E19） | 人の判断のモジュール |
| 起票の結果 | 実行の制御（起こす段。I21） | 起票の結果の事象（E20。作らなかったときは理由 `visibility_widened` か `destination_unregistered`） | 人の判断のモジュール |
| 移し中の印と移す途中の状態（止め終えたか・失効が終わったか・差し替えを始めたか・取り下げたか） | API の移しの作成・受け入れ・取り下げ・実行の制御（止め終えた）・見回り（印のあるプロジェクトを拾い、同じ移しの ID の移す途中の状態から最初の済んでいない段をやり直す。止め終えたかが偽なら E18 を出し直し、止め終えたかが真で失効が終わったかが偽なら失効を、差し替えを始めたかが偽なら差し替えの開始を出し直す。取り下げた移しは、そろった後に印を空にする） | プロジェクトのモジュールの関数を呼ぶ（`version` の条件つきの書き込み） | プロジェクトのモジュール |
| 進行表の DB の列（名前・用意の ID・用意のタスク・差し替えの番号と保留） | API の開始と移し・DB の用意の引き換えと完了の報告・見回り | プロジェクトのモジュールの関数を呼ぶ（`version` の条件つきの書き込み） | プロジェクトのモジュール |
| GitHub の token の世代番号 | 実行の制御（心拍の token の取り直し）・プロジェクトのモジュール（失効） | 実行の制御はプロジェクトのモジュールの取り直しの関数を呼ぶ | プロジェクトのモジュール |

### 不変条件

全体の設計の不変条件のうち 3 つの文を変え、6 つを足す。答えの送達の対象と対象外は、下の「用語」の「答えの送達」の行で決める。足す番号は I17 から振り、[全体の設計の不変条件](../../design/overview.md#不変条件) の表と、その下のテスト設計の表へ同じ番号で載せる。

| # | 集約 | 条件 | 破れたときの扱い |
| --- | --- | --- | --- |
| I4（意味の変更） | 承認の依頼・問い | 承認の依頼すべてと、人だけの区分の問いの答えを確定できるのは、人のログインのセッションからの要求だけ。つながっていない端末では確定しない。確定の時点でサーバーの今の状態（待っている・承認資料の要約値が同じ）と照らす | 合わなければ 409。委任からの確定は 403 `human_only` |
| I5（意味の変更） | 承認の依頼・問い | 送達の対象の答え（用語の「答えの送達」）は、NDF へ 1 回だけ書かれる（冪等の鍵は答えの ID）。結果が分からないまま起動し直したランナーは同じ答えの ID で打ち直し、違う答えの ID を作らない。正規の送達と承認の外の書き込みは、NDF の答えの事象の番号（`ndf answer` の結果の `metrics.seqs`、答えの一覧の `seq`）で見分ける。ランナーは `ndf answer` が返した番号を送達の事象（E14）に添え、API は答えの行に記す。番号は鍵に結んだ値（`ndf answer` の結果）からだけ得て、答えの一覧の `gate_id` や `by` から推して決めない。NDF の答えの一覧の事象のうち、そのレーンの答えの行に記した番号に無いものを「控えに無い答え」とする | 同じ鍵の 2 回目は NDF が書かない。控えに無い答えが現れたらレーンを止めて知らせる。鍵に結んだ番号を得られなければ、送達の事象を送らずにレーンを失敗（`answer_seq_unknown`）にして知らせる |
| I16（守り方の変更） | 利用者 | 1 つの IdP のアカウントは、ちょうど 1 人の利用者に結ぶ。IdP の主体ごとに一意の行を持ち、ログインの組の行と同じトランザクションで書く | 一意の行が既にあれば 409 |
| I17 | プロジェクト | 進行表の DB の資格情報の差し替えは、プロジェクトの差し替えの番号を DB の側の排他の鎖の下で照らし、DB に記した番号より大きいときだけパスワードと番号を書く。番号 n を書いたときも、記した番号が n と同じだったときも、タスクは役割の古い接続を切り、役割の接続が残っていないと読んでから完了を報告する | 記した番号が n より大きければ何も変えずに、記した番号を添えて `rotation_superseded` で終える。記した番号が n と同じなら、パスワードは書かずに古い接続を切り、残りが無いと読んでから記した番号を添えて `rotation_superseded` で終え、API は適用と同じく保留を下ろす。接続が残ると読んだら完了を報告せずに落ち、I22 で起こし直す |
| I18 | プロジェクト | 用意のタスクは、引き換えの要求に自分のタスクの ID（タスクのメタデータの端点の `TaskARN`。LIB3）を添える。API は管理の接続を返す前に、添えられたタスクの ID を `DescribeTasks` で読み、そのタスクが用意のタスクのクラスタにあり、`startedBy` が今の用意の ID で、`STOPPED` でないことを確かめる（違えば 409 で返さない。要求の値をそのまま信じない）。確かめた後、用意の ID が今の値と同じで、記したタスクの ID が空か同じことを条件に、そのタスクの ID をプロジェクトの行へ記す。管理の接続を得たタスクは、必ず ID が記されている。進行表の DB の状態を `作成中` から `無い` へ戻すのは、タスクの ID を記しているなら、そのタスクの `STOPPED` を `DescribeTasks` で読んだ後だけ。記していない（タスクが作られなかったか、引き換えの前で、API も ID を記す前に落ちた）なら、作成の時間切れを過ぎた後に、タスクの ID が空のままであることを条件に用意の ID を外す書き込みで戻す。外した用意の ID の引き換えは受けないため、引き換えの前のタスクは後から管理の接続を得られない。`ListTasks` は `startedBy` の用意の ID だけで絞り（ほかの絞りと併せられず、`desiredStatus` の既定は `RUNNING`）、見つかった動いているタスクを止める片付けにだけ使い、戻してよいかの判断には使わない | 止まったと読めないか、条件の書き込みが通らなければ（その間に引き換えが ID を記した）`作成中` のまま次の見回りでやり直す |
| I19 | プロジェクト | GitHub の token の失効の完了は、失効を始めたときの世代番号と今の世代番号が同じときだけ記録する | 違えば完了を記録せず、記録を読み直して失効をやり直す |
| I20 | プロジェクト | 割り当ての移しの間（移し中の印を書いてから、受け入れか取り下げで消すまで）と、進行表の DB の資格情報の差し替えの保留の間は、そのプロジェクトのスプリントの作成・レーンの割り当ての確定・割り当ての移しの作成を受けない。照らしは、その作成と確定の書き込みと同じトランザクションの中で、プロジェクトの行の移し中の印と差し替えの保留を読んで行う。プロジェクトの行を書かないスプリントの作成とレーンの割り当ての確定は `ConditionCheck` で、プロジェクトの行へ印を書く移しの作成はその `Update` の `ConditionExpression` で照らす（LIB1。1 つのトランザクションで同じ行を 2 回指せない） | 移しの間は 409 `project_transfer_in_progress`、差し替えの保留の間は 409 `credential_rotation_in_progress`。実行の制御はレーンを割り当てず、待ちのまま残す（移しの停止で取り消す） |
| I21 | 承認の依頼 | 起票の依頼から課題を作るのは、作成の要求の直前に読み直した宛先が次の 3 つをすべて満たすときだけ: (1) 今もそのプロジェクトに登録したリポジトリである（閲覧者を、割り当てたチームが登録した範囲に収める）、(2) 公開範囲が、承認資料に載せて人に示した宛先の公開範囲より広くない（承認の後に広がっていない）、(3) 公開範囲が、レーンのリポジトリの公開範囲より広くない | 作らずに、起票の結果を「作らなかった」（(1) は理由 `destination_unregistered`、(2)(3) は理由 `visibility_widened`）にして事象（E20）に残し、始めた人へ知らせる。承認の依頼は人が答えたため「答えた」のまま閉じる |
| I22 | プロジェクト | 差し替えの保留は、差し替えの期限（作成の時間切れと同じ設定の値）を過ぎても完了の報告が無ければ、見回りがそのタスクを止めて `STOPPED` を読んだ後に、同じ番号 n と保留の版の同じパスワードで、新しい用意の ID のタスクを起こし直す。タスクの ID を記していないときは、I18 と同じく、タスクの ID が空のままであることを条件に前の用意の ID を新しい用意の ID へ替える書き込みで起こし直す（引き換え済みのタスクは必ず ID が記されており、止めて `STOPPED` を読む側へ回る）。この書き込みが通らなければ（その間に引き換えが ID を記した）、その見回りでは起こし直さずに行を読み直し、次の見回りで止めて `STOPPED` を読む側へ回る。前の用意の ID の引き換えと完了の報告は受けない。保留を下ろすのは、番号の合う完了の報告（適用か、記した番号 = n の `rotation_superseded`。どちらも古い接続を切り終えた後に出す。I17）だけ | 起こし直しが上限の回数（設定の値、既定 3）を超えたら、保留を残したまま（I20 の 409 を続ける）運用の知らせへ送り、人が直す |

公開範囲の広さは `private` ＜ `internal` ＜ `public` の順で比べる（LIB2 のリポジトリの `visibility`）。

### ドメインイベント

要求の E1〜E5（設計の文書の改訂の流れ）を引き継ぐ。製品のドメインイベント（全体の設計の E5〜E17）は番号と意味を変えない。改訂の流れのイベントは次のとおり。

| # | イベント | 発生元 | 受け手 |
| --- | --- | --- | --- |
| E1 | 指摘ごとに、設計の中で正しい状態を決めた | この設計文書（設計の工程） | 実装の段（`docs/design/` の改訂） |
| E2 | 正しい状態に合わせて設計の文書を直した | 実装の段 | 設計の文書の読み手（子の課題の担当者） |
| E3 | 直さないと決めた指摘を、決定の記録に理由とともに書いた | この設計文書 | 決定の記録の読み手。11 件をすべて直すため、この変更では起きない（下の「指摘 11 件の扱い」） |
| E4 | 子の課題へ渡す欠けを、渡す先の子の課題の本文へ追記した | 実装の段 | 渡す先の子の課題の担当者 |
| E5 | 設計 PR が設計承認ゲートを通った | 承認する人 | 実装の段 |

製品のドメインイベントは、全体の設計の表の 3 行の受け手を書き分け、E18〜E20 を足す。足す行は全体の設計のドメインイベントの表へ同じ番号で載せる。

| # | イベント | 発生元 | 受け手 |
| --- | --- | --- | --- |
| E13（受け手の書き分け） | 人が答えた | 人の判断 | 実行の制御。後に続く処理は、依頼の種類と答えの選択肢の組で決める。送達の対象の答え（NDF の区間の報告から作った承認の依頼 `ndf-gate:*`・`ndf-ask:redline:<番号>` と問い。用語の「答えの送達」）は、選択肢によらずレーンへ渡し、渡した後の続きは選択肢で決める（承認しない・取り消すはレーンを取り消す。実行の文書の「差し戻し」）。`ndf-ask:human-action` の答えは「済んだ」のときだけ続きの区間を起こし、「取り消す」のときはレーンを取り消す（E19）。起票の依頼の答えは「起票する」のときだけ起こす段（I21）へ回し、「起票しない」のときは課題を作らずに閉じる |

| `project_transfers.create`・`project_transfers.accept`・`project_transfers.delete` | 作成は移し中の印と止める依頼（移す途中の状態の「止め終えたか」が偽）を 1 つの書き込みで書いてから E18 を出す。受け入れは、印が対象の移しの ID と同じで「取り下げたか」が偽であることを条件に入れ、今の割り当ての差し替えと同じ書き込みで印を空にして E17 を出す（条件が外れたら 409 `state_mismatch` で割り当てを変えない）。取り下げは「取り下げたか」を真にし、印を空にするのは下の「割り当てを移す流れ」の条件がそろった後だけ |
| `/v1/runner/answer_deliveries/create` | 要求の要素に、`ndf answer` の結果の `metrics.seqs`（NDF の答えの事象の番号）を足す（I5） |
| `/v1/runner/answers/list` | 応答の要素に `redeliver`（真偽）を足す。前の世代が受け取って渡し中のままの答えで真。応答に、そのレーンの「届いた」答えの行に記した NDF の答えの事象の番号の並び（`delivered_seqs`）を足す。届いた答えは要素に載せないが、番号はこの並びで返す（照らす守りの控え。I5） |
| `/v1/machine/heartbeats/create` | 最初の心拍（マシンが登録待ち）の応答に、マシンの ID・心拍の間隔・差し替えた登録の token を持たせる |
| `/v1/db_prep/exchanges/create` | 要求に、タスクのメタデータの端点から読んだタスクの ID を足す。API は管理の接続を返す前に、その ID のタスクを `DescribeTasks` で読んで `startedBy` が今の用意の ID で止まっていないことを確かめ、プロジェクトの行へ記す。確かめられないか、記した ID と違えば 409 で返さない（I18）。応答の役割の値に、データベースの名前・役割の名前・差し替えの番号（差し替えの種類だけ）を足す |
| `/v1/db_prep/completions/create` | 要求に差し替えの番号を持たせ、今の番号と同じときだけ受ける。`rotation_superseded` の終わりも受ける |

要素の項目の型と理由のコードの一覧は、形の正本の操作の定義が正本である（決定 3）。上の表は全体の設計の文に書く変わり目だけを示す。

## 処理の流れ

### 承認の依頼と問いの状態（R2）

承認の依頼と問いは同じ 3 つの状態を持つ。差し戻しは答えの語（`request_changes`）で表し、状態にしない。確定できる主体が違うため、図を集約ごとに分ける。

承認の依頼:

```mermaid
stateDiagram-v2
    [*] --> 待っている: 区間の報告から作る（E10）
    待っている --> 答えた: 人のログインのセッションが確定した（I4。委任は 403）
    待っている --> 取り消した: スプリントの取り消し・割り当ての移し・レーンの失敗
    答えた --> [*]
    取り消した --> [*]
```

問い:

```mermaid
stateDiagram-v2
    [*] --> 待っている: 区間の報告から作る（E10）
    待っている --> 答えた: 人だけの区分は人のログインのセッション、ほかは人か委任が確定した（I4）
    待っている --> 取り消した: スプリントの取り消し・割り当ての移し・レーンの失敗
    答えた --> [*]
    取り消した --> [*]
```

| 遷移 | 決まり |
| --- | --- |
| 答えた（語が `request_changes`） | 前の依頼は「答えた」で閉じる。NDF がもう一度承認ゲートに着いたら、新しい依頼を作る |
| 答えた（起票の依頼） | 状態は「答えた」で閉じ、作ったかどうかは起票の結果（作った・作らなかった）で持つ。作成の直前の照らし（I21）で作らなかったときも「答えた」のまま |
| 取り消した | 答えを受けない（確定は 409 `state_mismatch`）。知らせの送っていない分を捨てる |

### 答えの送達（指摘 4）

```mermaid
stateDiagram-v2
    [*] --> 未渡し: 答えを確定した（E13）
    未渡し --> 渡し中: ランナーが受け取った（受け取った世代を記す）
    渡し中 --> 渡し中: 新しい世代のランナーが受け取り直した（redeliver）
    渡し中 --> 届いた: 送達の事象を受けた（E14）
    未渡し --> 失敗: レーンが失敗・取り消し（E19）
    渡し中 --> 失敗: レーンが失敗・取り消し・照らす守り（E19）
    届いた --> [*]: 後からレーンが失敗・取り消しになっても「届いた」のまま
    失敗 --> [*]
```

| 段 | 決まり |
| --- | --- |
| 対象 | 用語の「答えの送達」のとおり。承認ゲートの承認の依頼の答えと、`ndf-ask:human-action` を除く問いの答え（委任が確定した問いを含む）を送達し、届いたらレーンを続ける。`ndf-ask:human-action` の答えと起票の依頼の答えは `/v1/runner/answers/list` に載せず、送達の状態を持たない |
| 受け取る | ランナーは起動の後と指示の問い合わせのたびに答えを読む。渡し中のまま前の世代が受け取った答えは `redeliver` が真 |
| 打ち直す | `redeliver` が真の答えは、同じ答えの ID を `--key` にして `ndf answer` を打ち直す。NDF は同じ鍵の 2 回目を書かない（STD1）。新しい答えの ID を作らない |
| 番号を添える | ランナーは `ndf answer` の結果の `metrics.seqs`（書いた答えの事象の番号）を送達の事象（E14）に添える。番号は鍵に結んだ `ndf answer` の結果からだけ得る。打ち直しで `metrics.replayed` が真なのに `metrics.seqs` が空のときは、答えの一覧の `gate_id` や `by` から番号を推さず、送達の事象を送らずにレーンを失敗（`answer_seq_unknown`）にし、始めた人とチームの持ち主へ知らせる（I5）。同じ鍵の 2 回目が最初の番号を返すかは #6 の詳細設計で実測し、返さないなら決定 5 を決め直して設計承認ゲートへ戻す（未確認のまま残すこと） |
| 照らす | 照らす守りの控えは、API が `/v1/runner/answers/list` の応答の `delivered_seqs` で返すそのレーンの届いた答えの事象の番号から組む。起動し直したランナーも、受け取りの 1 回目で控えを取り直す。NDF の答えの一覧の事象のうち、控えの番号に無いものがあれば「控えに無い答え」としてレーンを止める（I5）。未渡し・渡し中の答えがあるうちは照らしを待ち、番号が届いてから照らす。ランナーの手元の控えが起動し直しで消えても、渡した答えを控えに無いと読まない |

### 進行表の DB の用意と差し替え（R9・指摘 7〜9）

| 失敗の場面 | 扱い |
| --- | --- |
| 番号 n のパスワードを書いた後、古い接続を切る前か完了の報告の前に落ちた | 起こし直したタスクは、記した番号 = n を読んでパスワードを書かず、役割の古い接続を切り、残りが無いと読んでから `rotation_superseded` を返す。DB のパスワードは保留の版と同じで古い接続も残らないため、API は保留を下ろす |
| 書く前に落ちた・起動しなかった | 起こし直したタスクが番号 n で書く |
| RunTask がタスクの ID を返さなかった・API がタスクの ID を記す前に落ちた | タスクが引き換えたなら、引き換えがタスクの ID を記しているため、見回りはそのタスクを止めて `STOPPED` を読む。管理の接続を引き換え済みのタスクは、`ListTasks` に出なくても必ず止めてから進む。ID が空のままなら、引き換えたタスクは無い。見回りは期限を過ぎた後に、ID が空であることを条件に用意の ID を替え（作成なら `無い` へ戻す）、新しい用意の ID で起こし直す。前の用意の ID のタスクが後から動いても、引き換えを受けないため DB へ着けない。`ListTasks` は動いているタスクを片付けるためだけに使う（`startedBy` はほかの絞りと併せられず、既定は `desiredStatus` = `RUNNING` で止まりかけのタスクを返さないため、判断には使わない） |
| 起こし直しが上限を超えた | 保留を残し、スプリントの開始と割り当ての移しを止めたまま、運用の知らせで人が直す（安全の側に倒す） |

### ホステッドの起こし直し（R9・指摘 4）

```mermaid
sequenceDiagram
    participant H as 人
    participant API as 実行の制御
    participant R as 新しい世代のランナー
    participant N as NDF と claude
    H->>API: 答えを確定（E13）
    API->>API: 世代を 1 上げ、引き換えの token を作る
    API->>R: RunTask（clientToken はレーンと世代）
    alt 起動の期限を過ぎた・契約の版が合わない
        API->>API: レーンを失敗にする
    end
    R->>API: 引き換え・状態の S3 からファイルを戻す
    R->>API: 答えを受け取る（redeliver つき）
    R->>N: ndf answer（同じ答えの ID を --key）
    alt 書けた・同じ鍵で既に書かれていたと読め、鍵に結んだ事象の番号（metrics.seqs）を得た
        R->>API: 送達の事象（E14。届いた・事象の番号）
        R->>N: 続きの区間（block-next）
    else 同じ鍵で書き込み済みと読めたが、事象の番号を得られない
        R->>API: 送達の事象を送らず、レーンを失敗（answer_seq_unknown）にする事象（I5）
    else ndf answer が失敗した
        R->>API: レーンを失敗にする事象（送達は失敗になる）
    end
```

「同じ鍵で既に書かれていた」ときの `ndf answer` の終了コードと出力は実測していない（下の「確かめられなかったこと」）。#6 の詳細設計で実測し、2 回目が成功の終了コードを返すなら図のとおりにする。失敗の終了コードを返すなら、ランナーはその出力が同じ鍵の書き込み済みを示すときだけ書き込み済みとして扱う。どちらの場合も「届いた」として E14 と続きの区間へ進むのは、鍵に結んだ事象の番号を得たときだけで、得られなければ I5 のとおり `answer_seq_unknown` でレーンを失敗にする。どちらでもなく見分けられないなら、決定 5 を決め直して設計承認ゲートへ戻す。

### 決定 5: 結果が分からない送達を失わず 2 重にも書かないため、起動し直したランナーは同じ答えの ID で打ち直し、NDF の冪等の鍵に任せる

NDF の答えの事象は鍵を持たない（実行の文書の決定 70）。そこで、正規の送達と承認の外の書き込みを見分ける根拠は、NDF と API の両方に残る NDF の答えの事象の番号にする。`ndf answer` は結果の `metrics.seqs` に書いた事象の番号を返し、答えの一覧の各事象は `seq` を持つ（STD1）。ランナーが番号を送達の事象に添えて API の答えの行に記せば、起動し直した後も、照らす守りは API の記録だけから「控えに無い答え」を決められる。答えの ID の一覧だけでは、NDF の事象にその ID が無いため照らせない。

採らなかった案: `ndf progress show` で答えの事象を探してから打つ形は、答えの事象が鍵を持たず（実行の文書の決定 70）、どの答えかを照らせない。

- 比べた候補: STD1

### 決定 6: 承認の依頼と問いの状態を文書の間で 1 つにするため、状態を「待っている・答えた・取り消した」の 3 つにし、差し戻しは答えの語で表す

### 決定 8: 古い差し替えが新しいパスワードを上書きしないため、差し替えの番号を API が上げ、DB の用意のタスクが DB の側の排他の鎖の下で番号を照らしてから書く

差し替えのタスクは移しのたびに起きる。保留の間は移しの作成を 409 で止めるため（I20・決定 11）、番号の違う 2 つの差し替えのタスクが同時に動くことは起きない。I17 が守るのは、同じ番号 n のタスクを起こし直す場面（I22）である。番号 n を書いた後、完了の報告の前に落ちたタスクの後で、起こし直したタスクが同じ書き込みを繰り返しても何も変えず、記した番号 = n を返せば API は保留を下ろせる。番号の照らしが完了の報告にだけ掛かると、この場面で起こし直しが書き終えたかを DB から読めない。DB の側で `pg_advisory_xact_lock` を取り（STD2）、記した番号より大きいときだけパスワードと番号を同じトランザクションで書く。パスワードと番号を書いた後、古い接続を切る前に落ちると、記した番号 = n でも古いパスワードでの接続が残る。そこで記した番号 = n のときも古い接続を切り、役割の接続が残っていないと読んでから完了を報告する。保留を下ろす条件を「古い接続が残っていない」まで含めれば、古い接続を残したまま移す先の受け入れを通さない。`StopTask` の後に `STOPPED` を読み違えた・同じタスクが 2 回起動したといった、止めの守りが外れた場面でも、番号の小さいタスクは何も変えない（守りを 2 重にする）。

採らなかった案: サービスの表の条件つきの書き込みだけで排他する形は、タスクが DB へ書く時点を縛れない（LIB1 は DynamoDB の中だけを照らす）。

- 作り方: 標準に倣う・自前で作る
- 比べた候補: STD2 / LIB1

書き先: platform.md 決定 95。

根拠: Value 9（MVV 版 1）

### 決定 9: 2 つのタスクが同じデータベースと役割を変えないため、作成の時間切れでは前のタスクを止めて停止を読んでから「無い」へ戻す

時間切れの後に「無い」へ戻すと、次の開始が新しいタスクを起こし、前のタスクが動いたままなら同じデータベースと役割を 2 つのタスクが変える。`StopTask` は SIGTERM の後 既定 30 秒で SIGKILL を送り、`DescribeTasks` の `lastStatus` で止まったことを読める（LIB3）。完了の報告の token は用意の ID に結ぶため、戻した後に前のタスクが報告しても受けない。`RunTask` がタスクの ID を返さないか、API がタスクの ID を記す前に落ちると、止める先の ID が無い。そこで、タスクは引き換えの要求に、タスクのメタデータの端点から読んだ自分のタスクの ID を添え、API は管理の接続を返す前にその ID を記す（LIB3）。管理の接続を得たタスクは必ず ID が記されているため、止めて停止を読む側へ回る。ID が空のままなら引き換えたタスクは無く、作成の時間切れを過ぎた後に、ID が空であることを条件に用意の ID を外して戻す。後から前の用意の ID のタスクが動いても、引き換えを受けないため DB へ着けない。`clientToken` にも用意の ID を付け、同じ用意の ID の起動を 1 つに保つ。

採らなかった案: 時間切れの後に一定の時間を待つ形は、止まったことを確かめない。`ListTasks` を `startedBy` で絞ってタスクを探す形は、`startedBy` をほかの絞りと併せられず、既定の `desiredStatus` が `RUNNING` のため止まりかけのタスクを返さない。結果整合で起動の直後に出ないこともある（LIB3）。見つからないことを「タスクが無い」の根拠にできないため、片付けにだけ使う。

- 作り方: ライブラリやサービスを使う
- 比べた候補: LIB3

書き先: platform.md 決定 96。

根拠: Value 9（MVV 版 1）

### 決定 10: 失効の後に渡した token を残したまま受け入れないため、失効の完了を GitHub の token の世代番号の条件つきの書き込みで記録する

失効の間に心拍の取り直しが新しい token を渡すと、記録の行と世代番号が増える。完了の記録が世代番号を照らさないと、新しい token が残ったまま期限の最大値が空になり、移す先の受け入れが通る。世代番号が失効を始めたときと同じことを条件に書けば（LIB1 の条件式）、間に渡した token があれば完了にならず、読み直してやり直す。

採らなかった案: 失効の間は token の取り直しを拒むだけの形は、拒みと失効の間の競り合いを残す。拒みは既にあり（割り当ての変更の後は取り直しを断る）、世代番号の照らしはその後ろの守りとして重ねる。

- 作り方: ライブラリやサービスを使う
- 比べた候補: LIB1

### 決定 11: 差し替えの途中の資格情報をレーンへ渡さないため、差し替えが終わるまでスプリントの開始と割り当ての移しの作成を 409 で止める

取り下げの後も、止めたレーンへ渡した古いパスワードは差し替えで断つ必要があり、差し替えを途中で止めない。その間にスプリントを始めると、保留の版と今の版のどちらを渡すかが決まらない。移しの作成を受けると、差し替えの番号が重なる。止める単位は実行の場所によらずプロジェクトにし、規則を 1 つにする。差し替えは数分で終わり、待ちは短い。差し替えの保留は、レーンを止めた後に始まる。移しを始めてから保留が立つまでの間に新しいレーンが作られると、停止と資格情報の失効の対象から漏れる。そこで移しの作成で、レーンを止める前に移し中の印を書き（E18 はその後に出す）、スプリントの作成とレーンの割り当ての確定は、その書き込みと同じトランザクションで印と保留を照らす（LIB1 の `ConditionCheck`）。

採らなかった案: ホステッドのレーンの割り当てだけを止める形は、手元のマシンのレーンを待たせずに済むが、止める場所が実行の制御の割り当てと API の開始の 2 か所に分かれる。

### 決定 12: 人が承認した後に広がった宛先へ起こさないため、作成の要求の直前に宛先とレーンのリポジトリの公開範囲を読み直す
