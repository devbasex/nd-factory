# 設計の作り方: 全体の設計をどう分け、どこに置き、何で確かめるか

全体の設計（[overview.md](../../design/overview.md) ほか 6 本）を、どの規約で書き、どう分け、どこに置き、何で確かめたかを置く。設計そのものは設計文書にある。

## 工程と要求

| 項目 | 中身 |
| --- | --- |
| 当たるモード | `standard`（NDF の工程の振り分けの区分）。設計と詳細設計を書き、設計承認ゲートで人が承認してから実装へ進む |
| 要求と受け入れ条件 | #24 の本文にある。写しは [requirements.md](requirements.md)（`spec-copy.py write` で作り直す） |
| 設計文書が扱うこと | 「どう作るか」だけ。要求は写しを読む |
| 成果物 | 設計文書。#24 は実装の Pull Request を持たず、実装のファイルを触らない。設計を実装するのは子の課題である（[plan.md](plan.md)） |
| ドメインイベントの番号 | E1〜E4 は要求（#24）の番号で、設計の工程のイベントである。nd-factory の振る舞いのイベントは E5 から振る |

## 主題を MVV に置く

設計を書く前に、旧い設計の文書と旧い側の機能をどう扱うかを決めた。設計文書の決定の記録には置かず、ここに置く。

### 決定 1: 設計が目指す姿からぶれないため、主題を MVV に置き、旧い側の機能は採否を決める材料に留める

結論: 全体の設計の各節は MVV の項目から起こし、全体の設計に MVV の 13 項目と節の対応の表を置く。旧い側の機能は付録（[legacy.md](legacy.md)）で 1 行ずつ MVV に照らして採否を決め、本文に同等・凍結・入れ替えを主題にした節を作らない。

理由: 旧い設計は、旧い側との同等を網羅することを軸にした。そのため、旧い側が目指す姿から離れた点（機能ごとに増えた画面・チームの単位の認可・画面にしか無い操作）まで引き継いだ。利用者は「作り直しは手段で目的ではない」と差し戻した（[history.md](history.md#利用者の指示)）。

採らなかった案: 旧い設計の章立てを残し、MVV の節を足す。主題が 2 つになり、どちらで判断するかが節ごとに揺れる。

根拠: Mission・Value 1（MVV 版 1）

### 決定 6: 子を閉じる条件を受け入れ条件とテストにするため、対応表の試走をやめる

結論: 子の課題は、受け入れ条件・受け持つ不変条件のテスト・I14 の検査で閉じる。旧い設計の対応表の試走（#3）は閉じる。

理由: 対応表の試走は旧い側と同じ振る舞いをそろえることを確かめる仕組みで、決定 1 で主題から外した。MVV に照らして入れる機能は、受け入れ条件とテストで確かめられる。

採らなかった案: 対応表を新しい機能一覧で作り直して試走を続ける。受け入れ条件とテストと同じものを 2 か所で持つ。

根拠: Mission・Value 1（MVV 版 1）

### 設計文書に書かないこと

設計文書には、経緯・作り方・計画を書かない（利用者の指示、2026-11-18）。

| 種 | 中身 | 置き場 |
| --- | --- | --- |
| 経緯 | 今の nd-factory と旧い側の状態と数、旧い側・骨組みとの比べ、利用者の指示の日付つきの引用、作り直しに至った理由 | [history.md](history.md) |
| 作り方 | 文書の分け方と置き場、受け入れ条件との照らし、NDF の検査、cross-review と設計承認ゲート、#24 の扱い | この文書 |
| 計画 | 子の課題と順序、どの子が何を受け持ち確かめるか、骨組みからの移り方、運用する環境の切り替え | [plan.md](plan.md) |
| 旧い側の機能の採否 | 旧い側の機能を MVV に照らした採否 | [legacy.md](legacy.md) |

決定の理由は、MVV の項目・利用者と場面・外部の一次情報・費用や性能など、システムそのものの理由で書く。理由が経緯だけの決定は、理由を書き直すか、決定ごとここへ出した（決定 1・6・7 はこの文書、決定 9 は [plan.md](plan.md#決定-9-画面先行を子の順序で守るため検査と形の正本--画面の土台--機能の画面--api-の順に子を並べる)）。番号は振り直さない。

### 書き方の決まり

| 決まり | 中身 |
| --- | --- |
| 語と番号 | 語・番号（S・F・I・E）・不変条件は全体の設計のものを使う |
| 粒度 | 子の課題の担当者が、全体の設計だけを読んで詳細設計へ進める所まで書く |
| 本文の並び | 画面の文書は「土台」の行（UX の土台の 6 節）→「機能の画面」の行（その上に置く 3 節）の順に本文を並べる |
| 決定の置き場 | 文書をまたぐ決定は決定の記録の文書に、文書の中だけの決定は各文書の「決定の記録」に置く。詳細設計で決めたものは、もと「（この文書で決めた）」と注記した（置き場の 7 か所・`infra/setup/` の扱い・委任と登録の token の形・記録の区切りの鍵） |
| ファイルの単位 | 詳細設計はファイルの単位の配置を持たない。置き場をディレクトリの単位で決める |
| 外部の調査 | 製品の比べは、全体にかかる判断（主題・範囲・子の切り方）を変えない。主題と範囲は MVV と利用者の指示で決めた。主なブラウザでの Badging・Background Sync は、調べの上限の手前で止めた |
| 文書の運びの言い回し | 「この文書は〜を受ける」「頭の文書の〜」「受ける項目」「この設計で受ける所」「ほかの文書が持つもの」のような運びの言い回しは、設計文書では「全体の設計の〜」や中身だけの文へ言い換えた |
| 題 | 設計文書の題に課題の番号を付けない |

### NDF との契約の調べ方

NDF との契約は、固定の点のコミットの内容を `gh api` で読んで確かめた（2026-11-17）。出典は実行の文書の外部の調査（STD62）にある。

### 既存の部品の確かめ方

詳細設計の横断の部品ごとに、使える既存の部品があるかを次の範囲で確かめた。結果の表は [history.md の既存の部品の再利用](history.md#既存の部品の再利用) にある。

- worktree の 8 つの置き場: `apps/` の `api/src/`・`web/src/`、`packages/contracts/` の `src/`・`scripts/`、`infra/` の `lib/`・`setup/`・`bin/`、`tools/` の `ref-check/src/`
- 依存のライブラリ: 各 `package.json` と `package-lock.json`
- 手段: 部品ごとに `grep` で呼び出しと依存の名前を探し、件数を数えた

## 置き場と確定仕様化

### 決定 7: 設計文書を主題の名前で置くため、確定仕様化のときに `docs/design/` へ移し、`docs/design/rebuild/` を外す

結論: 設計の間は NDF の規約どおり `issues/issue-24-design*.md` に置く。確定仕様化（`plan-to-spec`）で `docs/design/` へ主題ごとの名前（例 `docs/design/screens.md`）で移す。同じ変更で `docs/design/rebuild/` を外し、`AGENTS.md` の「リポジトリの形」の行を直す。

理由: 置き場の名前が「作り直し」だと、読み手は作り直しの記録として読む。設計承認の前に旧い文書を外すと、承認の前に材料が読めなくなる。

採らなかった案: 今の PR で `docs/design/rebuild/` を外す。設計承認で差し戻されたときに材料が main から消える。

根拠: Mission（MVV 版 1）・利用者の指示（2026-11-17）

旧い設計の文書ごとの扱いは [legacy.md の旧い設計の文書の扱い](legacy.md#旧い設計の文書の扱い) にある。

## 受け入れ条件との照らし方

#24 の成果物は文書で、受け入れ条件は設計文書を読んで判定する。受け入れ条件 1〜14 の本文は [要求の写し](requirements.md) にある。全体の設計のテスト設計の表は不変条件 I1〜I16 だけを持ち、受け入れ条件の行はここに置く。

| 受け入れ条件 | どの振る舞いで縛るか | どう壊したら落ちるべきか |
| --- | --- | --- |
| 1 | MVV と設計の節の対応の表が 13 行で、各行のリンク先の見出しがある | 行を消す・リンク先の見出しを消すと、レビューで数が合わない |
| 2 | 機能一覧の各行の「場面」の列が、利用の場面の表の番号を指す | 場面の列が空の行があると合わない |
| 3 | 画面一覧の「機能」の列と、操作の一覧の「機能」の列が、F1〜F20 を 1 回以上ずつ持つ | どちらかに無い F があると合わない |
| 4 | 画面の設計の節の並びが、土台の 5 つ → 画面ごとの項目の順 | 機能の画面が土台より先に来ると合わない |
| 5 | 操作の一覧の各行が、本文の形を配列で書く | 単数の本文の行があると合わない |
| 6 | 認可の節の出口の表が 7 行（要求の「7 経路」） | 行が欠けると合わない |
| 7 | 付録の表の各行が「MVV の項目」と「採否」の列を埋める | 空のセルがあると合わない |
| 8 | 付録を除く本文に、同等・凍結・入れ替えを主題にした見出しが無い | 見出しがあると合わない |
| 9 | 詳細設計がモジュールの置き場と依存の向き・横断の部品の関数の仕様と異常系の節を持ち、NDF の詳細設計の検査（`design-survey.py check --require-detail`）が通る | 節が無い・異常系の無い関数があると落ちる |
| 10 | 子の切り方の表（[plan.md](plan.md)）が、土台 → 画面 → API の順で、各行に F と I の列がある | 列が空の行があると合わない |
| 11 | `wc -l issues/issue-24-design*.md` が各 1,000 以下、NDF の用語集の検査（`glossary.py check`）の当たり 0 件 | 1 本が 1,001 行・未登録の語で落ちる |
| 12 | 漏れの検査（参照の検査）が設計文書を含む差分で通る | 実際の値を 1 つ書くと落ちる |
| 13・14 | cross-review の記録・設計承認ゲートの答え・#24 と子の課題の本文 | 記録が無いまま閉じると止まる |

認可の出口の表は、要求の「7 経路」を、プロジェクトの値が外へ出る 7 つの出口として扱った。設計文書では「プロジェクトの値が外へ出る出口を、次の 7 つとして扱う」と書く。

## NDF の検査

| 検査 | 打ち方 | 何を見るか |
| --- | --- | --- |
| 行の数 | `wc -l docs/design/*.md docs/design-process/issue-24/*.md` | 各 1,000 行以下 |
| 用語集の検査 | `glossary.py check --file <設計文書>` | 用語集（`.ndf/glossary.json`）に無い語の当たり 0 件 |
| 詳細設計の検査 | `design-survey.py check --require-detail` | 詳細設計の必須の節と、関数ごとの異常系 |
| 要求の写し | `spec-copy.py write` | #24 の本文から [requirements.md](requirements.md) を作り直す。手で直さない |
| 参照の検査 | `npm run -s ref-check`（照合の語を見るのは CI の「参照の検査」のジョブ） | 旧い側の名前（リポジトリ・表・バケット）の照合の語が設計文書を含む作業の木に無いこと、NDF の固定の値が 1 か所であること、版の数字の比べが無いこと。照合の語の照合が走るのは、環境変数 `REF_CHECK_TERMS` が渡ったときだけである。CI は秘密 `REF_CHECK_TERMS` から渡し、変数 `REF_CHECK_REQUIRE_TERMS` が `1` のリポジトリでの main への push と同じリポジトリの枝からの PR では、語が無ければ終了コード 2 で落ちる。手元で語を渡さずに打つと照合を飛ばし（`skip:` の行）、要求 12 を確かめたことにならない。要求 12 の判定は、PR の CI の「参照の検査」のジョブが語ありで通った記録で行う |
| 実際のインフラの値の確かめ | `grep -rnoE '\b[0-9]{12}\b\|arn:aws[a-z-]*:\|[a-z0-9.-]+\.amazonaws\.com' issues/ \| grep -v 123456789012` と、目での読み | 参照の検査は、アカウント ID・ARN・資源の ID・端点・実在の profile と運用する環境の名前を探さない。これらを形で探す漏れの検査（[土台の決定 92](../../design/platform.md#決定の記録)）は子の課題で足すため、それまでは左の grep で形の当たりが作り物の値（`123456789012`・UUID の一部）だけであることを確かめ、profile と環境の名前は作り物（`acme`・`test`）だけであることを PR の差分を読んで確かめる |
| 設計の検査（レッドライン） | NDF の設計の検査 | 全体の設計の「人へ残す判断」のレッドラインの定義の表を、列「レッドライン」で読む |

## cross-review と設計承認ゲート

| 段 | 中身 |
| --- | --- |
| cross-review | 設計文書をレビューし、記録を残す（受け入れ条件 13・14） |
| 設計承認ゲート | 承認する人は、全体の設計の「人へ残す判断」の 5 件を決める。どれもレッドラインに当たるため、AI が決めずに人へ残す。各行の「推しの案」はこの設計が採った案で、承認するとこの案で子の課題が進む。理由と採らなかった案は「詳しい置き場」の決定にある |
| NDF への起票 | 「人へ残す判断」の 5 行目（NDF が複数の課題を 1 回で受ける起動の口）は、NDF（devbasex/ai-plugins）へ口を求める課題を出すかを、設計承認と同じ問いで人が決める。他のリポジトリへの起票（C5）だからである |
