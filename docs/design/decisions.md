## 決定の記録

### 決定 1: 子の課題が 1 つの答えを読めるよう、食い違う事柄ごとに正本の文書を 1 つ決め、ほかの文書はリンクで指す

結論: 文書の間で同じ事柄を 2 か所に書かない。事柄ごとに正本の文書の節を 1 つ決めて答えを置き、ほかの文書はその節をリンクで指す。

理由: 同じ規則を 2 つの文書が文で持つと、片方だけを直したときに食い違いが戻る。たとえば問いに人だけが答える範囲を API の文書と実行の文書が別の文で持つと、2 つの答えになる。正本を決めればレビューは 1 か所を見ればよい。

採らなかった案: 両方の文書に同じ文をコピーして照らす検査を置く形。文の照らしが言い換えに弱く、検査を作る手間が答えを 1 か所に置く手間より大きい。

根拠: 根拠なし（MVV バージョン 3）

### 決定 2: サービスの器を 1 つにするため、個人で使う人を 1 人のチームとして扱い、「アカウント」の語をサービスの器に使わない

結論: プロジェクトを割り当てる単位は「チーム」だけで、個人で使う人は作成のときに 1 人のチーム（持ち主は本人）を持つ。サービスの器としての「アカウント」「個人のアカウント」の語を使わず、「アカウント」は AWS のアカウントの意味だけで使う。

理由: 器が 2 種類あると、画面の分岐・認可の判定・料金の線引きがどれも 2 通りになる。MVV の Vision と Value 9 は「チームに割り当てる」とだけ書き、個人の器を求めていない。AWS のアカウントと語が重なると、設置の文書と画面の文書で同じ語が別のものを指す。

採らなかった案: 個人のアカウントとチームのアカウントを分ける形。器ごとに画面と判定が分かれる。

根拠: Value 1・Value 9（MVV バージョン 3）

### 決定 3: 並列とリリースを NDF に任せるため、レーンを 1 つのリポジトリ分の NDF のスプリントにし、サービスはリリースをまとめない

結論: スプリントは 1 つのプロジェクトで選んだ課題のまとまりで、リポジトリごとに 1 つのレーンを持つ。レーンの中の課題の並列は NDF に任せる（NDF は worktree で同時 3 本まで回す。契約が複数の課題を 1 回で渡す口を持つまでは順に流す）。リリースもレーンごとに NDF が行う。リポジトリをまたぐ順序は計画の `after` で表す。サービスは「リリースのまとめ」を持たない。

レーンの中では、既存の NDF の流れ（`supervise.py new sprint` のプランとキュー）をそのまま使う。

理由: Vision は「課題を指せばスプリントが並列に回る」ことを求め、NDF は 1 つのスプリントの中の並列を既に持つ。ただし固定した NDF の契約は、Factory の実行に複数の課題を 1 回で渡す口を持たない（[決定 61](execution.md#決定の記録)）。口が足されるまでは、レーンの中の課題を順に流し、並列はリポジトリの間だけになる。サービスが工程の中身を持たなければ、NDF との境界は契約だけになる。

採らなかった案:

1. レーンを課題・ループ・リリースごとに分け、サービスのコードがリリースを 1 本にまとめる形。サービスが NDF の工程の中身（リリースの待ち・止まったリリース）を知る必要があり、NDF を変えるたびにサービスを直す
2. NDF の並列の計画（`--parallel`）のオーガナイザーをレーンに置く形。オーガナイザーのセッションが常に動き、費用と待ちが増える。複数のリポジトリを 1 つのプロジェクトで回す要求が育ったら、後で比べ直す

- 作り方: ライブラリやサービスを使う
- 比べた候補: STD62（[実行の文書の NDF の契約のファイル](execution.md#標準仕様)）

根拠: Vision・Value 1・Value 6（MVV バージョン 3）

### 決定 4: 手元の Claude Code と同じく会話しながら開発を進められるよう、ログインの後に最初に開く画面を AI のオーガナイザーの一覧と最後に開いた会話にする

結論: ログインの後は、オーガナイザーの一覧と最後に開いた会話を出す（狭い幅では会話を 1 つ出し、一覧へ切り替えられる）。人を待つもの（承認の依頼・問い）は、会話の知らせと付属の画面「承認待ちの一覧」の両方から辿る。知らせからは承認・問いの画面を直に開く（[オーガナイザー](organizer.md)）。

理由: Mission は工程を Web の画面から人も AI も同じく回すことを、Vision は何が動き何が人を待つかが分かることを求める。利用者は手元で conductor と会話しながら承認に答え、途中で指示し、起票を頼んで進めている。Web の画面でも同じ体験にする（#140 の利用者の決定、2026-11-24。旧い側では同じ方向の設計 #254 を 2026-11-14 に承認していた）。

採らなかった案:
- ホーム（いま）を最初の画面にし、人を待つものを先頭にスプリントを並べる（#24 の設計の結論）。待つものは読めるが、指示を出す・起票を頼む・進み方を相談する入口が無く、手元の会話の体験に届かない。人を待つものの 1 枚は「承認待ちの一覧」として残した（決定 155）
- スプリントの一覧を最初の画面にする。人を待つものが一覧の行の中に散る

根拠: Mission・Vision・Value 1・Value 4（MVV バージョン 3）

### 決定 5: 最初の版を迷わない広さにするため、開発ループ・役割の流れの画面などを後に回す

結論: 最初の版は機能一覧の F1〜F25 に限る。開発ループ・起票の依頼を一覧する画面・役割の流れの画面・レーンの木の画面・バックログの画面・料金の請求・メールの知らせは後に回す。AI のオーガナイザーとの会話（F24・F25）は、#140 の利用者の決定で最初の版に入れた。
理由: Value 1 は機能の数より迷わない速さを優先する。後に回すものは、F1〜F25 の上に足せる（モデルと API の規約を変えない）。

採らなかった案: 後に回す機能もすべて最初の版に入れる。画面の数が増え、Value 1 の手数の目標を満たせない。

根拠: Value 1・Value 5「先回りしない」（MVV バージョン 3）

### 決定 6: どの文書も 1,000 行に収めるため、プラットフォームの文書の「状態の置き場」をデータの文書へ分ける

結論: 状態の置き場（置き場の分け方・サービスの表・状態の S3・進行表の DB・形の版・CRUD 図）を [data.md](data.md) に置く。プラットフォームの文書の決定（80〜99・140）はプラットフォームの文書に残し、data.md はそれをリンクで指す。arc42 の 8 章（横断の概念）は data.md を指す。

理由: プラットフォームの文書は書き足しで 1,000 行を超える。状態の置き場はデータの主題として独立して読める。

採らなかった案: インフラ・費用・反映と設置を分ける形。arc42 の配置の見方と費用の見込みが離れ、Value 6 の読み筋が 2 つの文書に割れる。

根拠: Value 6（MVV バージョン 3）

### 決定 7: 判断の材料と記録を同じ期間読めるよう、承認資料の本文をプロジェクトを閉じてから操作の記録と同じ保存期間で消す

結論: 承認資料の本文は、プロジェクトを閉じてから、操作の記録と同じ保存期間（既定 1 年。設置する人が設定のファイルで延ばせる）で消す（[データの承認資料の保存期間](data.md#承認資料の保存期間)）。

理由: 承認資料は人の判断の材料で、操作の記録は判断の跡である。片方だけが先に消えると、記録から材料をたどれない。保存期間の値を 1 つにすれば、設置する人が延ばすときも 1 つの値で足りる。

採らなかった案: 別の保存期間の値を持つ形。設定のキーが増え、2 つの値の食い違いを許す。

根拠: Value 4（MVV バージョン 3）

### 決定 8: 料金の扱いを国を越えて後から足せる形にするため、使える量の判定と通貨つきの費用の記録を最初から持ち、請求は後に回す

結論: 最初の版は、料金プランの値（設定の値）・使える量の判定（1 か所、I8）・月の上限額と費用の記録（通貨つき、I15）を持つ。利用者から支払いを受ける請求の仕組みは最初の版に持たず、サービスを公開する前に決める。自分で設置した環境は上限を切る。

理由: Value 5 は金額を通貨とともに扱うことを、Value 6 は安く運用できることを求める。判定と記録が最初から無いと、上限で費用を止められない。請求の仕組みは公開の範囲と法令（Value 5）で形が変わり、いま決めると先回りになる。

採らなかった案: 請求まで最初の版に入れる。公開の前に決まらない条件（国・税・事業者）で形が決まる。

根拠: Value 5・Value 6（MVV バージョン 3）

### 決定 9: 運用の知らせを費用を増やさずに 1 つの宛先へ集めるため、運用の知らせの資源を 1 つの SNS のトピックにする

結論: 予算の知らせ・パイプラインの失敗・見回りが見つけた止まったレーンの数・差し替えの起こし直しの上限を、1 つの SNS のトピック（`<prefix>-<environment>-ops`）へ送る。宛先のメールは設定のファイルで受け、空なら購読を作らない（[プラットフォームの文書の非機能の実現方式](platform.md#非機能の実現方式)）。

理由: 送り手が違う知らせをトピック 1 つに集めれば、宛先の設定が 1 か所になる。SNS は時間の課金を持たず、要求とメールの無料の枠の中に収まる（[プラットフォームの文書の LIB84](platform.md#ライブラリとサービス)）。

採らなかった案: 送り手ごとに宛先を設定する形。設定のキーが送り手の数だけ増える。

- 作り方: ライブラリやサービスを使う
- 比べた候補: LIB84（プラットフォームの文書）

根拠: Value 6（MVV バージョン 3）

### 決定 10: 知らせを端末で確実に受けるため、通知先を Web Push と Slack にし、メールを後に回す

結論: 最初の版の通知先は、端末に入れた Web アプリへの Web Push と、利用者と nd-factory の Slack アプリの DM の 2 つ。メールは後に回す。Slack をチャンネルでなく DM にするのは、チャンネルにはチームの外の参加者がいて、投稿そのものがプロジェクトの存在を伝えるためである（[実行の文書の決定 75](execution.md#決定の記録)）。

理由: Vision と Value 3 はスマートフォンで人を待つものを知ることを求める。Web Push は知らせから承認の画面を直に開ける。メールは送信の評判の管理と配信の費用が要り、Value 6 の安く設置できる構成に合わない。

採らなかった案: メールを最初から入れる。自分で設置する人が送信の設定（ドメインの検証）を求められる。

根拠: Vision・Value 3・Value 6（MVV バージョン 3）

## 外部の調査

| 種類 | 調べるか | 理由 |
| --- | --- | --- |
| 標準・仕様 | 調べる | 全体の設計の書き方（arc42・C4）に一次の定めがある。主題ごとの標準（MCP・Web の画面・API の値の形・インフラ）は各文書が調べる |
| 主要な製品 | 調べない | 全体にかかる判断（主題・範囲）は MVV で決まり、製品の比べで変わらない。主題ごとの製品の比べは各文書が持つ |
| ライブラリとサービス | 調べない | 全体にかかる判断はライブラリを選ばない。主題ごとの比べは各文書が持つ |
