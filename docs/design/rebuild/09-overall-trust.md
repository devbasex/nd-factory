## 信頼の境界と権限

### 主体と経路

すべての要求は、API が要求を受けた時点で、次のどれかの主体に決まる。主体の決まらない要求は 401 で断る。

| 主体 | 資格情報 | 通る経路 | 確定できない操作 |
| --- | --- | --- | --- |
| 人 | 利用者プールの access token（画面からのログイン） | 画面 → API | 無し（認可の判定の範囲で、人だけが確定できる操作も確定できる） |
| 委任されたエージェント・クライアント | 委任の資格情報（人が発行し、期限と範囲を持つ） | API・MCP | 人だけが確定できる操作（承認ゲートの承認・判断への答え・プロジェクトの割り当て・NDF の共通原則のレッドライン C1〜C8 と P1〜P3 に当たる操作） |
| ランナー | レーンの token | ランナー向けの経路だけ | ランナー向けの経路の外のすべて |
| 手元のマシン | 登録の token | 手元のマシン向けの経路だけ | 同上 |
| GitHub | Webhook の署名 | Webhook の受け口だけ | 同上 |
| DB の用意のタスク | 終わりの報告の token（引き換えのときに受ける。決定 27） | そのタスクの終わりと失敗の報告の経路だけ | 同上 |

### 認可の判定とプロジェクトを見せる範囲

認可の判定はサーバーの 1 か所（横断の部品の「認可の判定」）に置き、画面の表示を隠すことに頼らない（決定 5）。

| 決まり | 中身 |
| --- | --- |
| 見える範囲 | 主体が人なら、その人が席を持つチームに割り当てたプロジェクト。委任されたエージェントなら、委任した人の見える範囲と、委任の範囲の重なり。ランナーなら、そのレーンのプロジェクトだけ。手元のマシンなら、自分に割り当てたレーンのプロジェクトだけ。DB の用意のタスクなら、用意するプロジェクトだけ。プロジェクトを別のチームへ移すときは、移す前にそのプロジェクトのレーンをすべて止めて割り当てを外すため、移す前のチームのランナーと手元のマシンからは、移した後のプロジェクトが見えない（[チームへの割り当て](05-overall.md#チームへの割り当て)） |
| 見えないときの応答 | 存在しないときと同じ 404。理由の本文も同じにする |
| 一覧と件数 | 表から読んだ行を認可の判定で絞ってから数える。絞る前の件数を応答・ログ・指標に出さない |
| 記録と知らせ | 操作の記録の読み出し・知らせの一覧・Slack の通知・検索の結果も、同じ判定で絞る。Slack の通知先は、割り当てたチームが登録したものだけ |
| MCP | ツールの一覧と呼び出しは API と同じ操作の表を通り、同じ判定を受ける |
| 迷うとき | 見せない（プロジェクト MVV の Value 9） |
| 割り当ての操作 | 作る・変える・外す・見える範囲を広げるのは、人が画面で確定した要求だけ（I3、P3） |

テストは、割り当ての外の主体で、画面・API・MCP・記録・知らせ・検索・件数の 7 つの経路から読み、どれでも存在が分からないことを確かめる（I2）。

### ECS のタスクの種類と権限

ECS のタスクの役割には、どのタスクの種類でも AWS の権限を持たせない（決定 10、I11）。タスクが要るものは、すべて API から引き換えの token で受け取る。ECR からの取得とログの書き込みは、タスクの実行の役割（ECS のエージェントが使う役割）が受け持ち、タスクの中のプログラムからは使えない。秘密の置き場とサービスの表に書くのは API（VPC の外の Lambda）だけである。

| 処理 | 動く場所 | 役割の AWS の権限 | 受け取る資格情報 | 接続先 |
| --- | --- | --- | --- | --- |
| ホステッドのランナー | ECS のタスク | 無し | 引き換えの token → レーンの token・そのプロジェクトの進行表の DB の URL・1 つのリポジトリに絞った GitHub の token・状態の S3 の署名つき URL。`managed` のレーンだけ、推論の一時の資格情報も受ける（下の「推論の経路」） | API（443）・進行表の DB のそのプロジェクトのデータベース（5432）・状態の S3（署名つき URL）・`managed` なら Bedrock の推論の端点（443） |
| DB の用意 | ECS のタスク（プロジェクトの最初のレーンの前に 1 回と、プロジェクトを別のチームへ移す確定のたびに 1 回。作成の失敗の後の作り直しと差し替えのやり直しでも起こす（下の「進行表の DB の作成が失敗したとき」「差し替えが失敗したとき」）） | 無し | 引き換えの token → DB の管理の接続の URL・作るデータベースと役割の名前とパスワード（API が作り、秘密の器へ先に入れたもの）・終わりの報告の token。移す確定のときは、差し替える役割の名前と新しいパスワード | API（443。終わりを知らせる）・進行表の DB（5432、管理の接続） |
| サービスの表の移し | Lambda（VPC の外。移しの関数） | サービスの表の読み書きだけ | — | DynamoDB |
| API と MCP | Lambda（VPC の外） | サービスの表・状態の S3・秘密の置き場（nd-factory の名前の頭）・`RunTask`・推論の役割への `sts:AssumeRole`（その 1 つの役割だけ） | — | 進行表の DB には接続しない（決定 8） |
| 推論の役割 | タスクの役割とは別の IAM の役割（API だけが引き受ける） | `bedrock:InvokeModel`・`bedrock:InvokeModelWithResponseStream`・`bedrock:GetInferenceProfile` を、環境の設定で選んだ推論のプロファイルと、そのプロファイルが指す基盤モデルにだけ | — | — |

DB の用意のタスクが受ける管理の接続は、データベースと役割を作る権限を持つ強い資格情報である。そのため、このタスクは claude と NDF を含まない nd-factory 自身のイメージで動かす。引き換えの token の種類を分けて、ランナーの引き換えでは管理の接続を返さない。

#### 推論の経路

`managed` の実行の手段の推論の経路である。タスクの役割は権限を持たないまま（決定 10）、`managed` のレーンの Bedrock の推論は、API が渡す一時の資格情報で呼ぶ。

| 項目 | 決まり |
| --- | --- |
| 引き受け | API は引き換えのときに、推論の役割を `sts:AssumeRole` で引き受ける（セッションの名前はレーンの ID、期間は 1 時間） |
| 返す先 | 得た一時の資格情報を、`managed` のレーンの引き換えにだけ返す。`byok` のレーンには返さない（持ち込んだキーで呼ぶ） |
| ランナーでの持ち方 | メモリだけに置き、ファイルとログに書かない |
| 取り直し | 期限の前（claude が値を取り直す期限の 5 分前より先）に、レーンの token の取り直しと同じ心拍で API から取り直し、手元の値を差し替える |
| 取り直しを断られた後 | ランナーは手元の古い値を返し続け、推論は期限で切れる。API はレーンの終わり・取り消し・プロジェクトを別のチームへ移す確定の後は取り直しを断るため、資格情報は最長でも 1 時間の残りで切れる |
| 推論の役割の権限 | Bedrock の推論の呼び出しに必要な操作（[AWS の必要権限](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-prereq.html)、取得日 2026-11-16）から、推論のプロファイルを使う呼び出しに要る 3 つだけに絞る |
| Bedrock を使える地域でない環境 | `managed` を切るため、推論の役割を作らない |

**実行中の claude へは、起動時の環境の値では渡さない。** 起動時の環境の値は claude のプロセスの中で変わらない。取り直した値が届かないまま、1 時間を超える区間で推論が切れるためである。代わりに次の形にする。

- claude を Bedrock の形で起こすときの設定の `awsCredentialExport` に、小さなコマンドを置く。コマンドは、ランナーが持つ今の資格情報を `Credentials`（`AccessKeyId`・`SecretAccessKey`・`SessionToken`・`Expiration`）の JSON で標準出力へ返す
- `awsAuthRefresh` は置かない
- コマンドは、ランナーのプロセスがコンテナの中だけで開くローカルのソケットへ問い合わせて値を受け、ファイルとログに書かない
- claude の中から打てば値を読めるのは、環境の値で渡す形と同じである。推論の役割の権限の範囲を越えない

**文書の記述と、確かめていない点。** 文書（[Claude Code の Bedrock の設定](https://code.claude.com/docs/en/amazon-bedrock)、取得日 2026-11-16）は、このコマンドについて次のように書く。

- 「セッションの始まりと、資格情報の読み直しのたび」に打つ
- `Expiration` を返せば、「その 5 分前まで」値を手元に持つ
- 資格情報の誤りが返ると、手元の値を捨てて読み直す

ただし、手元の値が期限で切れたときの読み直しでこのコマンドを打ち直すことは、文書が別の節（既定の資格情報の連鎖の読み直し）で書く動きからの推しである。このコマンドについての明記は無い。そのため、1 時間を超える区間で claude が新しい値で推論を続けることは、M3（#6）が固定の版の claude で実測して確かめる（[未確認のまま残ること](05-overall.md#未確認のまま残ること)）。続かないときは、区間を 1 時間より短く切る形と推論を中継する形を比べ直すため、設計へ戻す。

採らなかった案:

| 案 | 採らない理由 |
| --- | --- |
| API を推論の中継にする形 | 長く流れる応答を Lambda で中継し、費用と時間の上限が増える |
| タスクの役割に推論の権限を付ける形 | `byok` と DB の用意のタスクにも推論の権限が付き、I11 を破る |

#### token と資格情報の寿命

| token・資格情報 | 寿命 | 誰が持つか | 失効 |
| --- | --- | --- | --- |
| 引き換えの token | 10 分・1 回だけ | `RunTask` の環境の上書き（タスクの記述から読めるため、短く 1 回にする） | 引き換えた時点 |
| レーンの token | 1 時間。心拍で取り直す | ランナー | レーンの終わり・取り消し・プロジェクトを別のチームへ移す前の停止で、期限の前でも断る |
| 推論の一時の資格情報 | 1 時間。心拍で取り直す | `managed` のレーンのランナー（メモリだけに置き、ファイルとログに書かない）。実行中の claude は `awsCredentialExport` のコマンドで今の値を受ける（上の「推論の経路」） | 期限。レーンの終わり・取り消し・プロジェクトを別のチームへ移す確定の後は、API が取り直しを断る |
| 進行表の DB の URL | プロジェクトの役割が続く間 | ランナー（そのプロジェクトの分だけ。メモリだけに置き、ファイルとログに書かない） | 役割のパスワードの差し替え（運用の手順）。プロジェクトを別のチームへ移す確定でも差し替える（下の「プロジェクトを別のチームへ移すときの DB の資格情報の失効」） |
| DB の管理の接続の URL | 運用の手順で差し替えるまで | DB の用意のタスク（その 1 回だけ。メモリだけに置く） | 管理のパスワードの差し替え（運用の手順） |
| 終わりの報告の token | そのタスクの時間切れの上限まで・そのタスクの 1 回の起動だけ | DB の用意のタスク（メモリだけに置く） | 終わりか失敗の報告を受けた時点・時間切れの上限 |
| 登録の token | 人が取り消すまで | 手元のマシン | 人の取り消し |
| 委任の資格情報 | 人が発行のときに決めた期限 | エージェント・クライアント | 期限・人の取り消し |
| GitHub App の導入の token | GitHub が決める（1 時間） | API（ランナーへは 1 つのリポジトリに絞った token を渡す） | 期限。プロジェクトを別のチームへ移す確定で、ランナーへ渡し済みのものを API が期限の前に失効させる（下の「プロジェクトを別のチームへ移すときの GitHub の token の失効」） |
| 利用者の access token | 利用者プールの設定 | 画面 | 期限・ログアウト |

#### プロジェクトを別のチームへ移すときの GitHub の token の失効

ランナーへ渡した、1 つのリポジトリに絞った GitHub の token は、レーンの token を断っても期限（1 時間）まで有効である。控えた token から、移した後のリポジトリと課題を GitHub の API で直接読み書きできる（I2）。そのため、次の決まりで期限の前に失効させる。

| 場面 | 決まり |
| --- | --- |
| 渡すとき | API は、ランナーへ GitHub の token を渡すたびに、渡した token・期限・レーンを、サービスの表のプロジェクトの集約の記録の行に書く。同じトランザクションで、プロジェクトの行の記録の世代番号を必ず 1 つ上げ、「渡した token の期限の最大値」を条件つきで上げる（[サービスの表](08-overall-state-infra.md#サービスの表)） |
| 記録の値の扱い | 保存時の暗号化に頼るだけでなく、ログと画面と API の応答に出さない。期限を過ぎた行は TTL で消す |
| 今のチームの持ち主の確定 | レーンを止めた後に、下の「失効の順」で行う |
| それ以外の失敗（GitHub の障害など） | 割り当ての行に失効の未完了を記録し、見回りが同じ手順でやり直す |
| 移す先の受け入れ | DB の役割のパスワードの差し替えと一緒に、プロジェクトの行の期限の最大値が無いか今より前であること（期限の前の token が残っていないこと）を、同じ条件つきの書き込みで照らす。そうでなければ 409 で拒む（I15） |
| 確定から受け入れまで | この間（と、取り下げた後に差し替えが終わるまで）はレーンを始めないため、新しい token は渡らない |

失効の順:

1. 記録のうち期限の前の token をすべて、GitHub の失効の API（`DELETE /installation/token`。その token 自身で呼ぶ。[Revoke an installation access token](https://docs.github.com/en/rest/apps/installations#revoke-an-installation-access-token)、取得日 2026-11-17）で失効させる
2. 失効を受けた token と、既に期限切れ・失効済みで GitHub が認証の失敗を返した token は、失効済みとして記録から消す
3. すべて消し終えたら、読み始めた時の期限の最大値と世代番号のどちらも変わっていないことを条件に、プロジェクトの行の期限の最大値を消す
4. 変わっていたら、失効の途中に記録の行が足されている。記録を読み直して同じ手順をやり直す

#### プロジェクトを別のチームへ移すときの DB の資格情報の失効

レーンの token を断っても、渡し済みの進行表の DB の URL（役割のパスワード）は、役割が続く間有効である。控えた URL を別のホステッドのレーンから使うと、共通のタスクの SG を通って、移した後のデータベースを読み書きできる。そのため、今のチームの持ち主の確定は、レーンを止めた後に次の順で行う。

1. API が新しいパスワードを作り、秘密の器へ保留の版（Secrets Manager の段の名札 `AWSPENDING`）として入れる。今の版（`AWSCURRENT`）は古いパスワードのまま残す
2. API が差し替えの ID を割り当ての行に記録し、DB の用意のタスクを差し替えの種類で起こす
3. タスクは管理の接続で、そのプロジェクトの役割のパスワードを保留の版の値へ差し替え、その役割の今の接続をすべて切る。差し替えの ID を添えて、終わりを API へ知らせる
4. API は、割り当ての行が待つ差し替えの ID と合う知らせだけを受ける。保留の版を今の版へ移し（名札の付け替え）、差し替えの終わりを割り当ての行に記録する

ランナーの引き換えは今の版の URL だけを返すため、DB と食い違うパスワードを受けない。

#### 進行表の DB がまだ無いプロジェクト

データベースと役割は、そのプロジェクトの最初のホステッドのレーンを始めるときにだけ作る（[名前空間が無い間の分け方](08-overall-state-infra.md#名前空間が無い間の分け方)）。そのため API は、プロジェクトの行に進行表の DB の状態（`無い`・`作成中`・`有る`）を持つ。最初のホステッドのレーンの開始で `作成中` にし、DB の用意のタスクが作成の終わりを知らせたら `有る` にする。

今のチームの持ち主の確定は、この状態を同じ条件つきの書き込みで照らす。

| 状態 | 移す確定での扱い |
| --- | --- |
| `無い`（ホステッドのレーンを一度も始めていない・手元のマシンのレーンだけのプロジェクト） | 渡し済みの URL が無いため、差し替えを起こさない。割り当ての行に差し替えの ID を記録せずに「差し替え不要」と記録する。受け入れは、差し替えが終わったものとして照らす（取り下げた後のレーンの開始も、差し替えを理由に拒まない）。移した後の最初のホステッドのレーンが、新しいチームの下でデータベースと役割を作る |
| `作成中` | 作成のタスクが終わるまで、確定を 409 で拒む。作り終える前の役割のパスワードを差し替えると、作成のタスクと差し替えのタスクが同じ役割を取り合うため |
| `有る` | 上の差し替えを行う |

#### 進行表の DB の作成が失敗したとき

`作成中` は終わりの知らせだけで `有る` になるため、作成のタスクが失敗すると抜ける経路が要る。

| 項目 | 決まり |
| --- | --- |
| 作成の ID | API は `作成中` にするとき、差し替えと同じプロジェクトごとの番号から作成の ID を採り、プロジェクトの行に記録する。その ID を添えて、DB の用意のタスクを作成の種類で起こす。終わりの知らせは、記録した ID と合うものだけを受ける |
| 失敗と時間切れ | タスクが失敗を知らせたか、時間切れの上限までに終わりが届かないとき、API（上限は見回りが照らす）は前のタスクの終わりを確かめる（I7 と同じ確かめ方。時間切れなら止めてから確かめる）。その後、条件つきの書き込みで `作成中` を `無い` へ戻し、作成の失敗を記録して E15 で今のチームの持ち主へ知らせる |
| 前のタスクの遅れ | 終わりを確かめてから戻すため、遅れて動いた前のタスクが、やり直しの後に役割のパスワードや権限を変えることはない |
| `作成中` の間に始めたレーン | 作成を起こしたレーンを含め、引き換えの前に待つ。実行の制御は `有る` になってからそのレーンの `RunTask` を打つため、引き換えの token の 10 分は `有る` の後から数える。`無い` へ戻ったら、DB を作れなかったことを理由に失敗で終わる |
| 作り直しの操作 | `無い` のプロジェクトでホステッドのレーンを始めること（画面と、同じ操作の API・MCP。Value 4）。そのたびに上と同じく `作成中` にしてタスクを起こし直す。別の操作は足さない |
| 秘密の器 | API は作り直しで秘密の器の値を作り直さない |
| `無い` へ戻った間の移す確定 | 渡し済みの URL が無いため、上の「差し替え不要」で進む（`作成中` の間だけ 409） |
| 時間切れの上限の長さ | 差し替えの上限と一緒に、M2（#5）の詳細設計で決める |

作成のタスクは、同じ値で起こし直しても結果が同じになるようにする。

- データベースの名前は、プロジェクトの行に記録した値を使う
- データベースと役割が既に有れば作らずに、初回の作成と同じ権限の設定をすべてやり直す。やり直すのは次のもの（[名前空間が無い間の分け方](08-overall-state-infra.md#名前空間が無い間の分け方)の「カタログと統計」の (2)・(4)・(5)）
  - `postgres`・`template1` とそのデータベースの `CONNECT`・`TEMPORARY` の外しと付与
  - 専用のスキーマと役割の `search_path`
  - `ALLOW_CONNECTIONS true`
  - カタログと統計の読み取りの外しと、読み取りの既定の役割に入れないこと
  - プロジェクトの役割以外の接続の切断
- それらを終え、役割のパスワードを秘密の器の今の版の値にする
- どれか 1 つでも失敗したら、終わりを知らせず失敗を知らせる。そのため、権限が欠けたまま `有る` にならない

#### 差し替えを 1 つずつにする

**差し替えの ID は、プロジェクトごとに（割り当ての行をまたいで）単調に増える番号にする。** 割り当ての行は移すたびに新しい行になるが、番号は行ごとに数え直さない。API がプロジェクトの単位で採り（プロジェクトの行の番号を条件つきの書き込みで 1 つ上げる）、採った番号を割り当ての行に記録する。下の記録の表もプロジェクトごとの最大の番号を持つ。そのため、行ごとに数え直すと次の移す確定のタスクが記録以下の番号になり、差し替えが行われない。

**記録の表を、管理の接続先のデータベースに置く。** 進行表の DB の、どのプロジェクトのデータベースでもない管理の接続先のデータベースに置く。表は、プロジェクトごとに最後に入れた差し替えの番号を持つ。この表は管理の接続だけが読み書きでき、プロジェクトの役割からは読めない。

DB の用意のタスクは、次の順で差し替える。

1. 管理の接続で 1 つのトランザクションを開き、そのプロジェクトの記録の行を行の lock（`SELECT ... FOR UPDATE`）で取る
2. 記録の番号が自分の ID 以上なら、パスワードを変えず接続も切らずに、何もしなかったことを知らせて終わる（遅れて動いた前のタスク）
3. 小さいときだけ、lock を持ったまま役割のパスワードを保留の版の値へ変え、記録の番号を自分の ID にしてトランザクションを確定する。確定の前は古いパスワードがまだ効くため、接続はここでは切らない
4. 確定の後に、その役割の接続をすべて `pg_terminate_backend` で切る
5. `pg_stat_activity` でその役割の接続が 0 本になったことを確かめてから、終わりを知らせる。0 本にならなければ失敗を知らせる

API は「何もしなかった」の知らせを、差し替えの終わりとして受けない。割り当ての行が待つ ID のタスクがこの知らせを返したときは、番号の採り方の誤りで、パスワードが保留の版の値になっていない。そのため、保留の版を今の版へ移さず、差し替えの失敗（下の「差し替えが失敗したとき」）として扱う。

この順で、次のことが成り立つ。

- 確定した後は、古いパスワードで新しく接続できない。保留の版の値はどのランナーにも渡っていない（引き換えは今の版だけを返す）。そのため、その役割の新しい接続は生まれない
- lock を持つ間は、別のタスクが同じ行で待つ。そのため 2 つのタスクのパスワードの変更は交わらず、前の ID のタスクが後から値を戻すことはない
- 前の ID のタスクは、記録の番号を見て接続を切らずに終わる。差し替えの終わりが記録されるまで、そのプロジェクトのレーンは始まらない（下の「受け入れと取り下げ」）。そのため、確定の後の切断が、再開したレーンの接続を切ることもない

#### 差し替えが失敗したとき

タスクが失敗を知らせたか、時間切れの上限までに終わりが届かないとき、API（上限は見回りが照らす）は割り当ての行を差し替えの失敗にし、E15 で今のチームの持ち主へ知らせる。今の版は古い値のままである。

| 項目 | 決まり |
| --- | --- |
| やり直し | 持ち主は差し替えをやり直せる（画面と、同じ操作の API・MCP。Value 4）。やり直しは、前のタスクの終わりを確かめてから（I7 と同じ確かめ方）、同じ保留の版の値に新しい差し替えの ID を付けてタスクを起こし直す |
| 時間切れのタスクが DB を変え終えていたとき | DB は保留の版の値で、記録の番号は前の ID になっている。やり直しのタスクは番号が大きいため、同じ値を入れ直して終わりを知らせる。API は今の版を保留の版の値へ移すため、DB と秘密の器は食い違わない |
| 前のタスクの知らせ | ID が合わないため記録されない |
| 時間切れの上限の長さ | 受け入れの期限と一緒に、M2（#5）の詳細設計で決める |
| 失敗が続くとき | 新しい操作は足さない。失敗のたびに E15 で今のチームの持ち主へ知らせ、知らせに運用者の手順の置き場を添える。手順（原因の調べ方と、やり直しを打つ前に直すこと）は、パスワードの差し替えの手順と一緒に M10 が運用の文書に書く（決定 9） |

#### 受け入れと取り下げ

| 場面 | 扱い | 理由 |
| --- | --- | --- |
| 移す先の受け入れ | 終わっていないレーンの有無と期限の前の GitHub の token の残り（上の「プロジェクトを別のチームへ移すときの GitHub の token の失効」）と一緒に、差し替えが終わったことを同じ条件つきの書き込みで照らす。終わっていなければ 409 で拒む（I15） | — |
| 確定の取り下げ | 差し替えを止めず、パスワードを戻さない | — |
| 取り下げた後の、もう一度の確定 | 前の差し替えが終わる前（失敗ならやり直しが終わる前）の要求は 409 で拒む | 保留の版の値を、差し替えの途中で入れ替えないため |
| 取り下げた後の、レーンの開始 | 差し替えが終わるまで（失敗ならやり直しが終わるまで）、そのプロジェクトでレーンを始める要求を 409 で拒む | DB がまだ古いパスワードのままか、遅れて動いた差し替えのタスクに接続を切られるため |
| 差し替えが終わった後のレーン | 引き換えで新しい URL を受ける | — |

差し替えを確定ごとに行うため、旧いチームのランナーが控えた URL はどの経路からも使えない。

### 承認ゲートを無効にさせない守り

NDF は `ndf answer --by service:<主体>` の答えをどこまで信用するかを決めていない（devbasex/ai-plugins#3364）。決まるまで、nd-factory は 2 つの守りを置く（仮置き、決定 11）。

**防ぐ守り。**

- コンテナの中で、ランナーと claude を別の OS の利用者で動かす
- NDF が答えを書き込むファイルはランナーの利用者が持ち、claude の利用者には書き込みの権限を与えない
- ファイルの権限は OS が掛ける。そのため、claude が起こす Python・Node などの子プロセスと、claude の中から打つ `ndf answer` にも同じく効き、人の答えの無い承認は書き込みの時点で失敗する
- 承認の依頼を書くファイルは、claude の利用者が書ける
- `ndf answer` を打てるのは、API から人の答えの ID を受けたランナーのプログラム（claude の外）だけ
- claude の許可の設定でも、`ndf answer` と答えのファイルへの書き込みを拒む。ただし許可の設定は、claude のツールと認識できるコマンドにだけ効き、子プロセスの間接のファイル操作を防がない（[Claude Code の許可の設定の適用範囲](https://code.claude.com/docs/en/permissions)、取得日 2026-11-16）。そのため、重ねる守りに留める
- 答えの置き場が DB の版では、この守りを迂回できる。ホステッドのレーンでは NDF の状態を進行表の DB に置き（決定 6）、コンテナの中の NDF は `NDF_PROGRESS_DB` の役割のパスワードで読み書きする。NDF が答えを DB の行として残す版では、claude の利用者とその子プロセスが同じ URL で答えの行を直接書け、ファイルの権限の分離を迂回できる。そのため、答えの置き場が DB かどうかを M3 で確かめ（下の表）、DB なら防ぐ守りが効かないものとして設計へ戻す（表の下の段落）

**照らす守り。**

- ランナーは、自分が打った `ndf answer` を 1 回ずつ控える（答えの ID・表の ID・時刻）
- 区間の後に NDF の進捗のファイルを読む。答えの事象（`answered`・`row_answered`）が、控えの無い時刻か表の ID で現れたら、ランナーの外で答えが書かれたとみなす
- そのときは、レーンを止め、人へ知らせ、進捗の事象に残す（I5）

2 つの守りの根拠と、確かめていない点:

| 点 | 根拠 | 状態 |
| --- | --- | --- |
| `ndf answer` が冪等の鍵を受けること | `C/schemas/io/answer.args.schema.json` の `--key`（31〜34 行目、「冪等の鍵（同じ鍵の答え直しは書かない）」） | 契約にある |
| 答えの鍵が NDF の記録に残ること | 契約の事象の表 `C/workflow/progress.json` の `answered`（45 行目）と `row_answered`（54 行目）は、鍵の項目を持たない | 契約に無い。照らす守りは鍵を比べず、ランナーの控えと答えの事象の有無を比べる |
| 進捗のファイルの答えの事象が、表の ID と時刻を持つこと | 契約の事象の表は種類と主体だけを定める | 未確認。M3（#6）が固定の版の NDF で、答えの事象の 1 行の項目を確かめる |
| 防ぐ設定で起こした claude の中でも、承認ゲートが承認の依頼を書き、区間が `判断が要る` で終わること | 契約ファイルに、承認ゲートが書くファイルと答えを書くファイルの区別の記述が無い | 未確認。M3（#6）が固定の版の NDF で、答えを書くファイルの一覧を特定し、claude の利用者から書けない権限の下で承認ゲートを 1 回通して確かめる。あわせて、claude の利用者から `ndf answer` を打つと書き込みが失敗し、答えの事象が現れないことを確かめる。M5（#8）は確かめた結果を承認の確定の流れに使う |
| 答えが進行表の DB の行に書かれないこと | 契約の事象の表は答えの事象の置き場を定めない。`NDF_PROGRESS_DB`（`C/domains/env.json` の `/rows/53`）は NDF の状態の置き場の URL で、claude の利用者の子プロセスからも読める | 未確認。M3（#6）が固定の版の NDF で、承認ゲートを 1 回通した後に進行表の DB の表を読み、答え（`answered`・`row_answered` に当たる行や列）が DB に書かれるかを確かめる。あわせて、claude の利用者から `NDF_PROGRESS_DB` の URL で答えに当たる行を書き込めるかを確かめる |

M3 の確認で次のどれかが分かったときは、防ぐ守りを外して照らす守りだけで進めず、設計へ戻して人の判断を受ける。

- 答えを書くファイルが承認の依頼と同じファイルで、権限を分けられない
- 防ぐ設定の下で、承認ゲートが動かない
- 答えが進行表の DB に書かれる（claude の利用者が `NDF_PROGRESS_DB` の URL で答えの行を書ける）

NDF の側で信用の規則が決まったら、照らす守りの比べ方をその規則へ差し替える。防ぐ守りは残す。

### 承認の確定

| 決まり | 中身 |
| --- | --- |
| 人だけ | 承認ゲートの承認と判断への答えは、人の access token の要求だけが確定できる。委任の資格情報からは依頼と材料を読めるが、確定は 403（I3・I4） |
| つながらないとき | 画面は、つながっていない間は確定のボタンを確定待ちの操作に変え、確定しない。つながった後に、サーバーの今の状態（承認の依頼がまだ待っている・承認資料の要約値が画面で読んだものと同じ）と照らし、合えば確定する。合わなければ 409 を返し、画面は読み直しを促す |
| 1 回だけ渡す | 答えの ID を `ndf answer --key` に渡す。ランナーは送達の事象を送り、API は答えの送達の状態を持つ（I5） |

### 伏せ字

ログ・進捗の事象・会話・知らせへ書く前に、横断の部品の伏せ字を通す。伏せ字の対象は、形の正本の秘密の形の表（登録の token・委任の資格情報・レーンの token・引き換えの token・終わりの報告の token・DB の URL・推論の一時の資格情報・GitHub と OAuth の秘密）である。値の一部も残さない。ランナーは、NDF のファイルを翻訳して API へ送る前と、外へ送る本文（起票の依頼・会話）にも同じ伏せ字を通す。操作の記録は、秘密と個人情報の値を書かず、種類と ID だけを書く（I9）。

### API と MCP の認可

| 決まり | 中身 |
| --- | --- |
| 1 つの操作の表 | 操作ごとに、人だけが確定できるか・使える量の判定が要るか・委任の範囲のどれに当たるかの印を持つ（[入出力の規約と形の正本](07-overall-contracts.md#入出力の規約と形の正本)） |
| 主体の確かめ | 委任の資格情報は、だれの委任か（利用者）と、どのエージェント・クライアントかを持ち、要求ごとに期限と取り消しを確かめる |
| 記録 | 読み取りを含むすべての操作を、だれが・いつ・どの経路（画面・API・MCP・ランナー）で・何を行ったかとして、追記だけの記録に残す |
| 抜け道を作らない | MCP にしか無い操作、API にしか無い操作、画面にしか無い操作を作らない。検査（#1）が、操作の表に無い経路の登録を落とす |

## 料金プランの線引き

**作り直しの未決（料金プランの課金の範囲）への答え。** コードはすべて公開し、運営のクラウドでだけ料金プランで線を引く。自分で設置した環境は上限なしの行を使い、すべての機能を使える（PRD1・PRD2、決定 16）。この線引きは設計の答えで、課金に関わるため、設計承認ゲートでの承認がその採否になる。金額はこの設計で決めない。

| 区分 | 使える機能 | 使える量 |
| --- | --- | --- |
| 自分で設置 | すべての機能 | 上限なしの行（同時の数・月の token・月の上限額の判定を切る）。課金の連携を作らない |
| クラウドの free | 個人。`local` の実行の手段（手元のマシン）だけ。ランナー・承認・画面・タイムライン・API と MCP からの操作はすべて使える。プロジェクトは作った個人のアカウント（1 人のチーム）へ自動で割り当てる | 同時のスプリントの実行の数を小さく持つ |
| クラウドの pro・max | 個人。free に加えて、`byok` と `managed` の実行の手段（ホステッドのレーン）・Slack の通知。プロジェクトの割り当ては free と同じ | プランごとの同時の数と月の token |
| クラウドの team | 席と役割・チームでの承認の回し方・チームのアカウントへの割り当てとチームの間で移す操作・AI のオーガナイザー・月の上限額・操作の記録の閲覧 | 席の種類ごとの使える量 |
| enterprise（作り直しでは作らない） | SAML の SSO・SCIM・操作の記録の書き出しと長期の保持・個別の契約 | 個別 |

無料のままにするもの: ランナーと nd ランタイム・承認の流れ・CDK の定義。nd-factory を信頼する材料そのものだからである。

この線引きで決めていること:

| 点 | 決まり | 理由 |
| --- | --- | --- |
| プランで制限するもの | 機能と使える量（同時の数・月の token・実行の手段の種類）。操作の経路（画面・API・MCP）では制限しない | Value 4 と API の規約（[入出力の規約と形の正本](07-overall-contracts.md#入出力の規約と形の正本)）は、画面にしか無い操作を作らないことを求める。MCP を一部のプランに限ると、そのプランでは画面にしか無い操作が生まれる。共通原則の優先順位で MVV が料金プランの線引きより上にあるため、経路はどのプランでも同じにする |
| 個人のプランでのプロジェクトの割り当て | 個人のアカウントを 1 人のチームとして、作成と同じ操作で割り当てる（[チームへの割り当て](05-overall.md#チームへの割り当て)の表）。team の列が持つのは、チームのアカウントへの割り当てと、チームの間で移す操作だけ | I2 は割り当てたチームの人だけがプロジェクトを見られるとし、E3 は E4 の前提である。個人のプランで割り当てが使えないと、だれもプロジェクトを見られない |

### 上限なしへの切り替え方

| 決まり | 中身 |
| --- | --- |
| 切り替えの場所 | 設定のファイルの項目 1 つ（料金プランの表の選び方: 運営のクラウドの表か、上限なしの行か）。既定は上限なしの行 |
