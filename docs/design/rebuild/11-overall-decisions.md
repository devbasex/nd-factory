# 作り直しの全体設計: 決定の記録

頭の文書は [05-overall.md](05-overall.md) にある。決定ごとに、文脈・決定・採らなかった案と理由・影響を書く。番号は頭の文書とほかの設計文書から引く。

## 決定の記録

### 決定 1: 旧い事情を新しいリポジトリへ持ち込まないため、段階的な置き換えでなく一括の入れ替えにする

- 文脈: 作り直しはデータを移さず（利用者の答え（データを移さない））、App とクライアントを新しく作る（利用者の答え（App とクライアントを新しく作る））。新しいリポジトリは公開する
- 決定: 新しいリポジトリで空から作り、機能の対応表の試走で同等を確かめてから、利用者の使う先を替える（[比較の表](06-overall-architecture.md#一括の入れ替えと段階的な置き換え)）
- 採らなかった案と理由: API の経路ごとに振り分ける段階的な置き換え（STD3・STD4）は、旧い側とのデータの同期と振り分ける層を要し、データを移さない決定と公開の制約に合わない
- 影響: 試走（#3）と入れ替えの判定（#15）が同等の唯一の確かめになる。戻し方は決定 22

根拠: Value 7（MVV 版 1）

### 決定 2: NDF の改修を待たずに作れるよう、NDF とは公開された言語で話し、ランナーを腐敗防止層にする

- 文脈: NDF が上流で、nd-factory は NDF の集約を変えられない。旧い側は NDF の内部のスクリプトと状態のファイルを直に扱い、NDF 11 で動かなくなる（作り直しの調査（旧い側。移していない）の 4 節の 1・3・5）
- 決定: やり取りは契約ファイルのエントリポイントと形だけにする。NDF の語を nd-factory の語へ変えるのはランナーだけで、API と画面は NDF の語を持たない
- 採らなかった案と理由: NDF の進行表の DB をサービスが直に読む形は、NDF の表の形に nd-factory が縛られ、NDF の形の変更で API が壊れる
- 影響: 契約の照合のジョブ（#1）が翻訳を見本で照らす。翻訳の入力は NDF の側で事象の流れ（devbasex/ai-plugins#3694）が出たら差し替える

根拠: Value 4 / Vision（MVV 版 1）

### 決定 3: 1 語 1 意味にするため、決まった芯をリリースのまとめの集約にし、AI のオーガナイザーと分ける

- 文脈: 旧い側は「Factory のオーガナイザー」の語で、サーバーのコードと AI のセッションの 2 つを指す
- 決定: 決まった芯の役割は実行のコンテキストの「リリースのまとめ」、AI のセッションはオーガナイザーのコンテキストの「AI のオーガナイザー」にする。「Factory のオーガナイザー」の語は新しいリポジトリで使わない
- 採らなかった案と理由: 1 つの集約にまとめると、会話を持たないリリースのまとめが会話の集約の持ち主の制約を受ける。改名を待つと、子の設計が語を決められない
- 影響: M3 がリリースのまとめ、M7 が AI のオーガナイザーを受け持つ。改名の保留が解けたら名前だけを差し替える

根拠: Value 1（MVV 版 1）

### 決定 4: NDF の未決を待たずに作れるよう、プロジェクトは主 1・サブ N の器だけを先に置く

- 文脈: プロジェクトの宣言の形（devbasex/ai-plugins#2653）は NDF の側で未決。1 レーンは 1 リポジトリ
- 決定: プロジェクトは主リポジトリ 1 つとサブリポジトリ 0 以上の一覧と、チームへの割り当てだけを持つ。リポジトリをまたぐ作業は計画の宣言のレーンの `repo` と `after` で表す
- 採らなかった案と理由: 宣言のファイル（`.ndf/repos.json`）を nd-factory が先に決めると、NDF の決定と食い違ったときに作り直しになる
- 影響: M2 が器と割り当てを作る。宣言の形が決まったら、器から宣言を作る口を足す

根拠: Vision / Value 9（MVV 版 1）

### 決定 5: 割り当ての外から存在が見えないよう、認可の判定をサーバーの 1 か所に置く

- 文脈: プロジェクトは割り当てたチームにだけ見せる（Value 9）。画面・API・MCP・記録・知らせ・検索・件数のどれかが判定を抜けると、存在が漏れる
- 決定: 横断の部品の「認可の判定」だけが見える範囲を決め、すべての経路がそこを通る。見えないプロジェクトは存在しないときと同じ 404 にし、件数は絞った後に数える
- 採らなかった案と理由: 経路ごとに判定を書く形は、経路を足すたびに判定の抜けが起きうる。画面で隠す形は API と MCP を守らない
- 影響: 検査（#1）が、判定を通らない読み出しを落とす。I2 のテストは 7 つの経路で行う

根拠: Value 9 / Value 4 / P3（MVV 版 1）

### 決定 6: 使わない間の費用を止めつつ DBOS を動かすため、進行表の DB を Aurora Serverless v2 にする

- 文脈: 作り直しの未決（進行表の DB の置き場）。DBOS は advisory lock と LISTEN を使う（LIB1）
- 決定: Aurora Serverless v2（PostgreSQL、最小 0 ACU）を出口の無いサブネットに置き、ECS のタスクから直に接続する。RDS Proxy と Data API を使わない
- 採らなかった案と理由: Aurora DSQL は lock を取らない同時実行の制御・1 時間で切れる接続・一時表の無さが DBOS の使い方と合わない（LIB3）。RDS Proxy は LISTEN とセッションの advisory lock でピン留めになり、一時停止も妨げる（LIB4）
- 影響: 一時停止と再開と keepalive の実測を M10 が受け持つ（[未確認のまま残ること](05-overall.md#未確認のまま残ること)）

- 作り方: ライブラリやサービスを使う
- 比べた候補: LIB2 / LIB3 / LIB4 / LIB1

根拠: Value 6（MVV 版 1）

### 決定 7: NDF の名前空間が無い間もプロジェクトの間で状態が混ざらないよう、プロジェクトごとにデータベースと役割を分ける

- 文脈: `NDF_NAMESPACE`（devbasex/ai-plugins#3694）は NDF に無い。1 つのデータベースを共有すると、別のプロジェクトの進行表が同じ表に入り、コンテナの中の claude が同じ URL で読める。見せる範囲の単位はプロジェクトである（I2、Value 9）
- 決定: 1 つのクラスタの中で、プロジェクトごとにデータベースとログインの役割を作る（仮置き、I10）
- 採らなかった案と理由: アカウントごとに分ける形は、同じアカウントのプロジェクトを別のチームへ移したとき（I15 の移す操作）に、移した先のチームのレーンから元のチームのプロジェクトの状態が読める。プロジェクトごとにクラスタを作る形は、最小の費用（ストレージ）がプロジェクトの数だけ掛かる。スキーマで分ける形は、NDF が接続の URL のスキーマを選べるかを確かめていない
- 影響: DB の用意のタスク（M10）が要る。名前空間が入ったら、新しいプロジェクトから共有に入れる

根拠: Value 9 / Value 6（MVV 版 1）

### 決定 8: Lambda を VPC の外に置けるよう、進行表の DB に触れるのは ECS のタスクだけにする

- 文脈: Lambda を VPC の外に置く（作り直しの親の課題（旧い側））。出口の無いサブネットの DB へ、VPC の外の Lambda は届かない
- 決定: サービスは進行表の DB を読み書きしない。DB に接続するのは、ホステッドのランナーと DB の用意の ECS のタスクだけ。サービスの表の移しは VPC の外の Lambda が行い、進行表の DB に接続しない（NDF が進行表の形を持つため、nd-factory は進行表を移さない）
- 採らなかった案と理由: Data API を使う形は、Data API の接続が一時停止を妨げるかを確かめておらず、NDF の表をサービスが読む形（決定 2 で採らない）につながる
- 影響: サービスが NDF の状態を知る経路は、ランナーが送る進捗の事象だけになる

根拠: Value 6 / Value 4（MVV 版 1）

### 決定 9: NDF が token を取り直せないため、進行表の DB の認証はパスワードにする

- 文脈: IAM 認証の token は 15 分で、確立した接続には効かない（LIB2 の IAM 認証の頁）。NDF の DB の接続は URL 1 つ（`NDF_PROGRESS_DB`）で、再接続のときに token を取り直す口を持たない
- 決定: プロジェクトごとの役割のパスワードを含む URL を秘密の置き場に置き、API がレーンへ渡す。経路は Aurora の SG（タスクの SG からの 5432 だけ）で絞る
- 採らなかった案と理由: IAM 認証は、15 分を過ぎた後の再接続で失敗する
- 影響: パスワードの差し替えの手順を M10 が運用の文書に書く。NDF が token の取り直しを持ったら IAM 認証へ移る

根拠: Value 7（MVV 版 1）

### 決定 10: タスクから AWS の資源を直に触らせないため、タスクの役割に権限を持たせず、引き換えの token で始める

- 文脈: 作り直しの親の課題（旧い側）は、タスクの役割をそのジョブの行とキーの範囲に絞り、token をジョブの間だけ有効にすることを求める。旧い側では、レーンごとに秘密の器を作る形が権限の不足を起こした
- 決定: タスクの役割は、ホステッドのランナーと DB の用意のどちらの種類でも AWS の権限を持たない（[ECS のタスクの種類と権限](09-overall-trust.md#ecs-のタスクの種類と権限)）。`RunTask` には 10 分・1 回だけの引き換えの token を渡し、タスクは API でレーンの token と DB の URL に引き換える。秘密の器を作るのとサービスの表を書くのは API だけで、DB の用意のタスクは API が作った値を受けてデータベースと役割を作る。範囲の絞り込みは API のレーンの token の判定が行う
- 採らなかった案と理由: タスクの役割に表とキーの条件つきの権限を付ける形は、レーンごとの条件を IAM で表せず、絞り込みが粗くなる。レーンの token を環境の上書きで渡す形は、タスクの記述から 1 時間有効な token が読める
- 影響: M3 が引き換えの経路を作る。`managed` のレーンの Bedrock の推論は、タスクの役割では呼ばない。API が推論の役割（推論の呼び出しだけを持つ別の役割）を引き受け、引き換えで渡す 1 時間の一時の資格情報で呼ぶ（[推論の経路](09-overall-trust.md#推論の経路)）。ECR とログはタスクの実行の役割が受け持つ。サービスの表の移しは Lambda の移しの関数が受け持つ（#2）

根拠: Value 7 / Value 4（MVV 版 1）

### 決定 11: NDF の信用の規則が決まるまで承認ゲートを無効にさせないよう、防ぐ守りと照らす守りを置く

- 文脈: `ndf answer --by service:<主体>` の信用の規則は未決（devbasex/ai-plugins#3364）。コンテナの中の claude が `ndf answer` を打てば、人の答え無しに承認ゲートを通れる
- 決定: claude を、`ndf answer` の実行と答えを書くファイルへの書き込みを拒む設定で起こす（防ぐ）。ランナーが打った `ndf answer` の控えと、NDF の進捗のファイルの答えの事象を照らす（照らす）。答えの鍵が NDF の記録に残ることは契約に無いため、鍵では照らさない。仮置き
- 採らなかった案と理由: 防ぐ守りだけでは、設定を抜ける経路を見逃す。照らす守りだけでは、通った後にしか分からない
- 影響: M3 と M5 が受け持つ。答えの事象の項目と、防ぐ設定の下で承認ゲートが動くことは未確認で、M3 が固定の版の NDF で確かめる（[承認ゲートを無効にさせない守り](09-overall-trust.md#承認ゲートを無効にさせない守り)）。NDF の規則が決まったら照らす比べ方を差し替える

根拠: Value 4（MVV 版 1）

### 決定 12: 形の正本を 1 つにするため、zod の定義から型・JSON Schema・OpenAPI・環境変数の表を生成する

- 文脈: NDF の作り直しでは形が 3 重に書かれ、1 PR のレビュー 24 件のうち 15 件が形の食い違いだった（反省点 9）
- 決定: `packages/contracts/` に zod で形を定義する。そこから型（`z.infer`）・JSON Schema（`z.toJSONSchema`）・OpenAPI（zod-openapi）・環境変数の表・設定のファイルの JSON Schema を生成する。往復の検査で生成物と照らす
- 採らなかった案と理由: TypeSpec は OpenAPI と JSON Schema を作れるが、実行時の入力の検証と型に別の生成が要り、正本と検証の 2 つを持つことになる（LIB6）
- 影響: 日時などの JSON Schema に表せない型は文字列の形式で持つ（LIB5）。#2 が置き場を作る

- 作り方: ライブラリやサービスを使う
- 比べた候補: LIB5 / LIB6

根拠: Value 2 / Value 4（MVV 版 1）

### 決定 13: 形の正本を CDK からも直に読めるよう、新しいリポジトリの CDK を TypeScript で書く

- 文脈: 旧い側の CDK は Python で、環境変数の名前は旧い側の `factory/.env.example` を介してだけつながる。形の正本を TypeScript に置くと、Python の CDK は生成物を読み直すことになる
- 決定: 新しいリポジトリの CDK のアプリとスタックのテストを TypeScript で書き、`packages/contracts/` の環境変数の表と設定のファイルの形を直に読む
- 採らなかった案と理由: Python の CDK を引き継ぐ形は、正本から Python 向けの生成物を作る経路と、その往復の検査が 1 つ増える
- 影響: スタックのテストは `aws-cdk-lib/assertions` と vitest で書く。骨組みが構成を作る

根拠: Value 2（MVV 版 1）

### 決定 14: 誰のアカウントにも設置できるよう、環境の値を profile と設定のファイルと秘密の器の 3 つから受ける

- 文脈: 旧い側は環境の設定に実際の値を持つ。新しいリポジトリは公開し、作り物の値だけを置く
- 決定: アカウントとリージョンは profile、それ以外の環境の値はリポジトリの外の設定のファイル、秘密は秘密の置き場の器から受ける。合成は資格情報なしで通る
- 採らなかった案と理由: SSM のパラメーターから読む形は、合成に資格情報が要り、CI の合成を作り物の値で通せない
- 影響: 運用する環境の設定のファイルの置き場を骨組みが決める。漏れの検査（#1）は探す値を非公開の置き場から受ける

根拠: Value 7 / Vision（MVV 版 1）

### 決定 15: 差分を人が承認した範囲だけを運用する環境へ届けるため、反映の経路を運用する環境と自分で設置する人で分ける

- 文脈: プロジェクト MVV の Value 8 は、運用する環境への反映を CD（CodePipeline）が人の承認した範囲だけ行うとする。作り直しの決まったことは、誰でも `cdk deploy` で設置できることを求める
- 決定: 運用する環境は反映のパイプラインの承認のアクションで人が差分を承認する。自分で設置する人は設置のコマンドで `cdk deploy` を打つ。どちらも同じ CDK のアプリと設定のファイルの形を使う
- 採らなかった案と理由: 設置のコマンドだけにする形は、運用する環境の反映を CD が行う Value 8 と合わない。反映のパイプラインだけにする形は、組織の接続を持たない設置する人が使えない
- 影響: 反映のパイプラインのスタックは設定のファイルで有効にしたときだけ作る。骨組みが両方を作る

根拠: Value 8 / Vision（MVV 版 1）

### 決定 16: 公開したコードを信頼の材料にするため、料金プランの線は運営のクラウドでだけ引き、自分で設置した環境は上限なしの行を使う

- 文脈: 作り直しの未決（料金プランの課金の範囲）。公開しつつ運営のクラウドで課金する製品は、自分で設置した版の機能を絞らない（PRD1・PRD2）
- 決定: [料金プランの線引き](09-overall-trust.md#料金プランの線引き)の表のとおり。切り替えは設定のファイルの項目 1 つで、判定は使える量の判定の 1 か所
- 採らなかった案と理由: 一部の機能を別のライセンスの置き場に分ける形（PRD3）は、enterprise の機能を作るまで分ける中身が無い。画面でプランの名前を見て分岐する形は、判定が 2 か所になる
- 影響: 機能の対応表（[対応表の設計](03-parity.md)）に「どのプランで使えるか」の列が要る。金額は決めない

根拠: Mission / Value 6（MVV 版 1）

### 決定 17: NDF 11.0 と 10.x を取り違えないよう、NDF の機能を版の数字でなく契約の版で判断する

- 文脈: 旧い側は版の下限を数字で比べ、11.0.0 は 10.x のどの下限も満たすため見分けられない（作り直しの調査（旧い側。移していない）の 4 節の 2）。`ndf capabilities` は NDF に無い
- 決定: 対応する契約の版（`contracts/version.json` の版と sha256）の集合を 1 か所に置いて照らし、契約の照合のジョブで見本に照らす（仮置き）
- 採らなかった案と理由: 版の数字の比べは上の理由で判断を誤る。機能の名前での判断は NDF の副命令が出るまで使えない
- 影響: 検査（#1）が版の数字の比べを落とす

版の付け方の標準（STD7）は版の数字の大小で前後を決め、大きな版で後方互換の無い変更を示すだけで、どの契約を満たすかを表さない。そのため 11.0.0 が 10.x の下限を満たすと読む今の誤りをそのまま持つ。契約の試験のツール（LIB7）は、使う側の試験から HTTP と message のやり取りの見本を作って照らす形で、NDF との境界（CLI の引数と契約ファイル）に当てる型を持たない。NDF が自分で公開する契約の版と sha256 を照らすだけで足りるため、照らす部分は自前で作る。

- 作り方: 自前で作る
- 比べた候補: STD7 / LIB7

根拠: Value 1（MVV 版 1）

### 決定 18: 結果の行が欠けた区間を成功と読まないよう、最後の結果の行だけを読み、無いか契約に無い値なら失敗にする

- 文脈: 結果の値 3 つは契約にあるが、読み方（最後の行で決める）は契約ファイルの外にしか無い（devbasex/ai-plugins#3242・devbasex/ai-plugins#3329）
- 決定: 最後の `- 結果:` の行の値で決め、行が無いか値が 3 つのどれでもなければ失敗にする（仮置き）
- 採らなかった案と理由: 最初の行で決める形は、区間の途中の報告を結果と読む。行が無いときに成功とみなす形は、権限の不足で終わった区間（devbasex/ai-plugins#3329 の事象）を見逃す
- 影響: M3 が受け持つ。I6 のテストで縛る

根拠: Value 4（MVV 版 1）

### 決定 19: 手元のマシンから出口の無いサブネットの DB へ届かないため、セルフホストのレーンには進行表の DB の URL を渡さない

- 文脈: 進行表の DB は出口の無いサブネットにあり、利用者の手元のマシンからは届かない
- 決定: セルフホストのレーンでは NDF の状態をコンテナの手元に置き、サービスはランナーが送る進捗の事象で状態を知る（仮置き。NDF の状態を読み書きするエントリポイントは devbasex/ai-plugins#2608）
- 採らなかった案と理由: DB を公開の端点にする形は、DB を外から接続できる状態にする
- 影響: M4 が受け持つ。NDF が状態を読み書きするエントリポイントを持ったら見直す

根拠: Value 7 / Value 3（MVV 版 1）

### 決定 20: NDF に事象の流れが無い間も進捗を届けるため、ランナーが NDF のファイルを読んで進捗の事象を送る

- 文脈: `ndf events --follow`（devbasex/ai-plugins#3694）は無い
- 決定: ランナーが `reader: service` のファイルを読み、翻訳した進捗の事象を API へ送る（仮置き）。サービスは進行表の DB を読まない（決定 8）
- 採らなかった案と理由: サービスが結果のファイルを問い合わせ続ける形は、ランナーの手元のファイルにサービスが届かない
- 影響: 事象の流れが出たら、ランナーの翻訳の入力をそれに差し替える

ファイルの変化を知らせるライブラリ（LIB8）は「変わった」ことを知らせるだけで、NDF の語を進捗の事象へ写す翻訳は持たない。読む時機を変化の通知で決めても翻訳の量は減らず、依存だけが増える。読む時機は M3（#6）の詳細設計で決め、通知の要否もそこで比べる。事象の封筒の標準（STD8）は `source` と `id` の組で重複を見分けるが、進捗の事象は形の正本（決定 12）で形を持ち、重複は連番（I13）で見分けるため、封筒を重ねない。翻訳は NDF の契約ファイルの形に合わせる部分で、既存の部品が無いため自前で作る。

- 作り方: 自前で作る
- 比べた候補: LIB8 / STD8

根拠: Value 4（MVV 版 1）

### 決定 21: 公開のサブネットの ECS が NAT なしで動き、検出結果に理由を残すため、ECS のサービスを作らず、ECS.2 の抑止を自動化ルールで定義する

- 文脈: ECS.2 は ECS のサービスの公開 IP の自動の割り当てを失敗にする（STD5）
- 決定: タスクは `RunTask` で起こし、ECS のサービスを作らない。後から ECS のサービスを足すときのために、ECS.2 を理由つきで `SUPPRESSED` にする自動化ルール（STD6）を CDK に定義し、設定のファイルで作るかを選ぶ
- 採らなかった案と理由: 検出結果を手で抑止する形は、反映のたびの差分に乗らず、どの環境で抑止したかが残らない。NAT を置く形は作り直しの決まったこと（NAT なし・Fargate を公開のサブネット）と合わない
- 影響: M10 が受け持ち、Security Hub を有効にした環境で検出結果を確かめる

- 作り方: ライブラリやサービスを使う
- 比べた候補: STD5 / STD6

根拠: Value 6 / Value 8（MVV 版 1）

### 決定 22: 旧い側と新しい側を同じアカウントに置いて戻せるよう、資源の接頭辞を設定で受け、入れ替えは案内する URL の切り替えにする

- 文脈: [判定の規則](01-rules.md)は、資源の名前の付け方と、利用者の使う先を替える手段をこの設計に割り振った。旧い側は非公開のテストまで残す（[判定の規則](01-rules.md)の R8）
- 決定: 資源の名前は `<接頭辞>-<環境>-<用途>` で、接頭辞は設定のファイルから受ける。入れ替えは、利用者へ案内する画面の URL を新しい側の URL に替えることとし、戻しは案内を旧い側の URL へ戻す
- 採らなかった案と理由: 独自のドメインを付け替える形は、今の環境が独自のドメインを持たず、ドメインと証明書の用意が新しく要る
- 影響: #15 が入れ替えと戻しの予行を受け持つ。新しい App とクライアントの戻り先は新しい側の URL

根拠: Value 6 / Value 8（MVV 版 1）

### 決定 23: 形を変えても読めなくならないよう、項目ごとに形の版を持ち、2 段で上げる

- 文脈: データを移さないのは作り直しの時だけで、作り直しの後は形の変更が続く
- 決定: サービスの表の項目は `schema_version` を持ち、読み手は今と 1 つ前の版を読む。形を変える PR は読み手を先に、書き手を後に上げ、残った項目は移しの関数（VPC の外の Lambda）が書き換える
- 採らなかった案と理由: 反映のときに全件を書き換える形は、反映の途中で読み手と書き手の版が合わない時間ができる
- 影響: #2 が版の持ち方を定義する

根拠: Value 3（MVV 版 1）

### 決定 24: 同じ役割の処理を重複させないため、横断の部品を 1 か所に置き、外での直の利用を検査で落とす

- 文脈: 旧い側には同じ役割の処理の重複が複数ある（旧い側の課題 4 件）
- 決定: 時計・lock・外部の呼び出し・再試行・ログと伏せ字・ID と冪等の鍵・認可の判定・使える量の判定を `packages/core/` に置く。検査（#1）が置き場の外での直の利用を落とす（[横断の部品の置き場](06-overall-architecture.md#横断の部品の置き場)）
- 採らなかった案と理由: 規約の文書だけで守る形は、NDF の作り直しで検査に載せたものだけが揃った記録（反省点の 1 節）と合わない
- 影響: #2 が部品を、#1 が検査を作る

伏せ字は、ログの部品（LIB9）の伏せ字が鍵の道筋（`a.b.c` と `*`）で選ぶ形で、値の形では選べない。nd-factory の伏せ字は秘密の形の表（[伏せ字](09-overall-trust.md#伏せ字)）に合う値をどの鍵の下でも伏せるため、伏せ字の部分は部品の中で自前で作る。部品の中でログの書き出しにライブラリを使うかは #2 が決め、外から見える約束は部品の関数だけにする。置き場の外での直の利用を落とす検査には、依存の規則のツール（LIB10）と lint の import の制限の規則（LIB11）がある。どちらも import の文だけを見るため、時計や `fetch` のようなグローバルの直の利用を落とせない。#1 は import の制限にどちらかを使ってよく、グローバルの直の利用を落とす分は自前の検査で足す。

- 作り方: 自前で作る
- 比べた候補: LIB9 / LIB10 / LIB11

根拠: Value 1（MVV 版 1）

### 決定 25: 承認の待ちの間の費用を止めるため、待ちが猶予を超えたらホステッドのレーンのタスクを止め、答えで起こし直す

- 文脈: 人が承認ゲートで答えるまでには数時間〜数日かかる。タスクを動かし続けると Fargate の費用が待ちの時間だけ掛かり、DBOS の LISTEN の接続が開いたままで Aurora も一時停止しない（LIB2）。作り直しの親の課題（旧い側）の費用の見込み（月 1〜6 ドル）は、計算の費用をタスクの動く時間に比例するとして出している
- 決定: 承認の依頼でセグメントが止まった後、猶予（既定 5 分）の間に答えが来なければ、ランナーは NDF のファイルを状態の S3 へ固め、DB の接続を閉じてタスクを終える。レーンの割り当ては外さない。人が答えを確定したら、実行の制御が同じレーンに新しいタスクを起こし、タスクはファイルを戻して指示の問い合わせで答えを受け、次のセグメントを始める（[進行表の DB](08-overall-state-infra.md#進行表の-db)）
- 採らなかった案と理由: 待ちの間もタスクを動かし続ける形は、待ちの時間だけ Fargate と Aurora の計算の費用が掛かり、月の予算 20 ドルと「使わない間は費用を止める」方針に合わない。猶予を持たずにすぐ止める形は、すぐ答えたときにも起こし直しの待ち（Aurora の再開 約 15 秒とタスクの起動）が掛かり、Value 1 の待ち時間を増やす
- 影響: M3 が止め方と起こし直しを作る。新しいタスクから NDF のループを続けられることは未確認で、M3 が固定の版の NDF で確かめる。答えた後にレーンが続くまでの時間が、猶予の後の答えではタスクの起動の分だけ延びる

根拠: Value 6 / Value 1（MVV 版 1）

### 決定 26: プロジェクトの持ち主とそれを見られるチームを食い違わせないため、持ち主を今の割り当てのチームにし、割り当ては 1 つだけにする

- 文脈: プロジェクトを見られるのは割り当てたチームだけである（I2、Value 9）。持ち主のアカウントと割り当てたチームを別に持つと、持ち主が見られるか・だれが割り当てを変えるか・使える量をどちらで数えるかが決まらない
- 決定: プロジェクトの今の割り当ては 1 つのチームだけで、そのチームのアカウントを持ち主とする（I15）。作るときに作った人のアカウントへ割り当て、変えるときは今のチームと移す先のチームの両方の持ち主が人として確定する。今のチームの確定がそのプロジェクトの終わっていないレーンをすべて止めてレーンの token を断ち、受け入れは停止が終わったことだけを照らす。今のチームの持ち主は受け入れの前なら確定を取り下げられる。外すのはプロジェクトを閉じる操作としてだけ持ち、割り当てたチームの外へ見せる操作は作り直しでは作らない（[チームへの割り当て](05-overall.md#チームへの割り当て)）
- 採らなかった案と理由: 1 つのプロジェクトを複数のチームへ割り当てる形は、使える量と課金と進行表の DB をどのチームに付けるかの規則が要り、見えるかの判定も複数のチームの席を照らすことになる。作り直しで要る場面が要求に無い
- 影響: M2 が割り当ての履歴の行と移す操作（今のチームの確定・確定の取り下げ・移す先の受け入れ）を作り、受け入れの期限を置くかとその長さを詳細設計で決める。料金プランの線引きでは、個人のプランも 1 人のチームへの割り当てを使う。M2 の時点ではレーンが無い。そのため、移す操作へのレーンの照らしは、レーンの停止と token を持つ M3 が M2 の移す操作へ足し、I15 のその部分をテストへ移す。移す操作へのレーンの照らしは、次の 3 つである
  - 今のチームの確定で、レーンを取り消しと同じ経路で止めて token を断ち、手元のマシンへの割り当てを外す
  - 受け入れの時点で、終わっていないレーンを照らす
  - 確定から受け入れまたは取り下げまでの間の、レーンの開始を拒む

根拠: Value 9 / P3（MVV 版 1）
