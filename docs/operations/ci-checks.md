# CI の検査の秘密と持ち主の操作

参照の検査と漏れの検査は、照合の語と実際の値の正規表現をリポジトリの外の秘密から受ける。この文書は、持ち主が GitHub の設定で行う操作と、検査ごとにどの実行が秘密を受け、誰に結果が見えるかをまとめる。仕組みは [漏れの検査の仕様](../specifications/leak-check.md) にある。

この文書の `<非公開リポジトリ>` は、持ち主が作る検査用の非公開リポジトリ（`<所有者>/<名前>`）を指す。実際の名前はリポジトリに書かない。

### 作業の記録

この文書の「作業の記録」は、担当者が誰でも同じものを読めるよう、次の場所に残す。停止を解く条件や引き継ぎは、この記録に未解決のものが無いことを条件にする。決めた理由は [#166 の設計の決定 4](../../issues/issue-166-design.md) の「作業の記録の置き場」にある。

| 記録 | 置き場 | 読める人 |
| --- | --- | --- |
| 結果不明のマージの要求（Pull Request の番号・要求の識別子・渡した head・送った時刻）、要求の記録を閉じたこと、承認したときの確認の行の一覧、`main` の更新を止めた時刻と解いた時刻、探した組（探したマージコミット・探した head・探した base）と実際の head | 対象の Pull Request のコメント。先頭の行を `作業の記録: <種類>` とする。結果不明の要求は、要求を送った先の Pull Request に書く | 公開のリポジトリなので誰でも読める。実際の値と秘密は書かない。漏れの検査の合否と当たりの有無も書かない |
| 結果不明の要求が残っている Pull Request の目印 | ラベル `merge-unresolved`。探しやすくするための写しで、正本はコメントである。付け方と外し方は下の「結果不明の要求の記録」にある | 同上 |
| 漏れの検査の結果（探しごとの成功・当たり・失敗・未実行、当たりの場所）、管理者への引き継ぎ、実際の値を含む証跡 | 運用の記録（公開しない保管先。用語は [反映のパイプラインの仕様の用語](../specifications/deploy-pipeline.md#用語)）。決め方は下の「運用の記録の保管先」にある | 保管先を読める担当者。当たりがあることを公開すると、どのコミットに実際の値があるかを示すことになるため、公開のコメントに置かない |

この文書の手順が、漏れの検査の結果を「作業の記録に残す」と書いている所も、結果は運用の記録に残す。公開のコメントには、探した組と実際の head だけを書く。

#### 運用の記録の保管先

検査結果と引き継ぎは、初回の運用前に持ち主か運用担当者が指定した非公開の保管先に記録する。指定した人は、保管先と、読み書きできる担当者を `<非公開リポジトリ>` の README に書く。同じ README には、下の「記録として数えるコメント」で使う担当者の名簿も置く。担当者は、作業前にこの README で、保管先と読み書きできる担当者を確認する。保管先が未指定なら、担当者間で指定して README に書いてから確認手順を始める。引き継ぐ相手が保管先を読めなければ、引き継ぐ前に、指定した人に読む権限を頼む。

#### 記録として数えるコメント

作業の記録として数えるコメントは、記録の種類ごとに書き手を限る。公開のリポジトリでは、GitHub のアカウントを持つ誰でもコメントを書けるためである。結果不明の要求は停止を続ける根拠なので、広く数える。記録を閉じた・停止を解いた・承認したときの一覧など、停止や記録を緩める根拠になるものは、今回の作業の担当者に任命した人が、担当の期間に書いたものだけを数える。任命した担当者と担当の期間は、`<非公開リポジトリ>` の README に置く担当者の名簿で決める。

名簿が要るのは、GitHub の権限だけでは、担当者に任命した人を決められないためである。

- 公開のリポジトリへの書き込みの権限は、今回の作業の担当者に任命していない人も持ち得る。権限を持つだけの人のコメントで記録を閉じられると、担当者の知らない所で停止が解かれる
- GitHub の権限を読む API は、照合する時点の権限しか返さない（[GitHub REST API の協力者の権限](https://docs.github.com/en/rest/collaborators/collaborators#get-repository-permissions-for-a-user)）。コメントを書いた時点の権限は分からないので、権限を外された担当者が担当中に書いた要求と、もともと権限の無い人のコメントを見分けられない

**担当者の名簿**は、担当者ごとに、GitHub のアカウント ID・名簿に書いた時点の login・担当を始めた日時（UTC）・担当を終えた日時（UTC。担当中は空）を 1 行に書く。照合にはアカウント ID を使う。login は持ち主が変えられ、手放した login を別の人が取れるためである。login は、読む人のための控えとして書く。アカウント ID は `gh api users/<login> --jq .id` で読む数字で、コメントの `user.id` と同じ値である。

- 名簿を変えられるのは、`<非公開リポジトリ>` に書き込みの権限を持つ人だけである。誰がいつ変えたかは、`<非公開リポジトリ>` のコミットの履歴に残る
- 担当者を足すときは、持ち主か運用担当者が、その人に書き込みの権限を与える前に、名簿へ行を足す
- 担当者が外れるときは、下の「担当者の交代」を終えてから、担当を終えた日時を書き、そのあと権限を外す
- 名簿の行は消さない。外れた担当者が担当中に書いた記録を、後から数えるためである

**権限を外すときは、どの場合も、名簿に担当を終えた日時を書くことを最初の手順にする。** 名簿を直すまでは、権限を外しても、その人の「記録を閉じた」「停止を解いた」のコメントが数えられ続けるためである。アカウントの乗っ取りや不正が分かったときなど、急いで権限を外すときは、名簿より先に権限を外してよい。その場合は次のとおりに行う。

1. 権限を外した直後に、名簿のその人の行に、担当を終えた日時として、権限を外した時刻を書く。名簿を直した時刻ではない。乗っ取りや不正が権限を外す前から始まっていた疑いがあれば、疑いの始まった時刻を書く
2. 1 で書いた時刻より後にその人が書いた、記録を閉じた・停止を解いた・承認したときの一覧などのコメントは、名簿を直す前に書かれたものでも数えない
3. ただし、1 で書いた時刻より後にその人が書いた結果不明の要求は、数えないと判定から消えるので、未解決の要求として数え続ける。時刻をさかのぼらせた期間（影響期間）に記録された要求も、実際に送られていれば後から成立し得るためである。この要求は、今の担当者が 4 で確かめて引き継ぐまで、名簿の担当の期間の外でも未解決として数える
4. 名簿を直した人は、1 で書いた時刻より後にその人が書いた作業の記録を、リポジトリ全体から探す（下のコマンド。`since` は更新の時刻で絞るので、その後に書かれたコメントはすべて出る）。見つけた記録は、種類ごとに次のとおり扱う
   - 結果不明の要求: 今の担当者が、送られた要求の中身（Pull Request の番号と渡した head、または push の送った SHA）を確かめ、下の「担当者の交代」の 2 の形で、元の識別子のまま引き継ぐ。引き継いだ要求は、ほかの要求と同じく確定させてから閉じる。閉じるまで、停止を解かない
   - 記録を閉じた・停止を解いた: それを根拠に閉じた記録や解いた停止を作業の記録に残す。閉じられた要求は未解決に戻し、下の「未解決の要求が無いことの確かめ方」で確かめ直す。結果不明の要求が残っていれば、停止をかけ直す

   ```bash
   gh api --paginate 'repos/devbasex/nd-factory/issues/comments?since=<1 で書いた時刻>&per_page=100' --jq '.[] | select(.user.id == <アカウント ID> and (.body | startswith("作業の記録: "))) | [.html_url, .created_at, (.body | split("\n")[0])] | @tsv'
   ```

コメントの書き手（`user.id`）ごとに、記録の種類で次のとおり数える。担当の期間は、名簿の担当を始めた日時から担当を終えた日時（空なら今）までである。

| 記録の種類 | 数える書き手 |
| --- | --- |
| 結果不明の要求（先頭の行が `作業の記録: 結果不明の要求`） | 次のどちらかに当たる人。名簿にあり、コメントの `created_at` が担当の期間にある人。または、今、公開のリポジトリに書き込みの権限を持つ人 |
| 結果不明の要求のほかのすべての作業の記録（記録を閉じた・停止を始めた・停止を解いた・承認したときの一覧・探した組など） | 名簿にあり、コメントの `created_at` が担当の期間にある人だけ。今、書き込みの権限を持つだけでは数えない |

確かめ方は次のとおりである。

| 当たること | 確かめ方 |
| --- | --- |
| 名簿にあり、`created_at` が担当の期間にある | `<非公開リポジトリ>` の README の名簿で、コメントの `user.id` と同じアカウント ID の行を読む。login では照合しない。名簿の行を誰がいつ変えたかは、その README のコミットの履歴で確かめる |
| 今、公開のリポジトリに書き込みの権限を持つ | `gh api repos/devbasex/nd-factory/collaborators/<書き手>/permission --jq .permission` が `admin`・`maintain`・`write` のどれかを返す。`<書き手>` には、コメントの `user.login`（API がアカウント ID から引いた今の login）を渡す |

- どちらにも当たらない人のコメントは、同じ体裁でも数えない。結果不明の要求のコメントでも、停止を続ける根拠にしない。ただし、上の「権限を外すときは」の 3 に当たる要求（急いで権限を外した人が、さかのぼらせた担当を終えた日時より後に書いたもの）は、引き継ぐまで未解決として数える。記録を閉じた・停止を解いたコメントでも、停止を解く根拠にも、承認を取り直す根拠にもしない
- 名簿を読めないとき（README を取得できない、名簿がまだ無いなど）は、結果不明の要求だけを今の権限で数える。記録を閉じたコメントなどは数えられないので、名簿を読めるまでは、停止を解かず、記録を閉じない
- 書いた後に編集されたコメント（コメントの `created_at` と `updated_at` が違うもの）は、記録を閉じた・停止を解いた・承認したときの一覧の根拠にしない。直すときは編集せず、新しいコメントで書き足す
- ただし、数える書き手が書いた結果不明の要求は、編集されていても未解決として数える。数えないと、残っている要求を見落とすためである

**担当者の交代**は、名簿と作業の記録の両方で引き継ぐ。外れる担当者の要求を、引き継ぐ担当者のコメントとして書き直しておけば、名簿を読めないときも今の権限で数えられる。

1. 引き継ぐ担当者が、外れる担当者の書いた結果不明の要求のうち閉じるコメントの無いものを、下の「未解決の要求が無いことの確かめ方」で洗い出す
2. 要求ごとに、同じ Pull Request へ、先頭の行を `作業の記録: 結果不明の要求`、2 行目を元の記録と同じ `要求: <要求の識別子>` とするコメントを書き、続けて `引き継ぎ: <元のコメントの URL>` を書く
3. 名簿の外れる担当者の行に、担当を終えた日時を書く。そのあとで、書き込みの権限を外す
4. 引き継いだ要求は、引き継いだ担当者が、同じ識別子の閉じるコメントで閉じる

急いで権限を外し、交代の 1・2 を済ませていないときも、名簿にある担当の期間に書いた要求は数える。名簿の担当を終えた日時は、上の「権限を外すときは」のとおり、外した直後に書く。引き継ぐ担当者は、気づいた時点で 1・2 を行う。このときの 1 では、担当の期間に書いた要求に加えて、上の「権限を外すときは」の 4 で見つけた、担当を終えた日時より後に書かれた結果不明の要求も洗い出して引き継ぐ。

#### 結果不明の要求の記録

結果不明の要求は、1 件ずつ要求の識別子を付けて記録し、同じ識別子で閉じる。要求の識別子は `<Pull Request の番号>-<送った時刻（UTC、YYYYMMDDTHHMMSSZ）>` とする。M6-3 で打ち直した要求も、応答が返らず結果が分からなければ、最初の要求とは別の要求として、打ち直した時刻の新しい識別子で記録する。記録するときは、次の順で行う。

1. 要求を送った先の Pull Request にラベルを付ける（`gh pr edit <番号> --repo devbasex/nd-factory --add-label merge-unresolved`）。ラベル `merge-unresolved` がまだ無ければ、先に作る。付けられなくても 2 に進む
2. その Pull Request に、先頭の行を `作業の記録: 結果不明の要求` とするコメントを書く。2 行目に `要求: <要求の識別子>` を書き、続けて渡した head と送った時刻を書く
3. 2 のコメントが載ったことを、その Pull Request のコメントを読み直して確かめる（下の「未解決の要求が無いことの確かめ方」の 3 のコマンド）。載っていなければ書き直す。1 で付けられなかったときは、ラベルも付け直す。コメントが載ったことを確かめ、ラベルが付くまでは、自分が担当する停止を解かない

結果が確定した要求は、識別子ごとに、同じ Pull Request に、先頭の行を `作業の記録: 記録を閉じた` とするコメントで閉じる。2 行目に同じ `要求: <要求の識別子>` を書き、続けて確定した結果を書く。1 つの Pull Request に記録した要求が複数あるときは、確定した要求だけを閉じ、ほかの要求は閉じない。ただし、Pull Request（`gh api repos/devbasex/nd-factory/pulls/<番号>`）の `merged` が真になったときは、その Pull Request に残るすべてのマージの要求を閉じてよい。下の「結果不明の直接の push の記録」は、Pull Request のマージとは関係が無いので、この方法では閉じない。マージ済みの Pull Request は、残りの要求でもう一度マージされることが無いためである。このときは、要求ごとに閉じるコメントを書き、結果に「Pull Request がマージ済みになった」と書く。どの要求がマージを作ったかは、下の「規則を変える Pull Request をマージの直前に確かめる」の手順 6 のとおり記録で決める。

ラベルは、その Pull Request のすべての結果不明の要求に、同じ識別子の閉じるコメントがそろってから外す。1 件でも閉じていない要求があれば、ほかの要求を閉じても外さない。Pull Request が閉じても外さない。

#### 結果不明の直接の push の記録

`main` への直接の push で、打った担当者にも成否が分からないものは、マージの要求とは別の形で記録する。成否は、push を送った ref と SHA で 1 件ずつ確定させる。`main` の先端を、止めた時点に控えた先端と比べるだけでは確定させない。止める前に複数の書き込みがあると、先端が進んでいても、どの push が成立したかは分からないためである。

記録は、停止を作業の記録に残した Pull Request に、上の「結果不明の要求の記録」の 1〜3 と同じ順で書く（ラベルも付ける）。先頭の行と 2 行目の形は同じにし、下の「未解決の要求が無いことの確かめ方」で、マージの要求と一緒に見つかるようにする。

同じ Pull Request には、複数の担当者の push の記録が集まる。送った時刻だけでは、同じ秒に送った別々の push を見分けられないので、記録する担当者が push ごとに一意な識別子を発行する。識別子は `push-<送った時刻（UTC、YYYYMMDDTHHMMSSZ）>-<記録する担当者のアカウント ID>-<無作為の 8 文字>` とし、無作為の 8 文字は記録する直前に `openssl rand -hex 4` で作る。引き継ぎのコメント（上の「担当者の交代」の 2）と閉じるコメントでは、新しい識別子を作らず、元の記録の識別子をそのまま写す。閉じるコメントとの照合は 2 行目の識別子の全体の一致で行い、送った時刻の部分だけでは照合しない。

```text
作業の記録: 結果不明の要求
要求: push-<送った時刻（UTC、YYYYMMDDTHHMMSSZ）>-<アカウント ID>-<無作為の 8 文字>
種類: 直接の push
ref: refs/heads/main
打った担当者のアカウント ID: <push を打った人のアカウント ID>
送る前の先端: <push の前に担当者が読んだ main の SHA。分からなければ「不明」>
送った SHA: <push で main に向けたコミットの SHA>
送った時刻: <UTC>
```

直接の push では、次の 2 つを分けて確かめる。

- **要求の成否**: 記録した push の要求そのものが、サーバーで受け入れられたか、拒否されたか。記録を閉じてよいかは、これだけで決める
- **探すコミット**: 成立した push で、`main` の ref が実際にどの SHA からどの SHA へ変わったか（実際の `before` と `after`）。新しい秘密で探し直す範囲は、記録の「送る前の先端」と「送った SHA」ではなく、これで決める。push の前に読んだ先端と、サーバーが更新したときの先端は同じとは限らないためである

**要求の成否**は、次の順で確かめる。不成立と確定するのは、対象の要求が拒否され、今後も処理されないという証拠があるときだけである。出力や記録があっても成否を確定できなければ、次の手順に進む。

1. 打った担当者が `git push` の出力を残していれば、`main` の行（`-> main` を含む行）を読む。出力の形は [git push の出力](https://git-scm.com/docs/git-push#_output) にある
   - 行の先頭の印が ` `（空白）か `+` で、更新を示していれば、成立とする
   - 印が `!` で、`[rejected]` か `[remote rejected]` が書かれていれば、不成立とする。`[rejected]` は送る前に手元で拒んだもの、`[remote rejected]` はサーバーが拒んだもので、どちらも更新は行われない
   - `main` の行が無い、印が `!` で `[remote failure]`（サーバーが更新の成否を返さなかった）、通信が切れた（`fatal: the remote end hung up unexpectedly` など）、`error:` の行しか無い、のどれかなら、成否を確定せずに 2 に進む
2. GitHub のリポジトリの活動の記録（[List repository activities](https://docs.github.com/en/rest/repos/repos#list-repository-activities)）で、`main` の更新を全ページ読む。次の 3 つがすべて当たる項目があれば、成立とする。`after` だけが同じで `actor.id` が違う項目は、別の担当者が同じ SHA を取り込んだ更新なので、この要求の成立とは扱わない。項目が見つからなくても、不成立とはしない。サーバーがまだ処理を終えていないことがあるためである
   - `after` が送った SHA と同じ
   - `actor.id` が、記録の「打った担当者のアカウント ID」と同じ
   - `timestamp` が、送った時刻と同じかそれより後

   ```bash
   gh api --paginate 'repos/devbasex/nd-factory/activity?ref=refs/heads/main&per_page=100' --jq '.[] | [.timestamp, .activity_type, .before, .after, .actor.id] | @tsv'
   ```

3. 1 と 2 で確定できなければ、停止を保ち、M6-5 と同じくリポジトリの管理者に渡して確定させてもらう。管理者が不成立とするのは、その要求が拒否され、今後も処理されないという証拠（GitHub のサポートの回答など）を得たときだけである。送った SHA が今の `main` から到達できるか（`git fetch origin main` の後の `git merge-base --is-ancestor <送った SHA> origin/main`）は、要求の成否の根拠にしない。到達できるのは、別の更新で同じコミットが入った場合もあるためである。到達できないことも、要求がこれから処理されないことを示さない

**探すコミット**は、成立が確定した後に、2 の活動の記録の項目から決める。

- 2 で成立とした項目の `before` と `after` を、実際の `before` と `after` とする
- 1 で成立としたときも、2 のコマンドで同じ 3 つの条件に当たる項目を探し、その `before` と `after` を使う。見つからなければ、1 の行の `<旧>..<新>`（強制の push では `<旧>...<新>`）の SHA を、打った担当者の手元の複製で `git rev-parse` を使って完全な SHA にしたものを使う。どちらも得られなければ、範囲を決められなかったものとして扱う

要求の成否がまだ確定していなくても、送った SHA が今の `main` から到達できれば（上の 3 のコマンドが終了コード `0` で終わる）、そのコミットは `main` に入っている。秘密を変える途中なら、要求の成否とは別に、送った SHA を新しい秘密で探す対象に加える。終了コード `1` は今の `main` から到達できないことを、それ以外の終了コードはコマンドの失敗を示す。失敗したときは到達できるかが分からないので、打ち直す。どの終了コードでも、要求の記録は閉じない。

確定したら、同じ識別子の `作業の記録: 記録を閉じた` のコメントで閉じる。コメントには、成立か不成立かと、確定できた手順の番号（1 か 2）と、そこで観測した結果（1 なら `main` の行の印と要約、2 なら項目の `timestamp`・`before`・`after`・`actor.id`）を書く。管理者が確定したときは、手順の番号の代わりに、管理者が判断の根拠にしたものを書く。成立したときは、あわせて実際の `before` と `after`（決められなければ、その旨）を書く。成立した push で足されたコミットは、`<実際の before>..<実際の after>` である。秘密を変える途中で成立した push は、閉じる前に、下の「切り替えの後に秘密を変えるとき」の 7 のとおり新しい秘密で探し直す。

#### 未解決の要求が無いことの確かめ方

未解決の要求が無いことは、正本のコメントで、リポジトリ全体を漏れなく読んで確かめる。今回の停止の前に洗い出した要求だけでなく、以前の作業から残っている要求も対象にする。ラベルは、コメントを読む Pull Request を探すためだけに使う。どのコマンドも全ページを取得する（`--paginate`）。件数に上限のある一覧（`gh pr list` の既定の 30 件など）や、反映が遅れ件数に上限のある検索は使わない。次の 3 つを行う。

1. ラベルの付いた Pull Request を、全ページ取得して集める

   ```bash
   gh api --paginate 'repos/devbasex/nd-factory/issues?labels=merge-unresolved&state=all&per_page=100' --jq '.[] | select(.pull_request) | .number'
   ```

2. ラベルを付け損ねた Pull Request を拾うため、リポジトリのすべてのコメントを全ページ取得し、結果不明の要求のコメントがある Pull Request を集める

   ```bash
   gh api --paginate 'repos/devbasex/nd-factory/issues/comments?per_page=100' --jq '.[] | select(.body | startswith("作業の記録: 結果不明の要求")) | .issue_url | split("/") | last'
   ```

3. 1 と 2 で集めた Pull Request ごとに、作業の記録のコメントを読む。上の「記録として数えるコメント」で数えるものだけを使い、結果不明の要求と閉じるコメントを要求の識別子で照合する

   ```bash
   gh api --paginate repos/devbasex/nd-factory/issues/<番号>/comments --jq '.[] | select(.body | startswith("作業の記録: 結果不明の要求") or startswith("作業の記録: 記録を閉じた")) | [.id, .user.id, .user.login, .created_at, .updated_at, (.body | split("\n")[0:2] | join(" / "))] | @tsv'
   ```

次の 3 つがすべてそろったときだけ、未解決の要求は無いと判定する。

- 1〜3 のどのコマンドも終了コード `0` で終わった。1 つでも失敗したら、取得できるまで打ち直し、それまで未解決の要求は無いと判定しない
- 閉じるコメントの無い要求が 1 件も無い
- ラベルが付いているのに、結果不明の要求のコメントが 1 件も無い Pull Request が無い

ラベルが付いているのに要求のコメントが無い Pull Request は、記録の途中か、コメントの書き込みに失敗したものとして扱う。結果の分からない要求が残っているかもしれないので、閉じた Pull Request でも、通常の閉じたものと同じには扱わない。ラベルを付けた担当者（`gh api --paginate repos/devbasex/nd-factory/issues/<番号>/events --jq '.[] | select(.event == "labeled" and .label.name == "merge-unresolved") | [.actor.id, .actor.login, .created_at] | @tsv'`）に確かめる。担当者は、送った要求の記録を書く。要求を送っていなかったと分かったときも、その旨を結果に書いた要求のコメントと閉じるコメントを書いてから、ラベルを外す。担当者が書き終えるまで、未解決の要求は無いと判定しない。

閉じていない要求があるのにラベルが無い Pull Request が見つかれば、ラベルを付け直す。

## 検査ごとの秘密の受け方と結果の見え方

| 検査 | 動く実行 | 受ける秘密 | 結果が見える人 |
| --- | --- | --- | --- |
| `ref-check`（`ci.yml`） | Pull Request と main への push | `REF_CHECK_TERMS`（Actions の秘密。Dependabot の Pull Request では Dependabot の秘密） | 誰でも（公開の記録） |
| `leak-check`（`ci.yml`） | Pull Request だけ | 受けない。既定の規則と `.gitleaks.toml` だけで、今の木と分岐点から head までを探す | 誰でも（公開の記録。必須のチェック） |
| `leak-check-push`（`ci.yml`） | main への push だけ | 環境 `leak-scan` の秘密 `LEAK_CHECK_PATTERN` と変数 `LEAK_CHECK_REQUIRE_PATTERN` | 誰でも（公開の記録）。実際の値の規則 `nd-real-value` の当たりは件数の行（`leak-scan-secret: nd-real-value: <件数> 件`）だけで、場所を出さない。必須のチェックではない |
| 非公開の検査（`leak-check-secret.yml`） | NDF が Pull Request をマージする直前に、`<非公開リポジトリ>` の呼び出しのワークフローを起動したとき（持ち主が手で起動したときも）。NDF 11.0.43 は起動しないので、[#198](https://github.com/devbasex/nd-factory/issues/198) が入るまでは、持ち主が手で起動したときだけ動く | `<非公開リポジトリ>` の Actions の秘密 `LEAK_CHECK_PATTERN`（必須。空なら落ちる） | `<非公開リポジトリ>` に読み取りの権限を持つ人と NDF だけ。当たりは規則・`file-<番号>`・行・コミットで出し、ファイルの名前は出さない。公開の Pull Request のチェック・コメント・通知には何も出ない |

- 非公開の検査は、Pull Request のマージコミットの木・分岐点から head までの各コミットのパッチ・その範囲のコミットに現れたすべてのパスの名前と中身を、既定の規則と、`.gitleaks.toml` に `nd-real-value` を重ねた設定で探す。動かすのは、公開のリポジトリの main の先頭（検査のコードのコミット）のスクリプトと設定だけで、Pull Request のコミットは読むだけである
- Pull Request を誰が作ったか（fork・同じリポジトリのブランチ・Dependabot）で、どの検査の振る舞いも変わらない。起動した人で分ける条件は置かない（CI の定義のテストが落とす）
- 非公開の検査の機能が入った NDF は、非公開の検査の成功を確かめられなければマージしない。NDF 11.0.43 はこの確かめをしないので、#198 が入るまで、通常の Pull Request に入った実際の値は機械では止まらない。結果は公開のリポジトリのチェックにならないので、`.ndf/project.json` の必須のチェック（`required_checks`）には載せない

### 残る経路と持ち主が見張る点

秘密を隔てても、次の経路は残る。

| 経路 | 届くもの | 持ち主がすること |
| --- | --- | --- |
| main に直に push できる人（main にはブランチの保護が無いので、書き込みの権限を持つ人） | main の上のワークフローを書き換えて、環境 `leak-scan` の秘密を読める。`leak-check-secret.yml` かそれが動かすスクリプトに秘密を外へ送る手順を足せば、次に NDF が起動したときに `<非公開リポジトリ>` の秘密つきで動く | main への直の push を見張る |
| 公開のリポジトリに `main` という名前のタグを作れる人 | 呼び出しのワークフローの `@main` の解決をタグへ向けられる（同じ名前のタグはブランチより優先される）。NDF は実際に動いた版を確かめて結果を退けるが、秘密が渡ることは止められない | `main` という名前のタグの作成を見張る |
| `<非公開リポジトリ>` に書き込みの権限を持つ人 | 呼び出しのワークフローを書き換えて秘密を読める | 書き込みの権限を持つ人を最小にする |
| GitHub の画面からのマージ | 非公開の検査を通らずにマージできる（止めるのは NDF が行うマージだけ） | 画面からマージしない |

## 秘密と変数の登録

| 置き場所 | 名前 | 種類 | 値 |
| --- | --- | --- | --- |
| `<非公開リポジトリ>` | `.github/workflows/<呼び出しのワークフローのファイル>` | ファイル | [`leak-check-caller.yml`](leak-check-caller.yml) を写したもの |
| `<非公開リポジトリ>` | `LEAK_CHECK_PATTERN` | Actions の秘密 | 実際の値の正規表現（`'''` と改行を含めない） |
| `<非公開リポジトリ>` | `LEAK_CHECK_GENERATION` | Actions の変数 | 設定の世代（`1` から始める正の整数。`0` は切り替え中） |
| 公開のリポジトリの環境 `leak-scan` | （環境の設定） | 環境 | 使えるブランチ（deployment branch policy）を `main` だけにする |
| 公開のリポジトリの環境 `leak-scan` | `LEAK_CHECK_PATTERN` | 環境の秘密 | `<非公開リポジトリ>` と同じ値 |
| 公開のリポジトリの環境 `leak-scan` か公開のリポジトリ | `LEAK_CHECK_REQUIRE_PATTERN` | 変数 | `1` にすると、秘密が空の `leak-check-push` が落ちる。`1` にする時機は「導入の順序」の手順 4 |
| 公開のリポジトリ | `REF_CHECK_TERMS` | Actions の秘密と Dependabot の秘密の 2 か所 | 照合の語（今のまま） |
| 公開のリポジトリ | `REF_CHECK_REQUIRE_TERMS` | Actions の変数 | 今のまま |

- 公開のリポジトリの Actions の秘密には `LEAK_CHECK_PATTERN` を置かない。登録していれば消す（`pull_request` の実行の Pull Request のコードから読めるため）
- **Dependabot の Pull Request で要る操作は無い。** Pull Request の側の `leak-check` は秘密を受けないので、Dependabot の Pull Request でも秘密の欠けで落ちない。Dependabot の Pull Request の全コミットは、ほかの Pull Request と同じく、NDF のマージの直前に非公開の検査で探す（非公開の検査の機能が入った NDF の場合。#198 が入るまでは探さない）。**Dependabot の秘密には `LEAK_CHECK_PATTERN` を登録しない**（Dependabot が起動した実行で、Pull Request のコードと更新した依存から読めるため）
- 環境 `leak-scan` を使えるのは main への push の `leak-check-push` だけである。Pull Request の側の実行はマージの参照（`refs/pull/<番号>/merge`）で動くので、ワークフローを書き換えて環境を指しても秘密を受けられない

## NDF の認証の権限

NDF の認証は、`<非公開リポジトリ>` に対して次の権限を持つ必要がある。ワークフローの起動の API と変数の取得の API は協力者（collaborator）としての権限を求め、個人のアクセストークン（classic）なら `repo` の範囲が要る。

| 操作 | API |
| --- | --- |
| 変数の読み取り | `GET /repos/<非公開リポジトリ>/actions/variables/LEAK_CHECK_GENERATION` |
| ワークフローの起動 | `POST /repos/<非公開リポジトリ>/actions/workflows/<呼び出しのワークフローのファイル>/dispatches` |
| 実行とジョブの読み取り | `GET /repos/<非公開リポジトリ>/actions/runs/<実行の ID>/attempts/1`・`.../attempts/1/jobs` |

- 認証に権限を足すか、協力者を足すのは、認証と認可の変更なので、人の承認を受けてから行う
- `<非公開リポジトリ>` に読み取りの権限を持つ人を最小にする（実行の記録に当たりの規則・行・コミットが出る）
- この権限は、1 つの記録の置き場所を共有する NDF の認証にだけ与える。マージの要求の排他は置き場所をまたいで効かないためである。**権限を与えた NDF の認証と、その記録の置き場所を控える**（「秘密を変える手順」の手順 2 で使う）

## 手元の検査に要る道具

この文書の手元の検査は、始める前に端末の道具の版を確かめる。

| 道具 | 最低の版 | 版の確かめ方 |
| --- | --- | --- |
| Python（`python3` の名前で起動するもの） | 3.11 | `python3 --version` |
| Git | 2.40 | `git --version` |

版が足りないと、`leak-scan.sh` は起動時に `leak-scan: python3 が 3.11 より古い` か `leak-scan: git が 2.40 より古い` を出して終了コード `1` で終える（Git の版は履歴の探しでだけ確かめる）。この終了は当たりの有無を判定していないので、道具を新しくしてから打ち直す。gitleaks は、各手順の `install-gitleaks.sh` が固定の版を置く。

## 秘密を変える手順

`<非公開リポジトリ>` の秘密 `LEAK_CHECK_PATTERN` の値か、呼び出しのワークフローを変えるときは、進行中のマージを終わらせるか止めてから変え、新しいマージは世代 `0` で締め出す。

人が手でマージしている間は、切り替えを始めない。手でのマージは、NDF の時間の上限と未解決の記録では見張れないためである。具体的には、下の「規則を変える Pull Request をマージの直前に確かめる」の手順 5 のマージ手順 M2 で世代を読んでから、手順 6 の確認（マージ後の照合）を終えるまでの間がこれに当たる。同じ手順 5 の M6 で結果の分からないマージの要求を記録していれば、その記録を閉じるまで始めない。ただし、記録が閉じる前に秘密が漏れたときは、リポジトリの管理者が、M6 の M6-6 のとおりにマージの停止を保ったまま切り替える。下の手順 2 の「待てないとき」の例外は、NDF のマージにだけ使える。手でマージする人と切り替える人が別のときは、始める前に互いに知らせる。

`main` への push を自動反映として扱う `.ndf/project.json` の変更（反映先の一覧の切り替え）が `main` に入った後は、下の手順 1・2 だけでは進行中のマージを止められない。NDF のマージ（`ndf ci merge`）は秘密の世代を照合しないので、世代を `0` にしても止まらない。T の待ちも、`ndf ci merge` が世代を読まないので意味を持たない。`ndf ci merge` は送った要求を NDF の未解決の記録に登録せず、規則を変える Pull Request の担当者が M6-1 で手で残す記録も、手順 2 の NDF の未解決の記録に載らない。そのため、切り替えの後は、手順 1 の前に次の準備 1〜4 を行う。手順 2 の T の待ちと NDF の未解決の記録の確かめは、この準備で置き換える。手順 1・3・4 は、そのまま行う。ただし、手順 1 の「この後の NDF のマージは人へ戻り」は成り立たないので、マージは準備 1 の停止で止める。

1. マージ先を変えられる担当者の間で、`main` へのマージ（`ndf ci merge` とマージの工程を含むすべての経路）と `main` への直接の push を止める。止めた時刻と、その時点の `main` の先端（`gh api repos/devbasex/nd-factory/commits/main --jq .sha`）を控え、作業の記録に残す。停止は、手順 4 で世代を正の値に戻すまで保つ
2. 止める前に送られた `main` への書き込みを、担当者ごとに確かめる。対象は、`ndf ci merge`（マージの工程の中のものを含む）、`gh pr merge`、GitHub の画面からのマージ、`main` への直接の push である。[#199](https://github.com/devbasex/nd-factory/issues/199) が入るまでは、`ndf ci merge` のほかの経路でもマージできるためである。呼び出しの途中のもの（`ndf ci merge`・`gh pr merge`・`git push`）は、終了するまで待ち、途中で打ち切らない。打ち切ると、要求を送ったかが分からなくなる。終了しても結果が分からなければ、準備 3 で結果不明として扱う
3. 終わった書き込みの結果を読む。規則を変える Pull Request に限らず、`main` 宛てのすべての Pull Request への書き込みを読む。通常の Pull Request の要求でも、後から成立すれば、世代が `0` のまま `main` が更新され、秘密を使う検査を終える前に本番への反映が起動し得るためである
   - `ndf ci merge` の結果は、下の「切り替えの後のマージ」の「`ndf ci merge` の結果の読み方」で読む
   - `gh pr merge` と GitHub の画面からのマージは、打った担当者に、マージした・断られた・分からないのどれかを確かめ、Pull Request の `merged` と `isInMergeQueue`（準備 4 のコマンド）を読む。マージされておらず、断られたと確かめられなければ、結果不明とする。キューに入っていれば、結果不明とする
   - `main` への直接の push は、打った担当者に成否を確かめる。分からなければ、上の「[結果不明の直接の push の記録](#結果不明の直接の-push-の記録)」のとおり、送った ref と SHA を記録し、その手順で成否を確定させる。`main` の先端を止めた時刻に控えた先端と比べるだけでは、個々の push の成否は決まらない。確定するまで切り替えを始めない
   - 要求を送ったか、GitHub が後でマージし得るか分からないマージの結果は、経路によらず、Pull Request の番号・渡した head（分からなければ打った時点の head）・打った時刻を、M6-1 と同じ形で作業の記録に載せる。`ndf ci merge` では、結果の JSON が出ない、`metrics` に `rounds` が無い `unknown`・`infra_wait`・`ci_pending` が当たる。載せた記録の結果は、M6-2 の読み直しで確かめ、確定しなければ M6-5 のとおりリポジトリの管理者に引き継いで確定させる。M6-3 の打ち直しはしない。打ち直しはマージの要求を送り直すことで、準備 1 の停止に反し、成立すれば `main` が更新されて本番への反映が起動し得るためである。M6-4 も、打ち直しの結果を読む手順なので使わない
   - `ndf ci merge` が必須のチェックの待ちで止まった結果（`metrics` に `rounds` がある）は、要求を送っていないので載せない
4. 作業の記録に未解決の要求が無いことと、マージキューが空であることを確かめる。未解決の要求は、上の「[未解決の要求が無いことの確かめ方](#未解決の要求が無いことの確かめ方)」の手順で、リポジトリ全体を読んで確かめる。準備 3 で今回載せた要求と M6-1 の記録だけでなく、以前の作業から残っている要求も対象にする。切り替えの後のマージの S8 でこの準備を使うときも同じである。未解決の記録があれば、結果が確定して記録が閉じるまで、準備 1 の停止を保ったまま切り替えを始めない。マージキューが空でも、結果の分からない要求が後から成立しないとは言えないので、記録を閉じる代わりにしない。記録が閉じる前に秘密が漏れたときは、リポジトリの管理者が M6-6 のとおりにマージの停止を保ったまま切り替える。切り替えの後の M6-6 の手順 2〜6 は、下の「切り替えの後のマージ」の「切り替えの後に秘密を変えるとき」の読み替えに従う。記録が複数あるときも、その読み替えのとおり、すべての記録の結果が確定し、探し直しが済むまで、世代と停止を戻さない
   - マージキューは、`main` 宛ての開いた Pull Request ごとに、GitHub GraphQL の `PullRequest.isInMergeQueue` で確かめる。NDF の GitHub の接続部分と同じ項目である。`gh pr view --json` はこの項目を扱わない版があるので使わない

     ```bash
     gh api graphql \
       -f query='query($owner:String!,$name:String!,$number:Int!){repository(owner:$owner,name:$name){pullRequest(number:$number){isInMergeQueue}}}' \
       -f owner=devbasex -f name=nd-factory -F number=<番号> \
       --jq '.data.repository.pullRequest.isInMergeQueue'
     ```

   - どの Pull Request でも `false` が出たときだけ、マージキューが空とする。`true` が出たら、その Pull Request がキューから外れるかマージされるまで切り替えを始めない
   - 終了コードが `0` でない、または `true` と `false` のどちらも出ないときは、取得に失敗したものとして切り替えを保留する。準備 1 の停止を保ったまま、取得できるまで打ち直す

切り替えの手順は次のとおりである。

1. 今の世代の値を控え、`<非公開リポジトリ>` の変数 `LEAK_CHECK_GENERATION` を `0` にする。この後の NDF のマージは人へ戻り、呼び出しのワークフローも探す前に失敗する
2. 手順 1 で世代を `0` にした時刻から、NDF の時間の上限（T）が過ぎるまで待つ。T は、NDF が世代を読んでからマージの API の呼び出しを終えるまでに使える時間で、このリポジトリをマージできる NDF の設定に置かれる
   - 世代を `0` にする前に世代を読んだ NDF は、T の中でマージを終えるか、T を過ぎてマージせずに止まる。T が過ぎれば、旧い秘密の結果で NDF がマージの API を新しく呼ぶことはない（すでに送った要求は、下の未解決の記録で確かめる）
   - T の値は、「NDF の認証の権限」で控えた認証を使うすべての NDF の設定で確かめ、最も長い値だけ待つ（未確認: 設定の名前と確かめ方は、NDF への非公開の検査の機能の依頼で決まる。設計の例は 30 分）。T の値を確かめられなければ、先へ進まない

   T が過ぎたら、控えた記録の置き場所で、NDF の未解決の記録の一覧（結果不明と未検証の状態の記録をリポジトリで絞ったもの）に、このリポジトリの記録が残っていないことを確かめる。権限を与えたのに置き場所を共有しない NDF の認証が見つかれば、その置き場所の記録も確かめ、権限を外す
   - 残っていれば、記録が閉じるまで待つ。**Pull Request が閉じていることや head が変わったことを理由に、記録が残っていても先へ進まない。** 応答を失ったマージの要求は、後から GitHub が処理しうる
   - 秘密が漏れたときなど待てないときは、残した記録を控えて先へ進んでよい。その後に NDF から世代の違いの知らせが来たら、マージでできたコミットを手元で新しい秘密で探し直し（「当たりの場所を手元で引く」）、マージを戻すかを判断する
3. 秘密か呼び出しのワークフローを変える
4. 変数 `LEAK_CHECK_GENERATION` を、控えた値に 1 を足した値にする。手でのマージの結果が分からないまま M6-6 で切り替えているときは、M6-6 の 5 か 6 に来るまで、この手順を打たずに世代を `0` のままにする

公開のリポジトリの環境 `leak-scan` の秘密を変えるときは、この切り替えは要らない（main への push の探しは push のたびに今の秘密で動き、マージを決めない）。2 か所の値は同じにしておく。

## 導入の順序

導入は 2 本の Pull Request に分ける。1 本目（実装）はワークフロー・見本・スクリプト・`ci.yml` の変更・テスト・この文書を入れ、`.ndf/project.json` を変えない。2 本目は `.ndf/project.json` に NDF の非公開の検査を有効にする項目を足す。

1. 作り物の値だけを使う検証用の公開リポジトリと非公開リポジトリで、このワークフローを動かして次のことを確かめる
   - 非公開リポジトリから公開のリポジトリの再利用できるワークフローを呼べ、秘密が名前で渡る。非公開リポジトリの実行の記録が、権限の無い利用者から画面でも API でも見えない
   - ワークフローの起動の API が実行の ID を返し、試行 1 の取得の API が `referenced_workflows` に実際に解決された SHA を返す
   - fork の Pull Request の `refs/pull/<番号>/head` と `refs/pull/<番号>/merge` を、資格情報を残さないチェックアウトから取り込める
   - `.gitleaksignore` を足した Pull Request と、`.gitattributes` の `export-ignore` で作り物の値のファイルを省こうとした Pull Request が落ちる
   - squash のマージでできたコミットの木が、同じ base の先頭と head のマージコミットの木と同じである
   - 呼び出しのワークフローが、世代が `0` か入力と違うときに探す前に失敗する。環境 `leak-scan` の秘密を Pull Request の側の実行が受けられない
   - NDF の受け入れの条件（[漏れの検査の仕様](../specifications/leak-check.md) の「NDF が非公開の検査の結果を受け入れる条件」）で、ジョブを作る前の失敗・探しの失敗・版の食い違い・未完了・成功を区別し、起動の後の push・base の先頭の前進と書き換え・世代の切り替え・検査のコードの変更（`tools/checks/leak_scan/` のモジュールの追加・変更・削除・改名を含む。対象は仕様の「秘密を受けて動くコードと設定の一覧」）・マージ先の変更・再実行の結果を退けられる
   - 同じ受け入れの条件で、次の場合に NDF がマージしない
     - 検査のコードのコミットが、今の main の先頭と分岐しているか、今の main の先頭より先に進んでいる（比較の API の `status` が `diverged` か `behind`）。`files` に一覧のファイルが無くてもマージしない
     - 比較の API の呼び出しが失敗する
     - 比較の API の応答から `files` を取得できない
     - マージ先が main で、base の先頭を読み直した後に main が進み、比較の API に渡す main の先頭の SHA が検査に渡した base の SHA と違う。進んだ変更が「秘密を受けて動くコードと設定の一覧」のファイルを含まなくてもマージしない
2. 1 本目をマージする前に、公開のリポジトリの環境 `leak-scan`（使えるブランチは main だけ）とその秘密 `LEAK_CHECK_PATTERN` を設定する。変数 `LEAK_CHECK_REQUIRE_PATTERN` は、この時点では `1` にしない
3. 1 本目の Pull Request を、マージの前に持ち主が手元で探す（下の「1 本目を手元で探す」）。**1 本目のマージから、NDF に非公開の検査の機能が入り、手順 6 で NDF の利用者の設定から非公開の検査を有効にするまで、NDF にほかの Pull Request をマージさせない。** 手で起動した探しの結果でもマージしない（今の NDF は、探した Pull Request の番号・head・マージ先・base の先頭の組を確かめずにマージするため）
4. 1 本目のマージで起きた main への push の `leak-check-push` で、秘密の規則を使って当たりなく探し終えたことを確かめる。次の 3 つがすべてそろえば、確かめられたことになる
   - ジョブが成功している
   - `dir` と `git` の両方の探しで、`leak-scan-secret: nd-real-value: 0 件` の行が出ている
   - `leak-scan-secret: 秘密 LEAK_CHECK_PATTERN が空なので .gitleaks.toml だけで探す` の行が出ていない

   3 つのどれかが欠ければ、今の木と履歴の両方で当たりと失敗が無くなるまで次へ進まず、変数 `LEAK_CHECK_REQUIRE_PATTERN` も `1` にしない。
   - 秘密が空の行が出ていれば、手順 2 の設定を直し、下の「コミットを入れずに GitHub の設定だけを直したとき」の手順で、今の main の先頭を探した `leak-check-push` の実行を確かめる。再実行は GitHub Actions の画面の「Re-run jobs」か `gh run rerun <実行の ID>` で行う。手元の探し直しは、GitHub Actions が直した後の環境から秘密を受け取れたことを確かめられないので、この確認の代わりにしない
   - 当たりや検査の失敗があれば、原因を解消する（当たりは「当たりの場所を手元で引く」で場所を引く）
   - 当たりや検査の失敗を直した後も、確かめるのは GitHub Actions の `leak-check-push` の記録である。手元の探し（下の「main のコミットを手元で探し直す」）は原因の特定に使い、手元で成功しても先へ進まない。手元の成功では、GitHub Actions でジョブが動き、環境 `leak-scan` から秘密を受け取れたことを確かめられないためである
     - 直すために main へコミットを入れたときは、そのコミットの push で動いた `leak-check-push` の記録で、上の 3 つがすべてそろうことを確かめる。元の実行を再実行しても、探すのは元の SHA のままなので、直した後のコミットを確かめたことにならない（[ワークフローの再実行](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs)）
     - コミットを入れずに GitHub の設定だけを直したとき（秘密が空だった場合を含む）も、確かめるのは、設定を直した後に今の main の先頭を探した記録である。待つ間に、ほかの変更で main が進んでいることがあるためである
       1. 設定を直した後で、今の main の先頭の SHA（`gh api repos/devbasex/nd-factory/commits/main --jq .sha`）を読み、その SHA への push で動いた `leak-check-push` の実行を選ぶ。元の実行の `head_sha`（`gh api repos/devbasex/nd-factory/actions/runs/<実行の ID> --jq .head_sha`）が同じなら、元の実行を選ぶ
       2. 選んだ実行の最新の試行が、設定を直す前に始まっていれば、その試行が終わるのを待ってから実行を再実行する。設定を直す前に始まった試行は、終わったのが直した後でも、直す前の設定で動いているためである。設定を直した後に始まった試行なら、終わるのを待つ
       3. 設定を直した後に始まった試行（再実行したなら再実行の試行）の記録で、上の 3 つがすべてそろうことを確かめる。設定を直す前に始まった試行の記録は、成功でも失敗でも判断に使わない
       4. 変数 `LEAK_CHECK_REQUIRE_PATTERN` を `1` にする直前に、今の main の先頭の SHA を読み直し、確かめた実行の `head_sha` と照らし合わせる。main が進んでいれば、新しい先頭の実行で 1 から確かめ直す

   確かめた後に、変数 `LEAK_CHECK_REQUIRE_PATTERN` を `1` にする
5. `<非公開リポジトリ>` を作り、[`leak-check-caller.yml`](leak-check-caller.yml) を写し、秘密 `LEAK_CHECK_PATTERN` と変数 `LEAK_CHECK_GENERATION`（値は `1`）を登録する。NDF がマージに使う今の認証で、「NDF の認証の権限」の 3 つの API が呼べることを確かめる。続けて、開いている Pull Request の 1 本で探しを手で起動して確かめる（下の「手で起動して確かめる」）。この結果で Pull Request をマージしない
6. NDF に非公開の検査の機能が入った後、NDF の利用者の設定で非公開の検査を有効にしてから、2 本目の Pull Request を出し、NDF にマージさせる。利用者の設定は、2 本目のマージの後も有効のまま残す。この手順を終えたと扱うのは、通常の Pull Request のマージのたびに NDF が分岐点から head までの全コミットを非公開の検査で探し、成功しなければマージしないことを確かめた後である（#198 で確かめる）。確かめるまでは、通常の Pull Request に入った実際の値は止まらない。NDF 11.0.43 はこの機能を持たない

**2 本目へ進む条件:** 手順 1・4・5 の確認が済み、手順 2 の設定があり、変数 `LEAK_CHECK_REQUIRE_PATTERN` が `1` で、NDF が非公開の検査の結果を受け入れられる。1 つでも欠ければ 2 本目を出さない。Dependabot の Pull Request での確認は条件にしない（Dependabot を有効にした後に、最初の Dependabot の Pull Request で確かめる）。

### 1 本目を手元で探す

秘密を渡す前に、秘密を受けて動くスクリプトと設定の一式を読んで確かめ、そのコミットに固定する。探す対象のコミットは、データとして取り込むだけで、そのチェックアウトのコードは動かさない。

1. 1 本目の Pull Request の head の SHA を控える（以後「確かめたコミット」）
2. 確かめたコミットの `tools/checks/export-tree.sh`・`tools/checks/leak-scan-secret.sh`・`tools/checks/leak-scan.sh`・`tools/checks/install-gitleaks.sh`・`.gitleaks.toml`・`tools/checks/gitleaks-default.toml` の 6 つと、`tools/checks/leak_scan/`（`leak-scan.sh` が起こす検査の本体）のすべてのファイルを、差分だけでなく全体を読む（[漏れの検査の仕様](../specifications/leak-check.md) の「秘密を受けて動くコードと設定の一覧」から、手元では動かさない `leak-check-secret.yml` を除いたもの）。秘密を外へ送る処理や、ほかのファイルを動かす処理が無いこと、`install-gitleaks.sh` の版と要約値が main の `ci.yml` の `leak-check` の値と同じことを確かめる
3. 確かめたコミットを、探す対象とは別のディレクトリにチェックアウトする。秘密を渡して動かすのは、このディレクトリのスクリプトと設定だけである。gitleaks は、このディレクトリの `install-gitleaks.sh` で置く（`GITHUB_PATH` を空にして打ち、置いた先を `PATH` に足す）
4. 探す対象は、`refs/pull/<番号>/head` と `refs/pull/<番号>/merge` を取り込んだ別のリポジトリにする。Pull Request の取得の API の `base.ref` で、マージ先のブランチが main であることを確かめる。取り込んだ head が確かめたコミットと同じで、マージコミットの最初の親が今の main の先頭、2 つ目の親が確かめたコミットであることを確かめる。このときの main の先頭の SHA を「探した base」として控える。どれかが違えば手順 1 からやり直す
5. 探す対象のリポジトリで、手順 3 のスクリプトを絶対パスで打つ。マージコミットの木を `export-tree.sh <マージコミット> <空のディレクトリ>` で、分岐点（`git merge-base <探した base> <確かめたコミット>`）から head までの履歴の項目を `export-tree.sh --history <分岐点> <確かめたコミット> <別の空のディレクトリ>` で、作業ツリーの外に取り出す。秘密を `LEAK_CHECK_PATTERN` に、`LEAK_CHECK_REQUIRE_PATTERN=1` を渡し、`leak-scan-secret.sh dir <木>`・`leak-scan-secret.sh history <履歴>`・`leak-scan-secret.sh git --range <分岐点>..<確かめたコミット>` を打つ。設定は、スクリプトが手順 3 のチェックアウトから絶対パスで読む
6. 当たりか失敗があれば、マージしない。NDF にマージさせる直前に、Pull Request の head が確かめたコミット、マージ先が main、main の先頭が探した base のままであることを読み直す。どれかが変わっていれば、マージせずに手順 1 からやり直す
7. NDF がマージした後に、Pull Request を読み、マージ先が main で、マージでできたコミット（`merge_commit_sha`）の最初の親が探した base で、head が確かめたコミットであることを確かめる。外れていれば、マージでできたコミットの木と、その最初の親と head から求めた分岐点から head までを、手順 3 のスクリプトで手元で探し、当たりがあればマージを戻すかを判断する

### 手で起動して確かめる

NDF と同じく、起動した 1 回の実行の初回の試行だけを確かめる。

1. 6 つの入力を取る。Pull Request の番号・head の SHA（`head.sha`）・base の先頭の SHA（`base.sha`）・マージコミットの SHA（`merge_commit_sha`）は、`gh api repos/devbasex/nd-factory/pulls/<番号>` で読む。`mergeable` が `null` なら読み直して待ち、真でなければ別の Pull Request を選ぶ。検査のコードのコミットは `gh api repos/devbasex/nd-factory/commits/main --jq .sha`、設定の世代は `<非公開リポジトリ>` の変数 `LEAK_CHECK_GENERATION` の値である
2. `<非公開リポジトリ>` の呼び出しのワークフローを、ワークフローの起動の API で起動し、応答の `workflow_run_id` を控える。送る本文には、`ref` に `<非公開リポジトリ>` の既定のブランチ（`gh api repos/<非公開リポジトリ> --jq .default_branch` で読む）を、`inputs` に手順 1 の 6 つの値を入れる。API のバージョン `2022-11-28` は、本文に `return_run_details: true` を入れたときだけ実行の ID を返すので、次の例のように入れる（バージョン `2026-03-10` は指定しなくても返す。[起動の API の仕様](https://docs.github.com/en/rest/actions/workflows?apiVersion=2022-11-28#create-a-workflow-dispatch-event)）。応答に `workflow_run_id` が無ければ、手順 3 へ進まない

   ```bash
   gh api --method POST \
     -H "X-GitHub-Api-Version: 2022-11-28" \
     "repos/<非公開リポジトリ>/actions/workflows/<呼び出しのワークフローのファイル>/dispatches" \
     -f ref='<既定のブランチ>' \
     -F return_run_details=true \
     -f 'inputs[pr_number]=<番号>' \
     -f 'inputs[head_sha]=<head の SHA>' \
     -f 'inputs[base_sha]=<base の先頭の SHA>' \
     -f 'inputs[merge_sha]=<マージコミットの SHA>' \
     -f 'inputs[code_sha]=<検査のコードのコミット>' \
     -f 'inputs[generation]=<設定の世代>' \
     --jq .workflow_run_id
   ```
3. 控えた実行の試行 1 が完了したら、次の 4 つを確かめる。1 つでも外れれば、承認していない版か、別の対象か設定で探した結果なので、手順 1 からやり直す
   - 試行 1（`gh api repos/<非公開リポジトリ>/actions/runs/<workflow_run_id>/attempts/1`）の `conclusion` が `success` である
   - 同じ応答の `referenced_workflows` に、`path` が `devbasex/nd-factory/.github/workflows/leak-check-secret.yml@main` の項目がちょうど 1 つあり、その `sha` が手順 1 の検査のコードのコミットと同じである（ジョブの表示名は入力から組むだけで、実際に動いた版を示さない）
   - 試行 1 のジョブの一覧（`gh api --paginate repos/<非公開リポジトリ>/actions/runs/<workflow_run_id>/attempts/1/jobs`）のすべてのジョブの `conclusion` が `success` である
   - 探しのジョブ `leak-check-secret` の表示名の番号・head・base・merge・code・gen の 6 つの値が、手順 1 の値と一致する

## 当たりの場所を手元で引く

非公開の記録と `leak-check-push` の記録には、ファイルの名前を出さない（名前も実際の値を含み得る）。持ち主は、記録の探した対象を手元で探し直してファイルを特定する。

1. 公開のリポジトリを、記録の表示名の検査のコードのコミットでチェックアウトし、`refs/pull/<番号>/head` と `refs/pull/<番号>/merge` を取り込む。取ったコミットが表示名の SHA と同じかを確かめる。マージの参照が進んでいれば、表示名のマージコミットの SHA を直に取る
2. コミットの列が空の当たり（`dir` と `history` の探し）は、`tools/checks/export-tree.sh <マージコミットの SHA> <木の出力先>` と `tools/checks/export-tree.sh --history <分岐点> <head の SHA> <履歴の出力先>` を、別々の空のディレクトリへ打つ。分岐点は `git merge-base <base の SHA> <head の SHA>` で求める。続けて秘密を渡し、`tools/checks/leak-scan-secret.sh dir <木の出力先> --details` と `tools/checks/leak-scan-secret.sh history <履歴の出力先> --details` を打つ
   - 履歴の当たりは、`paths/<通し番号>`（そのファイルの中身がパスの名前）か、`layers/<層の番号>/<元のパス>`・`binary-text/<層の番号>/<元のパス>`（中身）で出る
   - 中身の当たりのコミットは、`git hash-object --no-filters <履歴の出力先>/layers/<層の番号>/<元のパス>` で blob の SHA を求め、`git log --find-object=<blob の SHA> <分岐点>..<head の SHA>` で引く。`binary-text/<層の番号>/<元のパス>` の当たりは、同じ層と元のパスの `layers/<層の番号>/<元のパス>` で blob の SHA を求める
   - パスの名前の当たり（`paths/<通し番号>`）のコミットは、そのパスを足したか消したか変えたコミットである。ファイルの中身がパスの名前そのものなので、それをパスの指定に渡して引く。パスの名前には実際の値が含まれ得るので、出力は手元の端末にだけ出す

     ```bash
     path="$(cat '<履歴の出力先>/paths/<通し番号>')"
     git --literal-pathspecs log --full-history -m --format=%H '<分岐点>..<head の SHA>' -- "$path"
     unset path
     ```
   - 上の方法でコミットが出なければ、そのコミットは特定できない。そのときは、特定できなかったことと、探した範囲（分岐点と head の SHA）を記録に残す
3. コミットの列がある当たり（`git` の探し）は、`tools/checks/leak-scan-secret.sh git --range <分岐点>..<head の SHA> --details` を打つ
4. main への push（`leak-check-push`）の当たりは、その実行が探したコミットで探し直して引く。main は記録を確かめる間にも進むので、main の先頭では探さない
   - 対象の `leak-check-push` の実行の `head_sha`（`gh api repos/devbasex/nd-factory/actions/runs/<実行の ID> --jq .head_sha`）を控え、そのコミットを下の「main のコミットを手元で探し直す」で、`--details` を付けて探す。いつもの作業ディレクトリでは探さない。未追跡のファイルや別の版の gitleaks が混ざり、CI が出した当たりを引けなかったり、関係の無いファイルを当たりと取り違えたりするためである
   - 実行の後に環境 `leak-scan` の秘密を変えていた場合は、手元で渡す秘密が当時と同じ規則で探せるかを確かめる。同じ規則で探せなければ、元の当たりを引けないことがある
5. 出た実際のファイルの名前と行を、記録の当たりの規則と行と突き合わせる。**`--details` の出力は手元の端末にだけ出し、記録・Issue・Pull Request に貼らない。当たりの理由を公開の Pull Request に書かない。** 直しを頼むときは理由を伏せるか、Pull Request を閉じる

### main のコミットを手元で探し直す

1 つのコミットを、`leak-check-push` と同じ範囲と同じ設定の組み方で手元で探し直す。探す範囲は、そのコミットの木と、そのコミットから到達できる全履歴である。設定は、そのコミットの設定と、そのコミットが固定した gitleaks の版を使う。「導入の順序」の手順 4、上の手順 4、「正当な当たりを規則単位で外す」の表で使う。いつもの作業ディレクトリでは探さない。

当たりが無いかの判断は、`leak-check-push` と同じ `--count-only` で行う。ファイルの特定に使う `--details` は、設定の組み方が `leak-check-push` と違うので、合否の判断に使わない。

| 付ける引数 | 設定の組み方 | 使う場面 |
| --- | --- | --- |
| `--count-only`（`leak-check-push` と同じ） | 既定の規則・`.gitleaks.toml`・`nd-real-value` だけの設定で、1 回ずつ別々に探す | 当たりが無いかの判断 |
| `--details` | 既定の規則と、`.gitleaks.toml` を読み込んで（`[extend]`）`nd-real-value` を足した設定で探す | 当たりのファイルの特定。`.gitleaks.toml` を読み込むので、その内容によっては `--count-only` と結果が変わることがある |

1. 探すコミットの SHA を控える（以後「対象のコミット」）
2. 新しい空のディレクトリに公開のリポジトリを複製し（`git clone https://github.com/devbasex/nd-factory.git <空のディレクトリ>`）、そこへ移る。対象のコミットが main に無いとき（Pull Request のマージコミット）は、`git fetch origin refs/pull/<番号>/merge` で取り込む
3. `git checkout --detach <対象のコミット>` でチェックアウトし、`git rev-parse HEAD` が対象のコミットと同じこと、`git status --porcelain` が何も出さないことを確かめる
4. 対象のコミットがまだ main に無いときは、秘密を渡す前に、「1 本目を手元で探す」の手順 2 に挙げた 6 つのファイルと `tools/checks/leak_scan/` を、差分だけでなく全体を読み、秘密を外へ送る処理や、ほかのファイルを動かす処理が無いことを確かめる。秘密を受けて動くのは、このチェックアウトのスクリプトだからである。`install-gitleaks.sh` を少しでも変えるコミット（版・要約値だけでなく、取得先や取得の処理を変えるものも含む）では、対象のコミットの `install-gitleaks.sh` が取る配布物が gitleaks の公式の配布（`github.com/gitleaks/gitleaks` の Releases）で、要約値がその配布物を自分で取って `sha256sum` で求めた値と同じことも確かめてから打つ。main の `ci.yml` の値とは照らし合わせない（1 本目のマージの後の `ci.yml` は `install-gitleaks.sh` を呼ぶだけで、版と要約値を持たない）
5. このチェックアウトの `install-gitleaks.sh` で gitleaks を置き、置いた先を `PATH` の先頭に足す。`install-gitleaks.sh` が失敗したら（取得・要約値の確かめ・取り出しの失敗。終了コードが `0` でない）、先へ進まない。続けて、`command -v gitleaks` が今回置いた先の `gitleaks` を指すことと、`gitleaks version` が `install-gitleaks.sh` の `GITLEAKS_VERSION` と同じことを確かめる。版の番号だけでは、前から入っていた同じ版の gitleaks と見分けられないためである

   ```bash
   dest="<作業用の空のディレクトリ>/gitleaks"
   GITHUB_PATH= tools/checks/install-gitleaks.sh "$dest"; echo "終了コード: $?"   # 0 でなければ先へ進まない
   export PATH="$(cd "$dest" && pwd -P):$PATH"
   command -v gitleaks   # "$dest" の絶対パスの下の gitleaks であること
   gitleaks version
   ```
6. 秘密を `LEAK_CHECK_PATTERN` に、`LEAK_CHECK_REQUIRE_PATTERN=1` を渡し、`dir` と `git` の探しを順に打つ。それぞれの直後に、探しの名前と終了コードを表示する。表示の行が出なかった探しは、打たれていないものとして扱う（マージの後の探し直しの 7-7 と、M6-6 の 5 の表も、この行で見分ける）

   ```bash
   tools/checks/leak-scan-secret.sh dir --count-only
   echo "dir の終了コード: $?"
   tools/checks/leak-scan-secret.sh git --count-only
   echo "git の終了コード: $?"
   ```
7. 両方の終了コードが `0` のときだけ、当たりが無いと判断する。片方でも `0` でなければ、当たりか失敗が残っている
8. 当たりの場所を引くときは、`--count-only` を外し、両方を `--details` を付けて打ち直す。この結果は場所の特定にだけ使い、手順 7 の判断を置き換えない。`--details` で元の当たりを特定できなければ、下の「件数だけの探しと同じ組み方で場所を引く」で引く

### 件数だけの探しと同じ組み方で場所を引く

`--details` で元の当たりを特定できないときは、`--count-only` と同じ規則の組み方のまま、ファイルの名前を出して探す。`--details` は `nd-real-value` を `.gitleaks.toml` に重ねて探すので、`.gitleaks.toml` の内容によっては、`nd-real-value` だけで探した `--count-only` の当たりが再現しないことがある。たとえば `.gitleaks.toml` に全体の許可（最上位の `[[allowlists]]`）があれば、`--details` ではその許可が効き、`--count-only` では効かない。`leak-scan-secret.sh` は `--count-only` と `--details` を同時に受けないので、`leak-scan.sh` を直に打つ。

この手順では、元の探しと同じ確認済みのスクリプトで、元の探しと同じ対象を探す。検査のコードを置いたチェックアウトと、探す対象は同じとは限らない。マージの後の探し直しの 7-4・7-5 では、検査のコードは確認済みのチェックアウトにある。7-4・7-5 の `git` 系の検査（`git` と `git --range`）は、7-2 のチェックアウトで実行する。7-4 の `dir` は、実際にマージされたコミットから書き出した木を検査する。7-5 の `history` は、分岐点と実際に取り込んだ head から書き出した履歴を検査する。squash でできたコミットからは Pull Request の途中のコミットをたどれないので、7-5 の `history` はマージされたコミットからは再現できない。元の探しで当たった規則の組み方・対象・gitleaks の版は変えない。既定の規則か `.gitleaks.toml` の当たりは、`--details` で同じ組み方のまま引けるので、この手順は `nd-real-value` の当たりにだけ使う。

- スクリプト: 元の探しで使った確認済みのスクリプトを、作業ディレクトリを移った後も絶対パスで指定する。確認済みのスクリプトとは、「main のコミットを手元で探し直す」の手順 3〜5 でスクリプトを読み、gitleaks を置いたチェックアウトのものである。マージの後の探し直しでは 7-1・7-3・7-5 で使ったもので、7-5 の「変更前の設定を確認済みの検査のコードで探し直す」の結果を使うときは、スキャンのスクリプト（`leak-scan-secret.sh` と `leak-scan.sh`）は集めたディレクトリのもの、`export-tree.sh` は実際の base のチェックアウトのものである。集めたディレクトリには `export-tree.sh` を写していないためである。7-2 のチェックアウトのスクリプトは読んで確かめていないので、打たない
- 作業ディレクトリと対象: 元の探しと同じにする。元の探しごとに、次の表のとおりである

  | 元の探し | `dir` の対象（手順 3 の `<dir の対象>`） | `git`・`git --range` の作業ディレクトリ | `history` の対象（手順 3 の `<履歴の出力先>`） |
  | --- | --- | --- | --- |
  | 「main のコミットを手元で探し直す」と、マージの後の探し直しの 7-3 | そのチェックアウトの根。`dir` はチェックアウトそのものを探すので、書き出した木は無い | そのチェックアウト | 打っていない |
  | マージの後の探し直しの 7-4 | 7-4 で書き出した木（`$tree_out`） | 7-2 のチェックアウト | 打っていない |
  | マージの後の探し直しの 7-5 | 打っていない | 7-2 のチェックアウト | 7-5 で書き出した履歴（`$out`） |

  書き出した木や履歴は、元の書き出しが成功したと確認できる場合だけ使う。`export-tree.sh` は途中まで書き出してから失敗することがあり、手順 3 のコマンドは出力がそろっているかを確かめないためである。出力が残っていないか、元の書き出しの成功を確認できなければ、書き出し直す。書き出し直すときは、7-2 のチェックアウトで、7-4 の木は 7-1 の `export-tree.sh`、7-5 の履歴は当たりが出た検査の書き出しに使った `export-tree.sh` を、絶対パスで実行する。実際にマージされたコミットと Pull Request の head は 7-2 のチェックアウトにしか無く、スクリプトを置いたチェックアウトで実行すると書き出しが失敗するためである。7-5 の「変更前の設定を確認済みの検査のコードで探し直す」の結果を使う場合、集めたディレクトリには `export-tree.sh` が無いので、書き出しには実際の base のチェックアウトの `export-tree.sh` を使う。手順 3 の `leak-scan.sh` は、集めたディレクトリのものを使う。範囲は元と同じにし、出力先には新しい空のディレクトリを使う。その書き出しが成功した（終了コードが `0` の）場合だけ、その出力を手順 3 の対象にする。失敗したら、手順 3 は打たない

1. 元の探しと同じく、元の探しで `PATH` の先頭に足した gitleaks のディレクトリを、もう一度 `PATH` の先頭に足し、`command -v gitleaks` がそのディレクトリの中の `gitleaks` を指すことを確かめる。7-5 の「変更前の設定を確認済みの検査のコードで探し直す」の結果を使うときは、実際の base のチェックアウトで gitleaks を置いたディレクトリである
2. 秘密を `LEAK_CHECK_PATTERN` に入れ、探す木の外の新しい空のディレクトリに、`nd-real-value` だけの設定を書く。中身は `leak-scan-secret.sh` が `--count-only` で組む設定と同じである。書いたら、秘密を環境から消す。gitleaks に秘密を渡さないためである。秘密に `'''` か改行が含まれていれば、元の探しも失敗しているので、この手順は使わない

   ```bash
   checks='<元の探しで使った確認済みのスクリプトのディレクトリの絶対パス>'   # 例: <確認済みのチェックアウトの絶対パス>/tools/checks
   work="$(mktemp -d)"
   printf '[[rules]]\nid = "nd-real-value"\ndescription = "秘密 LEAK_CHECK_PATTERN の実際の値"\nregex = '"'''%s'''"'\n' "$LEAK_CHECK_PATTERN" >"$work/alone.toml"
   unset LEAK_CHECK_PATTERN
   ```
3. 元の探しと同じ対象で、`leak-scan.sh` に今の設定と `--paths` を渡して打つ。`--paths` を渡すと、実際のファイルの名前と gitleaks の出力が出る。対象と作業ディレクトリは、上の表のとおりである
   - `dir` の当たり: `(cd '<dir の対象>' && "$checks/leak-scan.sh" dir "$work/alone.toml" --paths)`
   - `git` の当たり: 上の表の作業ディレクトリで `"$checks/leak-scan.sh" git "$work/alone.toml" --paths`。`git --range` の当たりは、元と同じ範囲を `--range '<範囲>'` で足す
   - `history` の当たり: 履歴の出力先の `paths`・`layers/<層の番号>`・`binary-text/<層の番号>` を、1 つずつ探す木の根として打つ

     ```bash
     for root in '<履歴の出力先>'/paths '<履歴の出力先>'/layers/* '<履歴の出力先>'/binary-text/*; do
       [[ -d "$root" ]] || continue
       echo "探す木の根: $root"
       (cd "$root" && "$checks/leak-scan.sh" dir "$work/alone.toml" --paths)
     done
     ```
4. 打ち終えたら、`rm -rf "$work"` で、秘密を書いた設定を消す
5. 出力は、「当たりの場所を手元で引く」の手順 5 のとおり、手元の端末にだけ出す。この結果は場所の特定にだけ使い、当たり無しや失敗の解消の判断には使わない

## 正当な当たりを規則単位で外す

この節の手順は、NDF が通常の Pull Request に非公開の検査を起動するようになった後（「導入の順序」の手順 6 の後。#198）に使う。NDF 11.0.43 は起動しないので、それまでは通常の Pull Request で非公開の検査の当たりは出ない。

正当な当たり（誤検知）を `[[rules.allowlists]]` で外すときは、許可の変更だけの Pull Request を先に main へマージし、その後に対象を含む Pull Request をマージさせる。非公開の検査は、探す Pull Request の中の設定ではなく、検査のコードのコミット（main の先頭）の `.gitleaks.toml` と `tools/checks/gitleaks-default.toml` で探すためである。対象と許可を同じ Pull Request に入れると、公開の `leak-check`（Pull Request のマージの参照の設定で探す）は通っても、非公開の検査は許可の無い main の規則で探して落ち、NDF はマージしない。

1. 当たりの場所を手元で引き（上の「当たりの場所を手元で引く」）、正当な当たりかを判断する
2. 当てた規則の `[[rules.allowlists]]`（`.gitleaks.toml` か `tools/checks/gitleaks-default.toml`）に、理由を添えて許可を足す Pull Request を出す。この Pull Request には許可の変更だけを入れ、誤検知の対象を入れない。許可の条件に実際の値を書かない
3. 許可の Pull Request をレビューして、NDF にマージさせる。許可は以後のすべての Pull Request と main への push の探しに効くので、広げすぎていないかをレビューで見る
4. 対象を含む Pull Request から同じ許可の変更を外し、NDF にマージさせる。NDF が次に起動する非公開の検査は、許可の入った main の先頭の規則で探す

対象が過去のコミットにあるときは、次のように扱う。

| 対象のある所 | 扱い |
| --- | --- |
| Pull Request の途中のコミットだけ | 上の手順のままでよい。規則単位の許可は、履歴の探し（`history` と `git --range`）にも効く |
| main の木か履歴（規則か gitleaks の版を変えたために、前から在る内容に当たるようになった） | 規則・`tools/checks/gitleaks-default.toml`・gitleaks の版を変える Pull Request に、前から在る内容への許可を同じ Pull Request で入れる。許可を後の Pull Request に分けると、許可の Pull Request のマージコミットの木にも対象があるため、許可の Pull Request 自身が非公開の検査で落ちる。公開の `leak-check` が探すのは、マージコミットの木と、分岐点から head までのコミットだけで、main の過去のコミットにだけ残る内容は探さない。そのため、規則を変える Pull Request（範囲は下の「規則を変える Pull Request をマージの直前に確かめる」の冒頭のとおり）は、マージの前に、その Pull Request のマージコミット（`refs/pull/<番号>/merge` の SHA）を、「当たりの場所を手元で引く」の「main のコミットを手元で探し直す」で探す。そのコミットの設定と gitleaks の版で、そのコミットから到達できる全履歴（main の過去のコミットを含む）と木を探すことになる。手元の `main` に切り替えて探すと、変更前の設定で探すことになる。探さずにマージすると、マージ後の `leak-check-push` で初めて当たりに気付く。探した後に main か Pull Request の head が進むと、前の結果は新しいマージの候補を確かめていない。マージの直前に、下の「規則を変える Pull Request をマージの直前に確かめる」で、探したマージコミットが今の候補と同じことを確かめる |
| 実際の値の規則 `nd-real-value` の当たり | 許可を足せない（規則は秘密の中にあり、`[[rules.allowlists]]` を持たない）。誤検知なら、「秘密を変える手順」で秘密の正規表現を直す。実際の値なら、マージせずに「当たりの場所を手元で引く」の手順 5 のとおりに扱う |

### 規則を変える Pull Request をマージの直前に確かめる

この節の手順は、反映先の一覧の切り替えの前と後で、マージの要求を送る所が違う。反映先の一覧の切り替えは、`main` への push を自動反映として扱う `.ndf/project.json` の変更である。切り替えの時点は、切り替えを決めた設計の Pull Request がマージされた時点ではなく、`.ndf/project.json` を変える後続の Pull Request が `main` に入った時点とする。切り替えの後は、M5 と M6-3 でマージの API を直接打たない。マージの API を直接打つと、リリース承認ゲートを通らないためである。

この手順書で「規則を変える Pull Request」と呼ぶのは、漏れの検査の仕様の「[秘密を受けて動くコードと設定の一覧](../specifications/leak-check.md#秘密を受けて動くコードと設定の一覧)」に当たるファイルを、1 つでも足す・変える・消す・改名する Pull Request である。対象のファイルは、その一覧だけで決める。この手順書には対象のファイルを並べ直さないので、対象が増えたときも、その一覧を読めば範囲が分かる。一覧のどのファイルを変えても、検査が何を探し、どの gitleaks で探すかが変わり、漏れの検査で実際の値の混入を止められるかが変わる。この節の手順と、手順 5 の例外の表は、この範囲で当てはめる。

規則を変える Pull Request は、検査の入口のスクリプトを改名・移動・削除することがある。この節と「main のコミットを手元で探し直す」のコマンドは、`tools/checks/` の今のパスで候補のスクリプトを打つので、そのままでは打てない。そこで、候補のチェックアウトでスクリプトを打つ前に（S3・M2 の前と、マージの後に 7-1 のチェックアウトを使う前）、候補が実際に使う実行ファイルを次のとおりに決める。

1. `git diff --name-status -M '<探したマージコミット>^1' '<探したマージコミット>'` を打ち、一覧に当たるファイルのうち、改名（`R`）・削除（`D`）されたものと、一覧に当たるパスへ足された（`A`）ものを控える
2. どれも無ければ、候補の実行ファイルは今のパスのままである。手順のコマンドをそのまま打つ
3. あれば、候補のチェックアウトで、次の 4 つの働きを受け持つ実行ファイルを特定する。gitleaks を置く、木を書き出す（`export-tree.sh`）、履歴を書き出す（`export-tree.sh --history`）、秘密を受けて探す（`leak-scan-secret.sh` の `dir`・`git`・`history`・`git --range`）である。特定には、候補の `.github/workflows/leak-check-secret.yml` が呼ぶパスと、改名の差分を使う
4. 特定した実行ファイルと、それが読み込むファイルを、「main のコミットを手元で探し直す」の手順 4 の読み込みの対象にする。今のパスのファイルだけを読んで済ませない。特定したパスと、読んで確かめたことを作業の記録に残す
5. この節と「main のコミットを手元で探し直す」のコマンドの、候補のスクリプトのパスを、特定したパスに置き換えて打つ。引数や終了コードの意味が今の版と違えば、置き換えて打たず、6 のとおりに保留する
6. 4 つの働きのどれかを受け持つ実行ファイルが候補に無いか、特定できないか、引数や終了コードの意味が今の版と違うときは、マージしない。保留した理由を作業の記録に残し、持ち主に戻す。必要な検査を打てないまま、変更後の設定で探したことにはしないためである

規則を変える Pull Request をこの節の手順でマージしてよいかは、非公開の検査を有効にしたか（「導入の順序」の手順 6）と、切り替えの前か後かで、次のとおりに決める。

| 非公開の検査 | 反映先の一覧の切り替え | 扱い |
| --- | --- | --- |
| 有効にする前（「導入の順序」の手順 6 より前。[#198](https://github.com/devbasex/nd-factory/issues/198) で扱う） | 前でも後でも | この節の手順でマージせず、承認も求めない。M3 で非公開の検査の成功を確かめられないためである。規則を変える Pull Request は、非公開の検査を有効にするまでマージしない。ほかの Pull Request をこの間にマージしてよい条件は、手順 5 の項目の表にある。1 本目の Pull Request は「1 本目を手元で探す」で扱う |
| 有効にした後 | 前 | この節の手順 1〜7 と M1〜M6 のとおりにマージする |
| 有効にした後 | 後 | この節の最後の「切り替えの後のマージ」のとおり、持ち主の承認を受けてから `ndf ci merge` でマージする |

マージの参照（`refs/pull/<番号>/merge`）を読むだけでは、GitHub がマージの候補を作り直す前の古いコミットでも一致してしまう。そのため、Pull Request の取得の API で候補を作り直させ、作り直した候補が探したマージコミットと同じことを確かめる（[マージできるかの確かめ方](https://docs.github.com/en/enterprise-server%403.21/rest/guides/using-the-rest-api-to-interact-with-your-git-database#checking-mergeability-of-pull-requests)）。

1. `gh api repos/devbasex/nd-factory/pulls/<番号>` を打つ。この呼び出しで、GitHub がマージの候補の作り直しを始める
2. 応答の `mergeable` が `null` なら、少し待って手順 1 を打ち直す。`false` ならマージしない。`true` になるまで先へ進まない
3. `mergeable` が `true` の応答で、次の 4 つを確かめる
   - 応答の `base.ref` が `main` である。親の SHA の照合だけでは、main と同じコミットを指す別のブランチへ向けた Pull Request を見分けられないためである
   - `merge_commit_sha` が、探したマージコミットの SHA と同じである
   - 探したマージコミットの最初の親（`git rev-parse <探したマージコミット>^1`）が、今の main の先頭（`gh api repos/devbasex/nd-factory/commits/main --jq .sha`）と同じである
   - 探したマージコミットの 2 つ目の親（`git rev-parse <探したマージコミット>^2`）が、応答の `head.sha` と同じである
4. 1 つでも違えば、マージしない。`base.ref` が `main` 以外なら、この手順を中止する。候補を取り込み直してもマージ先は変わらないので、main 向けの Pull Request を選び直し、そのマージコミットを「main のコミットを手元で探し直す」で探すところからやり直す。マージ先が `main` で、残りの照合が一致しなければ、今のマージコミット（応答の `merge_commit_sha`）を取り込み、「main のコミットを手元で探し直す」で `dir` と `git` の両方を探し直してから、手順 1 に戻る
5. 4 つがそろったら、照合した Pull Request の番号と探した head を指定してマージする。マージ先は API で指定できず、照合してもマージ先の変更は防げない。そのため、マージが終わるまで、マージ先を変えられる担当者の間でマージ先の変更を止め、マージの直前に main 向けであることを照合する。マージの後に食い違いが分かったら、実際のマージ先を記録し、手順 7 に進む。手順 3 の確認の後に別の Pull Request が main に入るか、Pull Request の head かマージ先が変わると、探したのは古い候補になり、変更後の規則で全履歴を探していない候補がマージされうる
   - main は、マージのコミットを手元で探し直す前から、この Pull Request のマージを終えるまで止めておく。NDF にほかの Pull Request をマージさせず、画面からもマージせず、main へ直に push しない。マージの要求の結果が分からないときは、下の M6 のとおり、結果が確定するまで止めたままにする
   - マージを終えるまで、この Pull Request のマージ先を変えられる担当者（Pull Request の作者と、書き込みの権限を持つ人）に、マージ先を変えないよう知らせておく
   - 手順 3 で確かめた `head.sha` を「探した head」と呼ぶ
   - M2 で世代を読んでから、手順 6 の確認（マージ後の照合）を終えるまでは、「秘密を変える手順」の世代の切り替えと同時に行わない（M6 で結果の分からない要求を残したまま秘密が漏れたときの M6-6 だけは除く）。切り替えが始まっていれば、終わるのを待ってから M2 を始める。手元の `history` の探しと非公開の検査を、同じ世代の秘密で行うためである
   - `ndf ci merge` は使わない。NDF 11.0.35 の `ndf ci merge` は Pull Request の番号を受けず、`--branch` のブランチを head に持つ開いた Pull Request のうち最も新しいものをマージする。そのため、同じブランチから別のマージ先へ向けた Pull Request が開いていると、照合していない Pull Request をマージしうる。また、`ndf ci merge` は非公開の検査を起動せずにマージする
   - 非公開の検査を有効にする前（「導入の順序」の手順 6 より前）は、反映先の一覧の切り替えの前か後かによらず、この手順でマージしない（この節の冒頭の表）。1 本目の Pull Request は「1 本目を手元で探す」で扱う
   - 非公開の検査を有効にする前にマージしてよい Pull Request は、次のとおりである。「導入の順序」の手順 3 は、この間は NDF にほかの Pull Request をマージさせないと定めている。持ち主は 2026-11-26 に、非公開の検査を [#166](https://github.com/devbasex/nd-factory/issues/166) の切り替えの前提から外すと決め、#195 と #197 を個別に例外とした。下の表の、ほかの Pull Request にも例外を広げる行は、#166 の設計を書いた進める人・AI が提案したもので、持ち主はまだ認めていない（[#166 の設計の決定 5](../../issues/issue-166-design.md) と「人へ残す判断」）
     - #166 の設計の承認の前は、例外は #195 だけである
     - 承認の後は、持ち主が承認の記録のコメントで認めた行の Pull Request だけを、その行の条件でマージする。認めなかった行の Pull Request は、[#198](https://github.com/devbasex/nd-factory/issues/198) で手順 3 を直すまでマージしない
     - この例外は、#198 で手順 3 を直すまで使う。承認を受けられなかった Pull Request はマージしない

     | Pull Request | マージしてよい条件 |
     | --- | --- |
     | 規則を変える Pull Request（範囲はこの節の冒頭のとおり） | 例外に含めない。非公開の検査を有効にするまでマージしない |
     | #166 の設計 PR（[#195](https://github.com/devbasex/nd-factory/pull/195)）と、反映先の一覧を切り替える #166 の実装の Pull Request | #166 の設計の決定 5 の手順で、持ち主の承認を受けた後。実装の Pull Request は、設計の承認で持ち主がこの行を認めた場合だけ |
     | 切り替えの前の、スプリントの Pull Request | 工程「Pull Request」を流す前に、本文に未チェックの確認の行を置く。デプロイの工程のリリース承認ゲートで持ち主の承認を受け、#166 の設計の「影響と危険」の「切り替えの前に並行して進むスプリントの止め方」でマージする |
     | 切り替えの前の、単発の修正とクローズの Pull Request | 切り替えの前はマージしない。切り替えの後に、下の「切り替えの後の、設計 PR のほかの Pull Request」の行の条件でマージする |
     | 切り替えの後の設計 PR（規則を変えるものを除く） | 工程「設計」の設計承認ゲートで持ち主の承認を受けた後、#166 の設計の決定 10 の「切り替えの後の設計 PR」の手順で `ndf ci merge` でマージする。承認を取り直すときは、同じ手順のとおりマージの工程の承認ゲートで受け直す |
     | 切り替えの後の、設計 PR のほかの Pull Request（規則を変えるものを除く） | スプリントはデプロイの工程のリリース承認ゲートで、単発の修正とクローズはマージの工程の承認ゲートで、持ち主の承認を受けた後 |

     例外を広げる提案は、切り替えの前のスプリント・切り替えの前の単発の修正とクローズ・切り替えの後の設計 PR・切り替えの後のそのほかの Pull Request の 4 行に及ぶ。持ち主は、行ごとに認めるかを決める。どの行の Pull Request も、[#199](https://github.com/devbasex/nd-factory/issues/199) が入るまでは、本文に遷移の確認の行を置き、マージの直前に、反映の段への遷移が止まっているか、持ち主が承認した例外の対象にその反映が含まれることを確かめてからマージする（#166 の設計の決定 5 の「反映元の条件を満たさない間の遷移の確認」）。例外の対象に入らない Pull Request は、遷移が開いている間はマージしない
   - 非公開の検査を有効にした後は、変更前と変更後の両方の設定で、Pull Request の途中のコミットに現れたすべてのパスの名前と中身を探し終えてからマージする。手元の `dir` と `git` の探しは、途中のコミットで足され消されたパスの名前と中身を探さない。非公開の検査の `history` の探しはそれらを探すが、使う設定は変更前の main のものである。そのため、変更後の設定と gitleaks の版での `history` の探し（M2）と、非公開の検査の成功（M3）の両方を、マージの条件にする

   マージは次の M1〜M6 の順で行う。M1〜M6 の中で「手順 N」と書いたものは、この節の手順 1〜7 を指す。

   - **M1.** 公開のリポジトリを `origin` に持つ作業ディレクトリで、`ndf ci watch --pr <番号> --budget <待つ秒数>` に、`.ndf/project.json` の `required_checks` の名前を 1 つずつ `--required <名前>` で付けて打つ。必須のチェックがすべて通った結果が返るまで、次へ進まない
   - **M2.** 変更後の設定と gitleaks の版で、Pull Request の分岐点から探した head までの `history` を探す。分岐点の取得と履歴の書き出しが両方成功したときだけ検査を打ち、検査の終了コードが `0` のときだけ M3 へ進む。`export-tree.sh` は途中まで書き出してから失敗することがあり、`history` の検査は書き出しがそろっているかを確かめないためである
     1. 打つ前に、`<非公開リポジトリ>` の変数 `LEAK_CHECK_GENERATION` を読み（`gh api repos/<非公開リポジトリ>/actions/variables/LEAK_CHECK_GENERATION --jq .value`）、「検査した世代」として控える。`0`（切り替え中）なら打たず、切り替えが終わるのを待ってから読み直す
     2. 手元で渡す秘密は、検査した世代の秘密（そのときの `<非公開リポジトリ>` の `LEAK_CHECK_PATTERN` と同じ値）にする。探したマージコミットの `dir` と `git` の探し（「main のコミットを手元で探し直す」）を別の世代の秘密で行っていたら、検査した世代の秘密でその手順 6・7 を打ち直してから先へ進む
     3. 探したマージコミットを「main のコミットを手元で探し直す」の手順 3〜5 で用意したチェックアウト（スクリプトを読み、gitleaks を置いたディレクトリ）で、次を打つ。秘密は `LEAK_CHECK_PATTERN` に、`LEAK_CHECK_REQUIRE_PATTERN=1` を渡す。書き出しの先は毎回新しい空のディレクトリにし、失敗した書き出しの残りを使わない

        ```bash
        out='<新しい空のディレクトリ>'
        if base_point="$(git merge-base '<探したマージコミット>^1' '<探した head>')" \
           && tools/checks/export-tree.sh --history "$base_point" '<探した head>' "$out"; then
          tools/checks/leak-scan-secret.sh history "$out" --count-only
          echo "検査の終了コード: $?"   # 0 のときだけ M3 へ進む
        else
          echo "分岐点の取得か履歴の書き出しに失敗した。検査は打っていない"   # M3 へ進まない
        fi
        ```
     4. 「検査の終了コード」の行が出なければ、検査は打たれていない。原因を直し、新しい空のディレクトリで M2 の 3 を打ち直す。当たりなら `--count-only` を `--details` に替えて打ち直し、「当たりの場所を手元で引く」のとおりに扱う。検査の失敗なら原因を直し、M2 の 3 を打ち直す
   - **M3.** 照合した Pull Request で、「手で起動して確かめる」の手順 1〜3 のとおりに非公開の検査を起動して確かめる。
     - 「手で起動して確かめる」の手順 1 で読む値は、番号が照合した番号、`head.sha` が探した head、`base.sha` と検査のコードのコミットが探したマージコミットの最初の親（探した base。main を止めているので main の先頭と同じ）、`merge_commit_sha` が探したマージコミットと同じであることを確かめる。違えば起動せずに手順 4 に戻る
     - 同じ手順 1 で読む設定の世代が、M2 で控えた検査した世代と同じことを確かめる。`0` か、検査した世代と違えば起動せず、M4 の「世代が変わっていたとき」のとおりにやり直す
     - 「手で起動して確かめる」の手順 3 にある、検査結果の 4 項目（試行 1 の成功・実際に使われた検査のコードのコミット・すべてのジョブの成功・表示名の 6 つの値）をすべて確かめる。1 つでも欠ければマージしない
     - 当たりなら「当たりの場所を手元で引く」で場所を引いて扱い、検査の失敗なら原因を直してから、M3 を打ち直す
   - **M4.** マージの直前に、2 つを読み直し、反映の段への遷移を確かめる
     - 手順 1 の `gh api repos/devbasex/nd-factory/pulls/<番号>` を打ち直し、手順 3 の 4 つ（`base.ref` が `main` であることを含む）がそろったままであることを確かめる。1 つでも違えば、マージせずに手順 4 に戻る
     - `<非公開リポジトリ>` の変数 `LEAK_CHECK_GENERATION` を読み直し（`gh api repos/<非公開リポジトリ>/actions/variables/LEAK_CHECK_GENERATION --jq .value`）、検査した世代と同じことを確かめる。`0`（切り替え中）か、検査した世代と違えば、マージしない
     - [#199](https://github.com/devbasex/nd-factory/issues/199) が入るまでは、反映の段への遷移が止まっているか、持ち主が承認した例外の期間と対象に今回の反映が含まれることを確かめる。手順は #166 の設計の決定 5 の「[反映元の条件を満たさない間の遷移の確認](../../issues/issue-166-design.md#反映元の条件を満たさない間の遷移の確認)」の表の「マージの直前」の行のとおりである。どちらにも当たらなければ、マージしない。切り替えの前でも、マージは `main` への push で反映を起動し得るためである

     この 3 つ目の確認で例外に当たるとしたときは、マージの要求を送るたびに（M5 の初回と M6-3 の打ち直しの両方）、送る直前に、同じ表の「マージの要求を送る直前（例外に当たるとき）」の 3 つを確かめる。例外の期間が始まっていること、期間の終わりまでに応答を待ち終えられること、反映のパイプラインで終わっていないすべての実行（反映より前の段のものも含む）が例外の対象に入ることである。M5 の `gh api` には待ちの上限が無いので、2 つ目の待ちの上限には、応答を待つ秒数を自分で決めて使う。その秒数を過ぎても応答が返らなければ、返らなかったものとして M6 に進む。1 つでも外れれば、要求を送らない。例外の期間を終えた後は、M6-3 で打ち直さず、M6-2 と M6-5 だけで結果を確定させる（同じ表の「例外の期間を終えるとき」）

     **世代が変わっていたとき**（M3 か M4 で、`0` か検査した世代と違う値を読んだとき）は、切り替えが終わるのを待ち、切り替え後の秘密を手元に用意して、M2 からやり直す。M3 だけを打ち直すと、新しい秘密と変更後の規則を組み合わせた `history` の探しを一度もせずにマージしうる。古い世代の検査は、切り替える前の秘密で探した結果である
   - **M5.** M4 で例外に当たるとしたときは、M4 の後の段落の 3 つを確かめてから打つ。Pull Request の番号と探した head を指定して、マージの API を打つ。GitHub は、Pull Request の今の head が `sha` と違えばマージしない（[マージの API](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request)）。NDF が自分でマージするときも同じ API を使う

     ```bash

       -f sha='<探した head>' \
       -f merge_method=squash
     ```

     応答が返らなかったときは、次のとおりに結果を確定する。結果が確定するのは、Pull Request の `merged` が真になったときか、M6-5 で引き継いだリポジトリの管理者が確定させたときだけである。確定するまで、送った要求の記録を閉じず、main を止めたままにし、「秘密を変える手順」の切り替えも始めない。秘密が漏れたときだけは、M6-6 のとおりに切り替えてよい

     - **M6-2.** Pull Request（`gh api repos/devbasex/nd-factory/pulls/<番号>`）を読み直す。`merged` が真なら、この Pull Request に記録したすべての要求を、上の「結果不明の要求の記録」のとおり識別子ごとに閉じて手順 6 に進む
     - **M6-3.** `merged` が偽なら、M4 の 3 つの確認を打ち直す。M4 で例外に当たるとしたときは、M4 の後の段落の 3 つも確かめ直す。すべてそろえば、同じ `sha` でマージの API を打ち直す。1 つでもそろわないか、例外の期間を終えていれば打ち直さず、M6-5 に進む。例外の期間を終えた後に結果を確かめるのは、M6-2 の読み直しと M6-5 の引き継ぎだけである。main を止めているので、先の要求が後から処理されても、取り込まれるのは照合した組み合わせのままである
     - **M6-4.** 打ち直しの応答が返り、`merged` が真なら、この Pull Request に記録したすべての要求を識別子ごとに閉じて手順 6 に進む。断られたときは、記録を閉じずに M6-5 に進む。打ち直しが断られても、先の要求が処理されなかった証拠にはならない。打ち直しの応答も返らなければ、M6-2 に戻る前に、その打ち直しを打ち直した時刻の新しい識別子で、M6-1 と同じく記録する（上の「結果不明の要求の記録」）。記録しないと、引き継いだ人が最初の要求だけを確定させて停止を解き、残った打ち直しが後から成立し得るためである。M6-2〜M6-4 を繰り返しても確定しなければ、M6-5 に進む
     - **M6-5.** 記録（M6-1 の内容と、それまでの打ち直しの結果）をリポジトリの管理者（admin の権限を持つ人）に渡し、先の要求の結果を確定させてもらう。管理者が確定させるまで、記録を閉じず、main を止めたままにする。管理者は次のとおりに扱う
       - 要求の番号・`sha`・送った時刻を添えて、GitHub のサポートに処理状況を問い合わせる（未確認: GitHub のサポートが、個々のマージの要求が処理されたか、今後処理されないかをどこまで答えられるかは確かめていない）
       - 要求が成立した証拠（Pull Request の `merged` が真になった、または GitHub がその要求でマージしたと答えた）が得られたら、記録を閉じて手順 6 に進む
       - 要求が成立せず、今後も処理されないことを確かめられたら、記録を閉じて手順 4 に戻る。Pull Request が閉じていることや head が変わったことだけでは、未処理の証拠にしない
       - どちらも確かめられなければ、記録を閉じず、main を止めたままにする。秘密の切り替えは、漏れたときに M6-6 のとおりに行う場合を除き、始めない
     - **M6-6.** 結果が確定する前に `<非公開リポジトリ>` の秘密 `LEAK_CHECK_PATTERN` が漏れたときは、リポジトリの管理者が、マージの停止と記録を残したまま秘密を切り替えてよい。漏れた値を、結果が確定するまで使い続けないためである。「秘密を変える手順」の手順 2 の例外は NDF の未解決の記録と知らせを前提にしており、手でのマージの要求には使えないので、次の手順で行う。秘密は先に変えるが、世代は先の要求の結果が確定し、必要な探し直しが済むまで `0` のままにする。M6-1 の記録は手元にあり NDF は読まないので、NDF のマージは世代の `0` で止める。世代を先に正の値に戻すと、先の要求が未解決のまま NDF が別の Pull Request を main に取り込み、先の要求が検査したときと違う base に対して成立しうる
       1. main を止めたまま、M6-1 の記録を閉じずに、切り替える前の世代（M2 で控えた検査した世代）と切り替えを始めた時刻を記録に書き足す
       2. 「秘密を変える手順」の手順 1 で世代を `0` にし、同じ手順 2 のとおり、すべての NDF の時間の上限 T が過ぎるまで待つ。T の待機は省かない。T が過ぎた後に未解決の NDF の記録が残っていれば控え、記録が閉じる前でも次へ進んでよい（手順 2 の「待てないとき」）
       3. 「秘密を変える手順」の手順 3 で秘密を変える。同じ手順 4（世代を正の値に戻す）は、この M6-6 の 5 か 6 まで打たない
       4. 切り替えの後は、記録を閉じずに先の要求の結果を確かめる。M6-2 と M6-5 から使うのは結果の確かめ方だけで、そこにある「記録を閉じて手順 6 か手順 4 に進む」には従わない。この M6-6 で記録を閉じるのは、5 か 6 を終えたときだけだからである。まず、M6-2 と同じ API（`gh api repos/devbasex/nd-factory/pulls/<番号>`）で `merged` を確かめ、真なら M6-6 の 5 に進む。偽なら、M6-3 の打ち直しはせず、管理者が M6-5 の方法で先の要求の結果を確かめる。M6-3 で打ち直す前に確かめる世代が、検査した世代と違うためである。管理者が成立を確かめたら M6-6 の 5 に、成立せず今後も処理されないことを確かめたら M6-6 の 6 に進む。どちらも確かめられなければ、世代を `0` のまま、main を止めたままにする
       5. 先の要求が成立したと分かったら（切り替えの前か後かは問わない）、照合の結果にかかわらず、新しい秘密でマージを探し直してから記録を閉じる。マージの前の検査は漏れた古い秘密で探した結果で、新しい秘密の規則では探していないためである
          - 手順 6 で、実際のマージ先とマージでできたコミットを確かめ、作業の記録に残す
          - 手元で渡す秘密を、M6-6 の 3 で登録した新しい `LEAK_CHECK_PATTERN` にして、手順 7 の 7-1〜7-7 を行う。手順 6 の照合が通っても省かない
          - この間、`LEAK_CHECK_GENERATION` は `0` のままにする
          - 記録を閉じて「秘密を変える手順」の手順 4 で世代を正の値に戻してよいのは、次の表で探しが要るとされた範囲をすべて探し、当たりへの対応を終えたときだけである
          - 例外は 1 つだけである。7-6 で範囲を確定できず探せなかった途中のコミット（7-5 の `history` と `git --range`）だけは、表の最後の行の管理者の対応を終えれば、探さないまま世代を戻してよい。ほかの範囲は、探さないまま管理者の判断で戻すことはしない
          - 例外を絞るのは、新しい秘密で探せる履歴を探さないまま世代を戻すと、未検査の履歴を残したまま NDF が次の Pull Request を main にマージしうるためである
          - 次の表で、探しの状態ごとに世代を戻せるかを決める。探しの状態は、7-7 の後の段落の見分け方で決める。表の「打つはずの探し」は、終え方によって違う
            - 7-6 で終えたとき: マージされたコミットの木（`dir`）と全履歴（`git`）
            - 7-7 で終えたとき: 7-7 の条件に挙げたすべての探し

            | 終え方 | 探しの状態 | 世代 |
            | --- | --- | --- |
            | 7-7 で、当たり無しとして終える | 7-7 の条件がすべてそろった | 正の値に戻してよい |
            | 7-6 か 7-7 で、管理者に引き継ぐ | 打った探しのどれかに、失敗が残っている（原因を直せていないときも含む） | 失敗が残っているので、世代は `0` のままにする。原因を直して打ち直す |
            | 同上 | 打つはずの探しのどれかを、まだ打っていない（「終了コード」の行が出ていない） | 世代は `0` のままにする。原因を直して打つ |
            | 同上 | 当たりが残っている | 管理者がマージを戻すかを判断し、必要な対応を終えて作業の記録に残すまで、世代は `0` のままにする |
            | 7-6 で、管理者に引き継ぐ | 実際に取り込んだ組み合わせを確定できず、途中のコミット（7-5 の `history` と `git --range`）を探していない | その範囲を作業の記録に残し、管理者がその範囲を確かめてマージを戻すかを判断し、必要な対応を終えて作業の記録に残すまで、世代は `0` のままにする |

            管理者に引き継いだときは、打つはずの探しのすべてが、当たり無しか、当たりだけが残る状態になり、表の当てはまる行の対応をすべて終えたときにだけ、世代を正の値に戻してよい
       6. 先の要求が成立せず、今後も処理されないことを確かめられたら、記録を閉じ、「秘密を変える手順」の手順 4 で世代を正の値に戻してから、手順 4 に戻る。M2 からは切り替えた後の世代で進める
   - 止めている間に main が進んでしまったら、マージせずに手順 4 のとおり探し直す。ただし、結果の分からないマージの要求の記録が残っている間は、新しい候補のマージ（手順 4 からやり直した後の M5）へ進まない。先の要求が後から処理されると、検査したときと違う main に変更が取り込まれるためである。M6-5 のとおり管理者に引き継ぎ、記録が閉じてから進む
6. マージの後に、Pull Request を読み直し、マージでできたコミット（`merge_commit_sha`）が探した組み合わせで作られたことを確かめる。このリポジトリは squash でマージする（`.ndf/project.json` の `merge.commit` が `squash`。M5 の `merge_method` も `squash`）ので、できたコミットの親は 1 つだけで、取り込んだ head は親にならない。マージの後に読み直した Pull Request の `head.sha` は、マージの時点の head と同じとは限らないので、取り込んだ head の根拠にしない。取り込んだ head は、下の 1 つ目の項目のとおり、マージの要求に渡した `sha` から決める
   - 実際に取り込んだ head（以後「実際の head」）を、次のどちらかで決められ、それが探した head と同じである。決められなければ、照合は通らない
     - M5 か M6-4 の応答で `merged` が真だったときは、その要求に渡した `sha`（探した head）が実際の head である。GitHub は、Pull Request の今の head が `sha` と違えばマージしないためである
     - M6-2 か M6-5 で結果が確定したときは、どの要求がマージを作ったかが応答からは分からない。M6-1 の記録で、送った要求の `sha` がすべて同じであることと、この Pull Request を画面や NDF などほかの経路でマージしていないことを確かめられたときだけ、その `sha` を実際の head とする。`merged` が真であることだけでは、ほかの経路で別の head がマージされた場合と見分けられない
   - 応答の `base.ref` が `main` である
   - できたコミットの親がちょうど 1 つで、その親（`git rev-parse <コミット>^1`）が探したマージコミットの最初の親（探した base）と同じである
   - 木（`git rev-parse <コミット>^{tree}`）が、探したマージコミットの木と同じである。木が同じでも、途中のコミットが違う head がマージされていれば、その途中のコミットにだけ現れた秘密は探していない。そのため、木の一致を実際の head の確定の代わりにしない

   決めた実際の head を作業の記録に残す
7. 手順 6 の 1 つでも違ったとき、または M6-6 の 5 から進んだとき（手順 6 の照合が通ったかどうかによらない）は、この手順で探し直す。M6-6 の 5 から進んだときは、手元で渡す秘密を M6-6 の 3 で登録した新しい `LEAK_CHECK_PATTERN` にする。まず実際のマージ先（応答の `base.ref`）とマージでできたコミットを作業の記録に残す。そのうえで、実際にマージされたコミットの木と全履歴に加え、実際に取り込んだ base と head の間の途中のコミット（`history` と `git --range`）も探し直す。実際にマージされたコミットのスクリプトは読んで確かめていないので、秘密を外へ送る処理が入っていることがありうる。そのため、そのスクリプトを読んで確かめるまで、そのスクリプトに秘密を渡さない。7-1〜7-7 の順で行う
   - **7-1.** 手順 3 の照合を最後に通ったマージコミットを探したときのチェックアウト（「main のコミットを手元で探し直す」の手順 3〜5 で、スクリプトを読み、gitleaks を置いたディレクトリ）を、検査のコードとして使う。最初の照合で通ったなら、マージの前に探したときのチェックアウトである。手順 4 で探し直したなら、最後に探し直したマージコミットのチェックアウトである
   - **7-2.** 実際にマージされたコミットをチェックアウトし、手順 6 で決めた実際の head を手元に取り込む。head を決められなくても、マージされたコミットの木と全履歴は 7-3・7-4 で探す。探せなくなるのは途中のコミット（7-5）だけである
     - 7-1 とは別の新しい空のディレクトリに公開のリポジトリを複製し、実際にマージされたコミットを `git checkout --detach` でチェックアウトする。このチェックアウトのコードは動かさない
     - 手順 6 で実際の head を決められたときは、`git fetch origin refs/pull/<番号>/head` を打ち、`git cat-file -e '<実際の head>^{commit}'` で実際の head が手元にあることを確かめる。無ければ `git fetch origin '<実際の head>'` で取り込む
     - 実際の head を決められなかったか、取り込めなかったとき、またはできたコミットの親が 1 つでないときは、その旨を作業の記録に残す。7-3・7-4 は打ち、7-5 は打たずに 7-6 に進む
   - **7-3.** 実際にマージされたコミットの規則（`.gitleaks.toml`・`tools/checks/gitleaks-default.toml`）か gitleaks の版（`tools/checks/install-gitleaks.sh`）が、探したマージコミットと違えば、7-1 の検査のコードではそのコミットの規則と版で探せない。この場合は、7-4 の代わりに、実際にマージされたコミットを「main のコミットを手元で探し直す」で探す。7-5 の変更後の設定にも、このチェックアウトを使う
     - そのコミットが main に入っていても、その手順 4 の 6 つのファイルの読み込みを省かない。その手順 4 は main のコミットを読み込みの対象から外すが、マージの後の探し直しで探すコミットは、この手順のどこでも読んで確かめていないためである。gitleaks を置く（その手順 5）前に、6 つのファイルと `tools/checks/leak_scan/` を全体を読んで確かめ、`install-gitleaks.sh` が探したマージコミットと少しでも違えば、配布物と要約値も確かめる。秘密を渡すのは、そのあとである

       **変更前の設定を確認済みの検査のコードで探し直す**。変更前の設定の規則・対象・gitleaks の版は変えずに、失敗を報告できる確認済みの検査のコード（7-1 のディレクトリのスクリプト）で探す。`leak-scan-secret.sh` は、スクリプトを置いたチェックアウトの根から規則を読むので、確認済みのスクリプトと実際の base の規則を 1 つのディレクトリに集めて打つ
       1. 新しい空のディレクトリ（以後「集めたディレクトリ」）に `tools/checks` を作り、7-1 のディレクトリの `tools/checks/leak-scan-secret.sh`・`tools/checks/leak-scan.sh`・`tools/checks/leak_scan/`（ディレクトリごと。`leak-scan.sh` が本体を起こすのに要る）を写す。写した `leak-scan-secret.sh` に、上の段落で確かめた、失敗を報告する処理があることを、同じ見方で確かめる

       3. `PATH` の先頭には、上と同じく、実際の base のチェックアウトで gitleaks を置いたディレクトリを足し、`command -v gitleaks` がその中の `gitleaks` を指すことを確かめる
       4. 作業ディレクトリを 7-2 のチェックアウトにし、次のコマンドを打つ。上のコマンドと違い、履歴の書き出し（`export-tree.sh`）は元の `history` の探しと同じ、実際の base のチェックアウトの確認済みのスクリプトを絶対パスで打つ。集めたディレクトリには `export-tree.sh` を写していないためである。2 つのスキャンのスクリプトは、集めたディレクトリのものを絶対パスで打つ。範囲は元の探しと同じ実際の base と実際の head にし、書き出しの先は新しい空のディレクトリにする

          checks='<集めたディレクトリの絶対パス>/tools/checks'

              echo "履歴の書き出しに失敗した。history は打っていない"

       6. 記録と引き継ぎの「使った検査のコードのコミット」には、スクリプトを 7-1 のチェックアウトから、規則と gitleaks の版を実際の base から取ったことを残す
   - **7-6.** 実際に取り込んだ組み合わせを確定できないとき（できたコミットの親が 1 つでない、手順 6 で実際の head を決められない、7-2 でその head を取り込めない）は、途中のコミットを探す範囲を決められないので、当たり無しとして探し直しを終えられない。木と全履歴を探したら、検査の失敗の解消を待たずに、結果と探していない範囲をリポジトリの管理者に引き継ぎ、マージを戻すかを判断してもらう
     - 7-3 か 7-4 で、マージされたコミットの木と全履歴を探す
     - 探し終えたらすぐに、最初の引き継ぎを行う。探しごとの状態（成功・当たり・失敗・未実行）と、確かめられていない範囲を、実際の値を含めずに作業の記録に残して管理者に伝える。確かめられていない範囲には、範囲を決められず探していない途中のコミットに加え、失敗したか打てなかった探しの対象も含める。たとえば、木の書き出しに失敗して `dir` を打てなかったときは、マージされたコミットの木が確かめられていない。当たりと失敗の見分け方と、記録に残すものは 7-7 の後の段落のとおりである
     - 失敗したか打てなかった探しは、引き継ぎと並行して原因を直して打ち直し、その結果を追って管理者に伝える
   - **7-7.** 次のすべてがそろったときだけ、当たり無しとして探し直しを終える。「終了コード」の行が出なかった探しは、打たれていない。書き出しか分岐点の取得の原因を直し、新しい空のディレクトリで打ち直す
     - 7-4 の木の書き出しが成功し、`dir` と `git` の終了コードが `0` である（7-3 の場合は、その探しの `dir` と `git` の終了コードが `0` である）
     - 7-5 の変更前と変更後の両方の設定で、分岐点の取得と履歴の書き出しが成功し、`git --range` と `history` の終了コードが `0` である

     `0` でなかった探しは、当たりだけなのか、検査の失敗を含むのかを、`--count-only` の出力で見分ける。`nd-real-value` の件数の行だけでは、検査を終えたとは判定できない。`leak-scan.sh` は、読めないファイルを飛ばしても、読めた範囲の当たりを報告して `1` で終えるので、当たりと読み飛ばしが同時に起きても、件数と終了コードは当たりだけの場合と同じになるためである。そのため、件数とは別に、実際の値を含まない失敗の行が出ていないかを確かめる
     - `leak-scan-secret.sh` の終了コード `1` は、当たりがあるときにも、検査が失敗したときにも出る。探しはそれぞれ別々に打ち、それぞれの中でも規則ごとに別々に探すので、当たりと検査の失敗は同時に出ることがある
     - `--count-only` では、既定の規則と `.gitleaks.toml` の探しは、`leak-scan.sh` がファイルの名前を `file-<番号>` に替えて伏せた出力を出す。gitleaks の出力そのものではない。`nd-real-value` の探しは出力を捨て、件数の行（`leak-scan-secret: nd-real-value: <件数> 件`）を出す。その探しが当たりのほかの理由で失敗したときは、件数の行とは別に、失敗の行を出す
     - 次の表のどれかの行が出たか、終了コードが `2` なら、その探しは失敗を含む。件数の行が出ていないときも、`nd-real-value` で探していないので、失敗として扱う。どれにも当たらず、終了コードが `1` なら、当たりだけである。ただし、失敗の行を出さない版の検査のコード（7-5 の変更前の設定で、実際の base の `leak-scan-secret.sh` に、失敗を報告する処理が無いとき）の出力では、当たりだけとは判定しない。7-5 の「変更前の設定を確認済みの検査のコードで探し直す」の結果で判定する

       | 出る行 | 出す探し |
       | --- | --- |
       | `leak-scan: gitleaks が警告か誤りを出した` | 既定の規則か `.gitleaks.toml` の探し（読めずに飛ばした対象がある） |
       | `leak-scan: gitleaks の報告を読めない` | 既定の規則か `.gitleaks.toml` の探し |
      | `leak-scan: gitleaks が中身を読まずに飛ばしたファイルを探せなかった` | 既定の規則か `.gitleaks.toml` の `dir` の探し（飛ばしたファイル・名前で外したファイル・アーカイブの中を探せない） |
      | `leak-scan: 履歴を最後まで探し終えたことを確かめられなかった` | 既定の規則か `.gitleaks.toml` の `git` の探し（読み終えたことを確かめられないファイルがある） |
       | `leak-scan-secret: nd-real-value の探しが失敗した` | `nd-real-value` の探し（読めずに飛ばした対象があるか、gitleaks が失敗した） |
       | `leak-scan-secret: nd-real-value の件数を読めない` | `nd-real-value` の探し（報告を書けなかった） |

     - 失敗の原因を直したら、元と同じ検査のコード・設定・gitleaks の版で、`--count-only` を付けて打ち直す。失敗が解消したかも、この表で確かめる
     - 当たりの場所を引くときは、同じ検査のコード・設定・gitleaks の版で `--details` を付けて打つ。その結果は場所の特定にだけ使い、当たり無しや失敗の解消の判断には使わない。`--details` は `--count-only` と規則の組み方が違い、`nd-real-value` を `.gitleaks.toml` と組み合わせて探す（「main のコミットを手元で探し直す」の表）ためである。`--details` の出力は、「当たりの場所を手元で引く」の手順 5 のとおり、手元の端末にだけ出す
     - `--details` で元の当たりを特定できない場合は、元の探しの規則の組み方を変えずに場所を出す。手順は「件数だけの探しと同じ組み方で場所を引く」のとおりで、確認済みの検査のコードを使い、出力は手元の端末にだけ出す

     当たりと失敗は、次のとおりに扱う
     - 当たりがあれば、上の条件がそろうのを待たずに、すぐにリポジトリの管理者に引き継ぎ、マージを戻すかを判断してもらう。当たりは、対象のコミットに後からコミットを足しても消えないので、打ち直しても終了コードは `0` にならないためである
     - 作業の記録と引き継ぎには、実際の値を含まず、同じ探しを手元で作り直せる情報を残す。squash でできたコミットからは途中のコミットをたどれず、7-1 の検査のコードのコミットも対象のコミットとは別なので、対象のコミットだけでは同じ探しを作れないためである。残すのは次の情報である
       - 探しごとの状態（成功・当たり・失敗・未実行）。探しは `dir`・`git`・`history`・`git --range` と、変更前か変更後かの設定で分ける。当たりが出た探しは、当てた規則と件数も残す
       - マージでできたコミットと、実際の base と head の SHA。決められなかったものは、その旨を残す
       - 使った検査のコードのコミット（7-1 のチェックアウト、7-3 の実際にマージされたコミット、7-5 の変更前の設定の実際の base）と gitleaks の版
       - 使った秘密の世代。M6-6 の切り替えの途中で探したときは、M6-6 の 3 で登録した新しい秘密を使ったこと
     - 当たりの場所は、その世代の秘密の値を手元に持つ担当者が、手元の端末で特定する。管理者は秘密の値を受け取らずに、担当者が残した情報で対応を判断する。秘密は GitHub Actions の秘密として登録してあり、登録した後は管理者でも値を読み戻せないので、記録の世代だけでは同じ値を用意できないためである
       - その世代の値を手元に持つのは、その値を登録した人と、探し直しのためにその人から値を受けた担当者である。M6-6 の切り替えの途中で探したときは、M6-6 の 3 で新しい秘密を登録した管理者も、値を手元に持つので、自分で場所を特定してよい
       - 担当者は、当たりが出た探しを、検出時と同じ確認済みの検査のコードで打ち直して、当たりに対応するコミットを引く。特定できたら、その SHA を作業の記録に残して管理者に伝える。特定できなければ、特定できなかったことと、その探しの対象の範囲（`dir` はマージされたコミット、`git` は全履歴、`history` と `git --range` は分岐点と実際の head）を残して伝える。打ち直し方は次のとおりである
         - 検出時と同じ作業ディレクトリ、規則、gitleaks の版を使う。スキャンは、検出時に使った確認済みのスクリプトを絶対パスで指定し、`--count-only` を `--details` に替える。7-4 と 7-5 の作業ディレクトリ（7-2 のチェックアウト）の `tools/checks/` は読んで確かめていないので、相対パスで打たない。そのスクリプトに秘密を渡すと、そのコードを仕込んだ Pull Request の作成者に秘密の値が漏れることがあるためである
         - `history` の書き出しにも、検出時と同じ確認済みの `export-tree.sh` を絶対パスで指定する。7-5 の「変更前の設定を確認済みの検査のコードで探し直す」の結果を使う場合は、その探し直しで指定したそれぞれの絶対パス（スキャンは集めたディレクトリ、書き出しは実際の base のチェックアウト）を使う
         - まず、当たりが出たときと同じ範囲を `--details` で調べる。元の当たりを再現できなければ、「件数だけの探しと同じ組み方で場所を引く」の手順で、元の検査と同じ規則の組み方に戻して場所を特定する。その手順に移っても、確認済みのスクリプトを絶対パスで指定する。`git` と `git --range` は、元の検査と同じ作業ディレクトリ（7-3 ならそのチェックアウト、7-4・7-5 なら 7-2 のチェックアウト）で打つ。`dir` は、7-3 ならそのチェックアウトの根を、7-4 なら書き出した木を対象にする。`history` は、上の書き出しと同じ範囲で書き出した履歴を対象にする。`--details` は `--count-only` と規則の組み方が違い、同じ範囲でも元の当たりを再現できないことがあるためである
         - 範囲は探しごとに次のとおりで、「当たりの場所を手元で引く」の手順 3 の範囲（Pull Request の分岐点から head まで）とは限らない。下のコマンドの `$checks` は検出時に使った確認済みのスクリプトのディレクトリ、`$export_tree` は検出時に使った確認済みの `export-tree.sh` の、それぞれ絶対パスである
           - 全履歴の `git`: 7-4 か 7-3 で打った元のコマンドと同じく、範囲を付けずに打つ（`"$checks/leak-scan-secret.sh" git --details`）。squash でできたコミットとその祖先が対象になる
           - `git --range`: 7-5 の探し直しで求めた分岐点と実際の head を指定する（`"$checks/leak-scan-secret.sh" git --range '<分岐点>..<実際の head>' --details`）
           - `history`: 7-5 の分岐点と実際の head で、新しい空のディレクトリに書き出し直してから打つ（`"$export_tree" --history '<分岐点>' '<実際の head>' "$out"` が成功したときだけ、`"$checks/leak-scan-secret.sh" history "$out" --details`）。出た場所からコミットを引く方法は、「当たりの場所を手元で引く」の手順 2 の各項目のとおりである

         `git` と `git --range` の当たりはコミットの列に出る。`history` の中身の当たりは blob の SHA から、パスの名前の当たり（`paths/<通し番号>`）はそのパスを変えたコミットから引く。`dir` の当たりは、マージされたコミットの木にある。コミットの SHA は実際の値を含まない。ファイルの名前と行は記録・Issue・Pull Request に書かない。ファイルの名前も実際の値を含み得るためである
       - 管理者は、当てた規則・件数と、コミットの SHA（特定できなければ探しの対象の範囲）で、マージを戻すかを判断する。ファイルの名前が要る対処（値を消すなど）は、場所を特定した担当者が、管理者の判断に沿って行う
       - その世代の値を手元に持つ人がいなければ、場所は特定できない。その旨を作業の記録に残して管理者に伝え、管理者は当てた規則・件数と探しの対象のコミットで、マージを戻すかを判断する
       - 秘密の値は、記録にも引き継ぎにも書かない
     - 検査の失敗があれば、失敗した探しが対象の木や履歴にある別の当たりを見落としている可能性がある。当たりの引き継ぎと並行して失敗の原因を直し、失敗した探しを同じ検査のコード・設定・gitleaks の版で、`--count-only` を付けて打ち直す。失敗が無くなる（当たり無しで `0` になるか、当たりだけが残る）まで打ち直しを続け、その結果を作業の記録に残して管理者に渡す。打ち直しで新しく出た当たりも、上と同じく引き継ぐ

#### 切り替えの後のマージ

反映先の一覧の切り替えの後は、規則を変える Pull Request を、持ち主の承認を受けてから `ndf ci merge` でマージする。この節の手順 1〜7 と M1〜M6 を引き継ぎ、マージの要求を送る所だけを変える。そう決めた理由は、[全体の設計の決定 142](../design/platform.md#決定の記録)にある。切り替えの後のマージの手順は、この小見出しだけに書く。

使ってよいのは、非公開の検査を有効にした後だけである（この節の冒頭の表）。変えるのは次の 5 か所で、ほかの手順と禁止はそのまま行う。M1 の必須の CI の待ちと、手順 3・M4・手順 6 の候補の照合も省かない。この小見出しでは、下の 2 つ目の表の順を「S1」〜「S11」と書き、この節の手順 1〜7・M1〜M6 と分ける。

| この節の箇所 | 切り替えの後の扱い |
| --- | --- |
| 手順 5 の「`ndf ci merge` は使わない」 | 解除する。禁じた理由は、NDF 11.0.35 の `ndf ci merge` が Pull Request の番号を受けないことと、非公開の検査を起動しないことだった。NDF 11.0.43 は `--pr` と `--approved-head` を受ける。非公開の検査は、マージの前に M3 で確かめる |
| 手順 5 の「main は、マージのコミットを手元で探し直す前から（中略）止めておく」 | `main` を止め始める時点を、持ち主の承認の後、S9 の照合の前（下の S7）に移す。S2〜S5 の検査は、`main` を止めずに、S2 で固定した候補と M2 で控えた世代に対して行う。その結果は、S9 で候補と世代が同じだと確かめたときだけ使う。検査と承認を待つ間も止め続けると、そのあいだ別の承認済みの Pull Request を `main` に取り込めなくなるためである |
| M5 のマージの API | 下の S10 の `ndf ci merge` に置き換える |
| M6-3 の打ち直し | M4 の 3 つの確認（候補・秘密の世代・反映の段への遷移）と、最後に成功した反映の読み直し（S9。S6 が「未反映（初回）」なら、S9 と同じ判定で成功した実行がまだ無いことの確かめ直し）がそろったときだけ、S10 と同じ `ndf ci merge`（承認した head とマージ先を指定する）を打ち直す。S9 で例外に当たるとしてマージしたときは、M6-3 のとおり、M4 の後の段落の 3 つも確かめ直し、例外の期間を終えていれば打ち直さない。この 3 つの 2 つ目の待ちの上限は、打ち直す `ndf ci merge` の `--budget` の秒数である。最後に成功した反映が S6 の承認資料と違えば、打ち直さない。先の要求を送った後に別の反映が成功し、反映の範囲が持ち主の承認した範囲と変わったためである。その場合は記録を閉じずに M6-5 に進み、先の要求の結果が確定するまで `main` を止めたままにする。承認の取り直しは、結果が確定した後に行う |
| M6 の応答の表・M6-4・手順 6 の「要求に渡した `sha`」 | 下の「`ndf ci merge` の結果の読み方」の表で読む |

| 順 | 引き継ぐ手順 | すること |
| --- | --- | --- |
| S1 | M1 | 必須の CI がすべて通るのを待つ。省かない。NDF 11.0.43 の `ndf ci merge` は `--required` が空ならチェックの結果を読まず（`ci_cli.py` の `_failed_checks`）、[#199](https://github.com/devbasex/nd-factory/issues/199) が入るまで GitHub の保護も無いためである。待ち終えた HEAD を控える |
| S2 | 手順 1・2 と、手順 3 の 4 つのうち「探したマージコミット」と比べないもの | GitHub が作ったマージの候補とその親を読み、SHA を固定して作業の記録のコメントに残す。まだ何も検査していないので、手順 3 の「`merge_commit_sha` が探したマージコミットと同じ」は、ここでは確かめない。この時点では `main` を止めない。S3〜S5 は、ここで固定した候補に対して行う。次の順で行う<br>1. 手順 1・2 のとおり、`mergeable` が `true` の応答を得る。`false` ならマージしない<br>2. その応答で、`base.ref` が `main` であることを確かめる。違えば、手順 4 のとおり中止する<br>3. 応答の `merge_commit_sha` を、`git fetch origin refs/pull/<番号>/merge` で取り込んだコミットと同じことを確かめ、「探したマージコミット」として固定する。違えば、少し待って S2 の 1 からやり直す<br>4. そのコミットの最初の親（`git rev-parse <探したマージコミット>^1`）が今の `main` の先頭と同じで、2 つ目の親（`^2`）が応答の `head.sha` と同じことを確かめる。最初の親を「探した base」、`head.sha` を「探した head」として固定する。違えば、S2 の 1 からやり直す<br>5. 探した head が S1 で控えた HEAD と同じことを確かめる<br>手順 3 の 4 つの照合と手順 4 の探し直しは、S3 で探したマージコミットを検査した後に、S9 で初めて「探した組」として行う |
| S3 | 「main のコミットを手元で探し直す」 | S2 で固定した探したマージコミットを、その手順 1 の対象のコミットにする。探したマージコミットの木（`dir`）と全履歴（`git`）を、変更後の規則で探す。`main` の過去のコミットに残った値は、この探しで見つける |
| S4 | M2 | Pull Request の分岐点から探した head までの途中のコミットに現れたパスと中身を、変更後の規則で探す（`export-tree.sh --history`）。S3 とは範囲が違うので、S3 の代わりにしない。M2 で控えた「検査した世代」が、S3〜S5 で使った秘密の世代である |
| S5 | M3 | 非公開の検査を、この節の条件のまま確かめる。S3〜S5 の結果（探しごとの合否と当たりの有無）は運用の記録に残す |
| S6 | — | S1 と S2〜S5 がすべて成功した探した head と探した base で承認資料を出し、リリース承認ゲートで持ち主の承認を受ける。承認ゲートには NDF のマージの工程（テンプレート `merge`）のものを使い、回答の記録の仕方は下の「承認の受け方」に従う。承認資料には、次の 2 つの変更を示す。1 つは、最後に成功した反映のソースのコミットから探した base までの、まだ反映されていない変更である。もう 1 つは、今回の Pull Request が加える変更（規則の変更の中身を含む）である。根拠として、最後に成功した反映のソースのコミット（AWS を読み取りだけで調べ、実際の値は書かない）と、検査した探した head・探した base・探したマージコミットを添える。書き方は、[#166](https://github.com/devbasex/nd-factory/issues/166) の設計の決定 10「通常のマージの承認資料にも反映の範囲を書く」と同じである。反映の段が成功した実行が無いときは、設計の「[承認資料に書く反映の範囲](../../issues/issue-166-design.md#承認資料に書く反映の範囲)」の、最後に反映されたコミットの 3 つの扱いで決める。「未反映（初回）」と確かめられたら、最後に成功した反映のソースのコミットの代わりに「未反映（初回）」と確かめた日時を書き、まだ反映されていない変更として、探した base の全履歴（`git log <探した base>`）を示す。反映の履歴を確かめられなければ、承認資料を出さずに承認の依頼を保留する。この時点ではまだ `main` を止めていないので、保留しても止めたままの `main` は無い |
| S7 | 手順 5 の最初の 2 つの項目 | 持ち主の承認を受けた後（「承認の受け方」の 4 で承認の結果が `ok` だった後）に、`main` を止める。止めるのは、ほかの Pull Request のマージ、`main` への直接の push、この Pull Request のマージ先の変更である。止めたら、止めた時刻と、その時点の `main` の先端を控え、作業の記録に残す。停止は、表の下の「停止を解く時点」まで保つ |
| S8 | 「秘密を変える手順」の準備 2〜4 | 止める前にほかの担当者が送った `main` への書き込み（`ndf ci merge`・`gh pr merge`・画面からのマージ・直接の push）と、マージキューにある `main` 宛ての Pull Request の結果を確定させる。確定しなければ S9 に進まない |
| S9 | M4 | マージの直前に、候補と秘密の世代を照合し直す。候補は手順 1〜4 で読み直し、S2 で記録した探した組と同じことを確かめる。世代は、M2 で控えた検査した世代と同じことを確かめる。両方が同じときだけ、`main` を止める前の S3〜S5 の結果を使う。あわせて、最後に成功した反映を AWS を読み取りだけで読み直し、S6 の承認資料と同じことを確かめる。S6 で「未反映（初回）」としたときは、S6 と同じ判定で、反映の段が成功した実行がまだ無いことを確かめ直す。成功した実行があれば、S6 の承認資料と違うものとして扱う。判定できなければ、同じとは扱わず、マージしない。[#199](https://github.com/devbasex/nd-factory/issues/199) が入るまでは、M4 の 3 つ目の確認も行い、反映の段への遷移が止まっているか、持ち主が承認した例外に当たるかを確かめる。どちらにも当たらなければ、マージしない |
| S10 | M5 を置き換える | S9 で例外に当たるとしたときは、打つ直前に M4 の後の段落の 3 つ（例外の期間が始まっている・`--budget` の秒数を足しても期間の終わりより前・反映のパイプラインで終わっていないすべての実行が例外の対象に入る）を確かめる。確かめるのは、「承認の受け方」の 4 で行にチェックを付ける前である。1 つでも外れれば、チェックを付けず、打たない。そのうえで、`ndf ci merge --pr <番号> --approved-head <探した head> --approved-base main --method squash --budget <待つ秒数> --required=<必須のチェック>` を打つ。`--required` は `.ndf/project.json` の `ci.required_checks` の数だけ並べる。`--approved-base main` が照合するのはマージ先のブランチの名前だけで、`main` の先端は照合しない。そのため、S9 と S11 で候補を照合する。中の CI の待ちは、S1 と同じ HEAD の結果を読むだけになる |
| S11 | 手順 6 | マージの後に、できたコミットの親と木が探した組と同じことを確かめる。違えば手順 7 で探し直す |

S1〜S9 は、次の条件でやり直す。

| 起きたこと | やり直す所 |
| --- | --- |
| S1 で必須の CI が通らない | マージしない。直してから S1 をやり直す |
| S2 で、探した head が S1 で控えた HEAD と違う | S1 からやり直す |
| S9 で、HEAD・`main` の先端・候補の照合のどれかが S2 の記録と違う | マージしない。止める前の検査の結果は使えない。下の「停止を解く時点」の「S1 からやり直すとき」の行のとおり、未処理の要求を確かめてから停止を解く。手順 4 のとおり探し直して S1 からやり直す。HEAD か `main` の先端が変わったときは、下の「承認の受け方」の 6 で承認を取り直す。S7 と S8 は、承認を受けた後に行い直す |
| S9 で、候補の照合は S2 の記録と同じで、世代だけが検査した世代と違う（`0` を含む） | マージしない。止める前の検査の結果は、切り替える前の秘密で探したものなので使えない。M4 の「世代が変わっていたとき」の「M2 からやり直す」は、この小見出しでは使わない。M2 から直接やり直すと、切り替えと再検査を待つ間も `main` を止め続けることになるためである。次の順で行う<br>1. 「停止を解く時点」の「S1 からやり直すとき」の行のとおり、未処理の要求を確かめてから、S7 でこのマージのために掛けた停止だけを解く。秘密を変える人が「秘密を変える手順」の準備 1 で掛けた停止は、この手順では解かない。その停止は、秘密を変える人が同じ手順の手順 4 で世代を正の値に戻すまで続く。世代が `0` か、検査した世代と違う値を読んだときは、切り替えが進んでいるので、その停止が掛かっているものとして扱う。解けば、世代が `0` の間に別の担当者が `main` を更新し、切り替えた後の秘密で検査する前に本番への反映が起動し得るためである<br>2. 切り替えが終わるのを待ち、切り替え後の秘密を手元に用意する<br>3. S1 からやり直す。S3 は切り替え後の秘密で打ち直し（M2 の 2）、S4 は M2 の 1 で世代を読み直してから打つ<br>4. S2 で固定した候補・HEAD・`main` の先端・最後に成功した反映が、どれも前の S6 の承認資料と同じなら、承認は取り直さない。S5 の後に S7 と S8 で止め直し、S9 に進む<br>5. どれかが違えば、上の行と同じく「承認の受け方」の 6 で承認を取り直し、承認の後に S7 と S8 で止め直す |

- S9 で最後に成功した反映だけが S6 の承認資料と違っても、マージしない。承認を待つ間に先の反映が成功すると、反映の範囲が変わり、持ち主が承認した範囲と違うためである。HEAD とマージ先が同じままでは前の承認の証跡が使えてしまうので、HEAD を変えてから、手順 4 のとおり探し直して S1 からやり直し、下の「承認の受け方」の 6 で承認を取り直す
- M2 で世代を読んでから S11 を終えるまで、秘密の世代を切り替えない（手順 5 の項目と同じ。M6-6 だけは除く）。切り替えてしまったときは、S9 の世代の照合で見つける

**停止を解く時点**: S7 の停止は、この Pull Request のマージの要求が残っていないと確定したときにだけ解く。要求が残っていると、停止を解いた後にその要求が成立し、ほかの Pull Request と同時に `main` を進め得るためである。解いてよいのは次の 4 つのときで、それ以外では停止を保つ。どのときも、解いてよいのは S7 でこのマージのために掛けた停止だけである。秘密を変える人が「秘密を変える手順」の準備 1 で掛けた停止は、同じ手順の手順 4 で世代が正の値に戻るまで続き、この表では解かない。

| 時点 | 停止の扱い |
| --- | --- |
| S11 を終えたとき | 解く。S11 でマージの結果が確定している |
| マージを中止したとき（手順 4 で手順を中止した、など） | 下の「未処理の要求の確かめ」で要求が残っていないと確定したら、解く |
| S1 からやり直すとき（S9 で照合が違った、など） | 下の「未処理の要求の確かめ」で要求が残っていないと確定したら、解く。検査と承認の取り直しを待つ間、ほかの Pull Request を `main` に取り込めるようにするためである。やり直した後は、承認を受けてから S7 と S8 で止め直す。世代だけが違ってやり直し、承認を取り直さないときは、S5 の後に止め直す（上の「S1〜S9 は、次の条件でやり直す」の表） |
| S10 が `gate` を返し、S6 に戻るとき | 下の「未処理の要求の確かめ」で要求が残っていないと確定したら、解く。新しい承認を受けた後に、S7 と S8 で止め直す |

**未処理の要求の確かめ**: この Pull Request に実行した S10 と M6-3 の結果を、最初の要求から最後の要求まですべて確かめる。途中の呼び出しは終了を待ち、打ち切らない。どの結果も、下の「`ndf ci merge` の結果の読み方」で要求を送っていない結果か、マージせずに断られた結果で、結果不明の要求（M6-1 の記録）が残っていなければ、未処理の要求は残っていないと確定する。S10 が `gate` を返して提示し直した後に持ち主が却下した場合も、前の S10 を含めて確かめる。M6-1 の記録が残っているときは、却下や中止の後でも、M6 のとおり結果が確定して記録を閉じるまで停止を保つ。

**止める前の書き込みの確かめ**: S7 で止めた後は、S9 の前に S8 を必ず行う。承認を待つ間は `main` を止めていないので、その間にほかの担当者が送った書き込みが、止めた後に成立し得るためである。止めていなかった間に `main` が進んでいれば、S9 の照合で見つかるので、上の「S1〜S9 は、次の条件でやり直す」の表のとおり探し直して承認を取り直す。

##### 承認の受け方

持ち主の回答は、マージの工程の `approve-merge` のステップ（`ndf ci answer`）で、Pull Request に承認の証跡として書く。S10 の `ndf ci merge` が承認として読むのは、この証跡だけである。承認資料や通常の Pull Request のコメントに書いた回答は読まず、`status` が `gate` で止まる（NDF 11.0.43 の `ci_cli.py` の `_approved_by`・`_write_answer`、テンプレート `merge` の定義。コードを読んで決めた）。手順は、切り替えの後の設計 PR の承認（[#166](https://github.com/devbasex/nd-factory/issues/166) の設計の「クローズとマージの工程で、承認した対象だけをマージする」）と同じ形にする。

1. マージの工程を流す前に、Pull Request の本文に、持ち主の承認を確認する行（`- [ ] マージの前に決める: …`）を未チェックで置く。この行があると、証跡が書かれた後の工程の `merge` のステップ（`ndf ci merge --branch`）は、行を理由にマージを拒んで止まる。行が無いと、このステップが S9 の照合の前にマージしてしまう
2. S1・S2〜S5 が成功した後に、その Pull Request をマージの工程で流す（`ndf plan next <プランのファイル>`）。`merge` のステップが承認を求めたら、工程の保存先の `presented-merge.json` の `head` が探した head で、`base` が `main` であることを確かめてから、S6 の承認資料を持ち主に示す。違えば示さず、手順 4 に戻る
3. 持ち主の回答を受けたら、記録する直前に、最後に成功した反映と `main` の先端を読み直す。承認資料が「未反映（初回）」なら、最後に成功した反映は S9 と同じ判定で読み直す。どちらかが承認資料と違えば、回答を記録せず、6 の提示し直しに進む
4. 同じなら、回答を `ndf plan next --answer <回答> --by human` で記録する。工程は、承認なら `approve-merge`、却下なら `reject-merge` のステップへ進む。どちらも `ndf ci answer` を打つ。進んだステップの結果が、`status` が `ok` で、`metrics.answer` が今回の回答（`approved` か `rejected`）であることを確かめる
   - 承認で結果が `ok` なら、続く `merge` のステップは 1 の行で止まる。S7 と S8 で `main` を止めてから S9 に進む。S9 の照合がすべて同じで、S9 で例外に当たるとしたときは S10 の例外の 3 つの確認もそろったときに、S10 の直前に承認の記録をコメントに残し、行にチェックを付ける。S10 の `--approved-head` には `presented-merge.json` の `head` を渡す
   - 承認で結果が `ok` でなければ、証跡は書かれていない。行にチェックを付けず、止まった理由を読み、6 の提示し直しに進む
   - 却下なら、結果によらずマージしない。行を未チェックのまま残し、提示し直さない。却下の結果が `ok` でなければ、止まった理由を作業の記録に残す。却下の時点ではまだ S7 で `main` を止めていない
5. 下の「`ndf ci merge` の結果の読み方」の表で `gate` が返り、S6 に戻るときも、2〜4 で受け直す。受け直すときは、必ず 1 の状態を戻してから始める。S10 の直前に行へ付けたチェックを外し、本文に未チェックの行があることを確かめる。行にチェックが付いたまま流し直すと、`approve-merge` が新しい証跡を書いた直後に `merge` のステップがマージし、S9 の照合を通らない。行は、4 の後の S9 の照合がすべて同じになるまで未チェックのまま保つ。そのうえで、工程を新しい回として流し直す（`ndf plan next <プランのファイル> --fresh`）。`merge` のステップは、呼ばれるたびに新しい提示の識別子（`presented-merge.json` の `presented_id`）を書く。示す前に、識別子が前の提示と違うことを確かめる
6. 提示し直すときは、前の回答を記録しない。5 と同じく、まず 1 の状態を戻し（行にチェックが付いていれば外し）、S9 の照合を通るまで行を未チェックのまま保つ。HEAD を変えて push する。`main` が進んでいればブランチへ `main` を取り込み、進んでいなければ空のコミット（`git commit --allow-empty`）を足す。前の承認の証跡が、新しい HEAD に当たらなくなるためである。手順 4 のとおり探し直して S1 からやり直し、5 と同じく工程を新しい回として流し直す。示す前に、`presented-merge.json` の `head` が新しい HEAD で、`presented_id` が前の提示と違うことを確かめる。持ち主には、前の資料への回答は使えなくなったことを伝える

##### `ndf ci merge` の結果の読み方

`ndf ci merge` がマージの要求を送ったか、マージしたかは、結果の JSON の `status` と、`metrics.merge` か `cause.kind` で読む（NDF 11.0.43 の `ci_cli.py` の `_merge_pull`・`_merged`・`main`、`adapters/github.py` の `_enqueue`。コードを読んで決めた）。S10 の初回の要求も、M6-3 の打ち直しも、M6-4 でこの表で読む。「秘密を変える手順」の準備 3 も、この表で読む。

| 結果の JSON | M6 の表で当たる行 | 扱い |
| --- | --- | --- |
| `status` が `ok`、`metrics.merge` が `merged` | マージした | 手順 6 に進む。手順 6 の実際の head は、その呼び出しの `--approved-head` に渡した head である。NDF は今の head が `--approved-head` と同じことを確かめてから、その head を添えてマージの要求を送り、GitHub は head が違えばマージしない |
| `status` が `ok`、`metrics.merge` が `already` | — | NDF は要求を送っていないので、指定した head はマージされた head の証拠にならない。M6-2 で `merged` が真だったときと同じく扱い、手順 6 の実際の head は M6-1 の記録で決める |
| `status` が `stopped` で、`metrics` に `rounds` がある（`cause.kind` は `ci_pending`・`infra_wait`・`test_failed`・`check_failed` など） | — | 必須のチェックの待ちで止まった結果で、NDF はマージの要求を送っていない。`--required` のチェックが失敗したか、結論が出ないまま `--budget` を使い切ったときに返る（`ci_cli.py` の `_failed_checks`・`_report`。この結果だけが `rounds`・`elapsed`・`queued_for` を持つ）。初回の要求なら、手順 4 に戻り、S1 からやり直す。M6-3 の打ち直しで返ったときは、今回の要求を送らなかったことしか分からない。記録を閉じずに M6-5 に進み、先の要求の結果が確定するまで、記録と `main` の停止を保つ |
| `status` が `stopped`、`metrics` に `rounds` が無く、`cause.kind` が `unknown` か `infra_wait`。または結果の JSON が出ない | 返らなかった | GitHub が要求を処理したかが分からない。M6-1〜M6-5 で結果を確定する |
| `status` が `stopped`、`metrics` に `rounds` が無く、`cause.kind` が `ci_pending` | 返らなかった | マージキューの要るブランチで直接のマージを GitHub が受けなかったため、NDF は Pull Request をマージキューに入れた（`adapters/github.py` の `_enqueue`。`summary` は「マージキューへ入れた」）。マージそのものは断られておらず、GitHub がキューから後でマージし得る。初回でも打ち直しでも、返らなかったときと同じく M6-1〜M6-5 で結果を確定する。記録を閉じて新しい候補へ進んでよいのは、M6-2 で `merged` が真になったときか、M6-5 でリポジトリの管理者が、キューから外したことと、今後マージされないことを確かめたときだけである。それまで M6 の停止を保つ |
| `status` が `stopped`、`metrics` に `rounds` が無く、上に挙げたもの以外の `cause.kind`（`approval_stale`・`refused` など） | マージせずに断られた | 初回の要求なら、手順 4 に戻る。M6-3 の打ち直しが断られたときは、M6-4 のとおり記録を閉じずに M6-5 に進む。打ち直しが断られても、先の要求が処理されなかった証拠にはならないので、手順 4 に戻って新しい候補をマージしない |
| `status` が `gate` | — | 今回の要求はマージの要求を送っていない。初回の要求なら、今の HEAD とマージ先への承認の証跡が無いので、S6 に戻り、「承認の受け方」の 5 のとおり新しい提示で承認を受け直す。M6-3 の打ち直しで返ったときは、分かるのは今回の要求を送らなかったことだけで、先の要求の結果は分からない。記録を閉じずに M6-5 に進み、先の要求の結果が確定するまで、記録と `main` の停止を保つ。承認の取り直しは、結果が確定した後に行う |

NDF 11.0.43 の `ndf ci merge` は秘密の世代を照合せず、「秘密を変える手順」が見る NDF の未解決の記録にも、送った要求を登録しない。そのため、要求の結果が分からないときは、M6-1 のとおり、送った要求（番号・`--approved-head` に渡した head・時刻）を手で作業の記録に残す。M6-5 のとおりリポジトリの管理者が結果を確定するまで、マージ先を変えられる担当者の間で `main` へのマージを止めたままにする。

##### 切り替えの後に秘密を変えるとき

切り替えの後は、秘密の世代を `0` にしても `ndf ci merge` は止まらない。`ndf ci merge` が秘密の世代を照合しないためである。そのため、秘密を変えるときは、担当者の間の取り決めで `main` へのマージを止める。

M6-6 の「NDF のマージは世代の `0` で止める」は、切り替えの後は成り立たない。M6-6 で秘密を切り替えるときは、担当者の間で `main` の更新（ほかの Pull Request のマージと `main` への直接の push）を止めたままにする。この停止は、下の読み替えの 9 の条件がそろうまで解除しない。

同じ理由で、切り替えの後は M6-6 の手順 2 の T の待ちと NDF の未解決の記録の確かめが、漏れた秘密を替える前の待ちとして働かない。そのため、M6-6 の手順 2〜6 は次のとおりに読み替える。漏れた値を早く使えなくするため、秘密の交換の前に済ませるのは、未解決の要求を漏れなく記録に載せることだけである。要求の結果の確定と探し直しは、交換の後に行う。T の値を確かめられないことや、未解決の要求が残ることを理由に、秘密の交換を止めない。

交換の前に済ませること（M6-6 の手順 2 の読み替え）:

1. `main` の停止と、作業の記録にある結果不明の要求（M6-1 の記録。複数あれば、そのすべて）を閉じずに保つ
2. 「秘密を変える手順」の手順 1 で世代を `0` にする。呼び出しのワークフローを、探す前に失敗させるためである
3. 「秘密を変える手順」の準備 2 の対象のとおり、停止の前に送られた `main` への書き込みを担当者ごとに洗い出す。ここでは、準備 2 と違い、呼び出しの終了を待たない。必須の CI を待つ `ndf ci merge` の終了を待つ間も、漏れた値が有効なまま残るためである。呼び出しの途中のものと、終わったが要求を送ったか分からないものは、結果不明として作業の記録に書き足す。マージの要求は M6-1 と同じ形で、直接の push は「[結果不明の直接の push の記録](#結果不明の直接の-push-の記録)」の形（push ごとの識別子・対象の ref・打った担当者のアカウント ID・送る前の先端・送った SHA）で書く。途中の呼び出しは打ち切らずに終了させ、その結果は交換の後の 6 で読む。準備 3 にある結果の確定（M6-2 の読み直しと M6-5 の引き継ぎ）も、交換の後の 6 で行う
4. 準備 4 の方法で、`main` 宛ての開いた Pull Request ごとに、マージキューに入っているかを確かめる。キューにある Pull Request が作業の記録に無ければ、結果不明の要求として、番号・確かめた時刻・その時の head を記録に書き足す。キューにある Pull Request は、後から GitHub がマージし得るためである。取得に失敗した Pull Request も、結果不明として書き足す
5. 記録に未解決の要求が残っていても、M6-6 の手順 3 で秘密を変える。T の待ちと NDF の未解決の記録の確かめは行わない

交換の後に行うこと（M6-6 の手順 4〜6 の読み替え）。記録にあるすべての要求を 1 件ずつ扱う:

6. 要求ごとに結果を確かめる。マージの要求は M6-6 の手順 4 のとおり確かめる。直接の push は、Pull Request の `merged` では確かめられないので、「結果不明の直接の push の記録」の要求の成否の 1〜3 で確かめ、成立したら同じ節の「探すコミット」で実際の `before` と `after` を決める。3 で途中だった呼び出しは、終了を待ってから、準備 3 のとおり結果を読む。マージの要求も push も送り直さない（M6-3 の打ち直しはしない）
7. 成立した要求は、新しい秘密で、`main` に入ったコミットを探し直す。探し方は、要求の種類で次の 3 つの表に分かれる。どの表も、手元で渡す秘密は M6-6 の手順 3 で登録した新しい `LEAK_CHECK_PATTERN` にする

   この 7 と下の 3 つの表の「手順 3」「手順 6」「手順 7」と「7-1」〜「7-7」は、この読み替えの番号ではない。「[規則を変える Pull Request をマージの直前に確かめる](#規則を変える-pull-request-をマージの直前に確かめる)」の手順 3・6・7 と、その手順 7 の中の 7-1〜7-7 を指す。

   マージの要求の 2 つの表では、実際の head は、手順 6 の 1 つ目の項目（「実際に取り込んだ head」を決める条件）のとおり、要求に渡した SHA の記録から決める。上の 4 でマージキューを観測したときに記録した head は、実際の head に使わない。観測した時点の head は、要求を送った時点の head や、実際に取り込まれた head と同じとは限らないためである。

   **規則を変える Pull Request で、手順 3 の候補の照合を通したもの**（7-1 の検査のコードがある）:

   | 順 | 使う手順 | すること | 読み替えること |
   | --- | --- | --- | --- |
   | 1 | 手順 6 | 実際のマージ先とマージでできたコミットを確かめ、作業の記録に残す。実際の head を決める | なし |
   | 2 | 手順 7 の 7-1〜7-7 | M6-6 の手順 5 のとおり探し直す。手順 6 の照合が通っても省かない | なし |

   **それ以外の Pull Request**（規則を変えない Pull Request と、手順 3 の照合を通していない規則を変える Pull Request。7-1 の検査のコードが無い）:

   | 順 | 使う手順 | すること | 読み替えること |
   | --- | --- | --- | --- |
   | 1 | 手順 6 の 1 つ目の項目 | 実際の head を決める | なし |
   | 2 | 7-3 | マージでできたコミットを「main のコミットを手元で探し直す」で探す。規則と版が同じでも、7-4 は使わない | なし |
   | 3 | 7-5〜7-7 | 途中のコミットを探し、結果を判定する。1 で実際の head を決められなければ、7-5 を打たずに 7-6 に進む | 「7-1 のディレクトリ」と書かれた所を、2 の 7-3 のチェックアウトに読み替える |

   **`main` への直接の push**（Pull Request を通らないので、手順 6 の照合も 7-1 の検査のコードも無い）。成立を確定したときに決めた実際の `before` と `after` で、足されたコミットを決めて探す。記録の「送る前の先端」と「送った SHA」は使わない:

   | 順 | 使う手順 | すること | 読み替えること |
   | --- | --- | --- | --- |

漏れていないときの通常の切り替え（「秘密を変える手順」の手順 1〜4）でも、同じ理由で、世代を `0` にして待つだけでは `ndf ci merge` を止められない。手で残した記録も、NDF の未解決の記録には載らない。そのため、秘密を変える人は、「秘密を変える手順」の準備 1〜4 で、世代を `0` にする前にマージを止め、止める前に送られた `main` への書き込みの結果と、手で残した記録を確かめる。マージの停止は、「秘密を変える手順」の手順 4 で世代を正の値に戻すまで保つ。

## 見本の写し直し

[`leak-check-caller.yml`](leak-check-caller.yml) を変えたら、`<非公開リポジトリ>` の写しも直す。写しを変えるのは呼び出しのワークフローの変更なので、「秘密を変える手順」の手順 1〜4 で世代を切り替えて写し直す。写しが見本と違っても、公開のリポジトリのテストでは見つからない。

## 振る舞いの変化

- main への push で、gitleaks の設定の結合のテスト（`npm run test:integration -- leak-scan`）を打たなくなった。結合のテストは Pull Request の `leak-check` で打つ。環境 `leak-scan` を持つ `leak-check-push` では依存の導入の処理を動かさないためである
- Pull Request の `leak-check` は、秘密が空でも、同じリポジトリのブランチの Pull Request で落ちなくなった。実際の値の規則での Pull Request の探しは、非公開の検査が行う
- main への push の `nd-real-value` の当たりは、件数の行だけになった。場所は「当たりの場所を手元で引く」で引く
