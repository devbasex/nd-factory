## 何が起きたか

運用する環境へアプリを反映する仕組み（反映のパイプライン）は、差分を作る段（準備）の後に、人が差分を読んで承認する段（`Approve`）を持っていた。人が承認するまで、反映は進まなかった。

2026-11-25 に、push が続くと古い実行が承認の段にとどまり、新しい実行が先へ進めずに反映が止まっていた。同じ日に、持ち主が「パイプラインの実行は承認不要」と決めた。

承認の段を外す変更は、同じ日に PR「反映のパイプライン: 承認の段を外し、push から準備・反映まで人を待たずに進める」（ https://github.com/devbasex/nd-factory/pull/165 ）で main に入った。パイプライン自身も設置のコマンドで反映し直した（この課題のコメントの記録）。一方で、全体の設計・プロジェクトの MVV（判断の基準の文書）・開発の指針には、人の承認を前提にした文が残っている。

## 種類

機能追加（今の全体の設計と MVV の Value 8 が約束している「人が差分を見て承認した範囲だけを反映する」流れを、承認を待たずに反映する流れへ変えるため）

## 今の姿

反映のパイプラインは、起点のブランチへの push で動き、準備で合成の結果と差分と要約値（合成の結果の中身から数えたハッシュ）を作り、反映の段でその要約値を数え直して同じときだけ反映する。手順は [pipeline-approval.md](https://github.com/devbasex/nd-factory/blob/main/docs/operations/pipeline-approval.md)、設計は [全体の設計の「反映と設置」](https://github.com/devbasex/nd-factory/blob/main/docs/design/platform.md) にある。

置き場ごとの今の状態は次のとおりである（2026-11-25 に main で `git grep` を打って調べた）。

## 何を足すか・変えるか

| | 今（#165 の前） | 変えた後 |
| --- | --- | --- |
| 反映のパイプラインの流れ | push → 準備 → 人の承認 → 反映 | push → 準備 → 反映。人を待たない |
| 反映してよい合成の結果 | 人が承認したもの（要約値で照合する） | 準備で作ったもの（要約値で照合する） |
| 差分を人が読む時点 | 反映の前 | 反映の後に、準備の記録で読める |
| 反映するコミットの NDF の契約の照合の結論を見る人 | 承認する人 | 設計で決める（未決） |
| 承認を拒む方針（AI の主体に承認を送らせない IAM の方針） | パイプラインのスタックが作り、AI の主体へ付ける | 残すか消すかを設計で決める（未決） |
| パイプラインからのメールの通知 | 承認の依頼と実行の失敗 | 実行の失敗だけ |
| 全体の設計・MVV・開発の指針の記述 | 人の承認がある流れ | 承認の段の無い流れ |

## 今の利用者への影響と互換

- 運用する環境の持ち主: 起点のブランチへ push すると、承認なしで反映される。承認の依頼のメールは届かなくなる
- 自分で設置する人: 設置のコマンドで差分と確認の値を見てから反映する経路のままである。反映のパイプラインを使わない人は変わらない。パイプラインを併設している人は、この版へ上げる前に、アプリ専用の bootstrap を作る移行が要る（受け入れ条件 11）

## なぜ困るか

全体の設計と MVV が「人の承認の後に反映する」と書いたままだと、後から設計・実装・レビューを行う AI と人が、承認の段があるものとして判断する。

- 承認の段を戻す変更や、承認の段を前提にした手順が、設計どおりとして通る
- 決定 79 は「承認する人が反映するコミットの照合の結論を読む」ことで、NDF との契約の食い違いを反映の前に止めるとしている。承認の段が無い今、この確認はどこでも行われていないが、設計を読んでも気付けない
- MVV と食い違う変更は、承認ゲートの前の MVV の判定で、反する疑いとして止まり続ける

## 目的

起点のブランチへの push から、人の承認を待たずに準備と反映が続くようにする。手順書・`AGENTS.md`・全体の設計・MVV・開発の指針がその流れにそろい、承認の段を前提にした判断が生まれないようにする。

## 対象範囲

含む:

- パイプラインのスタックから承認の段を外し、準備の要約値をそのまま反映の段へ渡す（#165 で済み）
- 承認を拒む方針と、承認の依頼の通知の扱いを決め、パイプラインのスタックと手順書をそろえる
- 手順書 `docs/operations/pipeline-approval.md` と `AGENTS.md` の「反映の経路」
- 全体の設計の該当の記述: `docs/design/platform.md`（題・反映の道筋・構成要素の表・反映と設置の表）、`docs/design/overview.md` の場面 S14、`docs/design/execution.md` の決定 79
- MVV の Vision と Value 8 の改訂案。改訂が成立するのは持ち主の承認による
- 開発の指針の Skill に「反映のパイプラインの実行は承認不要」を書く
- パイプラインのスタックを設置のコマンドで反映し直す手順（#165 の後に反映し直し済み）

含まない:

- 自分で設置する人の経路（`nd-setup diff` → `deploy --confirm`）。変えない。ただし、反映のパイプラインを併設する人の bootstrap の移行は除く（受け入れ条件 11）
- 商用利用の開始後の本番の扱い。そのときに決め直す
- 設計を作った経緯の文書（`docs/design-process/`）。過去の記録なので書き換えない

## 前提

- 前提 1: 承認を待たずに反映する決定は、商用利用の開始前の運用に当てる。商用利用の開始後の扱いは、この課題では決めない

## 受け入れ条件

- [ ] 1. 起点のブランチへ push すると、人の操作なしに、取る → 準備 → 反映の順に段が進み、アプリのスタックが反映される。パイプラインの定義に承認（`Approve`）の段が無い
- [ ] 2. 反映の段は、準備で作った合成の結果の要約値を数え直し、準備の値（`EXPECTED_DIGEST`）と同じときだけ反映する。違えば反映せずに失敗で止まる（退行しない）
- [ ] 3. パイプラインの実行が失敗したとき、失敗の通知が通知の宛先（`pipeline.notify_emails`）へ届く（退行しない）
- [ ] 4. 承認を拒む方針を残すか消すかが設計で決まり、パイプラインのスタックと手順書が同じ扱いを書いている
- [ ] 5. 手順書 `docs/operations/pipeline-approval.md` が承認の段の無い流れで書かれ、承認する人が読む資料と、承認を拒む方針を AI の主体へ付ける手順を、今行う手順として書いた節が無い
- [ ] 6. `AGENTS.md` の「反映の経路」が、承認の段の無い流れを書いている
- [ ] 7. 全体の設計（`docs/design/` の下）に、「準備 → 人の承認 → 反映」の流れを今の姿として書いた文が無い。確認: `git grep -n -E "人の承認 → 反映|準備・人の承認" -- docs/design` が 0 件を返す
- [ ] 8. 実行の文書の決定 79 が、承認の段の無い流れで、反映するコミットの NDF の契約の照合の結論を誰がいつ確認するか、または確認しないならその理由を書いている
- [ ] 9. MVV の Vision と Value 8 を改訂するかを持ち主が決めている。改訂するなら、持ち主の承認で新しい版が `.ndf/mvv.json` に記録されている。改訂しないなら、その理由が課題に記録されている
- [ ] 10. 開発の指針の Skill（`.claude/skills/nd-factory-dev-guidelines/SKILL.md`）に、反映のパイプラインの実行は人の承認を待たないことが書かれている
- [ ] 11. 自分で設置する人の経路（`nd-setup diff` → `deploy --confirm`）は、反映のパイプラインを使わない設置（設定に `pipeline` が無い）では振る舞いが変わっていない。パイプラインを併設する設置では、打つコマンドは同じだが、アプリ専用の bootstrap が要る。既定の bootstrap だけで併設している人は、この版へ上げる前に移行する。移行の手順が `docs/operations/pipeline-approval.md` にあり、`docs/operations/setup.md` の「自分で設置する人」の節からその手順へ進める。`infra/setup/` に差分が無い。`docs/operations/setup.md` の差分は、「運用する環境」の節（`### 運用する環境`）と、「自分で設置する人」の節に足す移行の手順への案内の 1 項だけで、設置のコマンドの節（「diff」「足りない設定」「確認の値」「deploy」「終了コード」など、ほかのすべての節）に差分が無い（退行しない）
- [ ] 12. 起点のブランチと反映の経路が次をすべて満たす（箇条ごとに 1 つの要件。全体で 1 つの条件）
  - 起点のブランチが存在し、Pull Request 必須・レビューの承認 1 件以上・差分を変えるコミットで承認を失効させる・削除と強制 push を禁じる保護を持ち、ルールセットならブランチの作成も禁じ（従来のブランチの保護には作成を制限する設定が無いので、ブランチが存在し削除を許さないことで代える）、人を含めて誰もこれらを迂回できない。
  - 承認の件数と承認の失効は、使う方式の実効の値で確かめてある。
  - 既に動いている環境・初めての設置・起点の変更のどれでも、承認済みと確かめられる信頼する基点から先端までの変更がレビューを経たことを、パイプラインのスタックの反映の前に確かめてある。
  - ブランチの存在は、ルールの取得とは別に確かめてある。
  - 迂回できる主体が無いことは、各ルールセットの詳細の迂回の一覧、従来の保護の管理者への適用と個別の例外まで確かめてある。
  - 手動で始めた実行は、人が始めたものも反映されない。パイプラインを作ったときの最初の実行も反映されない。
  - 起点のブランチ名は、設定の正本で英数字と `.`・`_`・`-`・`/` だけに限られている。
  - AI の主体が、取り得るセッションと条件の値の範囲全体で、このパイプラインの実行を手動で始められず、反映の段への遷移を戻せず、反映の段をやり直せない。
  - AI の主体が、反映のプロジェクトを直に起動できず、その定義を変えられず、反映用のロールを渡すことも引き受けることもできない。
  - 既に動いている環境・初めての設置・起点の変更のどれでも、この変更を含むパイプラインのスタックを `--stack pipeline` で反映する前に、起点のブランチの保護と、信頼する基点から先端までの変更を確かめ、判定が課題に、実値を含む結果がアクセスを制限した運用の記録に残っている。
  - 確かめきれないか満たさない間は、反映の段への遷移が止まっている。
