# #2: 形の正本と横断の部品: 1 つの操作の表から型・API・MCP の道具・ダミーデータを作れる

正は課題の本文（#2）で、この文書は本文の写しである。本文を直したら同じ手順で作り直し、写しだけを手で直さない。

## 種類

新規作成（操作の表・横断の部品のパッケージ・サービスの表の列の定義は、まだリポジトリに無い。骨組みの 1 本の HTTP の経路 `PUT /v1/users` のコードに、引き継ぐ形だけがある）

## 今はどうしているか

形の正本（`packages/contracts/`）は、設定のファイルの形・終了コード・画面の設定の値と、骨組みの 1 本の HTTP の経路（`PUT /v1/users`、`src/users-api.ts`）の形だけを持つ。生成のスクリプト（`scripts/generate.ts`）は設定のファイルの JSON Schema・見本・設置の手順の終了コードの表の 3 つを作る。操作の表・値の形（UTC の日時・通貨つきの金額・ID）・OpenAPI・MCP の道具・HTTP の経路の登録・画面のダミーデータは無い。

横断の部品のパッケージ（`packages/core/`）は無い。時計・ログ・条件つきの書き込み・失敗の分類・要求の読みは、骨組みの API の関数（`apps/api/src/users-handler.ts`・`user-store.ts`）の中にその場の形で書かれている。サービスの表は利用者の表 1 つだけで、全体の設計（[データの表と鍵](https://github.com/devbasex/nd-factory/blob/main/docs/design/data.md#テーブルとキー)）の 10 の表のうち 19 の行と 3 つの索引には列の定義が無い。

## 誰が・どんな場面で困るか

- 画面の基盤（#12）と機能の画面の子は、操作の表から作る型とダミーデータが無いと、API の中身の前に画面を作り切れない（Value 2 の順が守れない）
- 各コンテキストの子（#4〜#8・#11・#29）は、操作の定義を書く枠・認可の判定・操作の記録の書き手・条件つきの書き込みが無いと、同じ処理を入口ごとに書き、I2 と I9 の守りが入口の数だけ散る
- 各コンテキストの子は、表の列と索引が決まっていないと、同じ表を読む別の子と列の名前と型が食い違う

## 目的

| MVV の項目 | この子で受けること |
| --- | --- |
| Value 2 画面先行 | API の入出力を機能（エンティティと操作）から起こし、取得・作成・更新・削除とも配列で受け渡す。画面のダミーデータを同じ形の正本から作る |
| Value 4 AI からも人と同じく | 画面・API・MCP の道具を 1 つの操作の表から作り、食い違わせない |
| Value 5 国や地域を越えて | 日時は UTC、金額は通貨とともに、を形の正本の検証で縛る |
| Value 9 割り当てたチームにだけ見せる | 認可の判定を横断の部品の 1 か所に置く |
| Value 4・Value 7 | 操作の記録の書き手とログの伏せ字を 1 か所に置き、秘密と個人情報の値を残さない |

機能一覧の行は持たない（F1〜F20 を支える仕組み）。受け持つ不変条件は次の 4 つである。

| # | 中身 |
| --- | --- |
| I2（判定の部品） | プロジェクトとその中身を読めるのは、割り当てたチームの席を持つ人とその人の委任だけ。ほかの主体には存在しないときと同じ応答を返す。判定は横断の部品の 1 か所で行う |
| I9 | 操作の記録は追記だけで、秘密と個人情報の値を含まない。読み取りを含むすべての要求が 1 つの記録の ID で残る。記録の行は要素の確定と同じトランザクションに入れる |
| I12 | 取得・作成・更新・削除とも配列で受け渡す。GitHub の Webhook は外す |
| I15 | 日時は UTC で保存し、金額は通貨とともに保存する |

## 要求から変えたこと

| 日付 | 誰の決定 | 変えたこと | 理由 |
| --- | --- | --- | --- |
| 2026-11-21 | 設計者（設計承認ゲートで確かめる） | MCP の受け口の 5 つの関数（`readMcpCall`・`createMcpHandler`・`createMcpServer`・`serveMcp`・`writeMcpResponse`）と MCP の SDK の足しを #11 へ渡す。この子は MCP の道具の定義（名前・入力と出力の形・注記）を操作の表から生成するまでを持つ | 開発の計画の構成要素の表は MCP を #11（K11）に置き、詳細設計の受け持つ子の表は `packages/core/` を #2 に置くため、MCP の受け口の受け持ちが 2 つに読める。この子で SDK を足すと、使う子（#11）より前に依存が入り、1 子 1 スプリントの大きさも越える |
| 2026-11-21 | 利用者の方針（「より堅牢で長期的に良いほうを選ぶ。今の実装からの切り替えの手間は考慮しない」）のもとで conductor が決めた（設計承認ゲートで確かめる） | MVV 版 2 の Value 15 に照らし、横断の部品の 4 つの作り方を既存のライブラリへ乗り換え、全体の設計（`docs/design/api.md` の決定 48・55 と LIB の行、`docs/design/detail.md` の関数の表と既存の部品の再利用の表）をこの課題の設計 Pull Request の中で直す。OpenAPI は `zod-openapi` で組む。Cognito の公開鍵の控えは `aws-jwt-verify` の組み込みを既定のまま使う（`createJwksCache` をやめる）。共通の再試行（`withRetry`）を持たず、HTTP は `ky`、AWS は SDK の再試行の設定、トランザクションの衝突は `p-retry` で繰り返す。ログは `pino` を書き手にする | 全体の設計の 4 つの決定は MVV 版 1 のもとで「依存を足さない」を得と見て自前で作るとしていた。MVV 版 2 の Value 15 は、広く使われ保守が活発な既存の部品があれば設計に含め、自前の実装をできるだけ避けることを求める |

## 対象範囲

含む:

- 操作の表の枠（操作の定義の型と、定義を足す関数）と、全体の設計の操作の一覧の全行（利用者向けの操作と、ランナー・手元のマシン・DB の用意のタスクの HTTP の経路）の印（名前・HTTP の経路・機能・読むか書くか・人だけか・委任の種類・全部か無か・冪等の鍵・記録に写す鍵）の登録
- 操作の表から、JSON Schema・OpenAPI・MCP の道具の定義・HTTP の経路の登録・理由のコードの一覧・ダミーデータ（操作ごとの正常・空・境目の値）を作る生成（`npm run generate`）と、生成物が古いと落ちる差の検査
- 値の形（配列の本文・UTC の日時・通貨つきの金額・`<種類の頭>_<UUIDv7>` の ID・言語・時刻帯）と、ID の頭・token の形・理由のコードの共通の集まり
- 事実と方針のデータ（再試行の方針・秘密の形・受ける NDF の契約の組・料金プランの既定の行）と、NDF の答えの語の集まり
- 横断の部品（`packages/core/`）: 時計・ID と冪等の鍵・ログと伏せ字・外部の呼び出しと再試行（方針の値の調整を含む）・条件つきの書き込み・認証・認可の判定・使える量の判定・操作の記録の書き手・HTTP の振り分け（`readHttpCall`・`dispatch`・`writeHttpResponse`）
- API の振り分けの起点（`apps/api/src/entries/`）と、骨組みのコードから引き継ぐ形（`createClock`・`claimIdempotency`・`putIfAbsent`・`createLogger`・`classifyFailure`・`awsClient`・`authorize`・`readHttpCall`・`dispatch`・`writeHttpResponse`・`authenticate`）。骨組みの `PUT /v1/users` は #4 が置き換えるまで今の関数のまま残し、中を横断の部品へ移す（新しい起点は #4 が反映する）
- サービスの表の 19 の行の列と 3 つの索引の鍵と写す列、行の形（形の正本）と、表と索引を作る部品（作るのは表を書く子）
- 表の移しの読み手（今と 1 つ前の版を読む）と、表の移しの関数

含まない:

- 各コンテキストのモジュール（利用者とチーム・プロジェクト・実行の制御ほか）の関数と、操作ごとの要素の項目・型・理由のコード（#4・#5・#6・#7・#8・#11・#13・#29。全体の設計の [操作の一覧](https://github.com/devbasex/nd-factory/blob/main/docs/design/api.md#操作の一覧) の受け持つ子の表）
- MCP の受け口の関数と MCP の SDK（#11。上の「要求から変えたこと」）
- `PUT /v1/users` の `sessions.create` への置き換えと、API の関数を `api-fn` にまとめて表と HTTP の経路をアプリのスタックへ入れること（#4）
- 検査そのもの（境界の検査・操作の一覧と画面と MCP の対応・依存の向き・漏れの検査。#1）
- 料金プランの値の集合（#29）
- 表の移しの関数の資源（Lambda）と起こし方。最初に形の版を上げる子が足す（今の行はどれも版 1 で、移すものが無い）

## 前提

- 前提 1: 全体の設計で決めたモデル・境界・入出力・状態の置き場・権限は決め直さない。全体の設計が「#2 が決める」と回した列と索引と、横断の部品の形の細部（ファイルの単位・型の項目の並び）だけを決める。横断の部品の 4 つの作り方（使うライブラリ）は「要求から変えたこと」のとおり全体の設計を直す
- 前提 2: NDF との契約は #41 の設計（PR #42、決定 104〜108）を正とする。受ける契約の組は `{版 8, sha256 ed8b036584bec284dfc93a2bb5b988e2385b4f8f297d659399f5d3cb91b520c4}` の 1 つで、NDF の版の数字の大小は比べない。#42 の承認で決定が変われば、受ける組のデータを直す
- 前提 3: 1 つの子は 1 つのスプリントで閉じる大きさにする（plan.md の決まり）。実装はレビューの単位に分けて同じスプリントで集める
- 前提 4: 設計の段では AWS に触れない。表と HTTP の経路を作る部品は合成の出力のテストで確かめる

## 受け入れ条件

- [ ] 1. 操作の表から JSON Schema・OpenAPI・MCP の道具の定義・HTTP の経路の登録・理由のコードの一覧・ダミーデータが生成され、生成物が古いと CI の `check` が落ちる
- [ ] 2. 横断の部品が `packages/core/` の 1 か所にあり、`apps/` の実行の時のコードが部品の外で時計・乱数の ID・`console.log`・`fetch`・AWS SDK のクライアントの直の生成・条件式の直の組み立てを使っていない（境界の検査（#1）が落とす形にそろえる）
- [ ] 3. I2（判定の部品）: 割り当ての外の主体で認可の判定を呼ぶと、存在しないときと同じ答え（404 `not_found`）になるテストがある。見えるときと同じ答えが返ると落ちる。全体の設計のテスト設計の I2 の行（7 つの出口と進行表の役割）は、出口を作る子が同じ判定の部品の上で足す
- [ ] 4. I9: 記録の更新・削除の試み、秘密の形の値を含む操作、記録の書き込みの失敗のテストがある。更新が通る・値が残る・操作が成功すると落ちる
- [ ] 5. I12: 配列でない本文の要求のテストがある。400 以外が返ると落ちる
- [ ] 6. I15: 時刻帯の無い日時・通貨の無い金額を形の正本の検証へ渡すテストがある。通ると落ちる
- [ ] 7. 形の往復: 操作ごとの見本を、zod の検証と、生成した JSON Schema の検証の両方へ通すテストがある。2 つの結果が食い違うと落ちる
- [ ] 8. サービスの表の 19 の行と 3 つの索引の列が詳細設計と形の正本の行の形にあり、`schema_version` の無い行・上書きの行で `version` の無い行を行の形の検証へ渡すと落ちる
- [ ] 9. 表の移しの読み手が今と 1 つ前の版の行を読め、それより古い版を拒むテストがある。表の移しの関数を 2 回走らせても行が同じになるテストがある
- [ ] 10. 受ける NDF の契約の組の集合が形の正本のデータの 1 か所にあり、空・重なり・版と sha256（64 桁）の対でない形だと落ちる
- [ ] 11. 詳細設計 `issues/issue-2-design-detail.md` を書き、全体の設計で決めたモデル・境界・入出力・状態の置き場・権限を決め直していない（横断の部品の 4 つの作り方は「要求から変えたこと」のとおり全体の設計を直した）

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 性能・拡張性 | `dispatch` は要素 1〜100 個を受け、書く要素ごとに 1 つのトランザクションで確定する。関数の残り時間が予備の時間を下回れば残りを処理せずに 503 で返す |
| 運用・保守性 | 形を変えるときは `packages/contracts/` を直して `npm run generate` を打つだけで、型・JSON Schema・OpenAPI・MCP の道具・HTTP の経路の登録・ダミーデータが同じ変更でそろう |
| セキュリティ | ログと操作の記録に秘密と個人情報の値を残さない。秘密の形はデータで 1 か所に持ち、伏せ字と漏れの検査が同じものを読む |
| システム環境 | 生成物と見本は作り物の値だけを持つ（AGENTS.md の作り物の値）。CI は AWS の資格情報を持たない |

| 対象 | 影響 |

## 検証手段

| 項目 | 手段 |
| --- | --- |
| テスト | CI の `check`（`npm run check`: lint・型検査・生成物の差・単体テスト）と `synth`。このリポジトリはテストを CI に寄せる（`.ndf/project.json` の `test.ci.only`） |
| 形の往復 | 単体テストで、操作ごとの見本と反例を zod と生成した JSON Schema の両方で検証し、結果を比べる |
| 値の混入 | 生成物と見本が作り物の値（アカウント `123456789012`・接頭辞 `acme`・メール `ops@example.com`）だけを持つことを生成のスクリプトが照らす |
| 手動確認（マージ前） | 設計承認ゲートで、承認する人が「要求から変えたこと」（MCP の受け口の受け持ち）を読む |

## 境界

| 区分 | 内容 |
| --- | --- |
| 常に行う | 形を変えたら `npm run generate` を打って生成物を同じ変更でコミットする。例・見本・テストに作り物の値だけを使う |
