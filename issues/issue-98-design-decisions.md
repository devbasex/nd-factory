# 漏れの検査の設計の決定の記録（#98）

[設計書](./issue-98-design.md)の決定を分けた文書である。「処理の流れ」「テスト設計」などの節の名前と、`STD1`・`LIB1`・`PRD1` などの番号（「外部の調査」の表）は、設計書を指す。

この文書の呼び名と、番号の指すものは次のとおりである。

| 呼び名 | 指すもの |
| --- | --- |
| 端点・置き場 | AWS のエンドポイント・S3 のバケット |
| 全体の許可 | gitleaks の設定の global allowlist（`[allowlist]`）。この許可に当たって検査の対象にならないことを「外す」と呼ぶ |
| 中継 | gitleaks が打つ `git log` の出力に目印の行を足す小さなスクリプト |
| 目印 | 中継が各ファイルの差分の末尾に足す行。専用の規則で当て、当たらなければ gitleaks がそのファイルを読み終えていないと分かる |
| 写し | 探し直すファイルを一時の Git リポジトリに複製したもの |
| 記録の段・飛ばした行 | gitleaks のログのレベル・gitleaks がファイルや当たりを飛ばしたことを知らせるログの行 |
| 固定の行 | ファイルの名前などを含まない、決まった文言の出力の 1 行 |
| LIB1・LIB2・LIB3・PRD1 | gitleaks・TruffleHog（置き換えの候補）・Python の標準ライブラリ・TruffleHog（比べた製品） |
| STD1〜STD6 | 順に、`git diff` の選択肢・予約済みのドメイン名（RFC 2606）・S3 のバケット名の規則・S3 のアクセスポイントの名前と別名・Cognito のドメインの規則・`git log` の `-S` と `-G` |

### 決定 1: サービスの token を形が少し変わっても止めるため、秘密の部分の長さで当てる 2 つの規則を `.gitleaks.toml` に置く

- **質問**: 委任の token と手元のマシンの登録の token を、どの形で、どの設定のファイルで当てるか
- **選んだ案**: `.gitleaks.toml` に `nd-delegation-token`（`ndfd_`）と `nd-machine-token`（`ndfm_`）の 2 つの規則を足す。形は「語の境（`\b`）の後に頭（`ndfd_` か `ndfm_`）、英数字と `_`・`-` の並び、`.`、同じ並び、`.`、base64url の文字が 32 字以上」とする。ID の部分の形（`usr_` と UUID など）は問わない。許可は持たない（プレースホルダー `<…>`・`${…}` は文字の種類で外れ、`EXAMPLE` のような短い作り物は 32 字に届かない）
- 採らなかった案: 今の token の形（`usr_<UUIDv7>`・秘密の部分 43 字）に正確に合わせる（ID の形や長さが変わったときと、記録に途中まで写った token を逃す）
- 採らなかった案: 既定の規則の設定（`tools/checks/gitleaks-default.toml`）に置く（このファイルの冒頭のコメントが、既定の規則の許可を外すためだけに使うと決めている。要求の起票者の推定 S2）
- **代償**: `ndfd_`・`ndfm_` で始まり、3 つ目の部分が 32 字以上の base64url の文字の、token でない文字列も当たる。今の木と main の全履歴には無い（実測）
- 作り方: ライブラリやサービスを使う
- 比べた候補: LIB1 / LIB2
- 根拠: Value 7（MVV バージョン 3）

### 決定 2: 履歴で探す対象をパッチと別に決め、そのすべてを gitleaks が読み終えたことを目印の行で確かめる

- **質問**: 履歴の探しで、Git がバイナリとしたファイルの中身をどう探し、探す対象をどう決め、すべて探し終えたことをどう確かめるか
- **選んだ案**: 次の 4 つを組み合わせる。仕組みの詳しい形は「処理の流れ」にある
  1. **探す対象をパッチの表示に頼らずに決める**: 範囲の各コミットが足したか変えたファイルを、`git diff-tree --raw` のファイルの一覧（パスと blob）から決める。受け入れ条件 2 の「スキャンの対象は `git log -p` のパッチの表示に頼らずに決める」を、文のとおりに満たす
  2. **バイナリのファイルの中身も gitleaks に読ませる**
     - `leak-scan.sh` が gitleaks に渡す `--log-opts` に `--text --no-textconv --no-ext-diff --no-renames` を足す。
     - Git がバイナリと判定したファイルも、足した行をパッチに出させる（STD1）。
     - gitleaks は `Binary files … differ` の項目を受け取らないので、飛ばす経路を通らない。
     - 足した行を探し、当たりのコミットと行の番号を元のリポジトリのまま報告する点は今と同じである
  3. **1 の対象のすべてを読み終えたことを確かめる**: gitleaks が打つ `git log` の出力に、`leak-scan.sh` の中継が、ファイルごとに目印の行を 1 行足す。1 の対象のどれか 1 つでも、中継の出力に無いか、目印が当たらなければ、当たりの有無によらず 1 で終える。gitleaks のパッチを読む部品（go-gitdiff）が途中で黙って読むのをやめても、Git が 0 で終えても、これで見分けられる
  4. **バイナリは変更後の blob 全体も読ませる**: 前からある行と足した行にまたがる秘密や、行の削除で成立した秘密を見つけるため、写しのリポジトリで探す。前からある当たりを区別するため、変更前の blob も探して比べる（「処理の流れ」の「コミットへの帰属」）。この探しも読み終えたことを確かめ、満たさなければ 3 と同じ固定の行で失敗にする
- 採らなかった案: パッチを読むだけにして、探す対象の決め方と読み終えたことの確かめを持たない（この設計の前の版）。受け入れ条件 2 の文を「バイナリの判定で対象から外れない」と読み替えないと満たせない。go-gitdiff が途中で読むのをやめたとき、Git は 0 で終えるので見逃す
- 採らなかった案: 範囲の各コミットの blob を書き出し、ファイルとして `gitleaks dir` で探す（非公開の検査が履歴を探すときの `history` と同じ形）。`gitleaks dir` は先頭のバイトの種類と名前で飛ばすので、決定 3 の探し直しが履歴の全体に要る。blob の全行を探すので、前から在る行も、そのファイルを変えたコミットの当たりとして重ねて出る。当たりのコミットを gitleaks が知らないので、コミットを条件にする許可（決定 5 の許可 5）が効かない。範囲を持たない main への push の探しでは、書き出す量が履歴の全体になる
- 採らなかった案: 範囲の各コミットの変更を写しの Git のリポジトリに作り直し、目印をファイルに足して探す。写しのコミットは元と別のハッシュになるので、コミットを条件にする許可（決定 5 の許可 5）が効かない。中継で出力に足せば、元のコミットのハッシュのまま探せる
- 採らなかった案: blob 全体の当たりを、足した行と重なるものだけに絞る。行の削除だけで成立した秘密は足した行と重ならないので、途中のコミットにだけ残る場合に見逃す
- 採らなかった案: 鍵の格納ファイルの拡張子（`.p12`・`.pfx`・`.jks`・`.keystore` など）を拒む（拡張子の無いファイルとほかの拡張子のバイナリを逃す。中身を探せば、拡張子を拒む必要が無い）
- **代償**: 足したバイナリのファイルの全バイトがパッチに載るので、大きなバイナリを足した範囲ほど探す時間が延びる。今の main の全履歴に、Git がバイナリとする項目は 0 件である（`git log -m --numstat`）。`--no-renames` で、名前を変えたファイルは中身の全体を足した行として探すので、名前の変更が多い範囲ほど時間が延びる。中継は `git log -p` の出力の形（ファイルの見出し・`@@` の見出し・行の頭の 1 字）を読むので、Git がこの形を変えると中継が読めずに失敗で止まる（通らないが見逃さない）。内部の `git log` の失敗を、gitleaks 8.30.1 の記録の文言（`command aborted`）で見分けるので、版を上げて文言が変わると見分けられなくなる。文言が変わったときは、テスト用の偽の `git` で途中で止める結合テストが、版を上げる Pull Request で落ちる。目印で確かめる部分は文言に頼らない
- 作り方: ライブラリやサービスを使う・自前で作る（中継と照らし合わせ）
- 比べた候補: STD1 / LIB1 / LIB2
- 根拠: Value 7・Value 15（MVV バージョン 3）。STD1

### 決定 3: 今の木で飛ばされたファイルを探すため、gitleaks の記録から集めて写しで探し直す

- **質問**: 今の木で gitleaks が中身を読まずに飛ばすファイル（先頭のバイトの種類・アーカイブに見える名前）を、どう探すか
- **選んだ案**: 飛ばしたファイルを、一時の Git のリポジトリに元のパスのまま写し、gitleaks の履歴の探しで読み直す。履歴の探しは、テキストのパッチの足した行を、ファイルの種類もアーカイブに見える名前も確かめずに探すためである。gitleaks がアーカイブかを確かめるのは、Git がバイナリとした項目だけである（[sources/git.go](https://github.com/gitleaks/gitleaks/blob/v8.30.1/sources/git.go#L327-L333)）。テキストのパッチは [L390-L404](https://github.com/gitleaks/gitleaks/blob/v8.30.1/sources/git.go#L390-L404) で元のパスと新しい側の行の番号のまま渡す
  - 1 回目は今と同じく木を探す。このとき gitleaks の記録の段を trace にする
  - 記録の飛ばした行を「処理の流れ」の表で分け、探し直す対象の行から `path` を取る。
    - 記録の行の項目を解析して `path` の値を取り、項目の並びには頼らない（アーカイブの行には `path` のほかに `max_archive_depth` があり、規則の許可の行には `rule-id` などが続く）。
    - 値に空白などを含むときは Go の引用の形になる。
    - 取り方は、実物の gitleaks 8.30.1 の記録で結合テストが確かめる
  - 1 件以上あれば、一時ディレクトリ（`mktemp -d`。終わりに消す）に Git のリポジトリを作る。探し直す対象ごとに、そのファイル 1 つだけを持つ親の無いコミットを作り、写しと対象を 1 対 1 に対応させる。ファイルは、木の根からの元の相対パスに中身を変えずに置く（全体の許可が外したファイルも同じ。展開した中のファイルは、決定 8 の評価のパス `<アーカイブのパス>/<中のパス>` に置く）。1 つのコミットにすべての写しを置くと、同じパスになった 2 つの写しの一方が上書きされる。上書きされた側は、探されないまま通る。履歴の探し直しでは、同じパスを変えた複数のコミットの blob が同じパスになる。zip は、同じ名前の項目を 2 つ持てる。対象ごとに別のコミットにすれば、写しのパスが同じでもコミットで区別できる
  - 写しのコミットは作業ツリーを使わずに作る。対象ごとに次の順で作る。中身を `git hash-object -w` で写しのリポジトリに入れる。インデックスを `git read-tree --empty` で空にし、`git update-index --add --cacheinfo` でそのファイルだけを登録する。`git write-tree` と `git commit-tree`（親を渡さない）でコミットを作る。コミットの本文に対象の番号を入れ、同じ中身とパスの対象でも別のコミットのハッシュにする。作ったコミットは `refs/leak-scan/<番号>` に置き、2 回目の `--log-opts` に `--all` を渡して、すべての写しのコミットを探させる。作者の名前と日時は環境変数（`GIT_AUTHOR_NAME` など）で固定の作り物の値を渡す。作者のメールアドレスだけは、対象の番号を入れた `<番号>@leak-scan.invalid` にする。報告の `Email` から対象を引くための印である（次の「元のコミットの許可」）。対象の番号から（元のコミット、親、元のパス、写しのパス、報告のパス）を引く表を、一時のファイルに持つ。元のリポジトリの Git 属性は再現しない。`.gitattributes` 自体が再検査の対象になった場合は、ほかの対象ファイルと同じ手順で検査する
  - **写しのリポジトリは、元のリポジトリと切り離して扱う**
    - Git のフックから呼ばれたときなどは、呼び出し元の環境に元のリポジトリを指す `GIT_DIR`・`GIT_WORK_TREE`・`GIT_INDEX_FILE` などが残っている。
    - これを引き継ぐと、写しのための `git update-index`・`git update-ref` などが元のリポジトリのインデックスと参照に書き込む。
    - そこで、次の操作はすべて下の (1)〜(3) の環境で打つ。対象は、写しのリポジトリの初期化、写しのコミットを作る操作、2 回目の gitleaks（とその中で打たれる Git）である。
      1. `git rev-parse --local-env-vars` が挙げる変数をすべて外す。これは、リポジトリを指す変数の一覧を Git 自身が出すものである（`GIT_DIR`・`GIT_WORK_TREE`・`GIT_INDEX_FILE`・`GIT_OBJECT_DIRECTORY`・`GIT_COMMON_DIR`・`GIT_CONFIG_PARAMETERS` など）。
      2. 利用者とシステムの Git の設定を読まない（`GIT_CONFIG_GLOBAL=/dev/null`・`GIT_CONFIG_NOSYSTEM=1`）。利用者の設定が写しの中身を変えないためである。
      3. Git には `-C <写しのディレクトリ>` を、gitleaks には写しのディレクトリを、明示して渡す。
    - 1 回目（元の木と元のリポジトリの探し）は、今と同じく呼び出し元の環境のまま打つ
  - 2 回目は、`gitleaks git` を写しのリポジトリに打つ。設定は、渡された設定から既定の全体の許可のパス条件を外し（決定 6）、目印の規則を足した一時の設定（「処理の流れ」）にし、ほかの引数は 1 回目と同じにする。ただし、生の報告（`--report-path`）と記録は 2 回目だけのファイルに受け、1 回目のファイルを共用しない（「処理の流れ」）。`--log-opts` には決定 2 と同じ `--text --no-textconv --no-ext-diff --no-renames` を渡し、決定 2 の中継で各ファイルに目印の行を足す。探し直す対象のどれか 1 つでも目印が当たらなければ失敗にする。go-gitdiff が途中で読むのをやめたときに、探し直す対象の残りを見逃さないためである。パスが元のままなので、パスを条件にする規則（`.p12` の名前などで当てる規則）と、規則の許可のうちパスで外すものが、先頭のバイトで飛ばしたファイルにも名前でアーカイブと見なしたファイルにも効く
  - **元のコミットの許可**: 元のコミットがある履歴の探し直しでは、中継がコミットヘッダー（`commit <写しのハッシュ>` の行）を元のコミットのハッシュに置き換える。ハッシュは、次の `Author:` の行のメールアドレスの番号から表で引く。こうすると、元のコミットを条件にする許可（決定 5 の許可 5）が写しにも効く。今の木の探し直しには元のコミットが無いので、中継は一時コミットのヘッダーを保持し、最終の報告の `Commit` を空にする。許可 5 は今の木の探し直しでは効かず、値は当たる。gitleaks は、報告を作る前に、当たりごとのコミットで許可を評価する（[detect/detect.go](https://github.com/gitleaks/gitleaks/blob/v8.30.1/detect/detect.go)）。報告のときに戻すのでは、許可が写しのハッシュで評価されてしまう。書き換えると、報告の `Commit` も元のコミットになる。同じコミットの 2 つの写し（たとえばマージのコミットの親ごとの blob）は、`Commit` と `File` が同じになりうるので、報告の `Email` の番号で対象を区別する
  - 2026-11-25 に、手元の gitleaks 8.30.1 で確かめた。コミットを条件にする許可を持つ設定で、同じ形の秘密を持つ 2 つの元のコミット（許可に載せたものと載せないもの）を、それぞれ親の無い写しのコミットにして探した。書き換えが無いと、どちらも写しのハッシュで当たりになった。書き換えると、許可に載せたコミットの写しは当たりにならず、載せないコミットの写しは元のコミットのハッシュで当たりになった。規則ごとの許可（`condition = "AND"` で `commits` と `regexes` を並べたもの）でも同じで、許可の対象の秘密だけが外れ、目印の当たりは残った
  - 2 回目の当たりは、目印の当たりを除き、当たりの `Email` の番号から表で報告のパス（展開した中のファイルのほかは元のパス）を取得し、その値を報告に使う。行の番号は変えない。`Commit` の扱いは、探しの種類で分ける。今の木の探し直しの当たりは、`Commit` を空にして 1 回目の当たりに足す。履歴の探し直しの当たりは、`Commit` に元のコミットを残す。各写しは親の無いコミットで全行を足すので、パッチの新しい側の行の番号は元のファイルの行の番号と同じである。目印の行は各ファイルの最後の行の後ろに足すので、元の行の番号を変えない。パスだけで当てる規則の当たりは、gitleaks が行の番号を設定しない（`0` のまま。[detect/detect.go](https://github.com/gitleaks/gitleaks/blob/v8.30.1/detect/detect.go#L394-L414)）ので、そのまま出す
  - 2026-11-25 に、手元の gitleaks 8.30.1 で、乱数から作った作り物の token を入れた 3 つのファイルを写しのリポジトリに置いて探した。3 つは、ELF の頭の `keys/a.p12`、テキストの `notes.zip`、テキストの `keys/b.p12.gz` である。3 つとも token の規則が元のパスと元の行の番号で当たり、パスだけの規則（`\.p12`）は `keys/a.p12` と `keys/b.p12.gz` に行の番号 0 で当たった

### 決定 4: 探し直しても読めないファイルを見逃さないため、当たりの有無によらず固定の行で失敗にする

- **質問**: 探し直しても中身を読めないファイルや、飛ばしたファイルを特定できないときをどう扱い、何を出すか
- **選んだ案**: 次のどれかに当たれば、当たりの有無によらず 1 で終える。1・2・9 に当たっても、確かめを通った対象は探し直す。取れた当たりは、失敗の行より先に出す
  1. 1 回目の記録に、対象外とも探し直す対象とも分けられない飛ばした行がある（「処理の流れ」の表の最後の行）
  2. 木から取る探し直す対象（飛ばした行のファイルと、外れたディレクトリの下のファイル）の `path` の値を読めないか、木の中の普通のファイル（シンボリックリンクでない）を指さない。展開した中のファイルは作業ツリーに無いので、この条件を当てず、9 で確かめる
  3. 写しの Git のリポジトリを作れないか、写しを書けないか、コミットできない
  4. 2 回目の gitleaks が 0 と 1 のほかの終了コードで終える
  5. 2 回目の報告のファイル（2 回目だけのファイル）が無いか、JSON の配列として読めない
  6. 2 回目の記録に、WRN・ERR・FTL の行（件数の行を除く）か、飛ばした行（対象外の行を除く）か、内部の Git が途中で止まった行（`command aborted`）がある
  7. 2 回目の当たりの `Email` の対象番号が対応表に無いか、`File`・`Commit` が表の値と違う（照合の手順は「処理の流れ」。8 も同じ）
  8. 探し直す対象の番号のどれかに、目印の当たりが無い（空の中のファイルは対象にしないので、番号を持たない。決定 8）
  9. アーカイブか圧縮ファイルを最後まで展開できないか、メンバー名が決定 8 の形でないか、展開の合計が上限を超える

  出すのは、ファイルの名前を含まない固定の 1 行（例: `leak-scan: gitleaks が中身を読まずに飛ばしたファイルを探せなかった`）である。`--paths` を渡していなければ、今と同じくファイルの名前を伏せたことを知らせる行（`leak-scan: ファイルの名前は伏せた。…`）も出す。今の WRN・ERR・FTL の扱い（`leak-scan: gitleaks が警告か誤りを出した`）は変えない。履歴の探しで、内部の `git log` が途中で止まったときと、探す対象のどれかで目印が当たらなかったときの行は、「処理の流れ」にある
- 採らなかった案: 飛ばしたファイルがあれば、探し直さずに失敗にする（今の main の `log.browser.test.ts` で必ず落ち、ファイルの名前を変えさせることになる）
- 採らなかった案: 新しい失敗も今の行（`leak-scan: gitleaks が警告か誤りを出した`）で出す（gitleaks は警告を出していないので行の意味と食い違い、CI の検査の手順の失敗の行の表で原因を引けなくなる）
- **代償**: gitleaks の版が変わり、履歴の探しでもテキストのパッチを飛ばすようになると、探せずに失敗で止まる（通らないが見逃さない）
- 根拠: Value 7（MVV バージョン 3）

### 決定 5: 実在の名前を作り物の例として通さないよう、端点と S3 の置き場の許可を名前の全体に当てて絞り、ARN の許可は資源の欄まで決まった例に絞る

- **質問**: 端点と S3 の置き場の作り物の許可を、どの形で名前の全体に当てるか。ほかの規則の許可も直すか（要求の未決 1。`nd-aws-arn` は下の「ARN の許可」）
- **選んだ案**: `nd-aws-endpoint` と `nd-aws-arn-s3` の許可を、誰かが実際に作れる名前を通さない形に替える。正規表現を合わせる先は次のとおりで、どちらも `^…$` で合わせる。
  - 原則: 名前（端点の資源の部分・置き場の名前）の全体
  - 許可 1・3・4: 規則が当てた文字列の全体（`regexTarget = "match"`）。サービスの部分まで含めて決めるためである

 許可ごとに、なぜその名前が作り物と言えるかを `.gitleaks.toml` の許可の `description` に書く

  | # | 許可 | 置く規則 | 作り物と言える理由 |
  | --- | --- | --- | --- |
  | 1 | S3 の置き場の名前が `amzn-s3-demo-` で始まり、その後ろが小文字と数字だけ（`-`・`.` を含まない）のもの（`amzn-s3-demo-bucket` の形） | `nd-aws-arn-s3`、`nd-aws-endpoint`（S3 の端点だけ） | AWS が、この接頭辞で始まる置き場を作れないと定め、例のために使っている（STD3）。接頭辞の後ろに `-`・`.` を許さないのは、アクセスポイントの別名を通さないためである（下の段落） |

  許可 1 は、S3 のアクセスポイントの別名を通さないよう、接頭辞の後ろを小文字と数字だけに絞る。AWS はアクセスポイントの名前から `<アクセスポイントの名前>-<メタデータ>-s3alias` の形の別名を作り、この別名は置き場の名前の代わりに使える（STD4）。置き場の作成の制限（STD3）はこの別名に掛からないので、`amzn-s3-demo-` で始まる別名は実在しうる。別名は必ず `-s3alias` か `-ext-s3alias` で終わり、ほかの予約された末尾（`--ol-s3`・`.mrap`・`--x-s3`・`--table-s3`）も `-` か `.` を含む。接頭辞の後ろに `-`・`.` が無い名前は、これらのどれにも当たらない

  - Cognito の端点: `acme-test-login`（`infra/test/app-stack-login.test.ts`・`infra/test/app-stack.test.ts`・`infra/test/nd-setup.test.ts`）

  - 設定は今のまま、AWS が受け付ける形（接頭辞 `acme`・環境 `test`）にする。ドメインの名前（`acme-test-login`）は、テンプレートの `AWS::Cognito::UserPoolDomain` の `Domain` の値として、今のとおり文字列で確かめる。ドメインの名前だけでは端点の規則（`.auth.<リージョン>.amazoncognito.com` まで含む形）に当たらない

- 採らなかった案: 予約済みのドメイン `example.com`・`example.net`・`example.org` か、その下の名前を許す（STD2）。予約で作り物と言えるのは、そのホスト名自体を調べるときだけである。S3 の置き場の名前は誰でも付けられるので（STD3）、`logs.example.com` という名前の置き場や、その端点（`logs.example.com` に `.s3.amazonaws.com` を続けた名前）は実在しうる

### 決定 6: 名前で外したファイルの中の秘密も止めるため、既定の全体の許可のパス条件を外した設定で、元のパスのまま探し直す

- **質問**: 既定の規則の設定が読む gitleaks の既定の全体の許可（`.bin`・`.pdf`・画像・`node_modules/` などを名前で外す）が外したファイルを、探す対象に入れるか。入れるなら、どう探すか
- **選んだ案**: 入れる。要求の「事象」2 の `blob.bin` のように、名前だけで外されたファイルの中の認証情報も、既定の規則で止める。1 回目の探しは設定の全体の許可をそのまま読む。外されたファイルは、写しのリポジトリに元のパスのまま置き、全体の許可のパス条件だけを外した設定で探し直す。規則、規則のパスの条件、規則単位の許可は、元のパスで評価される。外されたファイルのうち探し直さないのは、次の表のパスだけである。この一覧は `leak-scan.sh` が持つ。表に無い通常のファイルはすべて探し直し、探せなければ失敗にする

  表は探し直す対象を選ぶときにだけ使い、1 回目の探しの範囲は狭めない。

  依存のディレクトリの行は、gitleaks の全体の許可がディレクトリごと外す名前（`node_modules`・`bower_components`）だけを挙げる。ディレクトリの名前だけでは、外から取り込んだ依存かどうかを判断できない。そこで、この 2 つの下で外すのは Git が追跡していないファイルだけにする

  - 今の木では、`git ls-files -z` に載るファイルを追跡しているものとし、依存のディレクトリの下でも探し直す
  - 履歴の探す対象はすべて追跡されているファイルなので、依存のディレクトリの下を除かない
  - 探す木の根が Git の作業ツリーの最上位でないとき（非公開の検査がコミットから書き出した木など）は、追跡の有無を判断できないので、依存のディレクトリの下を除かない
  - `git ls-files` が失敗したときは、探せなかったものとして失敗にする

  `vendor` は表に入れない。全体の許可が外すのは `vendor/github.com/` などの一部の下位パスだけで（[config/gitleaks.toml](https://github.com/gitleaks/gitleaks/blob/v8.30.1/config/gitleaks.toml#L19-L45)）、ほかの `vendor` の下には自分で書いたファイルを置けるためである。全体の許可が外した `vendor` の下のファイルは、探し直す

  | 対象外のパス | 理由 |
  | --- | --- |
  | `--config` に渡した、実際に使う設定のファイル | 今の振る舞いのまま。gitleaks も自分の設定のファイルは探さない |
  | 名前が `node_modules`・`bower_components` のディレクトリの下の、Git が追跡していないファイル | 手元や CI に取り込んだ依存のファイルで、このリポジトリに入らない |
  | `.git` | Git の管理の情報で、リポジトリの中身ではない |

  - **パス条件を外した設定の作り方**
    - gitleaks の既定の設定のファイル（[config/gitleaks.toml](https://github.com/gitleaks/gitleaks/blob/v8.30.1/config/gitleaks.toml)）を、`install-gitleaks.sh` が gitleaks の本体と同じ版・固定の要約値で取り、本体の隣に置く。
    - `leak-scan.sh` は実行のたびに、先頭の `[allowlist]` の `paths` の配列だけを除いた写しを一時ディレクトリに作る。
    - 全体の許可の `regexes` と `stopwords`、規則と規則単位の許可は残る。
    - 渡された設定が `useDefault = true` で既定を読むときは、一時の写しでその行を、作った設定を読む `path` に置き換える。`[extend]` の段数は変わらない
  - **失敗にする条件**: 既定の設定のファイルが無い、除く `paths` がちょうど 1 つ見つからない、2 回目の探しが `skipping file: global allowlist` を出す、のどれかなら失敗にする。本来当たる規則を評価できないまま通さないためである
  - 2026-11-25 に gitleaks 8.30.1 で、この作り方の設定を乱数の値で確かめた。`a.bin`・`package-lock.json`・`gitleaks.toml.d/NuGet.config` が元のパスで当たった。`docs/allowed/` だけを許す `generic-api-key` の許可は、`docs/allowed/a.bin` だけを外し、同じ値の `docs/other/a.bin` は当たった
  - 今の木で探し直す対象の候補は、次の 2 つである。どちらの候補にも、上の表の対象外の条件を当てる
    - 1 回目の記録に `skipping file: global allowlist` があるファイル
    - `skipping directory: global allowlist` で外れたディレクトリの下の普通のファイル
  - 依存のディレクトリの下で除くのは、探す木の根が Git の作業ツリーの最上位で、追跡していないと確かめられたファイルだけである
  - 大きさが 0 と確かめられたファイルは、写しを作らず、目印も確かめない。足した行が無く、中継が目印を足す先が無いためである。大きさを確かめられないか、中身を読めなければ失敗にする
  - 履歴で探し直す対象に入れるのは、目印が当たらず、記録に同じコミットとパスの組の `skipping file: global allowlist` があるものだけである（「処理の流れ」）
  - 写しの中身は、今の木では木のファイル、履歴ではそのコミットの blob（`git cat-file blob`）をそのまま写す
  - 当たりは元のパスで出す。履歴では、そのコミットのハッシュで出す。行の番号は元のファイルの行の番号のままである。blob の全行を読ませるが、出すのはそのコミットで新しく成立した当たりだけである（「処理の流れ」の「コミットへの帰属」）
  - 履歴の探し直しの写しも、決定 3 の中継が `commit` の行を元のコミットのハッシュに書き換えるので、コミットを条件にする許可（決定 5 の許可 5）が元のコミットに効く
- 採らなかった案: gitleaks の全体の許可で外されたファイルを探し直さない（この設計の前の版）。この案では、要求の再現手順にある `blob.bin` の認証情報を、直した後も検出できない
- 採らなかった案: 接尾辞を足した名前や中立の名前の写しを置いて、全体の許可を避ける（この設計の前の版）。元のパスと違うので、ディレクトリを限った規則単位の許可が探し直しで効かない。ファイル名を条件にする規則を効かせるには、写しを何通りも置くことになる
- 採らなかった案: 既定の規則を写してリポジトリに持つ。gitleaks の版を上げるたびに手で写し直す（Value 13）。1 回目の探しから既定の全体の許可を外すと、追跡していない依存のディレクトリの誤検知も戻る
- 採らなかった案: 名前の拡張子（`.bin`・`.pdf` など）だけを選んで探し直す。どの許可で外れたかを記録から知る手段が無いので、許可の正規表現を `leak-scan.sh` に写すことになる
- **代償**:
  - 依存のディレクトリの下に追跡しているファイルがあれば、既定の規則で探すようになる。
  - 名前で外していた依存の固定のファイル（`package-lock.json`・`go.sum` など）と、画像・文書のファイルも、既定の規則で探すようになる。
  - 誤検知が出たら、今と同じく `docs/operations/ci-checks.md` の「正当な当たりを規則単位で外す」に従い、当てた規則の許可を `tools/checks/gitleaks-default.toml` に理由とともに足す。許可のパスは元のパスで書ける。

  - バイナリでもなく、全体の許可も外さないテキストのファイルは、履歴で blob の全体を探さない。そのため、行を消しただけで秘密の形になる変更は当てない（今の探しと同じ）。

  - 全体の許可が外す名前の今の結合テスト（`img/logo.png`）は、当たる側へ書き換える
- 根拠: Value 7・Value 13（MVV バージョン 3）。LIB1

### 決定 8: 圧縮された秘密を通さないため、アーカイブと圧縮ファイルを展開して中のファイルを検査する

- **質問**: アーカイブ（zip・tar）と圧縮ファイル（gzip など）の中身を、どう検査するか。受け入れ条件 4 は、中身を検査できないファイルがあれば成功にしないと定める
- **選んだ案**: `leak-scan.sh` が展開し、中のファイルを決定 3 の写しのリポジトリで探す。展開できないか検査できなければ失敗にする
  - **見分け方**: 名前ではなく中身で見分ける。見るのは先頭のバイトで、ZIP だけは末尾と中身の全体も見る（下の「ZIP の見分け方」）。名前を使うのは、下の「失敗にするもの」の `.br` の扱いだけである。今の木は対象外のパス（決定 6）を除くすべての普通のファイル、履歴は探す対象の一覧のすべての blob を調べる。展開して得た中身も、同じ方法でもう一度見分ける。中身がアーカイブでも圧縮でもなければ、名前がアーカイブに見えても通常のファイルとして探す
  - **ZIP の見分け方**: 自己展開形式などの ZIP は、ZIP のデータの前に別のデータを持つので、先頭のバイトでは見分けられない。そこで、先頭の 512 バイトがどの形式にも当たらないときは、標準ライブラリの `zipfile.is_zipfile` で末尾の ZIP のディレクトリ情報（end of central directory）を確かめ、当たれば ZIP として展開する
    - 展開に使う `zipfile.ZipFile` は、前のデータの分の位置のずれを補って読む。前のデータは、ファイル自身をバイト列として探すときに読む
    - 末尾の確かめを後にするのは、末尾の近くに ZIP のメンバーを持つ tar も、`is_zipfile` に当たるためである（2026-11-25 に手元の `python3` で確かめた）
    - 末尾のディレクトリ情報にも当たらないファイルは、中身の全体から ZIP のメンバーの先頭（local file header）を探す。前に別のデータを持つ ZIP が途中で切れて、末尾を失った場合を見逃さないためである。ファイルは分けて読むので、ヘッダーが読み取りの区切りをまたいでも見つけられるようにする
    - メンバーの先頭と見なすのは、次をすべて満たす位置である。`PK\x03\x04` の 4 バイトで始まる 30 バイトのヘッダーがある。展開に必要な版が 63 以下である。圧縮の方式が、ZIP の仕様（[PKWARE APPNOTE](https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT) 4.4.5）が定義する番号（0〜6・8〜10・12・14・16・18〜20・93〜99）のどれかである。予約の番号（7・11・13・15・17）は含めない。名前の長さが 1 以上で、名前がファイルの中に収まる
    - メンバーの先頭が 1 つでもあれば、ZIP だが展開できないものとして失敗にする。残っている圧縮されたメンバーは、バイト列として探しても秘密が当たらないためである
    - ZIP かどうかの識別と、展開できるかの判定は分ける。上の圧縮の方式の一覧は識別だけに使う。末尾のディレクトリ情報がある ZIP でも、`zipfile` が読めない方式のメンバーがあれば失敗にする
  - **tar の見分け方**: 旧形式（v7）の tar には、257 バイト目の `ustar` の文字列が無い。そこで、次のどちらかに当たれば tar と見なす。1 つは、先頭の 512 バイトをチェックサムの正しい tar のヘッダーとして読めること（`tarfile.TarInfo.frombuf` が読める）。もう 1 つは、257 バイト目に `ustar` の文字列があること。v7・ustar・GNU・pax の形式を展開する。tar と見なしたのに最後まで読めないもの（ヘッダーの破損、読めない形式の拡張など）は失敗にする
  - **展開する形式**: zip（`jar`・`docx` など zip の形のものを含む）・tar・gzip・bzip2・xz。Python の標準ライブラリで読み、`python3 -I` で打つ。中身は作業ツリーにもファイルにも書き出さず、読んだ内容を写しのリポジトリに入れる。tar は、終端の目印まで読めなければ、途中で切れていると見なす
  - **対象にするメンバー**
    - ディレクトリ・tar のリンク・デバイスは中身を持たないので、最初に検査の対象から除き、メンバー名も確かめない（`tar` でディレクトリを `.` からまとめると入る `./` は、失敗にしない）。
    - その後、残る通常のファイルは、空のものも含め、メンバー名を正規化して確かめる。
    - 正規化では、`.` だけの要素と連続する `/` を取り除いてから使う（`./app.env` は `app.env`）。
    - 絶対パス、`..` を含む名前、取り除くと空になる名前は失敗にする
  - **空のメンバー**: 最後まで読んで大きさが 0 と確かめられたメンバー（圧縮ファイルを展開した結果が空の場合を含む）は、写しを作らず、探し直す対象にも目印の確かめの対象にもしない。パスだけを条件にする規則も当てない。今の木の空のファイルを gitleaks が探さないのと同じ扱いである。メンバー名の確かめは、空のメンバーにも当てる
  - **失敗にするもの**
    - 壊れている・途中で切れている・暗号化されている
    - 7z・rar・zstd・lz4 のように展開できない形式と、`zipfile` が読めない圧縮の方式を使う ZIP のメンバー
    - `python3` が無い
    - 上のメンバー名の形でない
    - 入れ子が 5 段を超える
    - 展開の合計が上限を超える
    - brotli は先頭のバイトで見分けられないので、名前が `.br` で終わるファイルは、中身が NUL の無い UTF-8 のテキストである場合を除き、展開できない形式とする
  - **展開の上限**: `leak-scan.sh` の 1 回の実行で展開して得るバイトは、合計 1 GiB までとする。入れ子では各段で得たバイトをすべて足す。展開しながら固定の大きさ（1 MiB 以下）ずつ読み、読むたびに合計へ足す。1 回に読む量は「残りの量 + 1 バイト」を超えない。合計が上限を超えると分かった時点で読むのをやめて失敗にし、途中のメンバーは写しにしない。メンバー全体を展開してから大きさを判定してはいけない。大きな圧縮ファイルでプロセスが先に終了し、失敗の行が出なくなるためである。テストのために、環境変数で上限を 1 GiB より小さくできるようにする（大きくはできない）
  - **tar の読み取りにも上限を掛ける**: Python の `tarfile` は、通常のファイルを返す前に、PAX の拡張ヘッダーと GNU の長い名前を内部でまとめて読む。メンバーを読み出すループの上限は、この読み取りに効かない。そこで、次のようにする
    - `tarfile` には圧縮を解かせない。圧縮は上の上限を掛けた段で解き、`tarfile` には圧縮されていないストリームを、上限を掛ける部品で包んで渡す
    - 包む部品は、`tarfile` が読むバイト（ヘッダー・拡張ヘッダー・本体）を数える。上限は、その tar を開く時点の「残りの量」である。1 回の読み取りは「この上限までの残り + 1 バイト」を超えず、超えると分かった時点で失敗にする
    - この数は展開の合計に足さない。合計には、今の決まりのとおり、メンバーを読み出すループが足す
  - **2 つのパス**: 規則と許可を当てるパスと、当たりに表示するパスを分ける。行の番号は、どちらも中のファイルの行である

    | パス | 形 | 使う所 |
    | --- | --- | --- |
    | 評価のパス | `<アーカイブのパス>/<中のパス>`。入れ子は `/` で続ける | 写しのリポジトリのパス。規則と許可が見る |
    | 報告のパス | `<アーカイブのパス>!<中のパス>`。入れ子は `!` で続ける（gitleaks のアーカイブの当たりと同じ書き方） | 当たりの出力と `--report` |

    アーカイブをディレクトリのように扱うので、ZIP のルート直下の `app.env` にも、ファイル名を `(^|/)app\.env$` の形で条件にする規則が当たる。アーカイブを置いたディレクトリを条件にする許可も、中のファイルに効く。gzip・bzip2・xz はメンバー名を持たないものとして扱い、圧縮ファイルの名前から末尾の `.gz`・`.bz2`・`.xz` を除いた名前（末尾が違えば名前のまま）を `<中のパス>` にする。圧縮ファイルの評価のパスは、上の表の形の例外である。`<中のパス>` を圧縮ファイルと同じディレクトリに置いた形（`conf/app.env.gz` なら `conf/app.env`）にする。アーカイブのファイル自身も、今までどおりバイト列として探す
  - 失敗の固定の行は、今の木では決定 4 の行、履歴では履歴の固定の行を使う
- 採らなかった案: gitleaks の `--max-archive-depth` で展開する。2026-11-25 に gitleaks 8.30.1 で確かめると、次の 2 つは当たりも誤りの記録も無く 0 で終えた。名前が `.zip` で中身がテキストの、秘密を持つファイル。秘密を持つ zip を途中で切ったファイル。名前を `.dat` に変えた zip は、中身を読まずに飛ばした。展開できなければ失敗にする、を満たせない
- 採らなかった案: 展開せず、アーカイブがあれば失敗にする。秘密の無いアーカイブを 1 つも置けなくなる
- 採らなかった案: `unzip`・`tar`・`gzip` などのコマンドを形式ごとに呼ぶ。誤りの知らせ方と中の名前の扱いがコマンドごとに違い、確かめる組み合わせが増える
- 採らなかった案: libarchive の `bsdtar` を使う。CI と手元に追加の導入と版の固定が要る
- 採らなかった案: ZIP も先頭のバイトだけで見分ける。前に別のデータを持つ ZIP を展開せず、圧縮されたメンバーの中の秘密を見逃す
- 採らなかった案: tar を `ustar` の文字列だけで見分ける。旧形式の tar を gzip で圧縮すると、gzip だけを展開して、中の tar のメンバーを検査しないまま通る
- 採らなかった案: 評価のパスにも `<アーカイブのパス>!<中のパス>` を使う。ルート直下のメンバー名の前が `/` でないので、ファイル名を条件にする規則が当たらない
- 採らなかった案: 評価のパスを `<中のパス>` だけにする。アーカイブの中に許可済みのディレクトリと同じ名前を作れば、どこに置いたアーカイブでも許可される
- **代償**: `leak-scan.sh` が `python3` に頼る。展開できない形式のファイルは置けなくなる。履歴では、中身を変えていない中のファイルの当たりも、アーカイブを変えたコミットの当たりとして出る。どの形式にも当たらないファイルは中身の全体を読むので、探す時間が延びる。ZIP でないファイルでも、ZIP のメンバーの先頭と同じ形のバイト列を含めば失敗になる。今の木と main の全履歴にアーカイブは無く、`PK\x03\x04` のバイト列を持つファイルも無い（2026-11-25 に `git grep` と全履歴のパッチで確かめた）
