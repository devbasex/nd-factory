## タスク分解

変更の種類は不具合なので、最初に、今の設定では NDF のマージの判定が承認を求めないことを確かめる（再現の確認）。コードを足さないので、新しいテストは書かない（設計書の「テスト設計」）。各タスクの確認は、設計書の「受け入れ条件の確かめ方」のコマンドと読み合わせで行い、結果を課題か Pull Request に残す。

### Task 1: 今の設定でマージの判定が `manual` を返すことを確かめる

- **対象ファイル:** 無し（読むだけ）
- **変更内容:** `main` を取り込んだ作業場所の根で、設計書の受け入れ条件 4 のコマンド（`production_merge.judge_project_text`）を打ち、`manual` が返ることを記録する。あわせて、`.ndf/pace.json` で設計書の受け入れ条件 12 の 1 のコマンドを打ち、`False` が返ることを記録する。直した後の結果と並べて、Pull Request に残すためである
- **満たす受け入れ条件:** 4・12 の前段（直す前の値）
- **進め方:** 再現の確認。この後の Task 2・3 で、同じコマンドの結果が `automatic` と `True` に変わることを確かめる

### Task 2: 反映先の一覧を、実際の 3 つの経路に合わせる

- **対象ファイル:** `.ndf/project.json`
- **変更内容:** `ndf project branch-strategy write` で、反映先の一覧（`release.deliveries`）を決定 2 の 3 行にする。ファイルを手で書き換えない。自動の行に `result` を書かず（決定 6）、`release.cd` は `null` のままにする。「設定が古い」の解消はこの変更に含めない（決定 7）
- **満たす受け入れ条件:** 1・2・3・4・6・7
- **進め方:** 書き換えの後に、設計書の受け入れ条件 4 のコマンドで `automatic`、形の検査（`branch_strategy.validate`）で `[]` が返ることを確かめる。一覧を「パイプラインの承認の後」で検索し、当たらないことを確かめる。`ndf project check` の結果を残し、反映の経路の設定を指す指摘が無いことを確かめる。どの確認でもマージするコマンド（`ndf ci merge`）と、開いている Pull Request の番号を使わない

### Task 3: MVV 判定が、どのファイルを変えた Pull Request でも承認を省かないようにする

- **対象ファイル:** `.ndf/pace.json`
- **変更内容:** `boundary_paths` に `**` を足す（決定 9）。今ある 16 個のパスは消さない
- **満たす受け入れ条件:** 12
- **進め方:** 設計書の受け入れ条件 12 の 1〜3 を行う。1 は `True` が返ること、2 は 3 つのファイル名で 3 行とも `レッドラインのパスに当たる` で始まる文が返ることを確かめる。3 は使う NDF の版の `tests/adapters/test_ci_cli.py` を読み、設計書の表の 2 つの場面の id と NDF の版を結果に残す。見つからなければ合格にせず、「未確認」として持ち主へ戻す

### Task 4: 承認する時点を、指針・`AGENTS.md`・手順書・確定仕様で決定 142 にそろえる

- **対象ファイル:** `AGENTS.md`、`.claude/skills/nd-factory-dev-guidelines/SKILL.md`、`docs/operations/setup.md`、`docs/specifications/deploy-pipeline.md`、`docs/operations/pipeline-approval.md`（冒頭と「順序のまとめ」）
- **変更内容:** 修正対象の表のとおり、「承認を待たない」がマージの後のパイプラインの個々の実行を指すことと、`main` へのマージの前に承認を取ることを書く。決定 142 の文と食い違う言い方をしない。実装の前と Pull Request の前に `main` を取り込む（並行して進む作業も、この 3 つのファイルを触るため）
- **満たす受け入れ条件:** 8・9・11
- **進め方:** 書いた後に、5 つのファイルと決定 142 を「承認」で検索し、マージの前の承認を不要と読める文が無いことを読み合わせで確かめる。決定 142 に、掛けること・理由・事故の経緯（Pull Request の番号・原因・反映の結果）があることも、同じ読み合わせで確かめる

### Task 5: main へのマージの前の確認の手順を、手順書に定める

- **対象ファイル:** `docs/operations/pipeline-approval.md`（「main へのマージの前の確認」の節）、`docs/operations/ci-checks.md`（M4・M5・M6・M6-3・手順 5・手順 6）
- **変更内容:** 修正対象の表のとおり書く。中身は設計書の決定 4・5・10 と、「影響と危険」のクローズとマージの工程の手順に従う。誰が、何を見て確認し、済んでいなければマージしないかを書く。この課題に限らず、`main` へ入るどの課題の Pull Request にも使う一般の手順として書く
- **満たす受け入れ条件:** 10
- **進め方:** 書いた後に、未チェックの「マージの前に決める」の行がある本文を NDF の関数（`github_merge.premerge_risks`）へ渡すと行が返り、チェックを付けると返らないことを確かめる。設計書の「テスト設計」の表の、決定 4・5・10 と「影響と危険（クローズ・マージの工程）」の行を、不合格の文の例に照らして読み合わせる

| 時機 | 対象 | 理由 |

| 実装の前（準備のリファクタリング） | しない | コードを変えず、設定のファイル 2 つと文書 6 つを直すだけである。触るファイルの行数は 22〜902 行（最大は `docs/operations/ci-checks.md` の 902 行）。同じファイルを触るタスクは Task 4 と Task 5 の `docs/operations/pipeline-approval.md` の 1 つ（5 タスクのうち 2 つ）で、触る節が違う。このリポジトリのテストは触らない |

## リスクと対処

| リスク | 対処 |
| --- | --- |
| 後続の Pull Request をマージする時点では、`main` の設定がまだ「手で反映」なので、NDF のマージの判定が承認を求めずにマージする（要求仕様の前提 2） | Pull Request の本文に、未チェックの `- [ ] マージの前に決める: …` の行を置いて作る。工程「Pull Request」は流さずに終え、持ち主のリリースの承認を受けた HEAD だけを `ndf ci merge --approved-head … --approved-base main` でマージする（設計書の決定 5） |
| Pull Request の本文を作り直すと、確認の行が消え、承認なしでマージされる | 本文を直す人・AI が行を引き継ぎ、作った後と直した後に、本文を `premerge_risks` へ渡して行が返ることを確かめる（設計書の決定 4） |
| `AGENTS.md`・開発の指針・手順書は、並行して進むほかの作業も触る | 実装の前と Pull Request の前に `main` を取り込む |
| `.ndf/project.json` を手で書き換えると、形の検査に通らない値が入る | `ndf project branch-strategy write` で書き、形の検査で `[]` が返ることを確かめる |
| 確認の途中で、実在する Pull Request をマージしてしまう | 受け入れ条件 4・6 は設定を読むだけのコマンドで確かめる。マージするコマンドと、開いている Pull Request の番号を使わない（受け入れ条件 7） |

## 切り戻し手順

- 後続の Pull Request を打ち消す Pull Request（`git revert`）で戻せる。データの移行は無い
- 戻すと `main` へのマージに承認が掛からなくなるので、打ち消す Pull Request も、持ち主のリリースの承認を受けてからマージする
