## 何が起きたか

nd-factory には、運用する環境へアプリを反映する仕組み（反映のパイプライン）がある。2026-11-25 に、反映の前に人が承認する段を外し、main に変更が入ると、人を待たずに運用する環境へ反映されるようにした（ https://github.com/devbasex/nd-factory/issues/164 、 https://github.com/devbasex/nd-factory/pull/165 ）。

一方で、開発の工程を進める仕組み（NDF）に反映の経路を伝える設定（`.ndf/project.json` の反映先の一覧 `release.deliveries`）は直していない。設定は「人が手で反映する」の 1 行だけで、説明文も「反映のパイプラインの承認の後に反映される」のままである。この食い違いは、2026-11-25 のデプロイの工程で見つかった。

2026-11-26 には、反映の経路を変える実装の Pull Request（ https://github.com/devbasex/nd-factory/pull/190 ）と追いの Pull Request（ https://github.com/devbasex/nd-factory/pull/194 ）が、本番への反映の前に人が承認する関門（リリース承認ゲート）を通らずに main へマージされた。

- マージしたのは、スプリントの工程「Pull Request」の自動の流れ（`merge-sprint` プラン）である。設定が「手で反映」なので、NDF は main へのマージを本番へ届く操作と扱わなかった
- 反映のパイプラインは準備の段で失敗し、この 2 本の変更は運用する環境へ反映されなかった。反映されたのは文書だけの Pull Request（ https://github.com/devbasex/nd-factory/pull/192 ）である
- 設定が実態と食い違ったときに、NDF が承認を省く側に倒れないようにする直しは、NDF の側の課題にした（ https://github.com/devbasex/ai-plugins/issues/4579 ）

## 種類

不具合（本番へ自動で届くマージにはリリース承認ゲートを掛けるという NDF の約束があり、このリポジトリの設定が実態と食い違うためにその約束が働かないから）

## 今の姿

NDF はまず、マージ先が本番のブランチかを確かめる。本番のブランチなら反映先の一覧を見て、そこへ自動で反映する行（`kind` が `manual` でない行）があれば承認を求める。設定を読めず判定できない場合も、工程のマージでは承認を求める。対象のマージは、承認の記録が Pull Request に残るまで NDF が進めない。エージェントが直接打つマージのコマンドは、監視（hook の `merge-production`）が見る。NDF 11.0.43 の監視は、作業場所の設定に本番向けの自動で反映する行があれば、Pull Request のマージ先も承認の記録も確認せずに、直接の `gh pr merge` を止める。承認の後のマージは NDF の工程から実行する。規則の SSOT は NDF の「自動反映の本番チャネルへのマージ」（ https://github.com/devbasex/ai-plugins/blob/main/plugins/ndf/skills/development-workflow/references/production-merge.md ）である。

このリポジトリでは、本番のブランチと開発の起点のブランチが、どちらも main である。

実際の反映の経路は次の 3 つである（SSOT は [全体の設計の「反映と設置」](https://github.com/devbasex/nd-factory/blob/main/docs/design/platform.md#反映と設置)）。

| 経路 | 起こし方 | 人の承認 | 反映先の一覧の今の書き方 |
| --- | --- | --- | --- |
| 運用する環境のアプリ | main への push で反映のパイプラインが自動で反映する | パイプラインの個々の実行は承認を待たない | 手で反映する行の説明文に「パイプラインの承認の後」とあり、実態と違う |
| 運用する環境の反映のパイプライン自身 | 設置のコマンドに `--stack pipeline` を渡す | 差分をリリース承認ゲートで承認してから打つ | 専用の行が無い |
| 自分で設置する人 | `npm run nd-setup -- diff` で差分を見て、`deploy --confirm` で反映する | 設置する人が差分を読んで確認の値を渡す | 上の手で反映する行にまとめて書いてある |

## 事象

2026-11-26 に、NDF 11.0.43 の判定の部品へ今の `.ndf/project.json` とマージ先 `main` を渡すと、`manual`（手で反映する。承認は要らない）が返る。

```text
$ NDF_SRC=<NDF 11.0.43 の導入先>/src
$ python3 -I -B -c 'import sys; sys.path.insert(0, sys.argv[1]); from ndf.core import production_merge as p; r = "devbasex/nd-factory"; print(p.judge_project_text(open(".ndf/project.json").read(), "main", source_repo=r, repo=r).value)' "$NDF_SRC"
manual
```

`ndf project check` は、終了コード 3 の「設定が古い」で止まる。止まる理由は、NDF がこのリポジトリを分析した後に、CI の定義や `AGENTS.md` などの入力ファイルが変わったことである。`ndf project check` は、反映先の一覧と実態の食い違いを指摘しない。

## 期待する結果

main へのマージは運用する環境へ自動で届くので、NDF はそれを本番へ届く操作と扱い、リリース承認ゲートを通るまでマージしない。

## 再現手順

1. main の `.ndf/project.json` の反映先の一覧が、`kind` が `manual` の 1 行だけである状態にする（今の状態）
2. スプリントの工程「Pull Request」を流す
3. 必須の CI が通ると、承認を求めずに main へマージされる（2026-11-26 に Pull Request #190 と #194 で起きた）

## 環境

- NDF 11.0.43（上の判定を確認したバージョン）
- このリポジトリの main の `fa99756`

## なぜ困るか

- 本番へ届く変更が、人の承認なしに運用する環境へ反映され続ける。パイプラインは人を待たないので、マージの後に止める機会が無い
- 反映の前に人が済ませる操作（反映の段へ進むのを止める、反映用の権限を作る、など）が残っていても、マージが先に進む
- 反映先の一覧の説明文が「パイプラインの承認の後に反映される」のままなので、読んだ人と AI は、マージの後にもう一度承認があると判断する

## 目的

反映先の一覧を実際の反映の経路にそろえ、main へのマージに人の承認が掛かる状態にする。どの時点で人が承認し、どの時点では承認しないかを、決定の記録・開発の指針・手順書で同じにする。

## 対象範囲

含む:

- 反映先の一覧（`.ndf/project.json` の `release.deliveries`）を、今の反映の経路に合わせる
- 自分で設置する人の経路（手で反映する）の行を、運用する環境の自動の反映の行と分けて残す
- 「反映のパイプラインの実行は承認を待たない」という持ち主の決定（2026-11-25）と、main へのマージに掛けるリリース承認ゲートの関係を決め、決定の記録に残す
- 開発の指針の該当の行が決定の記録と食い違う場合の書き換え
- 実装の Pull Request をマージする前に人が済ませる操作を確認する手順を、手順書に書く
- MVV 判定が main へのマージの承認を省かないよう、`.ndf/pace.json` の `boundary_paths`（今は CI の定義・設置のコマンド・`.ndf/` の設定など 16 個のパス）に、すべてのファイルに当たる `**` を足す（受け入れ条件 12）

含まない:

- 反映のパイプラインそのものの変更（ #164 で済んだ）
- NDF の判定の仕組みの変更（ https://github.com/devbasex/ai-plugins/issues/4579 ）
- 2026-11-26 にマージ済みの変更の取り消しと、失敗した反映のやり直し
- 商用利用の開始後の本番の反映の承認方式（始める前に持ち主が決め直す）
- main へのマージに、非公開の漏れ検査の成功を条件として掛けること（ https://github.com/devbasex/nd-factory/issues/198 。持ち主の決定、2026-11-26）
- main の保護・マージ専用のアカウント・資格情報を分けたマージの仕組み（ https://github.com/devbasex/nd-factory/issues/199 。持ち主の決定、2026-11-26）
- NDF のリポジトリ（ai-plugins）への起票と依頼（持ち主の決定、2026-11-26）

## 前提

- 前提 1: 反映先の一覧は、設計で決めた反映の経路を表す。反映の段が一時的に止められている間や、準備の段が失敗している間も、main へのマージは「本番へ自動で届く」と扱う
- 前提 2: この課題の変更自身をマージする時点では、main の設定はまだ「手で反映」なので、NDF の判定はこの Pull Request を止めない。この Pull Request は、人がリリースを承認してからマージする
- 前提 3: 直し終わるまで、main へ入るスプリントのほかの Pull Request は、リリース承認ゲートを通さずにマージしない。直し終わるのは、改めた設計の承認と、設定を変える後続の Pull Request が main に入った時点である
- 前提 4: 非公開の漏れ検査と main の保護は、この課題の切り替えの前提にしない（ #198 ・ #199 ）。それが入るまで、GitHub の画面や人の端末からのマージ、main への直の push、非公開の漏れ検査が止めるべき変更は止まらない

## 受け入れ条件

反映先の一覧:

- [ ] 1. 反映先の一覧に、運用する環境のアプリの経路を表す行がある。その行は「main への push で自動で反映する」（`kind: auto`）で、本番のブランチ main に当たる
- [ ] 2. 自分で設置する人の経路（`nd-setup diff` → `deploy --confirm`）は、手で反映する行（`kind: manual`）として、1 の行と分けて残る
- [ ] 3. 反映先の一覧のどの行の説明にも、「パイプラインの承認の後に反映される」のような、今は無い承認の段が書かれていない。運用する環境のパイプライン自身を設置のコマンドで反映する経路は、手で反映するものとして一覧から読める

承認ゲートが掛かることの確認:

- [ ] 4. 直した設定とマージ先 `main` を NDF のマージの判定に渡すと、`automatic`（承認が要る）が返る。コマンドと結果を課題か Pull Request に残す
- [ ] 5. 直した設定が main に入った後、エージェントが直接打つ main へのマージのコマンド（`gh pr merge`）が、監視（hook の `merge-production`）で止まる。結果を残す
- [ ] 6. 直した後の `ndf project check` の結果を残す。反映の経路の設定を指す指摘が無い
- [ ] 7. 4〜6 の確認で、Pull Request はマージされず、運用する環境へ何も反映されない

決定の記録と手順書:

- [ ] 8. 設計の決定の記録に、main へのマージにリリース承認ゲートを掛けることと、その理由がある。理由には、2026-11-26 の事故の経緯（どの Pull Request が、なぜ承認ゲートを通らずにマージされ、反映がどうなったか）を含む
- [ ] 9. 決定の記録に、「パイプラインの個々の実行は承認を待たない」とマージの承認ゲートの関係（人が承認する時点はどこで、どこでは承認しないか）がある。開発の指針・`AGENTS.md`・反映の手順書の記述が、この決定と食い違わない
- [ ] 10. 手順書に、実装の Pull Request をマージする前に、その課題の設計書が「マージの前に人が行うこと」とした操作（反映の段へ進むのを止める操作など）が済んだことを確認する手順がある。この課題に限らず、main へ入るどの課題の Pull Request にも使う一般の手順として書く。誰が、何を見て確認し、済んでいなければマージしないことが書かれている

人の承認の強制:

- [ ] 12. 設定を切り替えた後、NDF の工程が main へマージするときは、リリース承認ゲートの質問に持ち主が答えた記録が無ければマージしない。GitHub の画面や人の端末からのマージと、main への直接の push は、#199 が入るまで止まらない（前提 4）。MVV 判定（AI がプロジェクトの判断の基準に照らして承認を省く判定）は、どのファイルを変えた Pull Request でも承認を省かない

  確かめ方: MVV 判定は、`.ndf/pace.json` の `boundary_paths` に当たるファイルを変えた Pull Request の承認を省かない。直した `boundary_paths` と、例として 1 つのファイル名（`README.md`）を NDF の判定の関数へ渡す。`レッドラインのパスに当たる` で始まる文が返れば合格、`None` なら不合格とする。`boundary_paths` が `**`（すべてのファイル）を持つことを確かめるので、例のファイルは 1 つでよい（コマンドは設計書の「受け入れ条件の確かめ方」）

注: MVV 判定は、進め方（`pace`）が `fast` か `auto` のときに NDF が承認を省く仕組みである。反映先の一覧の行の `kind: auto`（自動で反映する経路）とは別のものである。

退行しないこと:

- [ ] 11. 反映のパイプラインの段の構成と、自分で設置する人が打つコマンドは変わらない。マージの後のパイプラインの実行に、承認の操作は増えない

## 非機能の条件

| 大項目 | 条件 |
| --- | --- |
| 運用・保守性 | 手順書の確認の手順は、会話の記録や引継ぎのメモを読まなくても、手順書と課題・Pull Request だけで実行できる |
| セキュリティ | 設定・手順書・記録に、インフラの実際の値（アカウント ID・ARN・端点・profile の名前・運用する環境の名前）を書かない |

## 影響

| 対象 | 影響 |
| --- | --- |
| 公開インタフェース | 変わらない |
| 重さ | 直すまでは、本番へ届く変更が承認なしでマージされ得る。回避の手段は、main へ入る Pull Request を、人の承認なしにマージしないこと。直した後も、 #199 が入るまでは GitHub の画面や人の端末からのマージと main への直の push が、 #198 が入るまでは非公開の漏れ検査が止めるべき変更が止まらない |
| データ | スキーマの変更も移行も無い |
| 既存の振る舞い | main へのマージが、すべて NDF の承認の対象になる。文書だけの Pull Request も含む。NDF では、スプリントの Pull Request の承認はデプロイの工程で 1 回、スプリントを通さない修正は Pull Request ごとに 1 回、設計の Pull Request は設計の承認と合わせて 1 回になる |

## ドメインイベント

| # | イベント | 引き金 | 失敗したとき | 順序の前提 |
| --- | --- | --- | --- | --- |
| E1 | マージが本番へ届くかを判定した | NDF がマージの工程に入った、またはエージェントがマージのコマンドを打った | 設定を読めなければ、承認が要るとして扱う（NDF の規則） | — |
| E2 | 承認の記録が無いので、マージせずに Pull Request を開いたままにした | E1 の判定が「本番へ届く」 | 承認の記録が無ければマージしない | E1 |
| E3 | マージの前の人の操作が済んだことを確認した | 設計が「マージの前に人が行うこと」を持つ | 済んでいなければマージしない | E2 |
| E4 | 持ち主がリリースを承認した | デプロイの工程の質問への持ち主の回答 | 承認しなければ Pull Request は開いたまま。承認の後に、承認した Pull Request の HEAD・マージ先・main の先端・反映の範囲（最後に成功した反映のソースのコミットから今回のマージ候補までのコミット。設計書の決定 10）のどれかが変われば、承認を取り直す | E2、E3 |
| E5 | 承認した HEAD を main へマージした | E4 | マージの失敗は NDF の工程が止まる | E4 |
| E6 | パイプラインが運用する環境へ反映した | main への push | 反映の直前の検査などで失敗すれば反映されない。失敗は通知される | E5 |

上は、設定を切り替えた後の通常のスプリントの順序である。E2 では工程「Pull Request」がマージを見送って完了し、E4 の承認と E5 のマージはデプロイの工程（`release-merge`）で行う。この課題の変更自身は、設定を切り替える前にマージするので、この順序では止まらない。そのため、前提 2 のとおり人が承認してからマージする。その手順は、設計書（[issue-166-design.md](./issue-166-design.md)）の決定 5 にある。

## 検証手段

| 項目 | 手段 |
| --- | --- |
| テスト | `npm run check`（手順書や設定の変更で、生成物の差と単体テストが退行しないこと） |
| 静的解析・型検査 | `npm run check` に含まれる |
| 手動確認（マージ前） | 直した設定のファイルを NDF の判定の部品へ読み取りだけで渡し、`main` で `automatic` が返ることを確認する（受け入れ条件 4）。`ndf project check` の結果を残す（受け入れ条件 6） |
| 手動確認（マージ前） | 設計が「マージの前に人が行うこと」とした操作が済んだことを、手順書の手順で確認する（受け入れ条件 10） |
| 手動確認 | main に入った後、そのコミットを取り込んだ作業場所で、実在しない Pull Request 番号で `gh pr merge` を打つ。合格は、Bash の呼び出しが hook の拒否（`PreToolUse:Bash hook error` に続いて「直の gh pr merge を止めた」の文が出る）で終わり、`gh` 自身のエラー（Pull Request が見つからない）が出ないことである。`gh` のエラーが出たら、hook が働かずに `gh` が走ったので不合格とする（受け入れ条件 5・7） |

マージできるコマンド（`ndf ci merge` を開いている Pull Request へ打つ、など）は、確認に使わない。判定が期待と違うと、実際にマージされるためである。

> ## 目的
