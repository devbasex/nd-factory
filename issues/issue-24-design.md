# nd-factory: 人が承認と判断に集中し、どこからでも、AI からも同じく開発を回せる（#24）

## 目的

- **今どうなっているか**: nd-factory は、全体の設計・詳細設計・実装計画が無いまま機能を足してきた。画面は機能ごとに増え（旧い側で 34 経路と予定の 1 経路）、承認を待つものが何かを 1 か所で読めず、スマートフォンでは使えず、画面にしか無い操作があり、認可はアカウント（チーム）の単位でプロジェクトの単位でない
- **誰に効くか**: 開発を任せて承認する人、そのチームの人、人が任せた AI のエージェント、nd-factory を自分の AWS へ設置する人、運用する人。子の課題の担当者は、この設計だけを読んで詳細設計へ進める
- **変えると何が成り立つか**: プロジェクト MVV（版 1）の Mission・Vision・Value 1〜9 を、利用者と利用の場面から、機能・画面・API・データ・アーキテクチャ・運用まで一続きに受ける。旧い側との同等ではなく、MVV に照らして入れる機能だけを作る

## 適用範囲

- **働く範囲**: このリポジトリ（devbasex/nd-factory）の画面・API・MCP・形の正本・インフラの定義・設置のコマンド。NDF（devbasex/ai-plugins のプラグイン）は外部の系で、この設計は NDF を変えない
- **プロジェクトごとに違うもの**: AWS のアカウントとリージョンは profile から、ほかの環境の値は設定のファイル（リポジトリの外）から受ける（[docs/operations/settings.md](../docs/operations/settings.md)）。秘密の値は秘密の器から受ける
- **当たるモード**: `standard`

## MVV と設計の節の対応

MVV の各項目を、それを受ける設計の節へ対応づける。設計の判断で迷ったら、この表の行の MVV の項目を基準に戻る。

| MVV の項目 | 要点 | 受ける設計の節 |
| --- | --- | --- |
| Mission | 工程を Web の画面から、人も AI も同じく回す。承認は人。待ちと手間を減らす | [利用者と利用の場面](#利用者と利用の場面)・[機能一覧](#機能一覧) |
| Vision | 課題を指せば並列に回り、人を待つのは承認だけ。どこでも何が動き何が待つかが分かる。チームにだけ見える。API と MCP。国を越える。公開で安く設置。承認した範囲だけ反映 | [ホーム（いま）](issue-24-design-screens.md#ホームいま)・[スプリントを始める流れ](issue-24-design-execution.md#スプリントを始める流れ) |
| Value 1 操作を速く分かりやすく | 機能の数より迷わない速さ | [手数の目標](issue-24-design-screens.md#手数の目標)・[付録の採否](issue-24-design-legacy.md) |
| Value 2 画面先行 | UX の土台 → 機能の画面をダミーデータで → API をつなぐ。API は機能から起こし常に配列 | [子の切り方](issue-24-design-children.md)・[経路の規約](issue-24-design-api.md#経路の規約) |
| Value 3 どこでも、つながらなくても | スマートフォンとタブレット。オフラインで読める。端末のデータは暗号化。取り消せない操作はつながってから確定 | [オフライン](issue-24-design-screens.md#オフライン)・[端末の幅](issue-24-design-screens.md#端末の幅) |
| Value 4 AI からも人と同じく | 画面の操作はすべて API と MCP にも。承認の確定は人だけ。委任とクライアントを確かめる。すべての操作を記録 | [操作の一覧](issue-24-design-api.md#操作の一覧)・[MCP](issue-24-design-api.md#mcp)・[操作の記録](issue-24-design-api.md#操作の記録) |
| Value 5 国や地域を越えて | 翻訳のファイル・UTC で保存・通貨とともに・法令に応じられる作り。先回りしない | [国際化](issue-24-design-screens.md#国際化)・[値の形](issue-24-design-api.md#値の形) |
| Value 6 自前の構成で安く | 相乗りしない。NAT なし・Lambda は VPC の外・Fargate は公開のサブネット。費用が増える構成は理由と代案 | [インフラ](issue-24-design-platform.md#インフラ)・[費用](issue-24-design-platform.md#費用) |
| Value 7 公開を前提に値を置かない | 実際の値・秘密を置かない。検査で止める | [検査](issue-24-design-platform.md#検査) |
| Value 8 承認した範囲だけ反映 | パイプラインか設置のコマンドだけ。CI は資格情報を持たない | [反映と設置](issue-24-design-platform.md#反映と設置) |
| Value 9 割り当てたチームにだけ見せる | 認可はプロジェクトの単位でサーバーの側。存在も見せない | [認可](issue-24-design-api.md#認可) |
| P1 パイプラインと設置のコマンドの外の AWS の変更 | 人の承認 | [反映と設置](issue-24-design-platform.md#反映と設置)・[人へ残す判断](#人へ残す判断) |
| P2 プロジェクトの割り当てと見せる範囲 | 人の承認 | [割り当てを変える流れ](#割り当てを変える流れ)・[人へ残す判断](#人へ残す判断) |

## 利用者と利用の場面

### 利用者

| # | 利用者 | どう使うか | 主な端末 |
| --- | --- | --- | --- |
| A1 | 開発を任せる人 | 課題を指してスプリントを始め、承認ゲートと問いに答える。承認と判断に集中し、待ちと手間を減らしたい | スマートフォン・タブレット・PC。移動中を含む |
| A2 | チームの人 | 割り当てられたプロジェクトの進み具合を読み、スプリントを始め、自分に向いた問いに答える | PC・スマートフォン |
| A3 | チームの持ち主 | チームの人を足す・外す。プロジェクトを作り、チームへ割り当てる（P2）。実行の場所と上限額を決める | PC |
| A4 | 人が任せた AI のエージェント | 委任を受けて、API と MCP から人と同じ操作を行う。承認の依頼と材料を読めるが、承認を確定できない | —（API・MCP） |
| A5 | 連携するシステム | 委任を受けて API から状態を読み、決まった操作を行う（例: 社内のチャットへ流す・課題の管理から始める） | —（API） |
| A6 | 自分で設置する人 | 自分の AWS へ設置のコマンドで設置し、自分のチームで使う | PC |
| A7 | 運用する人 | 運用する環境を反映のパイプラインで反映し、費用と障害を見る | PC |

A1〜A3 は同じ人が兼ねてよい。チームの席の役割（持ち主・メンバー）で、A3 の操作を行えるかが決まる。

### 利用の場面

場面は、利用者が nd-factory を開く理由である。機能一覧の各行は、この表のどれかの場面から来る。

| # | 場面 | 利用者 | いま困っていること（MVV の項目） | nd-factory で成り立つこと |
| --- | --- | --- | --- | --- |
| S1 | 課題を指してスプリントを始める | A1・A2・A4 | 課題を選ぶ・始める手数が多い（Value 1） | プロジェクトの課題の候補から選んで 1 回の確定で始まる。リポジトリごとのレーンが並列に回る（レーンの中の並列は NDF の契約の口を待つ。未確認のまま残ること） |
| S2 | いま何が動いていて、何が人を待つかを知る | A1・A2・A4 | 画面を渡り歩かないと分からない（Vision） | ホーム 1 枚で、人を待つもの（承認・問い）が先頭に、動いているスプリントが続けて読める |
| S3 | 承認ゲートで承認する・差し戻す | A1（人だけ） | 材料を開くのに手数がかかり、スマートフォンで読めない（Value 1・3） | 承認資料を 1 画面で読み、承認か差し戻しを確定する。つながらない間は読めて、確定はつながってから |
| S4 | AI の問いに答える | A1・A2 | 何を問われているかが分かりにくい（Value 1） | 問いと選択肢と推しの案を読み、答える。承認ゲートとレッドラインに当たる問いは人だけ |
| S5 | 人を待つものができたと知る | A1・A2 | 画面を開くまで気づかない（Vision） | 端末への知らせ（Web Push）か Slack で知り、知らせから直に承認の画面を開く |
| S6 | 移動中に読む | A1・A2 | 電波が弱いと読めない（Value 3） | 最後に受け取ったスプリントの一覧・詳細・承認資料を、つながらなくても読める |
| S7 | プロジェクトを用意する | A3 | — | プロジェクトを作り、GitHub のリポジトリ（主 1・サブ 0 以上）を登録し、チームへ割り当てる |
| S8 | チームを整える | A3 | — | チームを作り、人を招き、役割を変え、外す |
| S9 | AI のエージェントに任せる | A1・A2 → A4 | 画面にしか無い操作がある（Value 4） | 範囲と期限を決めて委任を発行し、エージェントが MCP か API で同じ操作を行う。取り消せる |
| S10 | 実行の場所と費用を決める | A3 | — | ホステッド（サービスが起こすコンテナ）か手元のマシンかを選び、月の上限額を決め、使った額を通貨で読む |
| S11 | だれが何をしたかを確かめる | A3（運用する人 A7 は AWS の側の構造化ログで読む） | — | プロジェクトの操作の記録を、だれが・いつ・どの経路で・何をの形で読む |
| S12 | 自分の言語と時刻帯で使う | 全員 | 日本語だけで、時刻は端末の時刻帯と混ざる（Value 5） | 言語と時刻帯を選び、日時と金額がその形で出る |
| S13 | 自分の AWS へ設置する | A6 | — | 設置のコマンドで差分と確認の値を見て反映し、足りない設定の一覧を受ける |
| S14 | 運用する環境を反映する | A7 | — | 起点のブランチへの push から、準備・人の承認・反映が流れる |

### プロジェクトとチーム

プロジェクトは主リポジトリ 1 つとサブリポジトリ 0 以上の集まりで、課題・承認・リリースの順を共有する。どのチームのものかは割り当てだけで決まる。個人で使う人は 1 人のチームとして扱い、「個人のアカウント」という別の器を持たない。

| 問い | 決まり |
| --- | --- |
| 1 つのプロジェクトを割り当てるチームの数 | 同時にちょうど 1 つ（I3）。割り当ての変更は履歴の行として足す |
| プロジェクトの持ち主 | 今割り当てているチーム。割り当てと別に持ち主を持たない |
| 作ったとき | 作った人が選んだチームへ、作成と同じ操作で割り当てる。割り当ての無いプロジェクトを作る経路を持たない |
| 割り当てを変える | 下の「割り当てを変える流れ」。人だけが確定する（P2） |
| 割り当てを外す | プロジェクトを閉じる操作としてだけ持つ。閉じた後はどのチームからも見えない |
| 見える範囲を広げる（チームの外へ見せる） | 作らない。必要になったら MVV の P2 の承認を経て設計へ足す |

#### 割り当てを変える流れ

| 段 | 決まり |
| --- | --- |
| 始める | 今のチームの持ち主が画面で「移す」を確定する（人だけ）。終わっていないスプリントを取り消しと同じ経路で止め、レーンの token と渡し済みの GitHub の token を断つ |
| 受け入れる | 移す先のチームの持ち主が画面で受け入れる（人だけ）。止め終えたことと token が残っていないことを、割り当ての行の差し替えと同じ条件つきの書き込みで照らす。残っていれば 409 |
| 取り下げる | 受け入れの前なら、今のチームの持ち主が取り下げられる。止めたスプリントは戻らず、始め直す |
| 移した後 | レーンは移す先のチームの実行の場所にだけ割り当てる。進行表の DB の資格情報は差し替える（[状態の置き場](issue-24-design-platform.md#状態の置き場)） |

### 不変条件

| # | 集約 | 条件 | 破れたときの扱い |
| --- | --- | --- | --- |
| I1 | プロジェクト | リポジトリのうち主リポジトリはちょうど 1 つ | 主の無い登録・2 つ目の主の登録を 409 で拒む |
| I2 | プロジェクトの割り当て | プロジェクトとその中身（リポジトリ・課題・スプリント・承認の依頼・問い・知らせ・費用の記録・操作の記録）を読めるのは、割り当てたチームの席を持つ人と、その人の委任だけ。ランナーと手元のマシンは、自分に割り当てたレーンのプロジェクトの分だけを自分向けの経路で読める。割り当てを移す途中の移す先のチームの持ち主は、受け入れの前にプロジェクトの名前だけを読める。ほかの主体には、存在しないときと同じ応答を返す | 認可の判定が 404 を返す。一覧・検索・件数・知らせ・記録からも除く |
| I3 | プロジェクトの割り当て | 今の割り当ては 1 つのチームだけ。作成・変更・削除は人が画面で確定した要求だけが通る | 2 つ目を条件つきの書き込みで拒む。委任・レーンの token からの要求は 403 |
| I4 | 承認の依頼・問い | 承認ゲートとレッドラインに当たる答えを確定できるのは人だけで、つながっていない端末では確定しない。確定の時点でサーバーの今の状態（待っている・承認資料の要約値が同じ）と照らす。答えの ID（I5 の冪等の鍵）は押したときに画面が作る | 合わなければ 409。委任からの確定は 403 |
| I5 | 承認の依頼・問い | 1 つの依頼の答えは NDF へ 1 回だけ渡る（冪等の鍵は答えの ID）。人が読んだ承認資料の要約値と PR の head も添えて渡す | 同じ鍵の 2 回目は状態を変えない。違う鍵が 2 つ渡ったらレーンを止めて人へ知らせる |
| I6 | スプリント | 区間の結果の行が無いか、契約に無い値なら、その区間は失敗 | 区間を失敗で閉じ、理由を進捗の事象に残す |
| I7 | スプリント | 1 つのレーンを動かすコンテナは同時に 1 つだけ | 2 つ目の割り当てを条件つきの書き込みで拒む |
| I8 | チーム | 使える量の判定は 1 か所だけで行い、画面は料金プランの名前で分岐しない | 判定の外で上限を比べるコードを検査が落とす |
| I9 | 操作の記録 | 追記だけで、秘密と個人情報の値を含まない。読み取りを含むすべての操作が 1 件ずつ残る | 書けなければ操作を 503 で失敗させる |
| I10 | スプリント | 進行表の DB は、プロジェクトごとに別のデータベースとログインの役割を持つ | 他のプロジェクトの DB の資格情報を渡す経路を作らない |
| I11 | スプリント | レーンのコンテナは AWS の権限を持たず、レーンの token はレーンが動く間だけ有効 | レーンの終わり・取り消しで token を断つ |
| I12 | （すべての API） | 取得・作成・更新・削除とも配列で受け渡す。GitHub の Webhook は GitHub が形を決めるので外す | 配列でない本文を 400 で拒む |
| I13 | 進捗の事象 | 追記だけ。同じレーンの同じ連番は 1 件だけ | 2 件目は前の 1 件を返して足さない |
| I14 | （すべての API） | 画面で行える操作は、同じ API の操作で行え、MCP の道具にもある。画面だけの経路と API・MCP だけの経路を持たない。人だけの操作は MCP の道具を持たず、対になる読み出しの道具（依頼と材料と確定の場所を返す）で満たす | 形の正本の操作の一覧と画面・MCP の対応を検査が照らし、欠けを落とす |
| I15 | 利用者・費用の記録 | 日時は UTC で保存し、金額は通貨とともに保存する | 時刻帯の無い日時・通貨の無い金額を形の正本の検証が拒む |
| I16 | 利用者 | 1 つの IdP のアカウント（ログインの組の 1 つ）は、ちょうど 1 人の利用者に結ぶ | 別の利用者へ結ばれたログインをつなぐ要求を 409 で拒む |

### 用語

| 用語 | 意味 | 用語集への反映 |
| --- | --- | --- |
| チーム | プロジェクトを割り当てる単位で、席を持つ人の集まり。個人で使う人は 1 人のチーム | 追加 |
| 席 | 利用者がチームに属すること。役割（持ち主・メンバー）を持つ | 追加 |
| プロジェクト | 主リポジトリ 1 つとサブリポジトリ 0 以上の集まり。1 つのチームに割り当てる | 追加 |
| プロジェクトの割り当て | プロジェクトを見られるチームを決める関係。作る・変える・外すのは人だけ（P2） | 追加 |
| 委任 | 利用者が AI のエージェントか連携するシステムへ、範囲と期限を決めて自分の操作を任せること。承認の確定は含まない | 追加 |
| スプリント | 1 つのプロジェクトで、選んだ課題を NDF の工程で通す 1 回の実行。1 つ以上のレーンからなる | 追加 |

| 区間 | レーンの中で、ランナーが claude（`NDF_FACTORY_RUN` を入れた人のいない実行）を 1 回起動して次の区切り（承認・問い・終わり）まで動かした分 | 追加 |
| 実行の場所 | レーンを動かす所。ホステッド（サービスが起こすコンテナ）か手元のマシン | 追加 |
| 手元のマシン | チームが登録し、nd ランタイムがレーンを受けて動かす利用者のマシン | 追加 |
| 推論の手段 | レーンの claude が推論を呼ぶ手段。サービスの推論（`managed`）か持ち込みのキー（`byok`） | 追加 |
| 承認の依頼 | NDF の承認ゲート（設計・リリース）か、レッドラインに当たる操作で、人の承認を求めるもの | 追加 |
| 問い | NDF が区分を付けて人へ出す、承認の依頼でない問い | 追加 |
| 承認資料 | 承認の依頼が添える、承認の判断に要る材料（題・目的・差分の要約・リンク）。要約値で版を見分ける | 追加 |
| 知らせ | 人を待つものができた・終わった・止まったことを、利用者へ届けるもの。通知先へ送り、画面に並ぶ | 追加 |
| 進行表の DB | NDF の進行表と耐久の記録を置く PostgreSQL。プロジェクトごとに分ける | 追加 |

| 状態の S3 | 承認資料の本文と、休止したレーンの NDF のファイルを置く S3 のバケット | 追加 |

| ホーム（いま） | 人を待つものと動いているスプリントを 1 枚に並べる、ログインの後に最初に開く画面 | 追加 |

## 人へ残す判断

| 判断 | 当たるレッドライン | なぜ当たるか |
| --- | --- | --- |
| プロジェクトの割り当ての作り（1 チームだけ・作成と同時に割り当てる・移すときは両方の持ち主が確定する・チームの外へ見せる操作を作らない） | P2 | プロジェクトを見られる範囲と、それを変えられる人を決める |
| 認可と委任の作り（プロジェクトの単位の判定・委任の範囲と期限・人だけが確定できる操作と、問いの区分ごとに委任でも答えられる範囲） | C2 / P2 | だれが何をできるか、AI のエージェントへどこまで任せるかの規則そのものを決める |
| NDF の起票の依頼を承認の依頼として人へ出し、承認された依頼だけサービスがリポジトリへ起票する | C5 | 他のリポジトリへ書き込む操作の規則を決める |
| 秘密の置き方と渡し方（進行表の DB の資格情報・レーンの token・委任の token・通知先の宛先の値・端末に暗号化して置くログインの控え（refresh token）） | C1 | 秘密の値の置き場と、それを受け取れる主体を決める |
