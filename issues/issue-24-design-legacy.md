# 付録 旧い側の機能の採否: 旧い側の機能を MVV に照らして選び、今の骨組みから新しい設計へ移れる（#24）

この文書は、頭の文書（[issue-24-design.md](issue-24-design.md) ）の 2 つの行を受ける。「あるべき姿の根拠」の行「旧い側の画面の地図と機能の対応表」と、「MVV と設計の節の対応」の Value 1 の行である。頭の文書の機能一覧（F1〜F23）と MVV 版 1（`.ndf/mvv.md`）の項目を、旧い側の機能へ当てる。本文の文書と違い、この付録だけが旧い側を主題にする。

## 目的

- 旧い側の機能を 1 つずつ、MVV の項目に照らして「入れる」「形を変えて入れる」「後に回す」「入れない」のどれにするかを決め、表にする
- 入れる機能が、新しい設計の機能一覧（頭の文書の F1〜F23）のどの行へ入ったかを指す。後に回す機能は、入れる条件を書く
- あわせて、main にある骨組みのどれを使い・直し・捨てるかと、運用する環境の利用者が新しい側へ移る段取りの要点と、旧い設計の文書の外し方を決める

## 骨組みからの移り方

main にある骨組み（ログイン → API の 1 つの HTTP の経路 → 表 → 画面 1 枚の縦の切れ端と、設置のコマンド・反映のパイプライン・検査）を、まとまりの単位で次のように扱う。

| まとまり | 今の中身 | 扱い | 新しい設計でどうするか |
| --- | --- | --- | --- |
| 形の正本の設定のファイルの形（`packages/contracts/` の設定と JSON Schema） | 設定のファイルのキーと検証 | そのまま使う | 実行の場所・知らせ・進行表の DB の設定のキーを足すときも同じ形で足す |
| 形の正本の終了コード（`packages/contracts/` の終了コードと表） | 設置のコマンドの終了コード | そのまま使う | 足りない設定の一覧（F21）の終了コードを足す |
| 形の正本の画面の設定の値 | 画面が読む `config.json` の形 | そのまま使う | 通知先の公開鍵など、画面が要る値を足す |
| 形の正本の利用者の API の形（`PUT /v1/users` の配列の受け渡し） | 利用者の行の取得と作成の形 | 直す | 配列の受け渡し（I12）と、他人の ID に 404 と同じ答えを返す作りは残す。利用者の集約（呼び名・言語・時刻帯・ログインの組）へ広げ、HTTP の経路を [API の文書](issue-24-design-api.md) の規約に合わせる |
| 形の正本の生成のスクリプト | 型・JSON Schema・見本・文書の表の生成 | 直す | 操作の一覧から OpenAPI・MCP の道具・画面のダミーのデータを作り、画面と MCP の欠けを照らす（I14） |
| API（`apps/api/` の利用者の処理と表の読み書き） | 1 つの HTTP の経路の Lambda と DynamoDB の読み書き | 直す | 要求の検査・プロジェクトの認可の判定・操作の記録（I9）を通す共通の振り分けの後ろへ置き直す |
| 縦の切れ端のスタックの資源の名前（利用者の表 `<prefix>-<env>-accounts`・関数 `users-api`） | 表と関数の名前 | 直す | 「アカウント」を AWS のアカウントの意味だけで使う決まりに合わせ、表を `db-users`、関数を `api-fn` へ移す（[土台](issue-24-design-platform.md#状態の置き場)）。データを持たない縦の切れ端なので移しは作り直しで足りる |
| 画面のログイン（`apps/web/` の認可コードの流れと実行時の設定） | Cognito へのログインと戻り | そのまま使う | GitHub の IdP を足すときに選ぶ手段を足す |
| 画面の表示と API の呼び出し（`apps/web/` の 1 枚の画面と利用者のクライアント） | 5 つの状態を出す利用者の画面 | 直す | 画面の土台（PWA・Service Worker・暗号化した IndexedDB・翻訳のファイル・端末の幅・部品）の上へ置き直し、プロフィール（F2）の元にする |
| 画面の e2e（`apps/web/e2e/`、利用者プールと API を網の手前で差し替える） | ブラウザーでの通しの確かめ | そのまま使う | 機能の画面ごとの e2e を同じ差し替えの形で足す |
| アプリのスタック（`infra/lib/` の利用者プール・配信・HTTP API・利用者の表・秘密の器） | Google の IdP・CloudFront（OAC）・JWT の認可・DynamoDB | 直す | GitHub の IdP・残りの表・本文の S3・ECS と ECR・自前の VPC（NAT なし）・進行表の DB を足す。スタックの分け方は [土台の文書](issue-24-design-platform.md) が決める |
| 名前・設定のファイル・合成の要約値（`infra/lib/` の名前の付け方・設定の読み込み・合成の結果の要約） | 接頭辞からの名前とタグ、設定の読み込み、確認の値の元 | そのまま使う | 足す資源も同じ名前の付け方を通す |
| 反映のパイプラインのスタック | 起点のブランチへの push → 準備 → 人の承認 → 反映 | そのまま使う | 準備の段でサービスの成果物を作る（F22） |
| 設置のコマンド（`infra/setup/` の `diff`・`deploy --confirm`・AWS の読み取り） | 差分と確認の値、保存した合成の結果だけの反映、bootstrap の版の確かめ | そのまま使う | 足りない設定の一覧を返す（F21）を足す |
| 参照の検査（`tools/ref-check/`） | 照合の語を CI の秘密から受けて探す | そのまま使う | 設計文書と課題の本文も検査の対象に含める |
| CI の定義のテスト（`tools/test/`） | ワークフローに AWS の資格情報が無いことの確かめ | そのまま使う | 足すワークフローも同じテストで縛る |
| CI のワークフロー（`.github/workflows/`） | check・合成・e2e・参照の検査 | 直す | NDF の契約の見本との食い違いを知る定期の検査（F23）のジョブを足す |
| 運用の文書（`docs/operations/`） | 設置・設定のファイル・反映の承認・IdP と App の作り方 | そのまま使う | 子の課題が足した機能の手順を足す |
| 旧い設計の文書（`docs/design/rebuild/`） | 作り直しの判定の規則・対応表・全体の設計 | 捨てる | 下の「旧い設計の文書の扱い」 |

コードのまとまりで捨てるものは無い。骨組みは縦の切れ端を通すために作った。新しい設計の土台の形（形の正本・配列の受け渡し・設置のコマンド・反映のパイプライン・資格情報を持たない CI）と食い違わない。

## 運用する環境の切り替えとデータ

旧い側のデータは新しい側へ移さない（利用者の答え、2026-11-16）。運用する環境の利用者は、新しい側でチームとプロジェクトを作り直し、GitHub App を入れ直して始める。

| 段取り | 要点 |
| --- | --- |
| 前提 | 新しい側の運用する環境を反映のパイプラインで反映し、F1〜F20 の最初の版が通しで動くことを確かめてから切り替える |
| 切り替える | 利用者へ案内する画面の URL を新しい側の URL に替える。独自のドメインの付け替えは前提にしない。新しい側の IdP のクライアントと GitHub App の戻り先は新しい側の URL にする |
| 利用者がすること | 新しい側でログインし、チームを作り（個人は 1 人のチーム）、プロジェクトを作ってリポジトリを登録し、手元のマシンと通知先と委任を登録し直す。旧い側で動いていたスプリントは、旧い側で終えるか取り消してから新しい側で始め直す |
| 戻し方 | 案内の URL を旧い側へ戻す。旧い側の資源とデータは切り替えの後もしばらく残しておく。戻すと、新しい側で作ったチーム・プロジェクト・スプリントの記録は旧い側に無い。この事実を、切り替えのリリース承認ゲートの資料と戻しの手順に書く |
| 旧い側を閉じる | 戻す見込みが無くなったら旧い側を閉じる。閉じる判断と時期は子の課題で決める |

細かい手順（案内の文面・戻しの予行・旧い側を残す期間・閉じる手順）は子の課題（#15）へ回す。

## 旧い設計の文書の扱い

旧い設計の文書（`docs/design/rebuild/`）は、新しい設計の確定仕様化（承認した設計を `docs/design/` へ移す）のときにまとめて外す。作り直しという手段にだけ要るものは捨て、作り直しに依らない決まりは新しい設計がすでに取り込んでいるので、旧い文書を残して二重に持たない。

| 文書 | 中身 | 扱い | 理由 |
| --- | --- | --- | --- |
| `01-rules.md`・`02-rules-detail.md` | 作り直しの判定の規則（同等・凍結・入れ替え・やめる判断）とその詳細設計 | 捨てる | 旧い側との同等と入れ替えの判定は目的にしない。切り替えと戻しの要点は上の節と子の課題（#15）が持つ |
| `03-parity.md`・`04-parity-detail.md` | 機能の対応表と網羅の検査の設計 | 捨てる | この付録の採否の表が置き換える。試走（対応表の全行を毎スプリント流す）も行わない |
| `05-overall.md` | 作り直しの全体の設計の頭 | 捨てる | 頭の文書（[issue-24-design.md](issue-24-design.md)）が置き換える |
| `06-overall-architecture.md`・`07-overall-contracts.md`・`08-overall-state-infra.md`・`09-overall-trust.md` | アーキテクチャ・NDF との契約と API の規約・状態とインフラ・信頼の境界 | 捨てる | 作り直しに依らない決まりは、[実行](issue-24-design-execution.md)・[API と MCP](issue-24-design-api.md)・[土台](issue-24-design-platform.md) の文書が MVV の項目と事実で書き直して取り込んだ |
| `10-overall-children.md` | 子の切り方（試走と機能の子） | 捨てる | [子の切り方](issue-24-design-children.md) が置き換える。試走と凍結の子は作らない |
| `11-overall-decisions.md` | 決定の記録 | 捨てる | 採る決定は [決定の記録](issue-24-design-decisions.md) に理由を書き直して置いた |
| `12-overall-detail.md` | 詳細設計 | 捨てる | [詳細設計](issue-24-design-detail.md) が置き換える |

外すときは、旧い文書を指すリンク（`AGENTS.md` の「リポジトリの形」の `docs/design/rebuild/` の行を含む）を同じ変更で直す。旧い文書は git の履歴から読めるので、別の置き場へ写さない。

## 旧い側の機能の採否

### 表の読み方

| 列 | 中身 |
| --- | --- |
| 旧い側の機能 | 利用者から見た 1 つの振る舞い。旧い側の画面の地図の HTTP の経路 34 本と予定の 1 行、確定仕様 28 本（索引を除く）の節から拾った |
| 旧い側の置き場 | 画面の HTTP の経路か、確定仕様のファイル名と節の見出し。ファイル名は共通の頭と拡張子を除いて書く（例: `accounts-and-plans`）。確定仕様の外にあったものは「旧い側の運用の文書」などの種類で書く |
| 採否 | 入れる: ほぼ同じ振る舞いで入れる。形を変えて入れる: 目的は残し、単位・画面・手段を変えて入れる。後に回す: 最初の版に入れず、理由の列の条件がそろったら設計へ足す。入れない: 作らない |
| 新しい設計の行 | 機能一覧の F 番号。画面の土台・形の正本・検査のように F の行を持たないものは `—` |
| MVV の項目 | 採否を決めた基準の項目（Mission・Vision・Value 1〜9） |

採否は次の決まりに合わせた。

- 開発ループ・AI のオーガナイザーとの会話・起票の依頼の画面・役割の流れ・レーンの木（レーンの状況）・バックログの画面は後に回す
- 起票の依頼そのものは、承認の依頼（レッドライン C5）として承認の画面に並べる
- リリースのまとめは入れない（リリースはレーンごとに NDF が行う）
- 料金プランの請求は後に回す
- 旧い側のデータは移さない（利用者の答え、2026-11-16）ので、移行と読み替えの機能は入れない

### 利用者・ログイン・チーム

| 旧い側の機能 | 旧い側の置き場 | 採否 | 新しい設計の行 | MVV の項目 | 理由 |
| --- | --- | --- | --- | --- | --- |
| Google のアカウントでログインし、画面へ戻る | `/login`・`/callback`・`auth-stack` | 入れる | F1 | Mission | 工程を Web の画面から回す始まりで、Cognito の Google の IdP で受ける |
| GitHub のアカウントでログインする（GitHub の OAuth を OIDC へ仲立ちする） | `/login`・`auth-stack` | 入れる | F1 | Mission | 開発を任せる人の多くが持つ GitHub で入れる。GitHub を Cognito の IdP として直に受けられるか（仲立ちが要るか）は、利用者とチームの子（K6）が確かめる（[土台の文書の未確認のまま残ること](issue-24-design-platform.md#未確認のまま残ること)） |
| access token を要求ごとに確かめ、48 時間ごとに取り直す | `accounts-and-plans`「token の検証とアカウントの解決」 | 形を変えて入れる | F1 | Value 9 | token の検証は API の振り分けの前で行い、続く判定をアカウントの解決からプロジェクトの認可の判定 1 か所へ替える（I2） |

| 自分の利用者に別の IdP（Google・GitHub）をつなぐ・外す | `/settings/login-links`・`accounts-and-plans`「ログインの連携」 | 形を変えて入れる | F1 | Value 1 | 利用者のログインの組として持ち、どちらの IdP からでも同じ利用者に入れる。メールアドレスでまとめない決まりは残す |
| 自分のプロフィール（利用者の ID・ログインの手段）を読み、呼び名を変え、ログアウトする | `/settings`・`accounts-and-plans`「API の経路」 | 入れる | F1・F2 | Value 5 | 呼び名に言語と時刻帯を並べ、自分の設定を 1 画面で決める |

| 席を持つチームの一覧を読み、チームの設定へ移る | `/settings/teams` | 形を変えて入れる | F3 | Value 1 | 自分の設定とチームの設定を行き来させず、チームの画面へまとめる |

| 個人のアカウントという器を持つ | `accounts-and-plans`「集約」・`/accounts/:accountId/settings` | 形を変えて入れる | F3 | Value 9 | 個人は 1 人のチームにし、認可の器をチームとプロジェクトの 2 つに絞る |
| 席の一覧・追加・種類の変更・削除 | `/accounts/:accountId/settings/members`・`accounts-and-plans`「集約」 | 形を変えて入れる | F3 | Value 9 | 席の役割を持ち主とメンバーにし、見える範囲はプロジェクトの割り当てだけで決める |
| 席の役割で操作と表示を変える | `accounts-and-plans`「集約」・画面の地図「設定の画面」 | 形を変えて入れる | F3 | Value 9 | 役割の判定をサーバーの側に置き、画面は判定の答えに従って出し分けるだけにする |

| 他のアカウントの中身も有無も、同じ 404 で見せない | `accounts-and-plans`「常に成り立つ条件」・`timeline`・`sprint-views` | 形を変えて入れる | F4 | Value 9 | 境界をアカウントからプロジェクトの単位へ移し、記録・知らせ・件数まで含める（I2） |
| IdP の結び付きと使った印を旧い利用者から移す | `accounts-and-plans`「アカウントの表」の移行 | 入れない | — | Mission | 旧い側のデータを移さないので、移す元が無い。移しの手間を利用者にかけない |

### 使える量と費用

| 旧い側の機能 | 旧い側の置き場 | 採否 | 新しい設計の行 | MVV の項目 | 理由 |
| --- | --- | --- | --- | --- | --- |
| 料金プランごとの使える量（同時の実行・登録の数・月の token）を 1 つの表で判定し、超える操作を断る | `accounts-and-plans`「使える量の表と判定」 | 入れる | F19 | Value 1 | 判定を 1 か所に置き、画面は料金プランの名前で分岐しない（I8） |
