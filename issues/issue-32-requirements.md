# #32: 全体の設計: cross-review と要素の揃いのレビューで見つかった欠けと食い違いを直す

正は課題の本文（#32）で、この文書はその写しである。`spec-copy.py write` で作り直す。手で直さない。

## 目的

承認済みの全体の設計（`docs/design/` の 7 本の文書。設計 PR #27 で承認し、PR #30 で確定の置き場へ移した）には、文書の間で答えが食い違う箇所と、詳細設計へ回したまま行き先の無い箇所が残っている。#24 から切り出した子の課題（#2〜#16 のうち開いているもの）の担当者が詳細設計を書くときに、認可・起こし直し（区間の再開）・公開範囲・DB の用意について文書ごとに違う答えを読むと、その違いのまま実装される。

この課題で、全体の設計の文書の間の食い違いを無くし、欠けを「全体の設計で決める」か「子の課題の詳細設計へ渡す（渡す先の課題の本文に載せる）」かのどちらかに片付ける。達成したい状態は、子の課題の担当者が、下の 11 件と R1〜R15 のどれについても、全体の設計の 1 か所（または渡された子の課題の本文）から 1 つの答えを読めることである。

## 起票者の推定

題・本文のうち、利用者の指示の原文に無く起票者が推して足した条件。設計承認ゲートで確かめるまで、利用者の決定として扱わない。扱いを書いた行は、設計者が決めた判断として読む。

この課題の本文は、全体が起票者（PR #30 の cross-review と、要素の揃いのレビューを回した AI）の書いたものである。利用者が会話で書いた指示の原文は無い（下の「依頼（原文）」）。そのため、本文の条件のうち扱いを分ける必要のあるものを並べる。

## 前提

- 前提 1: 11 件と R1〜R15 は、全体の設計の文書（`docs/design/` の 7 本）と用語集の改訂と、子の課題の本文への追記だけで直せる。コード・形の正本（`packages/contracts/`）・インフラの定義は変えない。直すのにコードの変更が要ると分かった指摘は、この課題では設計の決定までを書き、コードの変更は受け持つ子の課題へ渡す
- 前提 2: 11 件の指摘の中身は PR #30 の cross-review が書いたとおりで、指摘の箇所は今の main に同じ文のまま残っている。要求を書く時点で箇所を検索して確かめた（下の「指摘の箇所の確認」）
- 前提 3: 指摘ごとの「設計の中で正しい状態」は、設計の工程（`design`）で決める。この要求は正しい状態の中身を決めず、決めた結果が文書の間で 1 つになっていることを条件にする
- 前提 4: 子の課題へ渡す欠けは、渡す先を #2〜#16 の開いている子の課題から選ぶ。どの子にも当たらない欠けが出たら、新しい子の課題を起票し、その番号を書く
- 前提 5: 直した後も、設計文書は 1 本 1,000 行以下に収める（#24 の受け入れ条件と同じ上限）。今の行数は `platform.md` 903 行・`api.md` 798 行・`execution.md` 745 行・`screens.md` 745 行で、書き足しで上限を超える文書は分割する
