## 何が起きたか

漏れの検査（CI の `leak-check` のジョブ）を見直すクロスレビューで、実際の値の正規表現（CI の秘密）で探せない経路と、その秘密が Pull Request の側のコードから読める経路が見つかった。

- fork からの Pull Request の途中のコミットにだけ実際の値（運用する環境の名前・profile の名前など）を入れ、後のコミットで消すと、その値はどの実行でも秘密の正規表現に当たらない。squash でマージすると main からも辿れなくなり、元のコミットは Pull Request の参照（`refs/pull/<番号>/head`）として公開のまま残る（ https://github.com/devbasex/nd-factory/pull/95 の指摘 r1-6・r1-1、 https://github.com/devbasex/nd-factory/pull/100 の指摘 r1-4）
- 同じリポジトリのブランチからの Pull Request では、秘密の正規表現を一時の設定のファイルに書いた後、その Pull Request のチェックアウトにある検査のスクリプトを同じ権限で動かす。スクリプトはその設定のファイルを読めるので、レビューの前に秘密が Pull Request の側のコードに渡る（ https://github.com/devbasex/nd-factory/pull/95 の指摘 r1-2）

どちらも CI を実際に動かしての確認はしていない（ワークフローを読んでの推定）。

## 種類

機能追加（今の漏れの検査の設計は、fork の Pull Request を秘密の正規表現で探さないと決めている。その範囲を Pull Request の全コミットへ広げ、秘密を Pull Request のコードから隔てる約束を足す）

## 今の姿

漏れの検査は、gitleaks で今のファイルと履歴のコミットを探し、値の混入を Pull Request とマージの時に止める。探しは 2 つの規則で行う。

| 規則 | 中身 | fork の Pull Request | 同じリポジトリのブランチからの Pull Request | main への push |
| --- | --- | --- | --- | --- |
| 既定の規則と nd-factory の規則 | gitleaks の既定の規則と、リポジトリの `.gitleaks.toml`（アカウント ID・ARN・端点など） | 分岐点から head までの全コミットを探す | 同じ | 到達できるすべてのコミットを探す |
| 実際の値の規則 | CI の秘密 `LEAK_CHECK_PATTERN` の正規表現を、一時の設定のファイルで重ねる | 秘密を受けないので探さない | 分岐点から head までの全コミットを探す | 到達できるすべてのコミットを探す |

- 設計: [#1 の設計の決定 3](https://github.com/devbasex/nd-factory/blob/main/docs/design-process/issue-1/design.md)（「fork の Pull Request は秘密を受けず実際の値の規則で探せないので、通常のマージで main に入ったそのコミットを push の時に探す」）
- ワークフロー: `.github/workflows/ci.yml` の `leak-check` の手順「今の木と履歴のコミットを探す」（コミット fa6aa1b の 146〜184 行目）。ワークフローの起動は `pull_request` と main への `push` だけで、`pull_request_target` は使っていない
- 検査のスクリプト: `tools/checks/leak-scan.sh`（Pull Request のチェックアウトにあるものを動かす）

設計は「通常のマージで main に入ったコミットを push の時に探す」としているが、リポジトリの NDF の設定のマージの方法は squash である（`.ndf/project.json` の `merge.commit`）。squash では Pull Request の途中のコミットは main に入らない。リポジトリは公開で、GitHub の設定は squash・マージのコミット・rebase のどれも許している（2026-11-24 に `gh api` で確認）。

## 何を足すか・変えるか

| | 今 | 足した後 |
| --- | --- | --- |
| fork の Pull Request の途中のコミット | 実際の値の規則で探さない | マージの前に、実際の値の規則で探す |
| 同じリポジトリのブランチからの Pull Request | 秘密の正規表現を書いた設定のファイルを、Pull Request のチェックアウトのスクリプトが読める | 秘密を使う探しは、信頼できる側（既定のブランチ）のワークフロー・スクリプト・設定だけで動かし、Pull Request の中身は探す対象のデータとしてだけ扱う |
| fork と同じリポジトリのブランチの扱い | 秘密の有無で分かれる | 秘密を使う探しについて、同じ扱いにする |

## 今の利用者への影響と互換

nd-factory 自体の開発で Pull Request を出す人には、必須のチェックの名前か数が変わる場合がある。変わるときは、リポジトリの必須のチェックの一覧（`.ndf/project.json` の `required_checks` と GitHub のブランチの保護）を同じ変更で直す。

## なぜ困るか

公開のリポジトリへの fork からの Pull Request で、途中のコミットにだけ入った実際の値が検査をすり抜け、`refs/pull/<番号>/head` に公開のまま残る。また、同じリポジトリのブランチの Pull Request では、レビューの前に Pull Request のコードが秘密の正規表現を読めるので、正規表現そのもの（運用する環境の名前などを含む）が CI の記録や外へ出るおそれがある。どちらも、値をリポジトリに置かず混入を検査で機械的に止めるという MVV の Value 7（MVV 版 3）を崩す。

## 目的

fork の Pull Request も同じリポジトリのブランチからの Pull Request も、マージの前にすべてのコミットが実際の値の規則で探され、その間、秘密の正規表現が Pull Request の側のコードに渡らない状態にする。

## 対象範囲

含む:

- Pull Request の全コミットを、秘密の正規表現でマージの前に探す仕組み（例: 既定のブランチの側のワークフローで、Pull Request の head の範囲を秘密つきで探すジョブ。`pull_request_target` で Pull Request のコードを動かさずに git の履歴だけを読む形など）
- その仕組みの安全性の検討（秘密と書き込みの権限を Pull Request のコードに渡さない）
- 同じリポジトリのブランチからの Pull Request で、今の `leak-check` が秘密を Pull Request の側のスクリプトに渡している経路をなくすこと
- 必須のチェックの名前か数が変わるときの、必須のチェックの一覧と手順書の更新

含まない:

- 既定の規則と nd-factory の規則の探し（今も fork の Pull Request の全コミットを探す）
- Dependabot の Pull Request で秘密が無く落ちること（ https://github.com/devbasex/nd-factory/issues/101 の範囲）。ただし、Dependabot が起動した実行で秘密を使う探しがどう動くかは、この課題の仕組みを決めるときに #101 とそろえる
- 秘密 `LEAK_CHECK_PATTERN` の登録そのもの（持ち主が GitHub の設定で行う。#1 の範囲）
- 既に公開の Pull Request の参照に残っているコミットを消すこと

## 前提

- 前提 1: 秘密を使う探しは、実際の値の正規表現に当たる値を記録に出さない。当たりは今の `tools/checks/leak-scan.sh` と同じく、規則・ファイル・行・コミットだけで出す

## 受け入れ条件

- [ ] 1. 前提: fork からの Pull Request の途中のコミットで、秘密の正規表現にだけ当たる値を足し、後のコミットで消した。結果: マージの前に必須のチェックが落ちる
- [ ] 2. 前提: 同じリポジトリのブランチからの Pull Request で、受け入れ条件 1 と同じコミットの並びを作った。結果: マージの前に必須のチェックが落ちる
- [ ] 3. 秘密の正規表現を使う手順は、既定のブランチのワークフロー・スクリプト・設定だけを動かし、Pull Request のコミットにあるスクリプト・設定・依存のライブラリを動かさない。fork の Pull Request と同じリポジトリのブランチの Pull Request の両方で成り立つ（CI の定義のテスト `tools/test/ci-definition.test.ts` が確認する）
- [ ] 4. 秘密の正規表現を使うジョブの GitHub のトークンは、リポジトリへの書き込みの権限を持たない（CI の定義のテストが確認する）
- [ ] 5. Pull Request に新しいコミットを push すると、秘密を使う探しがその head でやり直され、前の head の結果でマージできない
- [ ] 6. 秘密を使う探しで、Pull Request のコミットを取れない・探しが途中で失敗する、のどちらでも、必須のチェックは通らない
- [ ] 7. 当たりの出力（CI の記録）に、秘密の正規表現と当たった値が出ない（前提 1）
- [ ] 8. 既定の規則と nd-factory の規則で、fork の Pull Request の分岐点から head までの全コミットを今と同じく探す（退行しない）
- [ ] 9. main への push の探しは、今と同じく到達できるすべてのコミットを両方の規則で探す（退行しない）
- [ ] 10. ワークフローの点検（CI の `workflow-audit` のジョブ）が、変えたワークフローで当たり無しで通る
