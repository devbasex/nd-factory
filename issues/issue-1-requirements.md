# #1: 検査: 値の漏れと設計の決まりの破れと NDF の契約の食い違いを、PR ごとと定期の CI で止める

正は課題の本文（#1）で、この文書は設計を承認するときの写しである。手で直さない。

## 何が起きたか

nd-factory は公開のリポジトリで、全体の設計（`docs/design/`）は「実際の値と秘密を置かない」「横断の部品を 1 か所に置く」「使える量の判定は 1 か所」「画面の操作はすべて API と MCP にもある」「NDF の契約に載るものだけでやり取りする」を、検査で機械的に止めると決めている（[プラットフォームの設計の決まりを縛る検査](https://github.com/devbasex/nd-factory/blob/main/docs/design/platform.md#設計の決まりを縛る検査)）。今の CI が持つのは、そのうち参照の検査（`tools/ref-check`）と CI の定義のテスト（`tools/test/ci-definition.test.ts`）だけで、ほかの検査はまだ無い。子の課題（#2〜#16）がコードを足し始める前に、決まりの破れを Pull Request の CI で落とせるようにしておく必要がある。

## 種類

機能追加（今ある CI に、全体の設計が決めた検査を足し、今ある 2 つの検査の効く範囲を広げる。今の検査の約束を戻すのでなく、検査の約束そのものを足す）

## 今の姿

- CI は GitHub の workflow `.github/workflows/ci.yml` の 4 つのジョブ（`check`・`synth`・`e2e`・`ref-check`）で、AWS の資格情報を持たない。4 つは `.ndf/project.json` の `ci.required_checks` に宣言してある
- 参照の検査（`tools/ref-check`、CI の `ref-check`）は、照合の語（CI の秘密 `REF_CHECK_TERMS`）の当たり・NDF の固定の値（`ndf-pin.json` の `ndf_ref`）が 1 か所でないこと・NDF の版を読む式と大小の比べが同じ行にあることを落とす
- CI の定義のテスト（`tools/test/ci-definition.test.ts`、CI の `check` の中）は、`ci.yml` のジョブの集合と必須のチェックの宣言の食い違いと、`ci.yml` の中の AWS の資格情報の語を落とす。`ci.yml` 以外のワークフローは読まない
- 全体の設計は、足す検査を [プラットフォームの検査](https://github.com/devbasex/nd-factory/blob/main/docs/design/platform.md#検査)・[API と MCP の照らす検査（I14）](https://github.com/devbasex/nd-factory/blob/main/docs/design/api.md#照らす検査i14)・[実行の契約の照合の定期の検査](https://github.com/devbasex/nd-factory/blob/main/docs/design/execution.md#契約の照合の定期の検査) に、置き場を [詳細設計のファイル配置](https://github.com/devbasex/nd-factory/blob/main/docs/design/detail.md#クラスと関数の構造) の `tools/checks/` に決めている
- NDF との契約は #41 の設計（PR #42）で ndf v11.0.12（契約の版 8）へ移る。契約の照合の検査（F23）が予告として読む先は、止まった `develop` の先端でなく ai-plugins の既定の枝の先端になる（#41 の決定 107）

## 何を足すか・変えるか

| 検査 | 今 | 足した後 |
| --- | --- | --- |
| 漏れの検査 | 無い | 作り物でない AWS のアカウント ID の形（12 桁）・ARN・資源の ID・端点・秘密の形（私有鍵の頭・token の頭）を形で探し、CI の秘密から受ける実際の値（アカウント・profile・環境の名前）の当たりを探す。`docs/` を含む追跡しているファイルに掛ける |
| 形の往復 | 無い | 形の正本 → JSON Schema・OpenAPI・MCP の道具 → 見本の値の検証が往復で同じ結果になることを照らす（生成の側は #2） |
| 境界の検査 | 無い | `apps/` の実行時のコードで、横断の部品の外での直の利用（`Date.now`・`console.log`・`fetch` ほか）を落とす |
| 依存の向き | 無い | `packages/contracts` → `packages/core` → `apps/*` の一方向に反する import・`apps/*` どうしの import・`infra` から `apps/*` への import を落とす |
| 使える量の判定の外の比べ（I8） | 無い | 判定の外で上限の値と比べるコード・料金プランの名前で分ける画面を落とす |
| 操作の一覧と画面と MCP の対応（I14） | 無い | 形の正本の操作の表に画面の操作か MCP の道具の無い行・表に無い画面の操作を落とす |
| NDF の契約の照合（F23） | 無い | すべての Pull Request・main への push・毎日 1 回で固定の点の契約を照らし、`ndf-pin.json` を変える Pull Request・push・毎日 1 回で ai-plugins の既定の枝の先端の契約も照らす |
| 使っていないコード | 無い | どこからも読まれないファイル・使われない書き出し・使われない依存を落とす（2026-11-21 に足した） |
| ワークフローの点検 | 無い | ワークフローの危うい書き方（広すぎる権限・資格情報の持ち出し・固定していない動作の参照など）を落とす（2026-11-21 に足した） |
| 参照の検査 | `ref-check` の 1 つのジョブ | 足すワークフローも同じ検査の対象に入る（版の数字の比べを、足すワークフローの中でも落とす） |
| CI の定義のテスト | `ci.yml` だけを読む | `.github/workflows/` のすべてのワークフローを読み、資格情報の語を落とす。必須のチェックの宣言と足した検査の食い違いも落とす |

## なぜ困るか

子の課題が横断の部品・画面・API・ランナーのコードを足し始めると、実際の値の混入・部品の外での直の利用・判定の外の上限の比べ・画面だけの操作が、レビューの見落としのまま main へ入りうる。リポジトリは公開されているため、実際の値が一度入れば履歴から消せない。NDF の契約が次の配布で変わったときも、ランナーを作った後で食い違いに気づくことになる。

## 目的

| MVV の項目 | この課題で受けること |
| --- | --- |
| Value 7 公開を前提に値を置かない | 実際の値と秘密の形の混入を、漏れの検査で機械的に止める |
| Value 8 承認した範囲だけ反映 | CI が AWS の資格情報を持たないことを、足すワークフローも含めて検査で保つ |
| Value 4 AI からも人と同じく | 形の正本の操作の一覧と画面と MCP の対応を照らす（I14） |
| Value 1・Value 7（横断の部品を 1 か所に） | 横断の部品の外での直の利用と依存の向きの破れを落とす |
| Vision（人が差分を見て承認した範囲だけが反映される） | NDF の契約の食い違いを、反映の前に Pull Request ごとと定期の検査で知る（F23） |

達成したい状態: 全体の設計が「検査が落とす」と書いた決まりの破れを含む Pull Request が、CI の必須のチェックで落ちる。NDF の次の配布の契約の食い違いを、固定の点を変える前に検査の要約で読める。

## 対象範囲

含む:

- 漏れの検査: 形（作り物でない 12 桁のアカウント ID・ARN・資源の ID・端点・秘密の形）と、CI の秘密から受ける実際の値の当たりの 2 つで探す。`docs/` にも掛ける（#32 から渡された欠け）
- 形の往復: 形の正本 → JSON Schema・OpenAPI・MCP の道具 → 見本の値の検証が往復で同じ結果になる（#2 と分けて持つ）
- 境界の検査: 横断の部品を置き場の外で直に使うコードを落とす
- 依存の向きの検査（#32 から渡された欠け）
- 使える量の判定の外の比べ: 判定の外で上限と比べるコード・料金プランの名前で分ける画面を落とす（I8）
- 操作の一覧と画面と MCP の対応: 操作の表に画面の操作か MCP の道具の無い行・表に無い画面の操作を落とす（I14）
- NDF の版の数字の比べ（参照の検査）と CI の資格情報（CI の定義のテスト）を、足すワークフローにも効かせる
- NDF の契約の照合: 固定の点はすべての Pull Request・main への push・毎日 1 回、ai-plugins の既定の枝の先端は `ndf-pin.json` を変える Pull Request・push・毎日 1 回で照らす（F23。#41 の決定 107）。~~毎日 1 回と `ndf-pin.json` を変える Pull Request で照らす~~ → 固定の点はすべての Pull Request で照らす形へ変更（2026-11-21、利用者の指示「より堅牢で長期的に良い方を選ぶ」。全体の設計の「いつ」も同じ設計 PR で直す）
- 使っていないコードの検査とワークフローの点検（MVV 版 2 の Value 13・Value 8。2026-11-21 に足した。全体の設計の検査の表にも同じ設計 PR で行を足す）
- 足す検査を CI の必須のチェック（`.ndf/project.json` の宣言）へ同じ Pull Request で足す

含まない:

- 機能そのもの（操作の表・横断の部品・ランナー・画面）
- 形の正本の生成（型・JSON Schema・OpenAPI・MCP の道具の一覧の生成）と、受ける契約の組のデータ（#2）
- スタックのテストに足す行（#13）
- NDF の側の改名（済んでいる）
- NDF 11 への追随（#23 の改名・`spec-declarations` の改名の確かめ・全体の設計の NDF の契約の書き直し・`ndf-pin.json` の付け替え）。#41 が先に受ける
- `ask-journal` の `fields` を上流の契約へ足す依頼（#41 の決定 106）
- 照合の語（参照の検査が探す旧い側の名前）をリポジトリに書くこと。CI の秘密 `REF_CHECK_TERMS` から受ける
