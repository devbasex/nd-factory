## 決定の記録

### 決定 1: 設計が目指す姿からぶれないため、主題を MVV に置き、旧い側の機能は採否を決める材料に留める

結論: 全体の設計の各節は MVV の項目から起こし、頭の文書に MVV の 13 項目と節の対応の表を置く。旧い側の機能は付録で 1 行ずつ MVV に照らして採否を決め、本文に同等・凍結・入れ替えを主題にした節を作らない。

理由: 旧い設計は旧い側との同等を網羅することを軸にしたため、旧い側が目指す姿から離れた点（機能ごとに増えた画面・チームの単位の認可・画面にしか無い操作）まで引き継いだ。利用者は「作り直しは手段で目的ではない」と差し戻した。

採らなかった案: 旧い設計の章立てを残し、MVV の節を足す。主題が 2 つになり、どちらで判断するかが節ごとに揺れる。

根拠: Mission・Value 1（MVV 版 1）

### 決定 2: サービスの器を 1 つにするため、個人で使う人を 1 人のチームとして扱い、「アカウント」の語をサービスの器に使わない

結論: プロジェクトを割り当てる単位は「チーム」だけで、個人で使う人は作成のときに 1 人のチーム（持ち主は本人）を持つ。サービスの器としての「アカウント」「個人のアカウント」の語を使わず、「アカウント」は AWS のアカウントの意味だけで使う。

理由: 器が 2 種類あると、画面の分岐・認可の判定・料金の線引きがどれも 2 通りになる。MVV の Vision と Value 9 は「チームに割り当てる」とだけ書き、個人の器を求めていない。AWS のアカウントと語が重なると、設置の文書と画面の文書で同じ語が別のものを指す。

採らなかった案: 個人のアカウントとチームのアカウントを分ける形。器ごとに画面と判定が分かれる。

根拠: Value 1・Value 9（MVV 版 1）

### 決定 3: 並列とリリースを NDF に任せるため、レーンを 1 つのリポジトリ分の NDF のスプリントにし、サービスはリリースをまとめない

結論: スプリントは 1 つのプロジェクトで選んだ課題のまとまりで、リポジトリごとに 1 つのレーンを持つ。レーンの中では NDF が課題を並列に回し（同時 3 本）、リリースもレーンごとに NDF が行う。リポジトリをまたぐ順序は計画の `after` で表す。サービスは「リリースのまとめ」を持たない。

作り方: 既存の NDF の流れ（`supervise.py new sprint` のプランとキュー）をレーンの中でそのまま使う。

比べた候補: (1) 旧い側の形（レーンを課題・ループ・リリースごとに分け、サービスのコードがリリースを 1 本にまとめる）。サービスが NDF の工程の中身（リリースの待ち・止まったリリース）を知る必要があり、NDF を変えるたびにサービスを直す。(2) NDF の並列の計画（`--parallel`）のオーガナイザーをレーンに置く形。オーガナイザーのセッションが常に動き、費用と待ちが増える。複数のリポジトリを 1 つのプロジェクトで回す要求が育ったら、後で比べ直す。

理由: Vision は「課題を指せばスプリントが並列に回る」ことを求め、NDF は 1 つのスプリントの中の並列を既に持つ。ただし固定した NDF の契約は、Factory の実行に複数の課題を 1 回で渡す口を持たない（[決定 61](issue-24-design-execution.md#決定の記録)）。口が足されるまでは、レーンの中の課題を順に流し、並列はリポジトリの間だけになる。サービスが工程の中身を持たなければ、NDF との境界は契約だけになる。

根拠: Vision・Value 1・Value 6（MVV 版 1）

### 決定 4: 人を待つものを最初に読めるようにするため、ログインの後に最初に開く画面をホーム（いま）にする

結論: ホーム（いま）は、人を待つもの（承認の依頼・問い）を先頭に、動いているスプリントを続けて並べる。知らせからは承認・問いの画面を直に開く。

理由: Vision は「いま何が動いていて何が人を待っているかが分かる」ことを、Mission は人が承認と判断に集中できることを求める。旧い側はホームを会話の一覧に置き、承認待ちは別の画面にあった。

採らなかった案: スプリントの一覧をホームにする。人を待つものが一覧の行の中に散る。

根拠: Vision・Mission・Value 1（MVV 版 1）

### 決定 5: 最初の版を迷わない広さにするため、開発ループ・AI のオーガナイザーとの会話などを後に回す

結論: 最初の版は機能一覧の F1〜F23 に限る。開発ループ・AI のオーガナイザーとの会話・起票の依頼の画面・役割の流れの画面・レーンの木の画面・バックログの画面・料金の請求・メールの知らせは後に回す。後に回す機能ごとの、入れる条件は [付録](issue-24-design-legacy.md) にある。

理由: Value 1 は機能の数より迷わない速さを優先する。後に回すものは、F1〜F23 の上に足せる（モデルと API の規約を変えない）。

採らなかった案: 旧い側の機能をすべて最初の版に入れる。画面の数が旧い側と同じになり、Value 1 の手数の目標を満たせない。

根拠: Value 1・Value 5（先回りしない）（MVV 版 1）

### 決定 6: 子を閉じる条件を受け入れ条件とテストにするため、対応表の試走をやめる

結論: 子の課題は、受け入れ条件・受け持つ不変条件のテスト・I14 の検査で閉じる。旧い設計の対応表の試走（#3）は閉じる。

理由: 対応表の試走は旧い側と同じ振る舞いをそろえることを確かめる仕組みで、決定 1 で主題から外した。MVV に照らして入れる機能は、受け入れ条件とテストで確かめられる。

採らなかった案: 対応表を新しい機能一覧で作り直して試走を続ける。受け入れ条件とテストと同じものを 2 か所で持つ。

根拠: Mission・Value 1（MVV 版 1）

### 決定 7: 設計文書を主題の名前で置くため、確定仕様化のときに `docs/design/` へ移し、`docs/design/rebuild/` を外す

結論: 設計の間は NDF の規約どおり `issues/issue-24-design*.md` に置く。確定仕様化（`plan-to-spec`）で `docs/design/` へ主題ごとの名前（例 `docs/design/screens.md`）で移し、同じ変更で `docs/design/rebuild/` を外して `AGENTS.md` の「リポジトリの形」の行を直す。

理由: 置き場の名前が「作り直し」だと、読み手は作り直しの記録として読む。設計承認の前に旧い文書を外すと、承認の前に材料が読めなくなる。

採らなかった案: 今の PR で `docs/design/rebuild/` を外す。設計承認で差し戻されたときに材料が main から消える。

根拠: Mission（MVV 版 1）・利用者の指示（2026-11-17）

### 決定 8: 料金の扱いを国を越えて後から足せる形にするため、使える量の判定と通貨つきの費用の記録を最初から持ち、請求は後に回す

結論: 最初の版は、料金プランの値（設定の値）・使える量の判定（1 か所、I8）・月の上限額と費用の記録（通貨つき、I15）を持つ。利用者から支払いを受ける請求の仕組みは、サービスの公開（K15）の前に別の課題で決める。自分で設置した環境は上限を切る。

理由: Value 5 は金額を通貨とともに扱うことを、Value 6 は安く運用できることを求める。判定と記録が最初から無いと、上限で費用を止められない。請求の仕組みは公開の範囲と法令（Value 5）で形が変わり、いま決めると先回りになる。

採らなかった案: 請求まで最初の版に入れる。公開の前に決まらない条件（国・税・事業者）で形が決まる。

根拠: Value 5・Value 6（MVV 版 1）

### 決定 9: 画面先行を子の順序で守るため、検査と形の正本 → 画面の土台 → 機能の画面 → API の順に子を並べる

結論: [子の切り方](issue-24-design-children.md)の順序（K0 → K1・K2・K5 → K3 → K4 → K6 → …）にする。

理由: Value 2 は UX の土台を先に固め、機能の画面をダミーデータで作り切ってから API をつなぐ順を求める。画面が先に揃うと、API の形が 1 つの画面に寄らず機能から起こせる。

採らなかった案: 機能ごとに画面と API を同時に作る順（旧い設計の順）。画面の土台が機能の子ごとに少しずつ決まり、部品と見せ方がそろわない。

根拠: Value 2（MVV 版 1）

### 決定 10: 知らせを端末で確実に受けるため、通知先を Web Push と Slack にし、メールを後に回す

結論: 最初の版の通知先は、端末に入れた Web アプリへの Web Push と、チームの Slack（Incoming Webhook）の 2 つ。メールは後に回す。

理由: Vision と Value 3 はスマートフォンで人を待つものを知ることを求める。Web Push は知らせから承認の画面を直に開ける。メールは送信の評判の管理と配信の費用が要り、Value 6 の安く設置できる構成に合わない。

採らなかった案: メールを最初から入れる。自分で設置する人が送信の設定（ドメインの検証）を求められる。

根拠: Vision・Value 3・Value 6（MVV 版 1）
