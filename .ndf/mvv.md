# nd-factory のプロジェクト MVV

このリポジトリ（devbasex/nd-factory。Neural Development Factory のサービスの画面・API・形の正本と、インフラの AWS CDK の定義と設置のコマンド）の Mission（何のためにやるか）・Vision（目指す姿）・Value（判断の基準）。AI と人がこのプロジェクトで判断するときの基準にする。作り直しの前のリポジトリの MVV 版 1 を元にし、公開のリポジトリと自前のインフラの構成に合わせて書き直した。サービスの方針の一覧の正本は devbasex/ai-plugins#2168 の「方針（利用者の決定）」の表である。

## NDF の共通原則との関係

この MVV は、NDF の共通原則（上位の原則「人を守り、人の発展を支える」、優先順位、AI が自分で取れる行動は「進める / 止めて人へ戻す」の 2 つだけ、必ず承認が要る操作 C1〜C8）の範囲で定める。**共通原則の優先順位と C1〜C8、下の「必ず人の承認が要る操作」は、この MVV のどの項目よりも先に効く。** 以下の Vision と Value は、その範囲でだけ読む。承認ゲートの数と、だれが実行するかは NDF の決まりに従い、この MVV では定めない。

## Mission

NDF の開発工程（課題の選定・設計・実装・検査・配布）を、Web の画面から、人も人が任せた AI のエージェントも、同じように速く迷わず回せるようにする。承認は人が行う。そうして、開発を任せる人は承認と判断に集中でき、その人の待ち時間と操作の手間が減る。利用者のプロジェクトの開発では、nd-factory は NDF の UI に徹する。工程・検査・品質の確かめは NDF が担い、nd-factory はそれを起こし、見せ、人の答えを渡す。

## nd-factory 自体の開発と、nd-factory が回す開発

この MVV には開発が 2 つ出てくる。nd-factory 自体の開発は、このリポジトリのコード・CI・インフラの定義・設置のコマンドを作り続けることで、開発者が NDF を使って回す。nd-factory が回す開発は、利用者のプロジェクトのリポジトリで NDF の工程を回すことで、利用者と利用者が任せた AI のエージェントが nd-factory の画面・API・MCP から回す。Vision と Value 1〜7・9 は nd-factory が回す開発のための製品の姿を、開発の目標（Value 10〜17）は nd-factory 自体の開発の判断の基準を定める。設計・課題・Pull Request では、どちらの開発の話かを先に書く。

## Vision

課題を指せばスプリントが並列に回り、工程が人を待つのは承認ゲートだけになる。PC でもタブレットでもスマートフォンでも、電波の弱い移動中でも、いま何が動いていて何が人を待っているかが分かり、承認の判断に要る材料を読める。プロジェクトは複数のリポジトリからなり、チームに割り当てられる。プロジェクトを見られるのは割り当てられたチームだけで、他のチームからは画面・API・MCP・記録・通知のどこからも、その存在さえ見えない。画面で行える操作は、人が任せた AI のエージェントや連携するシステムも API と MCP から同じく安全に行える。提供は日本から始め、言語・時刻帯・通貨の違う国や地域の開発者も同じ nd-factory を使える。コードは公開され、誰でも自分の AWS へ安く設置して運用できる。

## Value

1. **操作を速く分かりやすく**: 機能の数より、利用者が迷わず速く操作できることを優先して判断する。操作の手数と待ち時間を減らす変更を選ぶ。
2. **画面先行**: 機能の画面を先に作る。画面の地図・部品・端末・オフラインの見せ方・国際化を画面の基盤として先に固め、その上に機能の画面をダミーデータで作り切ってから、API の中身をつなぐ。API の入出力は 1 つの画面に合わせず機能（エンティティと操作）から起こし、取得・作成・更新・削除とも常に配列で受け渡す（1 件のときも要素 1 個の配列）。
3. **どこでも、つながらなくても使える**: スマートフォンとタブレットで操作できる。つながらないときも、利用者は最後に受け取ったスプリントの一覧・詳細・承認資料を読め、端末のデータはつながったときにサーバーと食い違いなくそろう。端末に残すデータは暗号化して保存する。承認ゲートの承認のように取り消せない操作は、オフラインでは確定させず、つながってからサーバーの今の状態と照らして確定する。
4. **AI からも人と同じく使える**: 画面で行えるすべての操作を API と MCP からも行えるようにする。画面も同じ API を通して動かし、画面にしか無い操作も、API や MCP にしか無い抜け道も作らない。ただし、承認ゲートの承認と、共通原則の C1〜C8・この MVV の P に当たる操作の承認は人だけが行う。API と MCP からは承認の依頼と材料を読めるが、承認を確定できない（AI のエージェントの委任でも同じ）。API と MCP では、だれの委任で、どのエージェント・クライアントが動くかを確かめ、認可は人の操作と同じく掛ける。読み取りを含むすべての操作を、だれが・いつ・どの経路で・何を行ったかの追記だけの記録に残す。秘密と個人情報の値は記録に書かない。
5. **国や地域を越えて使える**: 画面の文言は国際化の仕組み（言語ごとの翻訳のファイル）で持ち、言語を足すときに画面のコードを書き換えない。日時は UTC で保存して利用者の時刻帯で表示し、金額（課金）は通貨とともに扱う。個人情報は展開する国の法令（EU の GDPR など）に応じられる作りにする。ただし、まだ出ていない国のための機能を先回りして作らず、後から足せる作りに留める。
6. **自前の構成で、誰でも安く設置できる**: インフラは他の資源に相乗りせず、このリポジトリのスタックだけで立つ形にする（自前の VPC・NAT を立てない・Lambda は VPC の外・Fargate は公開のサブネット）。誰でも自分の AWS へ設置でき、安く運用できる構成を選ぶ。運用の費用が増える構成や依存を足すときは、その理由と代わりの案を示す。特定の環境にしか無い資源を前提にする変更は選ばない。
7. **公開を前提に、値を置かない**: このリポジトリは公開されている。インフラの実際の値（アカウント ID・資源の ID・ARN・端点）・実在の profile の名前・運用する環境の名前・社内の事情・秘密の値を、リポジトリ・課題・PR・CI の記録・合成の出力に置かない。秘密の値は秘密の器から、AWS のアカウントとリージョンは profile から、ほかの値はリポジトリの外の設定のファイルから受ける。例・テスト・見本には作り物の値だけを使う。混入は検査（漏れの検査・秘密の形の検査・境界の検査）で機械的に止める。

9. **プロジェクトは割り当てられたチームにだけ見せる**: プロジェクトは複数のリポジトリをまとめた単位で、チームに割り当てる。プロジェクトとそのリポジトリ・課題・スプリント・承認資料は、割り当てられたチームの人と、その人が任せた AI のエージェントだけが見られる。他のチームからは、画面だけでなく API・MCP・記録・通知・検索・一覧の件数のどこからも、中身も存在も見えないようにする。認可の境界はプロジェクトの単位でサーバーの側に置き、画面の表示を隠すことに頼らない。見せてよいか迷うときは見せない方を選ぶ。

### 開発の目標

nd-factory 自体の開発の判断の基準。利用者のプロジェクトの開発には当てない（そちらの判断は NDF と利用者のプロジェクトの MVV が持つ）。

10. **正しいデータ構造から作る**: 同じ事実を 2 か所に持たない。履歴を残す事実は追記だけで持ち、今の値は最新の記録から引く。読む速さのための写し（索引・集計）は、根拠を設計文書に書いてから足す。
11. **責務の分かれた設計にする**: 業務の規則はドメインに置き、HTTP と AWS の SDK に依存させない。外部のシステムとの接続はインタフェースの裏に置き、テストで差し替えられるようにする。型を付け、型の検査で誤りを早く見つける。
12. **リファクタリングを続け、読みやすさと直しやすさを保つ**: AI が自動で開発を続けても品質が落ちないよう、保守しやすさとテストのしやすさを保つ変更を選ぶ。機能を足すたびに構造を見直し、読みにくくなった所・直しにくくなった所をその場で整える。構造を変える前に、振る舞いを固定するテストを置く。
13. **重複と冗長を作らない**: 同じ規則・定数・処理は 1 か所に置き、ほかから参照する。定義から作れるもの（型・API の仕様・MCP の道具・画面の文言の一覧など）は、手で写さず定義から生成する。使わなくなったコード・設定・文書は残さない。
14. **モダンな開発の手順で品質を確かめる**: テストを先に書き、変更のたびに自動のテスト・静的解析・型の検査を通す。テストは速く保ち、開発の流れを止めない。変更はレビューを通してから取り込む。依存するライブラリは新しく保ち、脆弱性の知らせに早く応じる。設計の判断は、理由と採らなかった案とともに設計文書に残す。
15. **車輪の再発明をしない**: 機能や画面を設計するときは、広く使われ、保守が活発で実績のある最新のライブラリやサービスがあるかを設計の時点で調べ、あれば設計に含める。自前の実装はできるだけ避ける。調べた候補と選んだ理由（使われている広さ・保守の活発さ・ライセンス・セキュリティの対応）は設計文書に書く。
16. **前の形に縛られず、最新の良い形を取り込む**: 作り直しの前の nd-factory の画面・データの形・機能の区切り方を、設計の出発点にしない。機能や画面を設計する時点で、類似・競合の製品と最新の考え方を調べ、良いものを取り込む。調べた製品・考え方と取り込んだ理由は設計文書に書く。
17. **目先の手間より、長く良い形を選ぶ**: 作り方や部品は、より堅牢で長く保守しやすい方を選ぶ。今ある実装や設計を書き換える手間は、選ばない理由にしない。

## 必ず人の承認が要る操作

| # | 操作 | 理由 |
| --- | --- | --- |
| P1 | 反映のパイプラインと設置のコマンドの外で AWS の資源を作る・変える・消す、`cdk bootstrap` を打つ・その版を上げる | 決まった反映の経路を通らず、反映した状態を照らす記録も残らない |
| P2 | プロジェクトをチームに割り当てる・割り当てを変える・外す、プロジェクトを見られる範囲を広げる（割り当てたチームの外の人・エージェント・連携するシステムへ見せる） | 他のチームへ一度見えた中身は取り消せず、認可の境界そのものを変える |

## 改訂

MVV は進化する。改訂は利用者の承認で成立し、版・理由・前の版との差分を記録に残す。方向の誤りは、人が AI の判断を覆した回数・AI が決められなかった回数・検査をすり抜けて利用者へ届いた不具合の件数で検出し、原因が MVV の文言にある覆しが閾値を超えたら改訂を提案する。手順の正本は NDF の `development-workflow` の `references/project-mvv.md` の「改訂」にある。
